## Introduction

В Processor Tycoon игрок не «подписывает» OEM-контракт напрямую. Он **отправляет предложение** (`Contract.AddOffer`, кнопка «Предложить» в русификаторе `ptru`) со своим CPU. Через год, в дату рассмотрения (`Contract.AcceptanceDate`), игра разыгрывает победителя среди лучших предложений каждой компании (`Contract.ChooseCpu`). Начиная с 0.2.0 окно контрактов показывает «вероятность подписи» (`ContractWindow.UpdateProbabilityText` → `Contract.ChanceToSign`, поле «Вероятность:»). Но игрок не видит, из чего она складывается. Не видит он и того, почему проиграл, и того, что сделала автоматика.

Разбор кода (`pt-modding/code/ProcessorTycoon/ContractSystem/`) показывает, почему игроки называют систему «непонятной» и «глючной»:

1. Показанный процент — это доля IPS (`Contract.CpuOffer.DefineChance`), а не вероятность выигрыша. `Contract.ChooseCpu` перебирает предложения по убыванию IPS и берёт первое, у которого `Chance ≥ rand[1..100]`. Поэтому при двух предложениях с IPS 60 и 40 игра показывает 40 %, а реальная вероятность — 21 %.
2. Проигрыш тендера проходит молча. Всплывающие окна есть только для подписанного контракта (`ContractManager.PromoteContractToActive`, «Контракт подписан») и для расторгнутого (`ContractManager.RemoveContract`, «Контракт расторгнут»). Если победил ИИ, игрок ничего не узнаёт.
3. Автоматика («Автоподписание контрактов», `ContractAutomation.SendOffers`) работает только 31 декабря, за день до рассмотрения. CPU, не прошедшие требования, `Contract.AddOffer` отбрасывает молча.
4. «Автоотмена предложений» (`Player.AutomateRejection`) в дату рассмотрения молча снимает предложения игрока, если не хватает производственных линий.
5. Разрыв контракта стоит `(Units/30) × daysLeft²` (`ContractHelper.FinesFromContract`). Для 50 000 шт./мес. и двух лет это около 888 млн $. При этом отправка предложения идёт без подтверждения.

### Feature Summary
Мод раскладывает шанс подписи на факторы по реальной формуле `Contract` и объясняет каждый проигрыш. Перед отправкой предложения он показывает экран проверки обязательств с двухшаговым подтверждением (по умолчанию — только для рискованных предложений). Каждое действие автоматики и автоотмены попадает в журнал с причиной.

### Business Value
- **Ценность для игрока.** Понятно, почему контракт не дался и что нужно изменить (IPS, потребление, корпус, мощности). Нет случайных предложений с убыточными или неисполнимыми обязательствами. Автоматике можно доверять: видно, что она сделает и что сделала.
- **Доказательства спроса** (I03, itch.io). Игроки просят «offer-then-confirm» и называют автоподпись и автоотмену глючными или непонятными. Разработчик лишь посоветовал включить автоотмену. В 0.2.0 появился процент, но без объяснения.
- **Для проекта.** Волна 1 роадмапа («просьбы игроков»). Фича только читает состояние и не меняет баланс, поэтому риск низкий и её можно выпустить сразу после `mod-framework`.

### Scope

**Входит:**
- разбор шанса подписи для пары «контракт + CPU игрока»: требования, лучшее предложение каждой компании, доля IPS, множители модов (`contract.signChance`, с разбивкой по источникам из `ModModifiers.Explain`), фактическая вероятность, «что изменить»;
- фактическая вероятность рядом с процентом игры в окне контрактов («40 % (факт. 21 %)»);
- экран проверки перед отправкой предложения (обязательства, прибыль, мощности, штрафы, риски) и двухшаговое подтверждение с режимами «всегда / только рискованные / никогда»;
- итоги тендеров на дату рассмотрения: выигрыш, проигрыш (кому и почему), «не состоялся»; уведомление и письмо-сводка одним письмом в день;
- журнал автоматики (`ContractAutomation.SendOffers`) и автоотмены (`Player.AutomateRejection` в `Contract.ChooseCpu`) с причинами и числами;
- окно журнала контрактов с фильтрами;
- предпросмотр «что сделает автоматика 31 декабря»;
- подтверждение перед подписью сделки между компаниями в `ContractNegotiationWindow` (BusinessContract) через `ModUI.Confirm`;
- оценка возможных конкурентов-ИИ (Could);
- события и предикаты для других фич (Could).

**Не входит:**
- изменение шансов, наград, штрафов и любых формул контрактов. Канал `contract.signChance` и его патч (P8, захват контракта P23) принадлежат `mod-framework`, множители в него пишут другие фичи (`platform-generations`, `press-reviews` и т. д.). Здесь эти множители только **показываются**;
- патчи на `Contract.GetBestOffers`: метод закреплён ядром (P23), фича его только вызывает;
- новые условия контрактов (идея I21 в план не входит);
- поведение ИИ при подаче предложений (`AIBehaviourContract.OnTick`) — это зона `rival-personalities`;
- изменение оценок переговоров BusinessContract (`ContractNegotiationWindow.UpdateScores`, `AIMath.GetClientScores`): игра их уже показывает;
- исправление ошибок игры (возможные бесконечные циклы в `Contract.ChooseCpu`, преимущество раннего предложения при равном IPS). Их мод только объясняет (решение владельца);
- обучение (`first-year-onboarding`) — оно может ссылаться на окна этой фичи.

## Requirements

### FR-1: Причины, по которым CPU не проходит требования контракта

**User Story:** Как игрок, я хочу видеть, какое требование контракта не прошёл мой CPU и на сколько, чтобы понять, что исправить в следующем CPU.

**Priority:** Must

#### Acceptance Criteria

1. WHEN игрок открывает разбор для пары «контракт + CPU» THEN мод SHALL показать три строки требований — IPS, потребление, корпус — с фактическим значением CPU, порогом контракта и отметкой «пройдено / не пройдено».
2. WHEN мод вычисляет порог IPS THEN мод SHALL брать его как `Contract.MinIps × mipsToleranceMultiplier` (значение поля читается из экземпляра `Contract`; в 0.2.3 это 0.75) и показывать одновременно «требуется» (`MinIps`) и «допустимый минимум» (75 %).
3. IF CPU не проходит требование IPS THEN мод SHALL показать недостающую величину в MIPS и в процентах от допустимого минимума.
4. IF CPU не проходит требование потребления THEN мод SHALL показать превышение в ваттах над `Contract.MaxPowerConsumption`.
5. IF CPU не проходит требование корпуса THEN мод SHALL показать требуемый тип (`Contract.PackageTypeString`) и тип CPU (`IPackage.PackageTypeString`).
6. IF хотя бы одно требование не пройдено THEN мод SHALL пометить, что `Contract.AddOffer` отклонит предложение молча, а шанс подписи равен 0 %.

#### Scenarios
- **AC-1.1** Given контракт с `MinIps` = 1.20 MIPS, `MaxPowerConsumption` = 60 Вт, корпус PGA/LGA, и CPU с 0.80 MIPS, 45 Вт, PGA. When игрок открывает разбор. Then строка IPS красная: «0.80 < 0.90 MIPS (75 % от 1.20), не хватает 0.10 MIPS (11 %)»; потребление и корпус зелёные; итог «предложение будет отклонено, шанс 0 %».
- **AC-1.2** Given CPU с 70 Вт для того же контракта. When игрок открывает разбор. Then строка потребления красная: «70 > 60 Вт, превышение 10 Вт».
- **AC-1.3** Given контракт с корпусом DIP/PLCC и CPU на PGA 1990. When игрок открывает разбор. Then строка корпуса красная: «нужен DIP или PLCC, у CPU — PGA».

#### Additional Details
- **Complexity:** Low
- **Dependencies:** `mod-framework` (ModUI, ModL10n); FR-12 (сверка с игрой)
- **Assumptions:** `Contract.FailsAtAnyRequirement` и `Contract.AddOffer` используют одни и те же три проверки (подтверждено чтением `Contract.cs`).

### FR-2: Разложение шанса подписи на факторы и фактическая вероятность

**User Story:** Как игрок, я хочу понимать, из чего складывается процент «вероятности подписи» и какова реальная вероятность выиграть контракт, чтобы решать, стоит ли подавать предложение и какой IPS для этого нужен.

**Priority:** Must

#### Acceptance Criteria

1. WHEN игрок открывает разбор THEN мод SHALL показать таблицу лучших предложений по компаниям — компания, CPU, IPS, шанс игры — и выделить CPU игрока. Набор предложений строится по правилу `Contract.ChanceToSign`: предложения компании игрока заменяются выбранным CPU, у каждой компании берётся CPU с максимальным IPS (`Contract.GetBestOffers`).
2. WHEN мод вычисляет шанс игры для каждого предложения THEN мод SHALL получать его вызовом приватного метода игры `Contract.GetBestOffers` (с учётом всех провайдеров канала `contract.signChance`: prefix ядра P23 на этом методе кладёт разбираемый контракт в `ModifierContext.Contract`, поэтому контрактозависимые множители видны так же, как в розыгрыше) и показывать рядом «ванильный» шанс `clamp(round(100 × IPS / ΣIPS_лучших), 1, 100)`.
3. IF шанс игры отличается от ванильного THEN мод SHALL показать строку «Модификаторы модов: ×k» и разложение по источникам: каждый `AppliedModifier` из `ModModifiers.Explain("contract.signChance", ctx)` с `ctx.Contract` = разбираемый контракт — фича-источник (`FeatureId`), множитель и текст причины (`ReasonKey` и `ReasonArgs` через `ModL10n`). IF `ModifierBreakdown.IsBalanceCapped` или `IsFuseCapped` THEN мод SHALL дописать «(ограничено)» (ключ `core.explain.capped`).
4. WHEN мод показывает фактическую вероятность THEN мод SHALL вычислять её по алгоритму `Contract.ChooseCpu`: предложения упорядочены по убыванию IPS (при равном IPS — в порядке первого предложения компании), проход берёт предложение *i* с вероятностью `q_i = Chance_i/100`, проходы повторяются до выбора: `P_i = q_i·Π_{j<i}(1−q_j) / (1 − Π_all(1−q_j))`.
5. WHEN разбор показан THEN мод SHALL вывести подсказку «что изменить»: IPS, при котором шанс игры станет 50 % (`IPS = ΣIPS_других`), и IPS, при котором CPU встанет первым в очереди розыгрыша (больше максимального IPS конкурентов).
6. IF игрок предложил несколько своих CPU THEN мод SHALL пометить, что учитывается только CPU с наибольшим IPS, а остальные «затенены».
7. IF в контракт ещё не поступило ни одного предложения THEN мод SHALL показать шанс 100 % (как `Contract.ChanceToSign`) и пояснение, что ИИ подаёт предложения ежемесячно (`AIBehaviourContract.OnTick` на `OnLateMonthPassed`) вплоть до даты рассмотрения.
8. WHERE включена настройка «Показывать фактическую вероятность» (по умолчанию включена) мод SHALL дописывать в поле вероятности окна контрактов текст вида «40 % (факт. 21 %)» после отработки `ContractWindow.UpdateProbabilityText`.

#### Scenarios
- **AC-2.1** Given в контракте предложение ИИ с IPS 60 и игрок выбирает CPU с IPS 40. When игрок открывает разбор. Then шанс игры 40 %, ванильный 40 %, фактическая вероятность 21.1 %, у ИИ 78.9 %; подсказка «для 50 % нужен IPS ≥ 60».
- **AC-2.2** Given три компании с IPS 50, 30, 20. When разбор открыт для CPU с IPS 20. Then шансы 50/30/20 %, фактические вероятности 69.4/20.8/9.7 %.
- **AC-2.3** Given ИИ с IPS 1000 и CPU игрока с IPS 1. When разбор открыт. Then шанс игры 1 % (минимум клампа), фактическая вероятность 0 %, пояснение «первое в очереди предложение со 100 % всегда выигрывает».
- **AC-2.4** Given игрок предложил CPU A (IPS 50) и CPU B (IPS 30). When разбор открыт для B. Then шанс считается так, как будто B заменил A (правило `ChanceToSign`); в таблице помечено, что на рассмотрении будет учтён только A.
- **AC-2.5** Given фича `platform-generations` даёт множитель ×1.25 к шансу CPU игрока в этом контракте (`ModModifiers.Explain` возвращает запись с `FeatureId = "platform-generations"`, `ReasonKey = "pg.reason.oemPrefers"` и аргументом названия платформы). When разбор открыт. Then видна строка «Модификаторы модов: ×1.25», под ней «platform-generations: OEM предпочитает платформу {название} ×1.25».
- **AC-2.6** Given два контракта делят один CPU игрока 1 января и провайдер канала зависит от клиента контракта. When разбор открыт для каждого контракта. Then множитель и причина относятся к разбираемому контракту, а шанс игры равен `Contract.ChanceToSign` этого контракта.

#### Additional Details
- **Complexity:** Medium
- **Dependencies:** `mod-framework` (ModHooks — доступ к приватным членам; ModModifiers — `Explain` и `ModifierContext.Contract`; ModCompanies); FR-12
- **Assumptions:** по `mod-framework/design.md` (патчи P8 и P23) канал `contract.signChance` применяется в postfix `Contract.CpuOffer.DefineChance`: `Chance = clamp(round(ipsShare × 100 × M), 1, 100)`, где `M = ModModifiers.Get("contract.signChance", {Company, Cpu, Contract})`. Контракт захватывает prefix ядра на приватный `Contract.GetBestOffers`, поэтому вызов этого метода из мода (разбор, повторный вызов в postfix `ChooseCpu`) возвращает итоговые шансы с тем же контекстом, что и розыгрыш и `ChanceToSign`. Канал не имеет балансового диапазона (только предохранитель [0; 5]). Ядро различает контракты в дневном кеше; если ключ кеша строится только по `Contract.ContractID` (индекс шаблона, не уникален), значения двух контрактов одного шаблона могут смешаться (см. «Открытые вопросы», п. 1).

### FR-3: Экран проверки перед отправкой предложения

**User Story:** Как игрок, я хочу перед отправкой предложения увидеть все обязательства и риски контракта, чтобы не подписаться на убыточный или неисполнимый контракт.

**Priority:** Must

#### Acceptance Criteria

1. WHEN игрок нажимает «Предложить» в окне контрактов и подтверждение требуется (FR-4) THEN мод SHALL не передавать предложение в `Contract.AddOffer` и SHALL открыть модальный экран проверки.
2. WHEN экран проверки открыт THEN мод SHALL показать: клиента и тип контракта; объём `Units` в месяц; оплату `PaymentPerUnit` за единицу; дату рассмотрения и дату окончания; срок в месяцах; требуемые линии (`ProductionMath.RequiredProductionLines`); мощность производителя (`FactoryBase.ProductionCapacity`), занятые линии (`ContractHelper.ContractedProductionLines`) и линии, обещанные в других предложениях (`ContractHelper.FutureProductionLinesDemand`); прибыль в месяц и за срок `Units × (PaymentPerUnit − Cpu.RealUnitCostWithNewPrice(PaymentPerUnit))`; маржу и порог автоматики `Player.ContractProfitMargin`; штраф за недопоставку `FinePerUnit` за единицу; оценку штрафа за разрыв в первый день `(Units/30) × D²`, где D — дни от даты рассмотрения до даты окончания; шанс игры и фактическую вероятность (FR-2).
3. WHEN мод находит риск THEN мод SHALL вывести его отдельной строкой-предупреждением. Риски: нехватка линий сейчас; перегрузка с учётом других предложений; отрицательная прибыль; маржа ниже порога автоматики; фактическая вероятность ниже порога из контента (по умолчанию 10 %); штраф за разрыв больше денег компании (`ICompany.MoneyAmount`); при включённой автоотмене — «предложение будет снято в дату рассмотрения».
4. WHEN игрок нажимает «Предложить» на экране проверки THEN мод SHALL вызвать `Contract.AddOffer` для этого CPU в обход проверки, обновить окно через `ContractWindow.TriggerUIUpdate` и записать в журнал запись «Предложение отправлено (вручную)».
5. WHEN игрок нажимает «Отмена» или закрывает экран THEN мод SHALL оставить предложение неотправленным и записать в журнал запись «Отправка отменена на экране проверки».
6. WHILE экран проверки открыт мод SHALL держать время на паузе (модальный шаблон `WindowTemplate.Modal` ядра ставит `PauseTrigger`).
7. IF CPU не проходит требования (FR-1) THEN мод SHALL не открывать экран проверки: кнопку игра и так блокирует (`ContractWindow.UpdateSendOfferButtons`).

#### Scenarios
- **AC-3.1** Given режим «только рискованные», контракт на 50 000 шт./мес. и 3 линии при свободных 1 из 5. When игрок нажимает «Предложить». Then открывается экран проверки с предупреждениями «не хватает 2 линий» и «штраф за разрыв ≈ 888 млн $ (срок 730 дней)»; предложение не отправлено.
- **AC-3.2** Given экран из AC-3.1. When игрок нажимает «Предложить» на экране. Then у контракта появляется предложение с этим CPU, в окне видна кнопка «Отозвать», в журнале — запись «вручную».
- **AC-3.3** Given экран из AC-3.1. When игрок нажимает «Отмена». Then предложения нет, кнопка «Предложить» остаётся, в журнале — запись «отменено на экране проверки».

#### Additional Details
- **Complexity:** Medium
- **Dependencies:** FR-2, FR-4, FR-8; `mod-framework` (ModUI, ModHooks)
- **Assumptions:** кнопка отправки окна вызывает `Contract.AddOffer(int)` напрямую (подтверждено: лямбда `ContractWindow.<Start>b__50_3`). Перехват идёт prefix-патчем на `Contract.AddOffer`, а не на лямбду.

### FR-4: Режимы подтверждения и автоподтверждение

**User Story:** Как игрок, я хочу выбрать, когда спрашивать подтверждение — всегда, только для рискованных предложений или никогда, — чтобы проверка не мешала опытной игре.

**Priority:** Must

#### Acceptance Criteria

1. WHERE режим подтверждения равен «Всегда» мод SHALL открывать экран проверки для каждого ручного предложения игрока.
2. WHERE режим равен «Только рискованные» (значение по умолчанию, решение владельца) мод SHALL открывать экран проверки, только если найден хотя бы один риск из FR-3.3. Иначе мод SHALL пропускать предложение без экрана и записывать в журнал «отправлено (автоподтверждение: рисков нет)».
3. WHERE режим равен «Никогда» мод SHALL пропускать все ручные предложения без экрана и всё равно записывать их в журнал.
4. WHEN игрок отмечает на экране проверки «Больше не спрашивать для безопасных» THEN мод SHALL переключить режим на «Только рискованные» и сохранить его в `ModSettings` (`confirmMode`).
5. IF предложение отправляет автоматика (`ContractAutomation.SendOffers`), ИИ (`AIBehaviourContract.OnTick`) или другая фича через API мода THEN мод SHALL никогда не открывать экран проверки.
6. WHEN игрок меняет режим в настройках фичи (хаб «Моды») THEN мод SHALL применять новый режим со следующего нажатия без перезагрузки.

#### Scenarios
- **AC-4.1** Given режим «Только рискованные» и безопасный контракт (линий хватает, прибыль выше порога, вероятность 45 %). When игрок отправляет предложение. Then экрана нет, предложение отправлено, в журнале «автоподтверждение: рисков нет».
- **AC-4.2** Given режим «Всегда». When 31 декабря автоматика отправляет предложения. Then экранов нет, в журнале записи с источником «автоматика».

#### Additional Details
- **Complexity:** Low
- **Dependencies:** FR-3; `mod-framework` (ModSettings)
- **Assumptions:** значение режима по умолчанию — «Только рискованные» (решение владельца, см. «Решения по умолчанию»).

### FR-5: Итоги тендеров на дату рассмотрения

**User Story:** Как игрок, я хочу узнавать, выиграл ли я каждый контракт, на который подавал предложение, а если проиграл — кому и почему, чтобы делать выводы.

**Priority:** Must

#### Acceptance Criteria

1. WHEN `Contract.ChooseCpu` завершается для контракта, в котором было хотя бы одно предложение игрока, THEN мод SHALL записать итог тендера: дата, клиент, CPU игрока, исход (выигран / проигран / не состоялся), победитель (компания и CPU), шанс игры и фактическая вероятность CPU игрока на момент розыгрыша, полный список предложений с шансами и список снятых предложений с причинами.
2. WHEN итог «проигран» THEN мод SHALL указать причину из списка: «победил конкурент (розыгрыш)», «снято автоотменой: не хватает линий», «затенено: учитывался ваш более мощный CPU», «CPU снят с производства».
3. WHEN итог «не состоялся» (`ChosenCpuID = −1`) THEN мод SHALL указать причину: «нет предложений после проверки мощностей» или «выбранный CPU снят с производства (`Cpu.IsRetired`)».
4. WHEN за игровой день появились новые итоги тендеров с участием игрока THEN мод SHALL в обработчике `TickPhase.DayPassed` того же дня отправить одно письмо-сводку через `ModMail.Send` (`Tag = "ct:tenders:<yyyy-MM-dd>"`, `Priority = MailPriority.Normal`; по строке на контракт: выиграно / проиграно / не состоялось; с действием «Открыть журнал») и, IF среди итогов есть проигрыш и включена настройка «Сообщать о проигранных тендерах», одно уведомление через `ModNotify` (решение владельца: одна сводка в день, а не письмо на каждый контракт).
5. WHILE идёт перемотка новой игры (`ModTicks.IsFastForwarding`) или загрузка (`ModTicks.IsLoading`) мод SHALL не записывать итоги и не отправлять писем (политика владельца: фичи нейтральны в перемотке). WHILE идёт пакетный прогон месяца (`ModTicks.IsBatchRun`) мод SHALL записывать итоги как обычно, а письмо и уведомление ядро показывает после `ModTicks.BatchEnded`.
6. WHEN игрок нажимает в письме-сводке действие «Открыть журнал» (`ModMailAction`, `Repeatable = true`, письмо не закрывается) THEN мод SHALL открыть окно журнала с фильтром «Итоги тендеров».

#### Scenarios
- **AC-5.1** Given игрок предложил CPU (IPS 40), ИИ — CPU (IPS 60), и розыгрыш выбрал ИИ. When наступает 1 января. Then приходит одно уведомление «Проиграно тендеров: 1» и письмо «Итоги тендеров 1986», где строка контракта: «проигран: победил Intel с CPU Y; ваш шанс 40 % (факт. 21 %)».
- **AC-5.2** Given включена автоотмена и у игрока свободна 1 линия при нужных 3. When наступает дата рассмотрения. Then итог «проигран: снято автоотменой — нужно 3, занято 4 из 5».
- **AC-5.3** Given игрок выиграл. When наступает дата рассмотрения. Then игра, как и раньше, показывает своё окно «Контракт подписан»; в письме-сводке строка «выигран».
- **AC-5.4** Given игрок нажимает «Следующий месяц» в декабре, и 1 января внутри пакетного прогона проиграно 3 контракта. When прогон завершён. Then в журнале 3 итога, письмо и уведомление приходят один раз после `BatchEnded`.

#### Additional Details
- **Complexity:** Medium
- **Dependencies:** FR-8; `mod-framework` (ModMail с тегами, приоритетами и действиями; ModNotify; ModTicks)
- **Assumptions:** пакет контрактов создаётся 1 января (`ContractManager` на `OnYearPassed`), а дата рассмотрения — тот же месяц следующего года (`Contract.Setup`). Поэтому почти все розыгрыши проходят 1 января в `OnEarlyTick`, и сводка обычно приходит раз в год.

### FR-6: Журнал автоматики предложений

**User Story:** Как игрок с включённой автоматикой контрактов, я хочу видеть, какие предложения она отправила и почему пропустила остальные, чтобы ей доверять и настраивать порог маржи.

**Priority:** Must

#### Acceptance Criteria

1. WHEN выполняется `ContractAutomation.SendOffers` и `Player.AutomateContracts` включён («Автоподписание контрактов») THEN мод SHALL записать в журнал решение по каждой паре «CPU игрока × доступный контракт» с причиной: «отправлено»; «уже было отправлено»; «пропущено: CPU снят с производства»; «пропущено: CPU не продаётся по контрактам (`SellOnContracts`)»; «пропущено: маржа X % < порога Y %»; «отклонено игрой: не прошёл требования» (с указанием требования).
2. WHEN мод записывает решение по марже THEN мод SHALL указать формулу и числа: `(PaymentPerUnit − Cpu.RealUnitCostWithNewPrice(PaymentPerUnit)) / PaymentPerUnit` и `Player.ContractProfitMargin / 100`.
3. WHEN `ContractAutomation.SendOffers` выполняется при выключенной автоматике THEN мод SHALL записать одну запись «автоматика выключена — предложения не отправлялись».
4. WHEN прогон автоматики завершён THEN мод SHALL записать итоговую запись «автоматика 31.12: отправлено N, пропущено M (по марже K, по требованиям L)».
5. IF фактический результат игры (разница `Contract.OffersIDs` до и после) расходится с предсказанным решением THEN мод SHALL записать фактический результат и пометку «расхождение с моделью» в `ModLog`.

#### Scenarios
- **AC-6.1** Given автоматика включена, порог 40 %, у игрока 2 CPU и 3 доступных контракта. When наступает 31 декабря. Then в журнале 6 записей решений и одна итоговая; число отправленных совпадает с числом новых предложений игрока в окне контрактов.
- **AC-6.2** Given CPU с маржой 35 % при пороге 40 %. When прогон автоматики. Then запись «пропущено: маржа 35 % < 40 % (оплата 199 $, себестоимость 129 $)».

#### Additional Details
- **Complexity:** Medium
- **Dependencies:** FR-8; `mod-framework` (ModHooks)
- **Assumptions:** `ContractAutomation.SendOffers` вызывается только в `OnDayPassed` 31 декабря (подтверждено кодом).

### FR-7: Журнал автоотмены предложений

**User Story:** Как игрок с включённой автоотменой («Автоотмена предложений»), я хочу знать, какие мои предложения игра сняла в дату рассмотрения и сколько линий не хватило, чтобы планировать расширение фабрики.

**Priority:** Must

#### Acceptance Criteria

1. WHEN в `Contract.ChooseCpu` из `Contract.OffersIDs` удаляется предложение CPU игрока THEN мод SHALL записать в журнал запись «снято автоотменой» с числами: нужно линий (`ProductionMath.RequiredProductionLines(cpu, Units)`), занято (`ContractHelper.ContractedProductionLines(Manufacturer.Owner)`), мощность (`FactoryBase.ProductionCapacity` производителя) и производитель (своя фабрика или литейщик).
2. IF автоотмена выключена THEN мод SHALL пометить в итоге тендера (FR-5), что игра проверку мощностей для игрока не делала и после подписи возможны штрафы за недопоставку `FinePerUnit`.
3. WHEN в `Contract.ChooseCpu` снимается предложение конкурента-ИИ из-за мощностей THEN мод SHALL отразить это в итоге тендера как «конкурент X выбыл: нет мощностей».

#### Scenarios
- **AC-7.1** Given автоотмена включена, мощность 5 линий, занято 4, нужно 3. When дата рассмотрения. Then в журнале «снято автоотменой: нужно 3, занято 4 из 5 (своя фабрика)».

#### Additional Details
- **Complexity:** Low
- **Dependencies:** FR-5, FR-8
- **Assumptions:** проверка мощностей для CPU игрока в `Contract.ChooseCpu` выполняется только при `Player.AutomateRejection = true`, для ИИ — всегда (подтверждено кодом).

### FR-8: Окно журнала контрактов

**User Story:** Как игрок, я хочу открыть журнал всех событий по контрактам с фильтрами, чтобы найти, что произошло и когда.

**Priority:** Must

#### Acceptance Criteria

1. WHEN игрок нажимает «Журнал» в окне контрактов или выбирает «Контракты: журнал» в хабе «Моды» THEN мод SHALL открыть окно журнала с записями от новых к старым.
2. WHEN окно открыто THEN мод SHALL дать фильтры: «Все», «Мои действия», «Автоматика», «Автоотмена», «Итоги тендеров», «Сделки между компаниями».
3. WHEN игрок выбирает запись THEN мод SHALL показать её подробности: числа, причину, связанный контракт и CPU.
4. WHILE журнал хранит записи мод SHALL держать не больше `log.capacity` записей (по умолчанию 500, из контента) и итоги тендеров не старше `tenderHistoryYears` лет (по умолчанию 10); старые удаляются первыми.
5. WHEN игра сохраняется THEN мод SHALL записать журнал в секцию `contract-transparency` бокового файла `ModSave` (участник `IModSaveParticipant`, версию секции `_schema` ведёт ядро); WHEN сейв загружается THEN мод SHALL восстановить журнал.

#### Scenarios
- **AC-8.1** Given в журнале 520 событий за игру. When игрок сохраняет и загружает игру. Then в журнале 500 самых новых записей, фильтры работают.

#### Additional Details
- **Complexity:** Medium
- **Dependencies:** `mod-framework` (ModUI, ModSave, хаб «Моды»)
- **Assumptions:** у контракта игры нет уникального ID. Связь записей с контрактом идёт через составной ключ (см. Glossary «ContractKey»).

### FR-9: Предпросмотр автоматики

**User Story:** Как игрок, я хочу заранее видеть, какие предложения отправит автоматика 31 декабря при текущем пороге маржи, чтобы настроить ползунок до того, как станет поздно.

**Priority:** Should

#### Acceptance Criteria

1. WHEN игрок открывает вкладку «Предпросмотр автоматики» в окне журнала THEN мод SHALL показать для текущего состояния решения по каждой паре «CPU × контракт» по тем же правилам, что FR-6, без отправки предложений.
2. WHEN игрок меняет ползунок маржи в окне контрактов THEN мод SHALL пересчитать предпросмотр при следующем открытии вкладки или по кнопке «Обновить».
3. IF автоматика выключена THEN мод SHALL показать предпросмотр с пометкой «автоматика выключена — 31 декабря ничего не будет отправлено».
4. WHEN предпросмотр показан THEN мод SHALL указать дату следующего прогона (31 декабря текущего года) и число дней до него.

#### Scenarios
- **AC-9.1** Given порог 40 % и 3 пары с маржой 55/38/20 %. When игрок открывает предпросмотр. Then 1 «будет отправлено» и 2 «будет пропущено по марже»; после установки порога 35 % и «Обновить» — 2 «будет отправлено».

#### Additional Details
- **Complexity:** Low
- **Dependencies:** FR-6, FR-8
- **Assumptions:** ползунок записывает значение в `Player.ContractProfitMargin` каждым `ContractAutomation.FixedUpdate`, поэтому предпросмотр читает `Player.ContractProfitMargin`.

### FR-10: Подтверждение подписи сделки между компаниями

**User Story:** Как игрок, заключающий сделку по услугам литейщика с другой компанией, я хочу подтвердить её условия перед подписью, чтобы не подписать сделку случайным кликом.

**Priority:** Should

#### Acceptance Criteria

1. WHEN игрок нажимает «Подписать контракт» в `ContractNegotiationWindow` и режим подтверждения не «Никогда» THEN мод SHALL не подписывать сделку сразу (prefix на `ContractNegotiationWindow.SignContract`) и SHALL открыть модальное подтверждение `ModUI.Confirm`.
2. WHEN подтверждение открыто THEN мод SHALL показать в его тексте поставщика, клиента, срок в годах, долю линий, наценку, эксклюзивность, штрафы поставщика и клиента (`BusinessMath.ProviderFines`, `BusinessMath.ClientFines`) и итоговую оценку согласия — значения из полей окна.
3. WHEN игрок подтверждает («Подписать») THEN мод SHALL вызвать исходную подпись (`ContractNegotiationWindow.SignContract`) и записать в журнал запись «Сделка подписана».
4. WHEN игрок отменяет THEN мод SHALL оставить окно переговоров открытым без изменений.

#### Scenarios
- **AC-10.1** Given окно переговоров с литейщиком: 5 лет, 40 %, наценка 110 %. When игрок нажимает «Подписать контракт» и затем «Нет». Then сделки нет, окно переговоров открыто с теми же значениями.

#### Additional Details
- **Complexity:** Low
- **Dependencies:** FR-4, FR-8; `mod-framework` (`ModUI.Confirm`)
- **Assumptions:** в режиме «Только рискованные» сделки подтверждаются всегда: у подписи BusinessContract нет числовой модели риска в этой спеке. Решение владельца об оставлении FR-10 принято по общему правилу (см. «Решения по умолчанию»).

### FR-11: Оценка возможных конкурентов

**User Story:** Как игрок, я хочу видеть, какие ИИ-компании ещё могут подать предложение до даты рассмотрения, чтобы понимать, насколько надёжен текущий шанс.

**Priority:** Could

#### Acceptance Criteria

1. WHEN разбор шанса открыт и до даты рассмотрения есть хотя бы один ежемесячный ход ИИ THEN мод SHALL показать список «возможные участники»: CPU ИИ, которые проходят требования (`Contract.FailsAtAnyRequirement` = false), не сняты с производства, продаются по контрактам и имеют маржу ≥ порога ИИ (0.45, копия литерала из `AIBehaviourContract.OnTick`, хранится в контенте).
2. WHEN список показан THEN мод SHALL показать «пессимистичную» фактическую вероятность, как если бы все возможные участники подали лучшие CPU, и пометку «оценка: фокус ИИ на типах контрактов не учитывается».

#### Scenarios
- **AC-11.1** Given текущий шанс 100 % (других предложений нет) и у двух ИИ есть подходящие CPU с IPS 50 и 70. When разбор открыт для CPU игрока с IPS 60. Then «возможные участники: 2», пессимистичная вероятность рассчитана по трём предложениям.

#### Additional Details
- **Complexity:** Low
- **Dependencies:** FR-2
- **Assumptions:** раскрытие этой информации не считается читом (решение владельца: возможных конкурентов-ИИ показываем).

### FR-12: Согласованность с игрой

**User Story:** Как игрок, я хочу быть уверен, что объяснения мода совпадают с тем, что реально делает игра, чтобы не принимать решений по неверным числам.

**Priority:** Must

#### Acceptance Criteria

1. WHEN мод строит разбор требований THEN мод SHALL сверить свой итог с `Contract.FailsAtAnyRequirement(cpu)`. IF они расходятся THEN мод SHALL показать итог игры, пометить панель «расхождение с игрой» и записать подробности в `ModLog`.
2. WHEN мод показывает шанс игры THEN мод SHALL сверить значение для CPU игрока с `Contract.ChanceToSign(cpu)`. IF они расходятся больше чем на 0.5 п. п. THEN мод SHALL показать значение `ChanceToSign` и записать расхождение в `ModLog`.
3. WHEN мод читает приватные члены игры (`Contract.mipsToleranceMultiplier`, `Contract.GetBestOffers`, вложенный тип `Contract.CpuOffer`, поля `ContractWindow`) и член не найден THEN мод SHALL отключить зависящие от него части фичи (разбор шанса, экран проверки, дописывание вероятности), оставить ванильное поведение и записать причину в `ModLog`.
4. WHEN фича работает THEN мод SHALL не менять результат розыгрыша, шансы, штрафы и выплаты. Единственное вмешательство — откладывание ручного `Contract.AddOffer` до подтверждения.

#### Scenarios
- **AC-12.1** Given другой мод поменял `mipsToleranceMultiplier` на 0.7. When разбор открыт. Then порог IPS считается как 0.7 × `MinIps` и совпадает с `FailsAtAnyRequirement`.

#### Additional Details
- **Complexity:** Medium
- **Dependencies:** `mod-framework` (ModHooks — самопроверка целей, ModLog)
- **Assumptions:** нет.

### FR-13: Настройки и выключение фичи

**User Story:** Как игрок, я хочу выключить фичу или отдельные её части, чтобы вернуть ванильное поведение без потери сейва.

**Priority:** Must

#### Acceptance Criteria

1. WHEN игрок выключает фичу в `ModSettings` THEN мод SHALL перестать перехватывать `Contract.AddOffer` и `ContractNegotiationWindow.SignContract`, перестать дописывать вероятность, скрыть добавленные кнопки и перестать писать журнал. Перезапуск игры при этом не нужен (`SupportsHotToggle = true`; ядро не вызывает обработчики неактивной фичи).
2. WHEN фича выключена THEN мод SHALL сохранять существующую секцию журнала в `ModSave` без изменений.
3. WHEN игрок открывает настройки фичи в хабе «Моды» THEN мод SHALL показать: «Включено», «Режим подтверждения» (Всегда / Только рискованные / Никогда), «Показывать фактическую вероятность», «Сообщать о проигранных тендерах», «Журнал автоматики».
4. IF открыт экран проверки и фичу выключают THEN мод SHALL закрыть экран без отправки предложения.

#### Scenarios
- **AC-13.1** Given фича выключена. When игрок отправляет предложение. Then предложение уходит сразу, как в ванильной игре; текста «факт.» нет; кнопок «Почему?» и «Журнал» нет.

#### Additional Details
- **Complexity:** Low
- **Dependencies:** `mod-framework` (ModSettings, хаб «Моды»)
- **Assumptions:** нет.

### FR-14: События и предикаты для других фич

**User Story:** Как автор другой фичи (`first-year-onboarding`, `scenarios-achievements`), я хочу подписаться на события «предложение отправлено» и «тендер разыгран» и использовать их в условиях, чтобы строить обучение и цели без своих патчей контрактов.

**Priority:** Could

#### Acceptance Criteria

1. WHEN предложение игрока отправлено (любым путём) THEN мод SHALL поднять событие `ContractTransparencyEvents.OfferSent` с ключом контракта, CPU и источником (вручную / автоматика / API) через `ModHooks.Raise` (ошибка подписчика изолируется и засчитывается его фиче).
2. WHEN тендер с участием игрока разыгран THEN мод SHALL поднять событие `ContractTransparencyEvents.TenderResolved` с итогом из FR-5 (не в перемотке и не при загрузке).
3. WHEN фича инициализируется THEN мод SHALL зарегистрировать в `ModConditions` предикаты `{ "type": "ct.offersSent", "atLeast": n }` и `{ "type": "ct.tendersWon", "atLeast": n }` (имена по соглашению о префиксах: `ct.<name>`; счётчики хранятся в секции `ModSave`).

#### Scenarios
- **AC-14.1** Given обучение ждёт первого отправленного предложения. When игрок отправляет предложение. Then событие `OfferSent` поднято один раз, предикат `{ "type": "ct.offersSent", "atLeast": 1 }` истинен.

#### Additional Details
- **Complexity:** Low
- **Dependencies:** `mod-framework` (ModConditions, ModIds)
- **Assumptions:** нет.

## Non-Functional Requirements

### NFR-1: Производительность
- WHEN идёт обычный игровой день THEN фича SHALL добавлять не больше 0.05 мс работы на тик: только проверку непустого буфера итогов в обработчике `TickPhase.DayPassed`.
- WHEN строится разбор шанса для контракта с 14 предложениями THEN мод SHALL укладываться в 5 мс.
- WHEN выполняется `ContractAutomation.SendOffers` для 50 CPU игрока и 20 контрактов THEN журналирование SHALL добавлять не больше 20 мс.
- WHEN разыгрывается контракт (`Contract.ChooseCpu`) THEN запись итога (с повторным вызовом `Contract.GetBestOffers`) SHALL занимать не больше 1 мс.

### NFR-2: Надёжность
- IF в любом патче фичи возникает исключение THEN мод SHALL перехватить его на границе хука (`ModHooks.Guard`), записать в `ModLog` и вернуть управление игре так, как будто патча нет. Prefix на `Contract.AddOffer` при ошибке возвращает `true`, и предложение уходит по-ванильному.
- IF число сбоев фичи за сессию достигло порога `hooks.faultThreshold` (по умолчанию 5, circuit breaker `mod-framework`) THEN фича SHALL перейти в состояние `Faulted` (ванильное поведение до перезапуска), а мод SHALL показать одно уведомление `ModNotify`. Своих счётчиков ошибок фича не ведёт.

### NFR-3: Совместимость сейвов
- WHEN загружается сейв без бокового файла или без секции `contract-transparency` THEN мод SHALL начать с пустого журнала без ошибок.
- WHEN мод удалён THEN сейв игры SHALL загружаться в ванильной игре: фича не пишет в `SaveObject` и не добавляет полей в классы игры.
- WHEN версия секции меняется THEN мод SHALL мигрировать данные по версии `schema`, которую ядро передаёт в `IModSaveParticipant.Read` (поле `_schema` секции пишет и читает ядро; в данных фичи поля версии нет).

### NFR-4: Локализация
- WHEN язык мода `ru` (по умолчанию) или `en` THEN все строки фичи SHALL браться из `ModL10n` по ключам `ct.*`, с английским фолбэком; числа SHALL форматироваться функциями игры `StringFormatter.FloatToMoney` и `StringFormatter.FloatToIps`.
- Термины интерфейса игры SHALL совпадать с переводом `ptru`: «Предложить» (`Send Offer`), «Отозвать» (`Cancel Offer`), «Вероятность:», «Автоотмена предложений» (`automateRejectionToggle`), «Автоподписание контрактов» (`automateContractsToggle`), «Контракт подписан» / «Контракт расторгнут», «Подписать контракт».
- Имена клиентов (`Contract.Company`) и CPU мод SHALL показывать как есть, без перевода (имена компаний и клиентов — реальные, как в русификаторе: Apple, Intel, IBM и т. д.).

### NFR-5: Удобство
- WHEN игрок в окне контрактов THEN разбор шанса SHALL открываться в 1 клик (кнопка «Почему?» рядом с вероятностью), журнал — в 1 клик (кнопка «Журнал»).
- WHEN показываются проценты и деньги THEN мод SHALL использовать цвета темы игры (положительный / отрицательный, `Colors.Instance`) и обновляться при смене темы (`ThemeManager.OnThemeChanged` через переприменение темы ядром).
- Экран проверки SHALL помещаться без прокрутки при разрешении 1280×720.

### NFR-6: Объём данных
- WHEN журнал заполнен до лимита THEN секция `contract-transparency` в `ModSave` SHALL занимать не больше 256 КБ.

### NFR-7: Безопасность данных
- WHEN мод читает секцию `ModSave` или `rules.json` THEN он SHALL проверять типы, диапазоны, длину строк (≤ 128 символов) и число записей. Невалидные записи отбрасываются с записью в `ModLog`, ничего не исполняется.
- WHEN мод выводит строки из сейва (имена клиентов, CPU) THEN он SHALL экранировать TMP-разметку (`<`, `>`).
- Фича SHALL не обращаться к сети и не читать файлы, кроме контента `ModContent` и бокового файла `ModSave`.

## Edge Cases

| # | Ситуация | Ожидаемое поведение |
|---|---|---|
| E1 | В контракте нет предложений | Шанс 100 % (как `ChanceToSign`), пояснение про ежемесячные предложения ИИ |
| E2 | Игрок предложил несколько своих CPU | Учитывается сильнейший, остальные помечены «затенено» (FR-2.6) |
| E3 | Равный IPS у двух компаний | Шансы равны, но первой в очереди стоит компания, предложившая раньше. Разбор показывает её преимущество (ошибка игры объясняется, не исправляется) |
| E4 | Шанс клампится до 1 % | Фактическая вероятность может быть 0 % (AC-2.3) |
| E5 | CPU игрока снят с производства после отправки предложения | В итоге тендера: если выбран снятый CPU, контракт «не состоялся» для всех |
| E6 | `CpuDataProvider.GetCpu` вернул `null` для ID из `OffersIDs` | Строка «неизвестный CPU» в разборе; в `ModLog` предупреждение о риске зависания игры в `Contract.ChooseCpu` (ошибка игры, мод её не исправляет) |
| E7 | CPU игрока производится у литейщика (`Cpu.IsOutsourced`) | Мощности берутся у производителя (`Cpu.Manufacturer`), себестоимость — с роялти 5 % |
| E8 | Другая фича добавила контракты не 1 января (`ContractInstantiator.AddNewContracts`) | Итоги приходят в день их рассмотрения, сводка отправляется в тот же день |
| E9 | Сейв загружен в середине года | Журнал восстановлен; итоги, разыгранные во время загрузки, не записываются (FR-5.5) |
| E10 | Экран проверки открыт, а контракт за это время разыгран | Невозможно: время на паузе (FR-3.6). Если пауза снята другим кодом и контракт исчез из `ContractManager.ContractExists`, экран закрывается с сообщением «контракт больше недоступен» |
| E11 | Выбран уровень сложности 5 (ИИ-лидеры принудительно берут все типы контрактов) | Оценка конкурентов (FR-11) помечена «на этой сложности ИИ активнее» |
| E12 | Шанс игры изменён модами больше 100 % до клампа | Показывается итог после клампа игры, множитель — до клампа |
| E13 | Провайдер канала `contract.signChance` не передал причину (`ReasonKey = null`) | Строка «Модификаторы модов: ×k» и под ней «{фича} ×k» без текста причины |
| E14 | Розыгрыш 1 января внутри пакетного прогона (`ModTicks.IsBatchRun`) | Итоги пишутся по дням; письмо и уведомление показываются после `BatchEnded` (FR-5.5) |

## Constraints and Assumptions

### Technical Constraints
- Только через сервисы `PTMod.Core` (ModHooks, ModSave, ModSettings, ModUI, ModMail, ModNotify, ModL10n, ModContent, ModConditions, ModModifiers, ModCompanies, ModLog, ModTicks). Поля в классы игры не добавляются. Точка входа — `[ModFeature] sealed class ContractTransparencyFeature : IModFeature`.
- Приватные члены игры (`Contract.ChooseCpu`, `Contract.mipsToleranceMultiplier`, `ContractAutomation.SendOffers`, `ContractWindow.UpdateProbabilityText`, `ContractNegotiationWindow.SignContract`) доступны только через Harmony/AccessTools. Приватный `Contract.GetBestOffers` фича **вызывает**, но не патчит: цель закреплена за ядром (P23), `ModHooks` отклонил бы такой патч. Наличие членов проверяет самопроверка `ModHooks`.
- Лямбды игры (`ContractWindow.<Start>b__50_3` и т. п.) не патчатся.
- Числовые пороги (риск по вероятности, лимиты журнала, порог маржи ИИ 0.45) лежат в `Content/contract-transparency/rules.json`.
- Тесты чистой логики — мини-раннер ядра (`python mod/build.py --tests`, .NET Framework 4.8, `mod/tests/PTMod.Tests/ContractTransparency/`); код `Logic/` использует общее подмножество API .NET Framework 4.8 и `mscorlib` Unity (без `init`, `record`, `Index`, `Range`). Сборка — `python mod/build.py --game-dir <папка игры>` (Roslyn `csc` из VS Build Tools).

### Business Constraints
- Баланс не меняется (FR-12.4). Это требование владельца к волне 1: фичи «просьб игроков» безопасны для сейвов и баланса.
- Ручная проверка в игре — шаг владельца.

### Assumptions
- `mod-framework` даёт (по `mod-framework/design.md` v0.2): `IModFeature` и `FeatureContext`; патчи `[ModPatch]` с `ModHooks.Guard` и circuit breaker; `ModTicks` с защитой от перемотки и загрузки, `IsBatchRun`, `BatchEnded`; `IModSaveParticipant` (версия секции — `_schema`, ядро); окна `ModUI.CreateWindow` (модальные — с паузой) и `ModUI.Confirm`; письма `ModMail` с тегами, приоритетами, выборами и действиями (`ModMailAction`); `ModModifiers.Explain` с `ModifierContext.Contract`; страницу хаба «Моды».
- Канал `contract.signChance` применяется в postfix `Contract.CpuOffer.DefineChance` (P8 `mod-framework`), контракт захватывает P23. `Contract.AddOffer`, `Contract.ChooseCpu`, `ContractAutomation.SendOffers`, `ContractWindow.*`, `ContractNegotiationWindow.SignContract` не закреплены ядром, поэтому фича может их патчить; `ModHooks.IsReserved` для них возвращает `false`.
- Игроки читают письма во внутриигровой почте (`EmailWindow`).

## Открытые вопросы владельцу

Остался один вопрос, который `owner-decisions.md` не решает. Он не блокирует реализацию: действует решение по умолчанию.

1. **Различение контрактов в дневном кеше ядра.** `mod-framework` включает «ID контракта» в ключ дневного кеша `contract.signChance`. Если это `Contract.ContractID`, то он — индекс шаблона данных (`ContractInstantiator.AddNewContracts`), а не уникальный номер: два контракта одного шаблона от разных клиентов могут получить общее значение кеша, и разбор покажет множитель соседнего контракта. По умолчанию: сверка шанса с `Contract.ChanceToSign` (FR-12.2) ловит такое расхождение и пишет его в `ModLog`; в ядре ключ кеша стоит строить по идентичности объекта `Contract`. Решает владелец `mod-framework`.

## Glossary

| Термин | Значение |
|---|---|
| OEM-контракт | `Contract`: заказ клиента (`Contract.Company`) на `Units` CPU в месяц по `PaymentPerUnit` с требованиями `MinIps`, `MaxPowerConsumption`, `PackageType` |
| Предложение (offer) | ID CPU в `Contract.OffersIDs`, добавленный `Contract.AddOffer` (кнопка «Предложить»; отзыв — «Отозвать»). «Предложить» в игре — аналог «подписи»: при выигрыше обязательства наступают автоматически |
| Дата рассмотрения | `Contract.AcceptanceDate`: день розыгрыша (`Contract.OnTick` → `Contract.ChooseCpu`) |
| Шанс игры | `Contract.CpuOffer.Chance`: доля IPS лучшего CPU компании, клампленная 1..100, с множителями модов |
| Ванильный шанс | Тот же шанс без модов: `clamp(round(100 × IPS / ΣIPS_лучших), 1, 100)` |
| Фактическая вероятность | Вероятность выигрыша с учётом порядка розыгрыша `Contract.ChooseCpu` (формула в FR-2.4) |
| Затенённое предложение | Предложение CPU, у компании которого есть предложение с бо́льшим IPS; в розыгрыше не участвует |
| Автоматика («Автоподписание контрактов») | `ContractAutomation.SendOffers`: 31 декабря отправляет предложения CPU игрока при марже ≥ `Player.ContractProfitMargin` (`Player.AutomateContracts`) |
| Автоотмена («Автоотмена предложений») | `Player.AutomateRejection`: в дату рассмотрения снимает предложения игрока, если не хватает линий |
| Итог тендера | Запись о результате розыгрыша контракта, в котором участвовал игрок |
| ContractKey | Составной ключ контракта для журнала: `Company|AcceptanceYear-AcceptanceMonth|Units|round(PaymentPerUnit)|ContractType` |
| Экран проверки | Модальное окно с обязательствами и рисками перед отправкой предложения |
| BusinessContract | Сделка между компаниями (услуги литейщика), подписывается в `ContractNegotiationWindow` |
| Тег письма | `ct:tenders:<yyyy-MM-dd>`: по нему фича находит свою сводку (`ModMail.Find`) |
