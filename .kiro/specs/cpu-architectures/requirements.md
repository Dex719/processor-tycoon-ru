## Introduction

В игре процессор описывается корпусом, техпроцессом, памятью, частотой, кэшем и числом ядер, но не архитектурой. При этом игра уже готовила это понятие: в инспекторе CPU есть поле «Architecture» с постоянным текстом «Default» (`CpuUI.SetCpu`), окно дизайна микроархитектуры `CreatorCoreDesign` пустое, а поле `SaveObject.Cpu.CoreDesignID` нигде не используется. Автор игры говорил, что архитектуры запланированы. Игроки просят эту прогрессию.

Фича вводит **семейства архитектур** (собственная ISA, x86, RISC — MIPS, PowerPC, SPARC, ARM, x86-64, ARM64, RISC-V) как отдельную ветку исследований. Архитектура исследуется **в той же лаборатории**, что и обычные технологии: пока идёт исследование архитектуры, технологии стоят (прогресс технологий сохраняется), скорость и стоимость считаются по формулам лаборатории. Архитектура становится атрибутом дизайна CPU и меняет IPC, потребление и стоимость разработки. Через стандартный канал `market.rating.cpu` она влияет на рейтинг CPU по сегментам рынка: например, ARM силён в «Промышленности», x86 — в потребительских сегментах, а собственная ISA устаревает после распространения x86. Компании без лицензии x86 платят роялти, но не получают запрета. На полном этапе добавляется **программная поддержка** (уровень 0…100 на компанию и архитектуру): она стоит денег каждый месяц и без вложений падает. Добавляется и **экосистема**: доля архитектуры в продажах рынка. Поддержка открывает полный эффект расширений (многоядерность, SMT). ИИ-соперники выбирают и исследуют архитектуры по своим историческим предпочтениям и получают те же множители и ту же общую лабораторию, что и игрок.

### Feature Summary

Архитектуры как ветка исследований в общей лаборатории и атрибут дизайна CPU: влияют на характеристики и на рейтинг по сегментам; на полном этапе добавляются программная поддержка, экосистема, опыт ISA, ворота расширений и роялти x86; ИИ выбирает архитектуру сам.

### Business Value

- **Для игрока**: новый стратегический выбор с долгими последствиями: на какую ISA ставить, когда переходить, сколько тратить на поддержку ПО, чем занять лабораторию — технологией или архитектурой. Исследования расширений окупаются не только «голыми» цифрами. Появляется историческая дуга индустрии 1971–2030: собственные ISA → победа x86 в ПК → ARM во встраиваемых → 64 бита → открытые ISA.
- **Доказательства спроса** (IDEAS.md, I09): игроки просят будущие архитектуры, разработчик объявлял архитектуры в планах (itch.io «planned features»); идея с fun 4/5. Код игры содержит заготовки (`CpuUI.architectureText` = «Default», пустой `CreatorCoreDesign.CreateCoreDesign`, неиспользуемое `CoreDesignID`).
- **Для проекта**: эталон «большой контентной» фичи на JSON-контенте, каналах `ModModifiers` (рейтинг и стоимость проекта), событиях `ModEvents` и общей лаборатории; первый потребитель API `research-tree-ux`.

### Scope

**Входит (этап 1 — MVP):**
- каталог 7 семейств архитектур в контент-JSON (утверждён владельцем);
- исследование архитектур в **общей лаборатории**: архитектура занимает единственный слот `ResearchSector` вместо технологии, скорость, стоимость и финансирование — лаборатории;
- вкладка «Архитектуры» в дереве исследований через API `research-tree-ux`; запасное окно в хабе «Моды»;
- выбор архитектуры в конструкторе CPU (`CreatorCpu`) и её влияние на IPC, потребление/температуру (патчи конструктора) и стоимость разработки (провайдер канала `development.cost.design`); то же для CPU ИИ;
- привязка архитектуры к каждому CPU (боковой файл `ModSave`), показ в инспекторе вместо «Default» и в окне сравнения;
- множитель рейтинга CPU по сегментам (провайдер стандартного канала `market.rating.cpu`): сродство архитектуры с сегментом и устаревание собственной ISA;
- ИИ: исторический посев по `AICompany.UniqueID`, выбор исследований по предпочтениям, смена «активной» архитектуры, та же общая лаборатория;
- посев при новой игре (`TickPhase.FastForwardEnded` для ИИ, `ModTicks.GameReady` для игрока) и миграция старых сейвов; нейтральность во время перемотки новой игры; выключение фичи.

**Входит (этап 2 — полная версия):**
- программная поддержка: уровни финансирования, содержание в месяц, сходимость и затухание, влияние на рейтинг;
- экосистема: доля архитектуры в продажах за 12 месяцев и её влияние на рейтинг;
- опыт ISA: ускоренное исследование преемника той же ISA, наследование поддержки, «незрелые инструменты» новой архитектуры (+25 % к стоимости проектов первые 12 месяцев);
- ворота расширений: многоядерность и SMT дают полный эффект на рынке только при достаточной поддержке;
- адаптивный ИИ: выбор активной архитектуры по сегментам, экосистеме и поддержке, финансирование поддержки;
- роялти за x86 без лицензии (без запрета);
- обзор архитектур: доли экосистем, сводка по соперникам, уведомления о вехах.

**Не входит:**
- дизайн микроархитектуры, планировка кристалла (I08, `CreatorCoreDesign`);
- продажа лицензий ISA соперникам (I17) и изменение механики отзыва лицензии x86 (`LicenseHelper.X86LicenseHasBeenRevoked`); здесь используется только простое роялти за x86 без лицензии (FR-16);
- поколения сокетов и установленная база платформ (`platform-generations`), GPU-архитектуры (`gpu-product-line`);
- архитектура как условие OEM-контрактов (I39), обзоры прессы (`press-reviews`);
- изменение `TechnologyType`, добавление объектов `Technology` и полей в классы игры;
- колонка «Архитектура» в таблице CPU `HardwareWindow` (решение по общему правилу: только инспектор и сравнение).

## Requirements

### FR-1: Каталог семейств архитектур (этап 1)

**User Story:** Как игрок, я хочу видеть набор архитектур с понятными сильными и слабыми сторонами и годами появления, чтобы планировать путь развития компании.

**Priority**: Must

#### Acceptance Criteria

1. WHEN мод загружает контент THEN мод SHALL прочитать семейства архитектур из `Content/cpu-architectures/architectures.json` (переопределяемого из `<папка игры>/PTMod/content/cpu-architectures/`) с полями: `id`, ISA-группа, год появления, зависимости, время и стоимость исследования, множители дизайна (IPC, мощность, стоимость разработки), сродство с 4 сегментами (порядок `Segment`: HighEnd, MidRange, LowEnd, Industries), параметры поддержки.
2. WHEN контент валиден THEN мод SHALL содержать по умолчанию 7 семейств (утверждены владельцем): `proprietary` (1971), `x86` (1978), `risc` (1986; MIPS, PowerPC, SPARC), `arm` (1987), `x86_64` (2003, требует `x86`), `arm64` (2011, требует `arm`), `riscv` (2014).
3. IF запись контента невалидна (неизвестная зависимость, множитель вне [0,5; 2,0], сродство вне [0,7; 1,3], повтор `id`, цикл зависимостей) THEN мод SHALL пропустить запись, записать причину в `ModLog` и продолжить работу с остальными.
4. IF в каталоге нет семейства `proprietary` или оно невалидно THEN мод SHALL отключить фичу целиком с записью в лог (это архитектура по умолчанию).
5. WHERE мод показывает архитектуру мод SHALL брать название и описание из `ModL10n` по ключам из контента (`arch.family.<id>.name`); названия — реальные (x86, x86-64, ARM, RISC-V).

**Сценарии:**
- **AC-1.1** Given стандартный контент; When старт игры; Then в логе «cpu-architectures: 7 семейств загружено».
- **AC-1.2** Given в пользовательском `architectures.json` у `arm64` зависимость `armv7` (нет такого `id`); When старт; Then `arm64` пропущен с предупреждением, остальные 6 работают.

**Complexity**: Low
**Dependencies**: `ModContent`, `ModL10n`, `ModLog`
**Assumptions**: стартовые числа семейств и диапазон рейтинга [0,80; 1,20] утверждены владельцем 2026-10-10

### FR-2: Исследование архитектур в общей лаборатории (этап 1)

**User Story:** Как игрок, я хочу исследовать новые архитектуры за деньги и время в той же лаборатории, что и обычные технологии, чтобы выбор между технологией и архитектурой был стратегическим.

**Priority**: Must

#### Acceptance Criteria

1. WHEN игрок выбирает доступное семейство (зависимости исследованы, само не исследовано) и нажимает «Исследовать» THEN мод SHALL занять лабораторию: IF `ResearchSector.CurrentResearch()` ≠ null THEN мод SHALL открыть подтверждение `ModUI.Confirm` («Лаборатория занята технологией …; прогресс сохранится»), после «Да» остановить технологию (`ResearchSector.StopResearching`), запомнить её как прерванную и скрыть панель текущего исследования; затем SHALL сделать семейство текущим исследованием архитектуры компании; прогресс прежнего текущего семейства SHALL сохраниться.
2. WHILE архитектура занимает лабораторию мод SHALL каждый игровой день (`TickPhase.Tick`) увеличивать прогресс на `ResearchMath.ResearchSpeed(F, company) / effDays`, где F = `ResearchSector.Funding` (финансирование лаборатории), и списывать `monthlyCost × Modifiers.GetModifier(ResearchCost, company) / 30 × F` через `ICompany.SpendMoney(..., ExpenseOrigin.Research)`, где `effDays` учитывает штраф за опережение года и бонус за отставание так же, как `TechnologyTimeUpdater.UpdateTechnologyTimes` для обычных технологий. Каналы `research.speed` и `research.cost` ядра действуют автоматически через `Modifiers.GetModifier`.
3. WHILE архитектура занимает лабораторию мод SHALL держать `ResearchSector.CurrentResearch()` = null, поэтому игра не двигает прогресс технологий и не списывает за них деньги (`ResearchSector.Update` без текущей технологии не начисляет ни прогресс, ни стоимость); технология и архитектура одной компании не исследуются одновременно.
4. WHEN прогресс достигает 1 THEN мод SHALL отметить семейство исследованным, освободить лабораторию, вернуть её к прерванной технологии (п. 8) и показать игроку уведомление `ModNotify` «Архитектура … исследована».
5. IF игрок выбирает технологию в дереве или списке (родной путь `ResearchSector.SetCurrentResearch(Technology)`), пока архитектура занимает лабораторию, THEN мод SHALL в начале следующего тика (`TickPhase.EarlyTick`, до начисления прогресса) приостановить исследование архитектуры без потери прогресса и показать `ModNotify` «Исследование архитектуры приостановлено: лаборатория занята технологией …»; продолжить архитектуру игрок может кнопкой «Продолжить» (она останавливает технологию, как п. 1).
6. IF у компании игрока `ICompany.IsInDefault` THEN мод SHALL приостановить исследование архитектуры игрока без потери прогресса и показать причину в UI. Признак дефолта берётся из игры (он уже учитывает порог, который применяет ядро, `ModCredit.ThresholdOf`); собственного порога дефолта фича не считает и `CentralBank.DebtLimit` не читает.
7. WHEN игрок нажимает «Остановить» THEN мод SHALL снять текущее исследование архитектуры, сохранив прогресс, и вернуть лабораторию к прерванной технологии (п. 8).
8. WHEN лаборатория игрока освобождается (завершение, «Остановить», выключение фичи) THEN мод SHALL, IF прерванная технология ещё доступна, назначить её текущей (`ResearchSector.SetCurrentResearch(Technology)`, `CurrentResearchUI.SetTechnology(Technology)`) и показать `ModNotify` «Лаборатория вернулась к исследованию …»; для ИИ лабораторию возвращает игра (`AIBehaviourResearch` выбирает технологию сама).
9. IF `baseDays` семейства = 0 THEN мод SHALL считать его исследованным сразу при доступности (как технологии с `BaseTime` = 0).
10. WHERE архитектура занимает лабораторию игрока мод SHALL сообщать об этом `research-tree-ux` через `ILabOccupancySource` (строка «Лаборатория занята: Архитектура x86 — 43 %»; напоминание о простое не показывается).

**Сценарии:**
- **AC-2.1** Given 1980 год, компания типа IDM, финансирование 100 %, x86 (1978, 240 дн., 5M/мес); When игрок начинает исследование; Then ETA ≈ 194 дн. (240 × 0,85 бонуса отставания / 1,05 бонус IDM), списание ≈ 166 667 в день в статье «Research».
- **AC-2.2** Given идёт исследование ARM 40 %, игрок запускает RISC (слот занят архитектурой, технологии нет — подтверждение не нужно); When через месяц возвращается к ARM; Then прогресс ARM = 40 %.
- **AC-2.3** Given идёт технология «DDR» (прогресс 30 %); When игрок запускает «x86» и подтверждает; Then технология остановлена с прогрессом 30 %, `CurrentResearch()` = null, растёт и оплачивается только x86; после завершения x86 лаборатория возвращается к «DDR» (30 %).
- **AC-2.4** Given идёт x86; When игрок выбирает «L1 64 KB» в дереве; Then в начале следующего дня x86 приостановлена («лаборатория занята технологией»), деньги за x86 не списываются, прогресс x86 сохранён.

**Complexity**: Medium
**Dependencies**: FR-1; `ModTicks`; канал `research.speed`/`research.cost` действует автоматически через `Modifiers.GetModifier`; `research-tree-ux` (признак занятой лаборатории, мягко)
**Assumptions**: общая лаборатория — решение владельца (вместо параллельной ветки); см. D2 в `design.md`

### FR-3: Вкладка «Архитектуры» и запасное окно (этап 1)

**User Story:** Как игрок, я хочу видеть архитектуры рядом с остальными исследованиями, с их эффектами и статусом, чтобы выбирать без поиска по меню.

**Priority**: Must

#### Acceptance Criteria

1. WHEN `ResearchTreeUxApi.IsActive` = true THEN мод SHALL зарегистрировать вкладку «Архитектуры» (`IResearchTabProvider`, `Order` = 200) в дереве исследований.
2. IF `research-tree-ux` выключена или отсутствует THEN мод SHALL показать кнопку «Архитектуры» на странице фичи в хабе «Моды» (`FeatureContext.HubPage`), открывающую окно с тем же содержимым; при включении `research-tree-ux` вкладка появляется без перезагрузки сцены.
3. WHERE панель архитектур показана мод SHALL выводить для каждого семейства карточку: название, ISA, год, статус (исследовано / доступно / в работе с % / приостановлено с причиной / заблокировано с причиной), время и стоимость исследования, множители IPC / мощности / разработки, сродство с 4 сегментами, кнопку «Исследовать» («Продолжить» у приостановленного).
4. WHERE панель показана мод SHALL выводить блок лаборатории: строку состояния («свободна» / «занята технологией …» / «занята архитектурой …»); для текущего исследования — название, полосу прогресса, ETA, стоимость в месяц, слайдер финансирования лаборатории, кнопки «Остановить» и «Продолжить».
5. WHEN игрок меняет слайдер финансирования THEN мод SHALL записать значение в `ResearchSector.Funding` игрока (диапазон 1–100 %, до 500 % при `ResearchSector.InnovationEffort`) и сразу пересчитать ETA и стоимость.
6. WHEN наступает новый день и панель видна THEN мод SHALL обновить прогресс, ETA и статусы.
7. WHEN становится доступным новое семейство THEN мод SHALL увеличить счётчик на вкладке (`BadgeCount`) до просмотра вкладки.

**Сценарии:**
- **AC-3.1** Given research-tree-ux включена; When игрок открывает дерево; Then вкладка «Архитектуры» последней в полосе; нажатие показывает 7 карточек.
- **AC-3.2** Given research-tree-ux выключена; When игрок открывает хаб «Моды» → «Архитектуры»; Then то же содержимое в отдельном окне.

**Complexity**: Medium
**Dependencies**: FR-1, FR-2; `research-tree-ux` FR-7 (`ResearchTreeUxApi`); `ModUI`
**Assumptions**: нет

### FR-4: Выбор архитектуры в конструкторе CPU (этап 1)

**User Story:** Как игрок, я хочу выбирать архитектуру при проектировании процессора и сразу видеть, как она меняет IPC, потребление и стоимость проекта, чтобы взвешивать компромиссы.

**Priority**: Must

#### Acceptance Criteria

1. WHEN открывается окно конструктора CPU (`CreatorCpu`) THEN мод SHALL показать выпадающий список «Архитектура» с исследованными семействами игрока; по умолчанию — последнее выбранное, иначе самое новое исследованное.
2. WHILE окно конструктора открыто мод SHALL применять множители выбранного семейства к расчётам конструктора: IPC и IPS (в том числе IPS без узкого места) × `design.ipc`; потребление × `design.power` с пересчётом температуры через `CpuMath.Temperature`; стоимость проекта × `design.devCost` — через провайдер канала ядра `development.cost.design` (патч `CpuMath.ProjectCost` принадлежит ядру, фича его не патчит).
3. WHEN игрок меняет архитектуру в списке THEN мод SHALL обновить показатели конструктора в том же кадре (расчёт `CreatorCpu.UpdateNumbers` идёт каждый кадр).
4. WHEN игрок создаёт CPU THEN мод SHALL зафиксировать выбранную архитектуру за проектом (FR-5); характеристики CPU SHALL сохраниться такими, как показал конструктор.
5. WHEN ИИ создаёт CPU (`AIBehaviourCreation.CreateCpu` → `DataConverter.CpuDesignToCpu`) THEN мод SHALL применить множители активной архитектуры ИИ к `Ipc`, `Ips`, `PowerConsumption` и пересчитать `Temperature`; стоимость проектов ИИ SHALL умножаться тем же провайдером канала `development.cost.design` по активной архитектуре ИИ (ключ компании — `ModCompanies.KeyOf`).
6. WHILE идёт перемотка новой игры (`DateController.IsFastFowardSimulating`) мод SHALL не применять множители дизайна (нейтральность перемотки, FR-9): провайдер канала возвращает 1,0, патчи конструктора и ИИ выходят первой строкой.
7. WHERE конструктор показан мод SHALL выводить строку «Рейтинг по сегментам: ВС ×… · СС ×… · НС ×… · Пром ×…» — ожидаемый множитель рейтинга FR-6 (и FR-10…FR-13 на этапе 2) для компании игрока по собственной математике фичи (без вкладов других фич).

**Сценарии:**
- **AC-4.1** Given исследованы `proprietary` и `x86`, дизайн с IPC 10, потреблением 20 Вт, стоимостью 50M; When игрок выбирает x86; Then IPC 10,5, потребление 22 Вт, стоимость 57,5M, температура пересчитана.
- **AC-4.2** Given выбран ARM; When игрок поднимает частоту; Then температура растёт медленнее, чем на x86 (мощность × 0,65).
- **AC-4.3** Given ИИ Intel с активной x86 создаёт CPU; When проект завершён; Then IPS CPU на 5 % выше ванильного расчёта для того же дизайна.

**Complexity**: High
**Dependencies**: FR-1, FR-5; `ModUI`; патчи `CreatorCpu.Initialize`, `CreatorCpu.UpdateUI`, `CreatorCpu.ConsumptionAndTemperature`, `CreatorCpu.Performance`, `CreatorCpu.CreateCpu`, `DataConverter.CpuDesignToCpu`; канал `development.cost.design` (патч P19 `mod-framework`)
**Assumptions**: `CpuMath.ProjectCost` вызывается только из `CreatorCpu.Project` и `AIBehaviourCreation.SimulateCpus` (проверено по коду), оба пути проходят через канал ядра; `DataConverter.CpuDesignToCpu` — только из `AIBehaviourCreation.CreateCpu`

### FR-5: Архитектура как атрибут CPU (этап 1)

**User Story:** Как игрок, я хочу видеть архитектуру каждого процессора — своего и чужого — в инспекторе и при сравнении, чтобы понимать расстановку сил на рынке.

**Priority**: Must

#### Acceptance Criteria

1. WHEN создаётся проект CPU (`Project.SetProjectType(SaveObject.CpuProject)`) вне загрузки сейва THEN мод SHALL записать ожидающую привязку «отпечаток проекта → архитектура», где отпечаток = (ID компании, имя, год, IPS).
2. WHEN готовый CPU регистрируется THEN мод SHALL найти ожидающую привязку по отпечатку и сохранить «`Cpu.SaveID` → архитектура»: для игрока — в собственный момент фичи `ProjectCompletedHandler.AddCpu` (проект завершён), для ИИ — по событию ядра `ModEvents.CpuReleased` (патча на `Company.AddCpu`/`AICompany.AddCpu` у фичи нет; события при перемотке и при загрузке сейва не обрабатываются).
3. IF у CPU нет привязки (CPU создан до установки мода, во время перемотки или привязка потеряна) THEN мод SHALL при первом обращении определить архитектуру по умолчанию по владельцу и году выпуска (FR-8) и сохранить её; IF CPU — вариант (`Cpu.Base` ≠ null) THEN мод SHALL взять архитектуру базового CPU.
4. WHEN инспектор показывает CPU (`CpuUI.SetCpu`) THEN мод SHALL вывести в поле «Architecture» название архитектуры вместо «Default».
5. WHERE открыто окно сравнения `research-tree-ux` мод SHALL добавить строки «Архитектура» и «Множитель рейтинга (ВС/СС/НС/Пром)».
6. WHEN игра сохраняется THEN мод SHALL записать привязки CPU и ожидающие привязки в секцию `cpu-architectures` бокового файла `ModSave` (участник `IModSaveParticipant`; версию секции `_schema` ведёт ядро, фича своего поля версии не хранит); WHEN сейв загружается THEN мод SHALL восстановить их, и они SHALL иметь приоритет над любой регистрацией во время загрузки.
7. WHEN сейв загружается THEN мод SHALL не менять существующие привязки: игра повторно вызывает `AICompany.AddCpu` для каждого CPU, но ядро не поднимает `CpuReleased` при `GameManager.get_IsLoading`.
8. WHEN CPU передаётся другой компании (`ModEvents.CpuTransferred`, `rival-acquisitions`) THEN привязка CPU SHALL остаться прежней (по `SaveID`), а мод SHALL сбросить кеш рейтинга обеих компаний (`ModModifiers.Invalidate`).

**Сценарии:**
- **AC-5.1** Given игрок создал «PT-386» на x86, сохранился посреди проекта и загрузился; When проект завершён; Then инспектор показывает «x86».
- **AC-5.2** Given сейв без мода с 12 CPU; When загрузка с модом; Then каждый CPU показывает архитектуру по умолчанию для владельца и года.

**Complexity**: High
**Dependencies**: FR-1, FR-8; `ModSave`; `ModEvents`; `research-tree-ux` FR-7 (строки сравнения)
**Assumptions**: `Cpu.SaveID` уникален и стабилен между сохранениями (`SaveIDHandler.NewID`); имя и IPS проекта переживают сохранение (`DataConverter.CpuToSaveProject` / `SaveProjectToCpu`)

### FR-6: Влияние архитектуры на рейтинг по сегментам (этап 1)

**User Story:** Как игрок, я хочу, чтобы выбор архитектуры влиял на спрос по сегментам (ПК, серверы, встраиваемые), чтобы архитектура была стратегическим, а не косметическим выбором.

**Priority**: Must

#### Acceptance Criteria

1. WHEN рынок считает рейтинг CPU в сегменте s (`Market.CalculateRatings`, патч P4 ядра) THEN мод SHALL вернуть через **провайдер стандартного канала `market.rating.cpu`** (контекст `ModifierContext`: `Cpu`, `Segment` = сегмент s, `Company`) множитель `m = clamp(A[s] × fade(Y, s) × f_sup × f_eco × Π f_ext, 0,80, 1,20)`; на этапе 1 `f_sup` = `f_eco` = `f_ext` = 1; для `Segment.Any` или `Cpu` = null провайдер возвращает 1,0. Новых каналов фича не объявляет.
2. WHERE семейство `proprietary` используется в потребительских сегментах (HighEnd, MidRange, LowEnd) мод SHALL применять устаревание `fade` = lerp(1, 0,90, InverseLerp(1985, 1995, год)); в «Промышленности» `fade` = 1.
3. WHERE мод считает множитель рейтинга мод SHALL применять его одинаково к CPU игрока и ИИ (одинаковые правила для всех).
4. WHILE идёт перемотка новой игры мод SHALL возвращать множитель 1,0 (FR-9).
5. WHEN множитель запрашивается повторно в тот же день для того же ключа (канал, компания, CPU, сегмент) THEN значение берётся из дневного кеша ядра (`ModModifiers`), провайдер не вызывается повторно (до 1 200 запросов в день: 3 прохода × 4 сегмента × CPU).
6. WHEN наступает новый месяц, меняется привязка CPU или параметры компании (поддержка, этап 2) THEN мод SHALL сбросить кеш затронутых каналов (`ModModifiers.Invalidate(ModChannels.MarketRatingCpu, companyKey)`; `Invalidate(ModChannels.MarketRatingCpu)` для всех).
7. WHERE провайдер возвращает множитель мод SHALL передавать причину (`ProviderResult.ReasonKey` = `arch.reason.rating`, аргумент — название семейства), чтобы `ModModifiers.Explain` показывал вклад архитектуры в подсказках.
8. WHERE мод указывает свой вклад в общий предел ядра THEN вклад в `market.rating.cpu` SHALL быть в диапазоне [0,80; 1,20] (при ручке силы 150 % — [0,70; 1,30]); вклада в `popularity.gain` нет. Итоговый предел произведения всех фич — [0,5; 2,0] на CPU, его применяет ядро, `Explain` показывает «(ограничено)».

**Сценарии:**
- **AC-6.1** Given 1996 год, два одинаковых CPU разных компаний: x86 и `proprietary`; When считается рейтинг в «Высоком сегменте»; Then множители 1,05 и 0,90.
- **AC-6.2** Given CPU на ARM в «Промышленности»; When рейтинг; Then множитель 1,10.
- **AC-6.3** Given вклад архитектуры 1,30 (ручка 150 %), вклад платформ 1,20 и вклад события 1,40 на один CPU; When ядро считает произведение 2,184; Then итог ограничен до 2,0 и `Explain` показывает «(ограничено)»; при вкладах 1,30 × 1,20 × 1,25 = 1,95 ограничения нет.

**Complexity**: Medium
**Dependencies**: FR-1, FR-5; `mod-framework` (`ModModifiers.RegisterReasonedProvider`, патч P4 `Market.CalculateRatings`, `ModModifiers.Invalidate`)
**Assumptions**: множитель применяется к `CpuRatings.Overall` до `NormalizeRatings`/`DiluteRatings`; при разбавлении `Overall²/T` одинаковый множитель всех CPU компании действует линейно

### FR-7: ИИ-соперники выбирают архитектуру (этап 1)

**User Story:** Как игрок, я хочу, чтобы соперники тоже переходили между архитектурами по своей истории (Intel — x86, Motorola — свои ISA и RISC, Texas Instruments — ARM), чтобы рынок был живым и узнаваемым.

**Priority**: Must

#### Acceptance Criteria

1. WHEN наступает новый месяц (`TickPhase.MonthPassed`) THEN мод SHALL для каждой ИИ-компании, которая проектирует CPU (не foundry, не банкрот), выполнить решение: если нет текущего исследования архитектуры — выбрать доступное семейство с наибольшим весом предпочтения из `ai-preferences.json` (вес > 0, год + задержка компании ≤ текущий год), если хватает резерва денег (≥ 6 × месячная стоимость × M4) и текущую технологию лаборатории можно прервать (осталось больше `ai.noInterruptTimeLeftDays` = 30 дней; иначе решение откладывается на следующий месяц); при старте ИИ прерывает технологию так же, как игрок (FR-2 п. 1, без подтверждения).
2. WHILE у ИИ есть текущее исследование архитектуры мод SHALL продвигать его ежедневно по формуле FR-2 с финансированием из таблицы сложности (`Player.DifficultyLevel` 0…4 → 0,6 / 0,8 / 1,0 / 1,3 / 1,6; значение записывается в `ResearchSector.Funding` ИИ при старте, пока лаборатория занята архитектурой) и списывать стоимость через `ICompany.SpendMoney`.
3. WHILE архитектура занимает лабораторию ИИ мод SHALL не давать игре выбрать новую технологию (prefix на `AIBehaviourResearch.ChooseANewResearch`); по завершении или паузе игра выбирает технологию сама. IF патч не применился (самопроверка) THEN ИИ не исследует архитектуры (часть `Ai` выключена), остальное работает.
4. IF баланс ИИ отрицательный THEN мод SHALL приостановить исследование архитектуры этой ИИ до восстановления баланса (лаборатория возвращается игре).
5. WHEN ИИ завершает исследование семейства, вес которого не меньше веса текущей активной архитектуры THEN мод SHALL сделать его активной архитектурой ИИ (этап 1: по весу, при равенстве — более новое).
6. WHERE предпочтения задаются мод SHALL сопоставлять компании по `AICompany.UniqueID` (индекс исторической компании в `CompanySpawner`) с запасной записью `default`; отображаемое имя компании берётся из игры; foundry-компании пропускаются.
7. WHEN ИИ меняет активную архитектуру THEN мод SHALL применять её к новым проектам CPU этой ИИ (FR-4.5) и записать событие в журнал фичи (для обзора FR-15).

**Сценарии:**
- **AC-7.1** Given 1979 год, Intel (вес x86 = 1,0), x86 не исследована; When 1 февраля; Then Intel начинает исследование x86, через ~8 месяцев x86 становится её активной архитектурой.
- **AC-7.2** Given Texas Instruments в 1988 году; When исследование ARM завершено; Then активная архитектура — ARM.
- **AC-7.3** Given Intel исследует технологию, которой осталось 20 дней; When наступает месяц; Then решение об архитектуре отложено на следующий месяц.

**Complexity**: Medium
**Dependencies**: FR-1, FR-2; `ModTicks`; `ModContent`
**Assumptions**: ИИ не исследует семейства будущих лет; решения детерминированы (без случайности), ничьи разрешаются по году и `id`

### FR-8: Посев новой игры и миграция старых сейвов (этап 1)

**User Story:** Как игрок, начинающий игру в 1995 году или загружающий старый сейв, я хочу, чтобы у меня и у соперников уже были исторически подходящие архитектуры, чтобы не начинать с нуля в позднюю эпоху.

**Priority**: Must

#### Acceptance Criteria

1. WHEN начинается новая игра THEN мод SHALL засеять состояние игрока на `ModTicks.GameReady` (причина `NewGame`; к этому моменту `Company.InitializeAsNewGame` уже применила стартовые технологии): исследованы `proprietary` и семейства из `seed.playerPath` (по умолчанию `proprietary`, `x86`, `x86_64`), год которых ≤ U, где U — наибольший `Technology.Year` среди исследованных игроком технологий (владелец: x86 и x86-64 при позднем старте даются без исследования).
2. WHEN заканчивается перемотка новой игры (`TickPhase.FastForwardEnded`, один раз; `IsFastFowardSimulating` уже сброшен) THEN мод SHALL засеять каждую существующую ИИ-компанию: исследованы `proprietary` и все семейства с весом > 0, у которых год + задержка ≤ текущий год (с замыканием по зависимостям); активная — с наибольшим весом (при равенстве — новее).
3. WHEN загружается сейв без секции `cpu-architectures` (старый сейв или мод установлен посреди игры) THEN мод SHALL на `ModTicks.GameReady` (причина `Loaded`) выполнить тот же посев для игрока (U по его исследованиям) и для ИИ (по текущему году) и определить архитектуру всех существующих CPU по умолчанию (FR-5.3).
4. WHEN в игре появляется новая ИИ-компания (спавн по истории или выделение) без состояния THEN мод SHALL засеять её при первом месячном решении по текущему году.
5. WHERE мод определяет архитектуру CPU по умолчанию мод SHALL использовать для ИИ — семейство с наибольшим весом среди доступных по году выпуска CPU с учётом задержки, для игрока — самое новое семейство `seed.playerPath` с годом ≤ году выпуска CPU.
6. WHERE посев задаёт начальную поддержку (этап 2) мод SHALL ставить: активной у ИИ — 60, прочим исследованным у ИИ — 35, самому новому у игрока — 50 (уровень «обычный»), прочим у игрока — 30 (уровень «выкл»).

**Сценарии:**
- **AC-8.1** Given новая игра со стартом 1995 (у игрока исследованы технологии до 1993); When игра началась; Then у игрока исследованы `proprietary` и `x86`; в конструкторе по умолчанию x86.
- **AC-8.2** Given старый сейв 2008 года; When загрузка; Then у Intel активна `x86_64`, у Texas Instruments — `arm`; CPU игрока 2001 года — `x86`.

**Complexity**: Medium
**Dependencies**: FR-1, FR-5, FR-7
**Assumptions**: при позднем старте игрок получает x86 без исследования (решение владельца)

### FR-9: Настройки, выключение фичи и нейтральность перемотки (этап 1)

**User Story:** Как игрок, я хочу включать и выключать архитектуры и не бояться за сейв, чтобы попробовать фичу без риска.

**Priority**: Must

#### Acceptance Criteria

1. WHERE открыт хаб «Моды» мод SHALL показать переключатель фичи `cpu-architectures` (строит ядро по `IModFeature`) и параметры (`ParamSpec`): «Сила влияния на рейтинг» (`ratingStrength`, 0–150 %, по умолчанию 100 %), которая масштабирует отклонение множителя от 1: `m′ = 1 + (m − 1) × k`, и «Уведомления архитектур» (`notifications`, по умолчанию вкл).
2. WHEN фича выключена посреди игры (`SupportsHotToggle` = true) THEN мод SHALL: поставить исследование архитектуры игрока на паузу и вернуть лабораторию к прерванной технологии (FR-2 п. 8); вернуть 1,0 во всех своих провайдерах каналов (ядро пропускает провайдеры выключенной фичи) и перестать применять множители дизайна и списывать деньги; скрыть вкладку, список в конструкторе и текст в инспекторе (инспектор снова показывает «Default»); состояние в `ModSave` SHALL сохраняться без изменений, провайдеры и записи SHALL не пересоздаваться и не удаляться.
3. WHEN фича снова включена THEN мод SHALL продолжить с сохранённого состояния (исследование архитектуры остаётся на паузе до нажатия «Продолжить»); CPU, созданные за время выключения, получают архитектуру по умолчанию (FR-5.3).
4. WHILE идёт перемотка новой игры мод SHALL быть нейтральным: множители дизайна и рейтинга = 1, исследования архитектур и поддержка не тикают, деньги не списываются; посев выполняется после перемотки (FR-8).
5. IF мод удалён полностью THEN сейв игры SHALL грузиться в ванильной игре; характеристики CPU, созданных с модом, SHALL остаться такими, какими были созданы (их значения хранятся в самом CPU).

**Сценарии:**
- **AC-9.1** Given идёт исследование x86 и поддержка ARM на «высоком»; When фича выключена на 3 месяца и включена; Then списаний за 3 месяца нет, прогресс и уровни на месте.
- **AC-9.2** Given x86 занимает лабораторию игрока, прерванная технология «DDR»; When фича выключается; Then «DDR» снова текущая, x86 на паузе с сохранённым прогрессом.

**Complexity**: Medium
**Dependencies**: `ModSettings`, `ModSave`, все FR этапа 1
**Assumptions**: нейтральность перемотки — общая политика владельца

### FR-10: Программная поддержка (этап 2)

**User Story:** Как игрок, я хочу вкладываться в поддержку ПО своей архитектуры (компиляторы, ОС, сделки с разработчиками), чтобы мои процессоры лучше продавались, и понимать, что без вложений поддержка падает.

**Priority**: Must (этап 2)

#### Acceptance Criteria

1. WHERE компания исследовала семейство мод SHALL хранить уровень поддержки S ∈ [0; 100] и уровень финансирования из набора {выкл, низкий, обычный, высокий}.
2. WHEN наступает новый месяц (`TickPhase.MonthPassed`) THEN мод SHALL обновить поддержку: `S′ = S + (T − S) × r`, где T и r берутся из уровня (выкл: T = 0, r = `decayRate` семейства; низкий: 40 / 0,10; обычный: 70 / 0,10; высокий: 95 / 0,10); для `proprietary` T ограничена 60.
3. WHEN наступает новый месяц THEN мод SHALL списать содержание `upkeepPerMonth × c(уровень) × eraCost(год) × InflationHandler.Instance.Inflation` через `ICompany.SpendMoney(..., ExpenseOrigin.Development)`, где c = 0 / 0,5 / 1 / 2.
4. WHERE множитель рейтинга считается (FR-6) мод SHALL учитывать поддержку владельца для архитектуры CPU: `f_sup = 0,90 + 0,20 × S / 100`.
5. WHEN игрок меняет уровень в панели поддержки THEN мод SHALL применить его со следующего месячного обновления и сразу показать новую стоимость в месяц.
6. IF компания игрока в дефолте (`ICompany.IsInDefault`) THEN мод SHALL автоматически перевести все уровни игрока на «выкл» до выхода из дефолта и уведомить игрока.
7. WHERE панель архитектур показана мод SHALL выводить для каждого исследованного семейства: шкалу поддержки, уровень, стоимость в месяц, прогноз через 12 месяцев.

**Сценарии:**
- **AC-10.1** Given x86, S = 30, уровень «обычный»; When прошло 12 месяцев; Then S ≈ 59 (30 + 40 × (1 − 0,9¹²) = 30 + 40 × 0,718); списано 12 × 1,5M × инфляция.
- **AC-10.2** Given ARM, S = 60, уровень «выкл», decayRate 0,04; When 12 месяцев; Then S ≈ 37.

**Complexity**: Medium
**Dependencies**: FR-1, FR-6; `ModTicks` (`TickPhase.MonthPassed`)
**Assumptions**: `InflationHandler.Inflation` — множитель индекса цен (как в `Project`)

### FR-11: Экосистема архитектуры (этап 2)

**User Story:** Как игрок, я хочу, чтобы популярная на рынке архитектура давала бонус всем её производителям (больше ПО, больше покупателей), чтобы выбор между «большой» и «нишевой» ISA имел вес.

**Priority**: Should (этап 2)

#### Acceptance Criteria

1. WHEN наступает новый месяц THEN мод SHALL пересчитать долю экосистемы каждого семейства: `E_a = Σ продаж CPU архитектуры a / Σ продаж всех CPU` за последние 12 полных месяцев, где продажи CPU за месяц = `CpuBase.MarketData.Sold[i] + CpuBase.MarketData.SoldByContracts[i]`.
2. WHERE множитель рейтинга считается мод SHALL учитывать `f_eco = 0,95 + 0,10 × √E_a`.
3. IF продаж за окно нет (ранняя игра) THEN мод SHALL использовать `E_a` = 1 для `proprietary` и 0 для остальных.
4. WHERE панель архитектур показана мод SHALL выводить долю экосистемы каждого семейства в процентах и её изменение за 12 месяцев.

**Сценарии:**
- **AC-11.1** Given за 12 месяцев продано 900 тыс. x86 и 100 тыс. RISC; When пересчёт; Then E(x86) = 0,9, `f_eco` = 1,045; E(risc) = 0,1, `f_eco` = 0,982.

**Complexity**: Medium
**Dependencies**: FR-5, FR-6
**Assumptions**: месячные ряды `CpuBase.MarketData` сохраняются игрой и доступны после загрузки

### FR-12: Опыт ISA и переход между архитектурами (этап 2)

**User Story:** Как игрок, я хочу, чтобы новая архитектура той же ISA (x86 → x86-64) давалась легче благодаря опыту, а переход на чужую ISA стоил дороже, чтобы смена пути была осмысленным решением.

**Priority**: Should (этап 2)

#### Acceptance Criteria

1. WHEN компания исследует семейство, у которого есть исследованное семейство той же ISA-группы THEN мод SHALL умножать `effDays` на 0,6 (опыт ISA).
2. WHEN компания завершает исследование семейства THEN мод SHALL выставить начальную поддержку `max(30, 0,5 × S_пред)`, где `S_пред` — наибольшая поддержка у семейств той же ISA; иначе 30.
3. WHILE с момента исследования семейства прошло меньше 12 месяцев мод SHALL увеличивать стоимость проектов CPU на этой архитектуре на `0,25 × (1 − месяцев / 12)` («незрелые инструменты», +25 % первые 12 месяцев — решение по общему правилу: оставить) через тот же провайдер канала `development.cost.design`.
4. WHERE конструктор показывает архитектуру в период незрелости мод SHALL выводить «Незрелые инструменты: +N % к стоимости, осталось M мес.».

**Сценарии:**
- **AC-12.1** Given исследована x86 с поддержкой 80; When завершено исследование x86-64; Then начальная поддержка x86-64 = 40; время исследования было × 0,6.
- **AC-12.2** Given ARM исследована 3 месяца назад; When дизайн CPU на ARM; Then стоимость проекта × 0,85 (devCost) × 1,1875 (незрелость).

**Complexity**: Low
**Dependencies**: FR-2, FR-4, FR-10
**Assumptions**: нет

### FR-13: Расширения требуют программной поддержки (этап 2)

**User Story:** Как игрок, я хочу, чтобы многоядерность и SMT раскрывались на рынке только при развитой поддержке ПО, чтобы исследования расширений окупались вместе с вложениями в поддержку.

**Priority**: Should (этап 2)

#### Acceptance Criteria

1. WHERE CPU использует расширение из `balance.json` (`multicore`: `CoreCount` ≥ 2; `smt`: `Smt` = true) мод SHALL умножать его рейтинг на `f_ext = lerp(penalty, 1, min(1, S / requiredSupport))`, где по умолчанию `multicore`: penalty 0,92, requiredSupport 40; `smt`: 0,95 и 50.
2. WHERE конструктор показывает CPU с расширением при недостаточной поддержке мод SHALL выводить предупреждение «Многоядерность раскроется при поддержке ≥ 40 (сейчас N)».
3. WHERE мод показывает подсказку технологии многоядерности или SMT (через `research-tree-ux`, `ITechTooltipLineSource`) мод SHALL добавить строку о требуемой поддержке.

**Сценарии:**
- **AC-13.1** Given четырёхъядерный CPU на x86 с поддержкой 20; When рейтинг; Then `f_ext` = 0,96 (половина пути от 0,92 к 1).

**Complexity**: Low
**Dependencies**: FR-6, FR-10; `research-tree-ux` FR-7
**Assumptions**: расширения определяются по полям CPU (`CoreCount`, `Smt`), новых технологий не добавляется

### FR-14: Адаптивный ИИ: сегменты, экосистема и поддержка (этап 2)

**User Story:** Как игрок, я хочу, чтобы соперники реагировали на рынок — уходили с проигрывающей ISA и финансировали поддержку, — чтобы архитектурная гонка была честной.

**Priority**: Should (этап 2)

#### Acceptance Criteria

1. WHEN наступает новый месяц THEN мод SHALL для каждой ИИ посчитать привлекательность каждого исследованного семейства: `att_a = w_a × Σ_s share_s × A_a[s] × fade_a(Y, s) × f_eco(E_a) × f_sup(S_a)`, где `share_s` — доля сегмента s в продажах ИИ за 3 месяца (суммы `CpuBase.MarketData.SoldByHighEnd` / `SoldByMidRange` / `SoldByLowEnd` / `SoldByIndustries` по CPU ИИ); если продаж нет — доли по сегментам цен текущих CPU компании (`ModSegments.Classify`, по одному голосу на CPU), если CPU нет — 0,25 каждому. Собственного определения «основного сегмента» фича не имеет.
2. IF `att` лучшего семейства ≥ 1,10 × `att` активного и поддержка лучшего ≥ 35 THEN мод SHALL сменить активную архитектуру ИИ.
3. WHEN наступает новый месяц THEN мод SHALL выставить уровни поддержки ИИ: активной — «обычный», если `MoneyAmount` ≥ 12 × стоимость «обычного» содержания, иначе «низкий»; кандидату на переход с `E_a` ≥ 0,2 — «низкий»; остальным — «выкл».
4. WHERE ИИ выбирает следующее исследование мод SHALL учитывать экосистему: вес × (1 + E_a).

**Сценарии:**
- **AC-14.1** Given Motorola с активной `proprietary` в 1996 году, исследован RISC с поддержкой 40; When месячное решение; Then Motorola переходит на RISC (привлекательность выше на ≥ 10 %).

**Complexity**: Medium
**Dependencies**: FR-7, FR-10, FR-11; `ModSegments`
**Assumptions**: `rival-personalities` меняет веса через API `ArchitectureApi.SetAiWeightOverride` (разрешено владельцем по общему правилу)

### FR-15: Обзор архитектур и уведомления (этап 2)

**User Story:** Как игрок, я хочу видеть, какие архитектуры у соперников и чья экосистема растёт, и получать уведомления о важных сдвигах, чтобы вовремя реагировать.

**Priority**: Could (этап 2)

#### Acceptance Criteria

1. WHERE панель архитектур показана мод SHALL выводить таблицу «Соперники»: компания, активная архитектура, текущее исследование архитектуры (если игроку известно — всегда, как в инспекторе игры).
2. WHEN ИИ меняет активную архитектуру THEN мод SHALL показать `ModNotify` «{Компания} переходит на {архитектуру}» (не при перемотке; в пакетном прогоне `NextMonth` показ откладывает ядро).
3. WHEN доля экосистемы семейства впервые пересекает 25 %, 50 % или 75 % THEN мод SHALL отправить письмо `ModMail` с короткой сводкой рынка (приоритет `Normal`, тег `arch:eco:<familyId>:<порог>`; повтор вехи исключён секцией `milestones`).
4. WHERE игрок выключил уведомления архитектур в хабе (`ParamSpec` `notifications`) мод SHALL не показывать их.

**Complexity**: Low
**Dependencies**: FR-11, FR-14; `ModNotify`, `ModMail`
**Assumptions**: показ архитектуры соперников не раскрывает больше, чем инспектор игры

### FR-16: Роялти за x86 без лицензии (этап 2)

**User Story:** Как игрок, я хочу, чтобы x86 была доступна всем, но компании без лицензии платили за неё роялти, чтобы историческая роль Intel и AMD как держателей лицензии ощущалась без запретов.

**Priority**: Should (этап 2)

#### Acceptance Criteria

1. WHERE компания не владеет лицензией x86 мод SHALL разрешать ей исследовать и проектировать семейства ISA-группы `x86` без запрета. Держатели лицензии — ИИ с `AICompany.UniqueID` из `balance.json` (`x86License.holderIds`, по умолчанию 0 — Intel и 1 — AMD, как `CompanyHelper.IsInlet` и `CompanyHelper.IsEMD`); у игрока и остальных ИИ лицензии нет.
2. WHEN наступает новый месяц (`TickPhase.MonthPassed`) THEN мод SHALL для каждой компании без лицензии начислить роялти `x86License.royaltyRate × доход от продаж её CPU семейств ISA `x86` за последний полный месяц` (`CpuBase.MarketData.Income[Count − 2]`) и списать через `ICompany.SpendMoney(..., ExpenseOrigin.Royalties)`; ставка по умолчанию 3 % (черновая).
3. WHEN роялти списано THEN мод SHALL зачислить сумму поровну живым держателям лицензии через `ICompany.EarnMoney(..., RevenueOrigin.Royalties)`; IF оба держателя обанкротились (`LicenseHelper.X86LicenseHasBeenRevoked`) THEN роялти не взимается (x86 свободна).
4. WHERE правило применяется мод SHALL применять его одинаково к игроку и ИИ; «невезучесть» Cyrix (×6 к стоимости исследований, `CompanyHelper.IsUnluckyCompany`) остаётся ванильной и не заменяется роялти.
5. WHILE идёт перемотка новой игры мод SHALL не начислять роялти (нейтральность).
6. WHERE панель архитектур показана мод SHALL выводить строку «Роялти x86: N/мес» для компании игрока без лицензии.

**Сценарии:**
- **AC-16.1** Given 1992 год, у игрока x86-CPU принесли $10M за прошлый месяц; When наступает новый месяц; Then списано $300k в статье «Royalties», Intel и AMD получили по $150k.
- **AC-16.2** Given Intel и AMD обанкротились (`X86LicenseHasBeenRevoked`); When наступает месяц; Then роялти нет.
- **AC-16.3** Given Intel (держатель) продаёт x86-CPU; When наступает месяц; Then роялти с Intel не взимается.

**Complexity**: Low
**Dependencies**: FR-1, FR-5; `ModTicks`; `ICompany.SpendMoney`/`EarnMoney`
**Assumptions**: ставка и состав держателей — черновые числа в `balance.json`; продажа лицензий ISA (I17) вне объёма

## Non-Functional Requirements

### NFR-1: Производительность

- WHEN проходит игровой день THEN мод SHALL тратить на исследования архитектур всех компаний (≤ 14) и арбитраж лаборатории не больше 0,1 мс.
- WHEN рынок запрашивает множитель рейтинга THEN мод SHALL отвечать за O(1) (провайдер вызывается ядром не чаще раза в день на ключ канала); суммарно ≤ 0,2 мс в день при 300 CPU на рынке.
- WHEN наступает новый месяц THEN мод SHALL пересчитать поддержку, экосистему (до 300 CPU × 12 месяцев), роялти и решения ИИ не дольше 3 мс.
- WHILE окно конструктора открыто постфиксы конструктора и провайдер `development.cost.design` SHALL добавлять не больше 0,05 мс на кадр (провайдер — не более 5 мкс на вызов).

### NFR-2: Надёжность

- WHEN в постфиксе, провайдере или обработчике возникает исключение THEN мод SHALL перехватить его на границе хука через `ModHooks.Guard` (счётчик и circuit breaker ведёт ядро) и вернуть ванильное значение (множитель 1, без изменения полей).
- IF самопроверка не нашла цель патча или приватное поле (`CreatorCpu.ipc`, `.ips`, `.ipsWithoutBottleneck`, `.consumption`, `.temperature`, `.currentPackage`, `.coreCountDropdown`, `CpuUI.architectureText`, `AIBehaviourResearch.company`, `CurrentResearchUI.targetTechnology` и `Hide`) THEN мод SHALL отключить только зависящую часть (конструктор / инспектор / ИИ / интерфейс лаборатории); рейтинг и исследования продолжают работать. Без `CurrentResearchUI.targetTechnology`/`Hide` часть `LabUi` выключена: игрок не может прервать технологию из панели архитектур и запускает архитектуру только на свободной лаборатории (остановив технологию родной кнопкой).
- IF `ModHooks` отклонил патч фичи как зарезервированный THEN мод SHALL записать причину и отключить зависящую часть; штатно фича не патчит зарезервированные цели (`Company.AddCpu`, `AICompany.AddCpu`, `CpuMath.ProjectCost`, `Market.CalculateRatings`).

### NFR-3: Совместимость сейвов

- Фича SHALL хранить состояние только в секции `cpu-architectures` бокового файла `ModSave` (участник `IModSaveParticipant`) и не добавлять поля в классы игры (в том числе не использовать неиспользуемое `SaveObject.Cpu.CoreDesignID`); поля версии секции фича не хранит, `_schema` пишет и читает ядро.
- WHEN загружается сейв без секции THEN мод SHALL выполнить миграцию FR-8.3.
- WHEN секция записана версией мода новее (ядро: `_schema` больше `SchemaVersion`) THEN ядро SHALL выдать участнику значения по умолчанию и записать исходную секцию как есть; мод SHALL выполнить миграцию FR-8.3 в памяти, показать в хабе предупреждение «данные архитектур записаны более новой версией мода и в этой сессии не сохраняются»; WHEN в секции битые записи THEN они отбрасываются с предупреждением, остальные читаются.

### NFR-4: Баланс и детерминизм

- Вклад фичи в `market.rating.cpu` SHALL быть в пределах [0,80; 1,20] (до ручки силы FR-9.1; при ручке 150 % — [0,70; 1,30]); вклад в `development.cost.design` — `design.devCost` в [0,5; 2,0], по умолчанию 0,80–1,15 (с незрелостью до 1,44); вклада в `popularity.gain` нет. Общий предел произведения всех фич на CPU — [0,5; 2,0] (ядро), в тестах эффектов ограничение учитывается.
- Множители дизайна SHALL быть в пределах контента [0,5; 2,0]; по умолчанию IPC 0,95–1,12, мощность 0,65–1,10, разработка 0,80–1,15.
- Решения ИИ SHALL быть детерминированными при одинаковом сейве (без случайности; если в будущем понадобится — только `ModRandom`).
- Все числа баланса SHALL лежать в `Content/cpu-architectures/*.json`.
- Правила для ИИ и игрока SHALL быть одинаковыми (множители, общая лаборатория, роялти); эффекты для ИИ на низкой сложности не ослабляются.

### NFR-5: Локализация

- WHERE мод показывает текст мод SHALL брать его из `ModL10n` (`ru` по умолчанию, `en` фолбэк); ключи фичи начинаются с `arch.` (соглашение ядра о префиксах); каждый ключ SHALL быть в обоих файлах (тест). Названия компаний берутся из игры (`ICompany.Name`), логика не опирается на переводимые строки.

### NFR-6: Удобство

- WHEN игрок наводит курсор на карточку семейства, строку поддержки или пункт списка в конструкторе THEN мод SHALL показать подсказку (`ModUI.Tooltip`) с формулой эффекта в цифрах (например, «Высокий сегмент: ×1,05 сродство × 1,04 поддержка × 1,03 экосистема = ×1,12»).
- UI фичи SHALL следовать теме игры (`ThemeManager.OnThemeChanged`).

### NFR-7: Соответствие контракту ядра

- Фича SHALL быть найдена ядром по `[ModFeature]` как `sealed class ArchitecturesFeature : IModFeature` в пространстве имён `PTMod.Features.CpuArchitectures` (Id = `cpu-architectures`, `NameKey`, `DescriptionKey`, `DependsOn` — только жёсткие зависимости (их нет: связи с `research-tree-ux`, `platform-generations`, `rival-*` мягкие), `EnabledByDefault`, `SupportsHotToggle`, `Register(FeatureContext)`, `OnEnabled`/`OnDisabled`).
- Фича SHALL получать тики через `FeatureContext.OnTick`, старт игры через `ModTicks.GameReady` и `TickPhase.FastForwardEnded`, выпуск CPU через `ModEvents.CpuReleased` и `ModEvents.CpuTransferred`, сегмент через `ModSegments`, состояние через `IModSaveParticipant`, настройки через `ctx.Param`; прямых подписок на `DateController`, `Player.OnNewGame`, `SaveHandler.*`, патчей на `Company.AddCpu`/`AICompany.AddCpu`/`CpuMath.ProjectCost` и собственных счётчиков ошибок SHALL не быть.
- Провайдеры `market.rating.cpu` и `development.cost.design` SHALL регистрироваться один раз в `Register` (или на `GameReady`); `OnEnabled`/`OnDisabled` их не пересоздают.

## Edge cases

- Компания становится fabless/foundry: foundry не проектирует CPU — исследования архитектур ИИ-foundry не ведутся; игрок-foundry видит вкладку, но конструктор CPU ему недоступен игрой.
- ИИ обанкротилась (`IsBankrupt`): решения, поддержка и исследование останавливаются; привязки её CPU остаются (CPU ретайрятся игрой).
- Лаборатория игрока свободна (нет текущей технологии): запуск архитектуры не требует подтверждения.
- Игрок остановил технологию родной кнопкой «Stop» в панели текущего исследования, пока идёт архитектура: ничего не происходит (технологии нет), архитектура продолжается.
- Прерванная технология исследована другим путём (завершилась, стала недоступна) к моменту возврата: лаборатория остаётся свободной, `ModNotify` не показывается.
- Игрок выбрал технологию и сразу архитектуру в один день: конфликт разрешается подтверждением FR-2 п. 1 (последний выбор побеждает).
- CPU сменил производителя (`CompanyHelper.ChangeCpuManufacturer`): архитектура привязана к `SaveID` CPU и не меняется; поддержка берётся у **владельца** CPU (`Cpu.Company`), не у фабрики.
- Компания куплена игроком (`rival-acquisitions`): состояние архитектур переносится через `ArchitectureApi.TransferCompanyState` (вызывает `rival-acquisitions`); незавершённое исследование архитектуры поглощённой компании не переносится (лаборатория принадлежит компании).
- Два проекта CPU с одинаковым именем, годом и IPS у одной компании: отпечатки совпадают — обе привязки одинаковой архитектуры не конфликтуют; если архитектуры разные, вторая регистрация получает суффикс-счётчик в отпечатке (FIFO при завершении).
- Игрок не исследовал ничего, кроме `proprietary`: список в конструкторе из одного пункта, по умолчанию `proprietary`.
- Сейв загружен, когда готовый CPU стоит в очереди выпуска (`ProjectCompletedHandler`): привязка уже сделана по `SaveID` при добавлении в очередь.
- Пользовательский контент удалил семейство, на которое ссылаются CPU в сейве: CPU показывают «Неизвестная архитектура (id)», множитель = 1, с предупреждением; привязка не удаляется.
- Деление на 0: `baseDays` = 0, `requiredSupport` = 0, пустое окно продаж — защищены.
- Отрицательные деньги у игрока в момент месячного списания: списание выполняется (как и у игры), затем срабатывает FR-10.6, если наступил дефолт.
- Ручка силы = 0 %: все множители рейтинга = 1, дизайн и исследования продолжают работать.
- Держатель лицензии x86 (Intel или AMD) обанкротился посреди игры: роялти прекращаются (`LicenseHelper.X86LicenseHasBeenRevoked`).

## Constraints and Assumptions

### Technical Constraints

- Нельзя добавлять значения в `TechnologyType` и объекты `Technology`: исследования игры индексируются по `Technology.ID` (`ResearchSector.researches[ID]`), новые ID ломают сейвы. Поэтому ветка архитектур — собственная модель мода (D1 в `design.md`), использующая слот лаборатории `ResearchSector` без новых технологий.
- Состояние — только в `ModSave`; классы игры не расширяются (`context.md`).
- Характеристики построенного CPU игра хранит в самом CPU (`Ipc`, `Ips`, `PowerConsumption`, `Temperature`); мод меняет их только в момент создания.
- Harmony 2.3.6 (решение 0002), runtime UI (решение 0005), контент в JSON (решение 0006), тесты на мини-раннере .NET Framework 4.8 (решение 0003); чистая логика `Features/CpuArchitectures/Logic/**` — общее подмножество C# и API .NET Framework 4.8, без типов `Assembly-CSharp` (сегмент — `Segment` ядра, остальное — числа и строки).

- XL-объём: реализация в два этапа; полная версия начинается после ручной проверки MVP владельцем (гейт TSK-020 в `tasks.md`).

### Acceptance Metrics

- 0 исключений `[PTMod]` от фичи за 2 часа игры.
- Вклад фичи в `market.rating.cpu` всегда в [0,80; 1,20] до ручки силы (тест на сетке параметров).
- Балансовая симуляция: к 1995 году x86 — активная у ≥ 3 из 5 «ПК-компаний» (Intel, AMD, Cyrix, VIA, IBM); к 2015 году ARM/ARM64 — активная у ≥ 2 из 3 «встраиваемых» (Texas Instruments, Toshiba, Zilog); ни одно семейство не даёт CPU больше +20 % рейтинга над `proprietary` до 1985 года.
- Производительность: дневной тик ≤ 0,1 мс, месячный ≤ 3 мс, рейтинг ≤ 0,2 мс/день (замеры `ModLog`).

## Glossary

| Термин | Значение |
|---|---|
| Семейство архитектур | запись каталога (`proprietary`, `x86`, …): ISA-группа, год, исследование, множители |
| ISA-группа | набор совместимых семейств (`x86` и `x86_64` — группа `x86`; `arm` и `arm64` — `arm`) |
| Общая лаборатория | единственный слот исследований компании (`ResearchSector`): в нём идёт либо технология, либо архитектура |
| Прерванная технология | технология, остановленная архитектурой; её прогресс хранит игра, мод запоминает ID для возврата |
| Активная архитектура ИИ | семейство, на котором ИИ проектирует новые CPU |
| Сродство A[s] | множитель рейтинга семейства в сегменте s (HighEnd, MidRange, LowEnd, Industries) |
| Устаревание `fade` | снижение сродства `proprietary` в потребительских сегментах 1985–1995 |
| Программная поддержка S | 0…100, на компанию и семейство; растёт от финансирования, падает без него |
| Экосистема E | доля семейства в продажах CPU за 12 месяцев |
| Расширение | свойство CPU (многоядерность, SMT), полный рыночный эффект которого требует поддержки |
| Роялти x86 | плата компании без лицензии x86 держателям лицензии (Intel, AMD): 3 % дохода x86-CPU |
| Отпечаток проекта | (ID компании, имя, год, IPS) — ключ ожидающей привязки архитектуры к проекту CPU |
| Посев | начальное состояние архитектур компании при новой игре, миграции или появлении ИИ |
| Перемотка | симуляция 1971 → стартовый год при новой игре (`DateController.SimulateUntilYear`) |
| `Segment` | тип ядра `PTMod.Core`: HighEnd (ВС), MidRange (СС), LowEnd (НС), Industries (Пром); индексы 0…3 |
| IDM | тип компании со своим производством и разработкой (не ИИ-соперник IBM) |
