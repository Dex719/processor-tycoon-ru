## Introduction

В игре уже считается `FailureRate` дизайна (`CpuMath.FailureRate`): от температуры, частоты относительно максимума, числа ядер и SMT. Сейчас он влияет только на себестоимость (`CpuMath.MaterialCost`, `CpuMath.RealUnitCost`) и на долю отбракованных кристаллов на фабрике (`Factory.ProduceWafers` → `CpuBase.FailedStock`). Последствий «на рынке» у агрессивного дизайна нет.

Фича добавляет скрытый брак, который проходит контроль на фабрике и всплывает у покупателей. При выпуске CPU мод решает, есть ли в дизайне скрытый дефект. Вероятность зависит от параметров дизайна. Дефект обнаруживают позже: свои инженеры (тихо) или пресса и покупатели (публично). Компания выбирает реакцию: отзыв, ревизию (новый степпинг), программную заплатку или игнор. У каждой реакции своя цена: деньги, репутация, популярность CPU, OEM-контракты. ИИ-соперники ловят брак по тем же правилам. Игрок узнаёт об их скандалах и может на них заработать.

Версия 0.2 вносит решения владельца и замечания кросс-ревью: выпуск и перенос CPU приходят событиями ядра (`ModEvents.CpuReleased`, `ModEvents.CpuTransferred`) вместо собственных патчей на `AddCpu`; письма различаются по тегу и приоритету (`ModMail`); порог дефолта берётся из `ModCredit`; версию секции сейва ведёт ядро (`_schema`); добавлены переключатель «спешка» в конструкторе (FR-20), передача брака вместе с CPU при поглощении (FR-19) и точка расширения для `rival-personalities` (FR-17).

### Feature Summary

Скрытый брак выпущенных CPU с вероятностью от параметров дизайна, отложенное обнаружение и выбор из четырёх реакций с прозрачной ценой; для игрока и ИИ.

### Business Value

- **Ценность для игрока.**
  - Новый риск-рычаг. Разгон, перегрев, много ядер, незрелый техпроцесс и спешка проекта дают сильный CPU или ранний выпуск, но повышают риск дорогого скандала.
  - Решения с последствиями. Как в случае FDIV 1994 года, ущерб определяет не сам дефект, а реакция на него.
  - Живые соперники. Чужие скандалы открывают окно возможностей.
- **Доказательства спроса.**
  - В `IDEAS.md` идея помечена «demand: unknown, fun: 4/5». Владелец выбрал группу «самое интересное по fun» целиком (`steering/roadmap.md`).
  - Похожая механика есть в Hardware Tycoon (Steam, ссылка выше).
  - Запрос на события с выбором подтверждён источниками идеи I13 (обсуждения Game Dev Tycoon на Steam и itch.io).
  - Исторический прецедент FDIV хорошо известен целевой аудитории.
- **Ожидаемый результат.** За партию 1975–2030 игрок сталкивается с 2–6 собственными инцидентами и видит 5–15 инцидентов соперников. Каждое решение принимается с известной ценой.

### Scope

**Входит:**
- бросок скрытого брака при выпуске CPU (игрок и ИИ) по событию ядра `ModEvents.CpuReleased`, наследование брака вариантами (`isVariant`);
- модель вероятности от `FailureRate`, разгона, перегрева, незрелости техпроцесса и спешки проекта, с множителями сложности и эпохи;
- типы и тяжесть брака из контент-JSON;
- обнаружение: ежемесячный шанс от продаж, внутреннее или внешнее, принудительное по сроку, истечение;
- четыре реакции с формулами стоимости и последствий, выбор с таймером через `event-system`;
- ревизия с отсчётом дней, заплатка с понижающим множителем рейтинга CPU, игнор с утечкой и сокрытием;
- изменения репутации (`ModReputation.Add`) и популярности CPU;
- отказ OEM-клиентов от контрактов на проблемный CPU;
- брак у ИИ, политика выбора ИИ, новости игроку;
- передача записи брака вместе с CPU при поглощении (`ModEvents.CpuTransferred`);
- переключатель «Ускоренный проект» (спешка) в конструкторе CPU;
- окно «Брак и отзывы» в хабе «Моды», пометка на карточке CPU;
- API для `press-reviews`, `historical-events` и `rival-personalities`, корректировщик обзоров прессы;
- настройки, секция `ModSave`, строки ru/en.

**Не входит:**
- движок событий и окно выбора (это `event-system`);
- игровой эффект репутации на спрос и популярность (это `press-reviews`) и хранение репутации (это `mod-framework`);
- изменение формулы `CpuMath.FailureRate`, выхода годных и себестоимости;
- новая статья расходов в финансовом отчёте игры (используются существующие `ExpenseOrigin`, решение D5 в design);
- осторожность ИИ при проектировании после брака (патч `AIBehaviourCreation.AcceptableFailureRate`) — решение владельца: это зона `rival-personalities`; здесь только данные и точка расширения (FR-17);
- причины отказов OEM в UI контрактов (это `contract-transparency`);
- слухи о внутренних браках ИИ (решение по умолчанию).

## Requirements

### FR-1: Скрытый брак при выпуске CPU

**User Story:** Как игрок, я хочу, чтобы у агрессивного дизайна был шанс скрытого дефекта, чтобы рискованные решения в конструкторе имели последствия после выпуска.

**Priority:** Must

#### Acceptance Criteria

1. WHEN ядро поднимает `ModEvents.CpuReleased(owner, cpu, isVariant, duringFastForward)` для нового CPU с `isVariant = false` и `duringFastForward = false` THEN мод SHALL один раз вычислить вероятность скрытого брака по FR-2 и бросить `ModRandom`. Загрузку сейва ядро отсекает само (событие при `GameManager.get_IsLoading` не поднимается).
2. IF бросок успешен THEN мод SHALL создать запись брака в состоянии `Hidden` с типом и тяжестью по FR-3 и SHALL NOT показывать игроку никаких сообщений.
3. IF `isVariant = true` (у CPU задан `Cpu.Base`) THEN мод SHALL NOT бросать отдельно, а SHALL привязать вариант к записи брака базового CPU (общий кристалл). Если у базового CPU записи нет, вариант считается исправным и записи не получает.
4. IF `duringFastForward = true` THEN мод SHALL NOT бросать брак для этого CPU и SHALL NOT создавать записей, сообщений и реакций (политика владельца: перемотка новой игры нейтральна).
5. IF для `Cpu.SaveID` бросок уже выполнялся (запись в `ModSave`) THEN мод SHALL NOT бросать повторно.
6. WHERE фича выключена в `ModSettings` мод SHALL NOT бросать брак и SHALL NOT менять игровые значения.
7. Фича SHALL NOT устанавливать собственные патчи на `Company.AddCpu` и `AICompany.AddCpu`: такие цели закреплены за службой ядра (`ModHooks` отклонит патч).

#### Scenarios

- **AC-1.1** Given игрок на сложности 2 выпускает CPU с `FailureRate` 0.30, разгоном 25 %, перегревом 5 % и прогрессом освоения техпроцесса 0.4, When ядро поднимает `CpuReleased`, Then мод считает p ≈ 0.23 и бросает один раз, а в `ModSave` появляется отметка о броске для этого `SaveID`.
- **AC-1.2** Given сейв загружается и `SaveHandler.Load` вызывает `Company.AddCpu` для каждого CPU, When идёт загрузка, Then `CpuReleased` не поднимается, новых бросков нет и число записей брака не меняется.
- **AC-1.3** Given базовый CPU с записью брака `Hidden`, When игрок выпускает вариант с `Cpu.Base` = этот CPU (`isVariant = true`), Then запись брака получает `SaveID` варианта в списке затронутых CPU.
- **AC-1.4** Given новая игра 1990 года с перемоткой, When ИИ выпускает CPU во время перемотки (`duringFastForward = true`), Then записей брака, писем и бросков нет.

**Complexity:** Medium
**Dependencies:** FR-2, FR-3, FR-16; `mod-framework` (`ModEvents`, `ModRandom`, `ModSave`).
**Assumptions:** ядро поднимает `CpuReleased` единственным postfix P20 на `Company.AddCpu` (вызывается из `ProjectReleaseWindow.ReleaseCpu`) и `AICompany.AddCpu` (из `AIBehaviourCreation`); не чаще одного раза на объект CPU.

### FR-2: Модель вероятности брака

**User Story:** Как игрок, я хочу понимать, какие параметры дизайна повышают риск, чтобы осознанно рисковать.

**Priority:** Must

#### Acceptance Criteria

1. WHEN мод вычисляет вероятность брака THEN мод SHALL использовать факторы:
   - `FailureRate` дизайна (`CpuBase.FailureRate`);
   - разгон: частота CPU относительно `ICompany.get_MaxFrequency` + `ResearchModifiers.FrequencyIncrease`;
   - перегрев: `CpuBase.Temperature` относительно `min(IPackage.get_SafeTemperature, 95)`;
   - незрелость техпроцесса: `1 − ICompany.CurrentNodeLearningProgress` производителя;
   - спешка проекта (FR-20): признак 0 или 1.

   Формула и коэффициенты — в design, раздел «Формулы и баланс».
2. WHEN вероятность вычислена THEN мод SHALL умножить её на множитель сложности (`Player.DifficultyLevel` 0–5) и множитель эпохи (по году выпуска) из контент-JSON и SHALL ограничить результат сверху значением `pMax` из контента. Множитель сложности одинаков для игрока и ИИ (политика владельца: правила для ИИ не ослабляются).
3. IF у производителя нет записи освоения техпроцесса (`CurrentNodeLearningProgress` вернул 0 при отсутствии `NodeOptimization`) THEN мод SHALL использовать значение незрелости `unknownNodeImmaturity` из контента (по умолчанию 0.5).
4. WHERE компания — ИИ мод SHALL применять ту же формулу с множителем `aiRiskMultiplier` из контента (по умолчанию 1.0, без ослабления на низкой сложности) и без признака спешки.

#### Scenarios

- **AC-2.1** Given коэффициенты по умолчанию, When считается дизайн 1980 года с FR 0.18, без разгона и перегрева, с незрелостью 0.4, Then p = (0.02 + 0.2·0.18 + 0.08·0.4) · 0.8 ≈ 0.070.
- **AC-2.2** Given сложность 0 (множитель 0.5), When тот же дизайн, Then p ≈ 0.035.
- **AC-2.3** Given коэффициенты, дающие p_raw > `pMax`, When считается вероятность, Then результат равен `pMax` (0.5).
- **AC-2.4** Given дизайн из AC-2.1, созданный со спешкой, When считается вероятность, Then p = (0.088 + 0.06) · 0.8 ≈ 0.118.

**Complexity:** Low
**Dependencies:** FR-15 (коэффициенты в контенте), FR-20.
**Assumptions:** `CpuBase.FailureRate`, `Temperature` и `Frequency` фиксируются при создании дизайна и не пересчитываются (CODEMAP, Gotchas раздела Hardware). Максимальная частота берётся на момент выпуска, а не начала проекта. Это занижает разгон, если исследование частоты продвинулось за время проекта.

### FR-3: Тип и тяжесть брака

**User Story:** Как игрок, я хочу, чтобы брак был разным (ошибка вычислений, нестабильность, перегрев, уязвимость), чтобы реакции имели смысл и соответствовали эпохе.

**Priority:** Must

#### Acceptance Criteria

1. WHEN создаётся запись брака THEN мод SHALL выбрать тяжесть (`Minor`, `Major`, `Critical`) по весам из контента, сдвинутым к тяжёлым при высоком p.
2. WHEN создаётся запись брака THEN мод SHALL выбрать тип из контента среди типов, у которых год выпуска CPU попадает в окно `[fromYear, toYear]`. Вес типа `stability` SHALL расти с разгоном, вес типа `thermal` — с перегревом.
3. IF ни один тип не доступен для года THEN мод SHALL использовать тип `arith` (ошибка вычислений) как запасной.
4. WHEN тип выбран THEN запись SHALL хранить параметры, зависящие от типа: доступность заплатки по году, потерю производительности при заплатке, доступность отзыва.

#### Scenarios

- **AC-3.1** Given CPU 2010 года, When выбирается тип, Then тип `security` недоступен (окно с 2015) и не выпадает.
- **AC-3.2** Given CPU с разгоном 0.4, When выбирается тип, Then вес `stability` равен базовому весу × (1 + 5·0.4) = 3 × 3 = 9.

**Complexity:** Low
**Dependencies:** FR-1, FR-15.
**Assumptions:** нет.

### FR-4: Обнаружение брака

**User Story:** Как игрок, я хочу, чтобы брак всплывал не сразу и чаще у массовых CPU, чтобы риск зависел от успеха продукта.

**Priority:** Must

#### Acceptance Criteria

1. WHEN наступает первое число месяца (подписка `ctx.OnTick(TickPhase.MonthPassed, …)`) THEN мод SHALL для каждой записи `Hidden` бросить шанс обнаружения `h` по формуле из design. `h` растёт с числом проданных единиц затронутых CPU (`CpuBase.MarketData.Sold` + `SoldByContracts`) и с тяжестью.
2. WHEN брак обнаружен THEN мод SHALL определить источник: внутренний (свои инженеры) с вероятностью `qInternal[тяжесть]`, иначе внешний (пресса и покупатели).
3. IF с выпуска прошло не меньше `maxHiddenMonths[тяжесть]` месяцев и продано больше 0 единиц THEN мод SHALL обнаружить брак принудительно, с внешним источником.
4. IF CPU снят с продажи (`IsRetired`) больше `expireAfterRetiredMonths` месяцев назад, или за `expireNoSalesMonths` месяцев не продано ни одной единицы THEN мод SHALL перевести запись в `Expired` и больше её не проверять.
5. IF компания-владелец обанкротилась (`ICompany.get_IsBankrupt`) или CPU не найден (`DataFinder.FindCpu` вернул null) THEN мод SHALL закрыть запись (`Closed`) без последствий.
6. WHILE запись находится в состоянии `InternalKnown` с реакцией «игнор» или «тихая ревизия» мод SHALL каждый месяц бросать шанс утечки `leakRate` из контента.
7. WHILE идёт пакетный прогон (`ModTicks.IsBatchRun`) тики дней и месяцев SHALL выполняться как обычно; показ писем и окон откладывают ядро и движок до `ModTicks.BatchEnded`. Фича SHALL NOT патчить `DateController.NextMonth`.

#### Scenarios

- **AC-4.1** Given запись `Major`, 1 000 000 проданных единиц, When проходит месяц, Then h = 0.04 · (1 + log10(1 + 10)) ≈ 0.082, и при успехе броска запись становится `InternalKnown` или `Public`.
- **AC-4.2** Given запись `Critical`, с выпуска прошло 24 месяца, продано 5 000 единиц, брак не найден, When проходит месяц, Then запись становится `Public` (принудительно, внешний источник).
- **AC-4.3** Given CPU снят 37 месяцев назад, брак не найден, When проходит месяц, Then запись становится `Expired`.

**Complexity:** Medium
**Dependencies:** FR-1, FR-15, FR-16; `mod-framework` (`ModTicks`).
**Assumptions:** `CpuBase.MarketData.Sold` и `SoldByContracts` — помесячные списки, которые сохраняет игра (CODEMAP, раздел Market, Persistence).

### FR-5: Окно решения с таймером

**User Story:** Как игрок, я хочу видеть цену каждой реакции до выбора и иметь время подумать, чтобы решение было осознанным.

**Priority:** Must

#### Acceptance Criteria

1. WHEN брак CPU игрока становится `InternalKnown` или `Public` THEN мод SHALL рассчитать котировку (стоимость, сроки и последствия четырёх реакций), сохранить её в записи и вызвать `EventBus.Fire` с событием выбора из контента. Идентификатор записи и отформатированные числа передаются в `EventFireContext.Args`; обработчики эффектов берут суммы вариантов из сохранённой котировки. Письмо выбора отправляет движок (приоритет `Critical`, тег `es:<instanceId>`); фича сопоставляет экземпляр с записью по `Args[0]` и своих писем выбора не отправляет.
2. WHEN показывается окно выбора THEN каждая кнопка SHALL показывать сумму, срок и ключевые последствия из сохранённой котировки. Применённые затем значения SHALL совпадать с показанными до единицы валюты.
3. IF реакция недоступна (заплатка для типа и года, NFR о доступности) THEN мод SHALL вызвать вариант события без этой кнопки.
4. IF таймер `timerDays` истёк без выбора THEN мод SHALL применить `defaultChoice` из контента: «заплатка», если доступна, иначе «игнор» (решение владельца). Срок таймера SHALL считаться от даты доставки письма (движок: `max(firedDay, DeliveredOn) + timerDays` по `ModMail.Delivered`), чтобы задержка доставки не съедала время на решение.
5. WHILE решение по публичному браку не принято мод SHALL умножать канал `contract.signChance` компании на `pendingSignChanceMultiplier` (0.8): OEM-клиенты ждут реакции. Запись `ModModifiers` создаётся со страховочным сроком `timerDays + pendingGraceDays` и снимается при решении.
6. IF у игрока уже открыто окно решения по другому браку THEN мод SHALL поставить новое решение в очередь и показать после закрытия текущего.
7. IF `EventBus.Fire` вернул `Disabled` (движок выключен посреди партии) THEN мод SHALL применить `defaultChoice` и отправить письмо `ModMail` (приоритет `Normal`, тег `dfr:auto:<recordId>`).

#### Scenarios

- **AC-5.1** Given публичный брак `Major` у CPU игрока, When открывается окно, Then в нём 4 кнопки с суммами; после выбора «Отзыв» списание равно сумме на кнопке.
- **AC-5.2** Given тип `arith` у CPU 1990 года (заплатка с 1995), When открывается окно, Then кнопки «Заплатка» нет.
- **AC-5.3** Given таймер 30 дней истёк от даты доставки письма, When наступает день 31 после доставки, Then применяется реакция по умолчанию, а в журнале событий отмечено «выбрано автоматически».
- **AC-5.4** Given брак обнаружен во время пакетного прогона, When прогон закончился (`BatchEnded`), Then письмо и окно показаны один раз, а срок таймера отсчитывается от доставки.

**Complexity:** Medium
**Dependencies:** `event-system` (`EventBus.Fire` с `EventFireContext`, `EventDefinition` с `timerDays`, `defaultChoice` и `important`, `EventEffects.Register`, `EventBus.OnChoiceResolved`); FR-6–FR-9; `mod-framework` (`ModMail.Delivered` — используется движком).
**Assumptions:** движок предвычисляет эффекты вариантов при срабатывании (`IEventEffectHandler.Resolve`) и показывает их описание (`Describe`) под кнопками; аргументы текстов позиционные (`{0}`, `{1}`…).

### FR-6: Отзыв (recall)

**User Story:** Как игрок, я хочу публично отозвать бракованную партию, чтобы закрыть проблему сразу и сохранить репутацию.

**Priority:** Must

#### Acceptance Criteria

1. WHEN выбран отзыв THEN мод SHALL списать `C_recall` (формула в design) через `ICompany.SpendMoney` с `ExpenseOrigin.Fines` за один раз.
2. WHEN выбран отзыв THEN мод SHALL перевести запись в `Resolved` (новые единицы считаются исправленными), применить изменение репутации из таблицы и снизить популярность затронутых CPU на `popHit.recall[тяжесть]`.
3. IF `C_recall` больше `recallCapShare` × выручка компании за 12 месяцев THEN мод SHALL ограничить сумму этим пределом (потолок включён, 30 % — решение владельца).
4. WHEN отзыв выполнен THEN мод SHALL NOT разрывать OEM-контракты на этот CPU.

#### Scenarios

- **AC-6.1** Given `Major`, 2 000 000 затронутых единиц, `RealUnitCost` 60, цена 400, инфляция 3.0, на складе 0, When выбран отзыв, Then списано 2 000 000 · 0.25 · (60 + 0.15 · 400) + 2 000 000 · 3.0 = 60 000 000 + 6 000 000 = 66 000 000.

**Complexity:** Low
**Dependencies:** FR-5, FR-10.
**Assumptions:** `ExpenseOrigin.Fines` (7) отражается в отчёте как штрафы — решение D5 в design (подтверждено владельцем).

### FR-7: Ревизия (новый степпинг)

**User Story:** Как игрок, я хочу выпустить исправленную ревизию кристалла: дешевле отзыва, но с риском, если о браке узнают позже.

**Priority:** Must

#### Acceptance Criteria

1. WHEN выбрана ревизия THEN мод SHALL запустить отсчёт `D_step[тяжесть]` дней и каждый день списывать `C_step / D_step` через `SpendMoney(ExpenseOrigin.Development)`.
2. WHILE ревизия идёт проданные единицы SHALL продолжать считаться затронутыми.
3. WHEN отсчёт ревизии завершён THEN мод SHALL перевести запись в `Resolved`; IF брак публичный THEN мод SHALL дополнительно списать остаточные претензии `C_resid` (формула в design) с `ExpenseOrigin.Fines`.
4. IF ревизия выбрана для внутреннего брака (тихая ревизия) THEN мод SHALL бросать утечку `leakRate.quietStepping` каждый месяц до конца ревизии и `leakRate.tail` ещё `leakTailMonths` месяцев после.
5. WHEN тихая ревизия «утекает» THEN мод SHALL перевести запись в `Public` с флагом `CoverUp`, списать полный `C_recall` (претензии за единицы, проданные до исправления) и применить репутацию с множителем сокрытия `coverUpMultiplier`.
6. IF у CPU действует программная заплатка и игрок оплатил ревизию из окна «Брак и отзывы» THEN мод SHALL снять понижающий множитель рейтинга по завершении ревизии.
7. WHILE фича выключена ревизия SHALL NOT идти и SHALL NOT оплачиваться; при включении сроки ревизии сдвигаются на длительность паузы (NFR-2).

#### Scenarios

- **AC-7.1** Given `Major`, `DevelopmentCost` CPU 80 000 000, инфляция с момента выпуска не менялась, When выбрана ревизия, Then `C_step` = 0.25 · 80 000 000 = 20 000 000, отсчёт 90 дней, ежедневное списание ≈ 222 222.
- **AC-7.2** Given тихая ревизия завершена 5 месяцев назад, When бросок утечки успешен, Then запись `Public` + `CoverUp`, списан `C_recall`, репутация = (−5 + 0) · 2 = −10.

**Complexity:** Medium
**Dependencies:** FR-4, FR-5, FR-10.
**Assumptions:** нет.

### FR-8: Программная заплатка

**User Story:** Как игрок, я хочу закрыть брак дешёвой заплаткой ценой временной потери производительности, чтобы не платить сразу крупную сумму.

**Priority:** Must

#### Acceptance Criteria

1. WHEN выбрана заплатка THEN мод SHALL списать `C_patch` с `ExpenseOrigin.Development` и добавить для каждого затронутого CPU запись `ModModifiers` на канал `market.rating.cpu` с областью CPU (`ModifierScope.Cpu`), множителем `1 − ipsLoss[тип][тяжесть]`, сроком `mitigationMonths[тяжесть]` месяцев и причиной `dfr.mod.patch`.
2. WHILE заплатка действует запись SHALL находиться в состоянии `Mitigated` и SHALL NOT обнаруживаться заново.
3. WHEN срок заплатки истёк THEN мод SHALL снять множитель и перевести запись в `Resolved`.
4. IF тип брака или год не допускают заплатку (`patchFromYear` > текущий год или `patchable = false`) THEN реакция SHALL быть недоступна.
5. WHEN игрок оплачивает ревизию для CPU с заплаткой (кнопка в окне «Брак и отзывы») THEN мод SHALL запустить отсчёт ревизии по FR-7 и снять множитель по её завершении.
6. Вклад заплатки в канал `market.rating.cpu` SHALL лежать в [0,75; 1,00] при контенте по умолчанию (валидатор ограничивает `ipsLoss` ≤ 0,5, то есть множитель ≥ 0,5). Заплатка рейтинг не повышает. Общий предел [0,5; 2,0] на CPU применяет ядро; в тестах эффекта его учитывать.

#### Scenarios

- **AC-8.1** Given тип `security`, `Major`, When выбрана заплатка, Then у затронутых CPU `Overall` в `Market.CalculateRatings` умножается на 0.88 в течение 18 месяцев.
- **AC-8.2** Given заплатка действует 6 месяцев, When сейв загружается, Then запись `ModModifiers` восстановлена из бокового файла с оставшимся сроком 12 месяцев, а журнал фичи показывает тот же остаток.
- **AC-8.3** Given заплатка действует, а фича выключена в хабе, When фича включена снова, Then записи `ModModifiers` не пересоздавались и сохранили исходный срок окончания.

**Complexity:** Medium
**Dependencies:** FR-5; `mod-framework` (канал `market.rating.cpu`, объявлен с областью CPU и сегмента; записи со сроком сохраняет фреймворк).
**Assumptions:** множитель применяется к `Cpu.Ratings.Overall` после расчёта рейтинга и до `Market.NormalizeRatings`. `Market.DiluteRatings` перераспределяет покупателей между CPU одной компании (раздел «Формулы и баланс» design).

### FR-9: Игнор

**User Story:** Как игрок, я хочу иметь возможность ничего не делать, понимая, что за это придётся платить репутацией и клиентами.

**Priority:** Must

#### Acceptance Criteria

1. WHEN выбран игнор для публичного брака THEN мод SHALL:
   - применить репутацию из таблицы;
   - снизить популярность затронутых CPU на `popHit.ignore[тяжесть]`;
   - на 12 месяцев умножить `contract.signChance` компании на `ignoreSignChance[тяжесть]`;
   - для каждого активного контракта на затронутые CPU (`ContractHelper.ContractsWithCpu`) с вероятностью `oemCancel[тяжесть]` вызвать `ContractManager.RemoveContract` (клиент уходит без штрафа для поставщика).
2. WHILE публичный брак проигнорирован (до `ignoreDrainMonths` месяцев) мод SHALL каждый месяц применять `ModReputation.Add(company, −1, "dfr.rep.drain")`.
3. WHILE публичный брак проигнорирован мод SHALL каждый месяц бросать шанс коллективного иска `classAction[тяжесть]`, не больше одного иска на запись. Иск списывает `U_aff × цена × suitShare` с `ExpenseOrigin.Fines`.
4. WHEN выбран игнор для внутреннего брака THEN мод SHALL NOT применять последствий сразу и SHALL бросать утечку `leakRate.ignore` каждый месяц.
5. WHEN внутренний игнорированный брак «утекает» THEN мод SHALL перевести запись в `Public` + `CoverUp`, применить последствия п. 1 с множителем сокрытия к репутации и SHALL заново предложить выбор из трёх реакций (без игнора).
6. IF игнорированный брак становится `Expired` по FR-4 THEN мод SHALL закрыть запись без последствий.

#### Scenarios

- **AC-9.1** Given публичный `Critical` и 3 активных контракта на CPU, When выбран игнор, Then каждый контракт разрывается с вероятностью 0.6, игрок видит игровой попап о прекращении контракта, штраф не списан.
- **AC-9.2** Given внутренний брак проигнорирован, When через 4 месяца утечка, Then открывается окно с тремя кнопками (отзыв, ревизия, заплатка).

**Complexity:** Medium
**Dependencies:** FR-4, FR-5, FR-10.
**Assumptions:** `ContractManager.RemoveContract` показывает игровой попап прекращения только для CPU игрока (код `ContractManager.RemoveContract`).

### FR-10: Репутация и популярность

**User Story:** Как игрок, я хочу, чтобы реакция влияла на репутацию бренда, а не только на деньги, чтобы ответственное поведение окупалось.

**Priority:** Must

#### Acceptance Criteria

1. WHEN брак становится публичным THEN мод SHALL вызвать `ModReputation.Add(company, base[тяжесть], "dfr.rep.public")`. Причина — ключ L10n фичи; идентификатор записи SHALL писаться в `ModLog`, а не в причину.
2. WHEN применяется реакция THEN мод SHALL вызвать `ModReputation.Add` с дельтой реакции из таблицы контента и причиной `dfr.rep.recall`, `dfr.rep.stepping`, `dfr.rep.patch`, `dfr.rep.ignore` или `dfr.rep.leak`. Для `CoverUp` сумма базовой и ответной дельт SHALL умножаться на `coverUpMultiplier`.
3. WHEN снижается популярность THEN мод SHALL умножить каждый элемент `CpuBase.Popularities` затронутых CPU на `(1 − hit)` и SHALL NOT опускать значение ниже 0. Индекс элемента списка совпадает с индексом сегмента `Segment`.
4. WHERE фича `press-reviews` выключена мод SHALL всё равно записывать изменения в `ModReputation` (хранилище — `mod-framework`). Игровой эффект репутации SHALL оставаться зоной `press-reviews`. Дрейф репутации к 50 выполняет ядро; фича его не реализует.

#### Scenarios

- **AC-10.1** Given публичный `Major` и отзыв, When реакция применена, Then суммарная дельта репутации = −5 + 2 = −3.
- **AC-10.2** Given популярность CPU [0.6, 0.4, 0.1, 0.05] и hit 0.05, When применено снижение, Then [0.57, 0.38, 0.095, 0.0475]. На следующий день игра сама поднимет значения ниже 0.05 до 0.05 для неустаревших CPU (`Market.UpdatePopularities`).

**Complexity:** Low
**Dependencies:** `mod-framework` (`ModReputation`); `press-reviews` (эффект).
**Assumptions:** нет.

### FR-11: Брак у ИИ-соперников

**User Story:** Как игрок, я хочу, чтобы соперники тоже ошибались и платили за это, чтобы мир был честным и давал мне возможности.

**Priority:** Must

#### Acceptance Criteria

1. WHEN ядро поднимает `ModEvents.CpuReleased` для CPU ИИ (`duringFastForward = false`) THEN мод SHALL бросать брак по FR-1–FR-3.
2. WHEN брак ИИ обнаружен THEN мод SHALL выбрать реакцию политикой `AiFlawPolicy`: веса из контента, поправка на денежный запас (`MoneyAmount − ModCredit.ThresholdOf(company)`, то есть деньги плюс лимит долга, который применяет игра) и, если зарегистрирован, смещение `IFlawResponseBias` (FR-17).
3. WHEN реакция ИИ выбрана THEN мод SHALL применить к ИИ те же последствия, что и к игроку: деньги через `AICompany.SpendMoney`, репутация, популярность, множитель рейтинга, разрыв контрактов.
4. WHEN брак ИИ становится публичным THEN мод SHALL сообщить игроку: `Major` и `Critical` — письмом `ModMail` (приоритет `Normal`, тег `dfr:news:<recordId>`), `Minor` — уведомлением `ModNotify`. Сообщение SHALL содержать компанию, CPU, тип, тяжесть и реакцию. Показ в перемотку, загрузку и пакетный прогон откладывает ядро.
5. IF брак ИИ найден внутренне и ИИ выбрал тихую ревизию или игнор THEN мод SHALL NOT сообщать игроку до утечки (слухов нет).

#### Scenarios

- **AC-11.1** Given у AMD публичный `Critical`, денежный запас меньше 1.5 × `C_recall`, When ИИ выбирает, Then вес отзыва 0, выбор из ревизии, заплатки и игнора; игрок получает письмо.

**Complexity:** Medium
**Dependencies:** FR-1–FR-10; `mod-framework` (`ModCredit`, `ModMail`, `ModNotify`); `rival-personalities` (необязательно, FR-17).
**Assumptions:** ИИ не получает окно выбора; решение мгновенное.

### FR-12: Окно «Брак и отзывы» и пометка на карточке CPU

**User Story:** Как игрок, я хочу видеть все известные инциденты, их статус и сроки, чтобы управлять последствиями.

**Priority:** Should

#### Acceptance Criteria

1. WHEN игрок открывает хаб «Моды» → «Брак и отзывы» THEN мод SHALL показать страницу хаба (`ModUI`) с вкладками «Мои CPU» и «Соперники». Столбцы: CPU, компания, тип, тяжесть, статус, реакция, осталось дней, затраты.
2. IF брак игрока в состоянии `Mitigated` THEN строка SHALL содержать кнопку «Профинансировать ревизию» с суммой и сроком (FR-8 п. 5); нажатие SHALL требовать подтверждения `ModUI.Confirm`.
3. WHERE брак игрока известен (не `Hidden`) и не закрыт карточка CPU на боковой панели (`CpuSalesUI`) SHALL показывать пометку «Брак: <статус>».
4. IF запись `Hidden` THEN окно SHALL NOT показывать её и SHALL NOT намекать на её существование.

#### Scenarios

- **AC-12.1** Given у игрока заплатка с остатком 200 дней, When открыто окно, Then строка показывает «Заплатка, −12 %, 200 дн.» и кнопку «Профинансировать ревизию — 20 млн, 90 дн.».

**Complexity:** Medium
**Dependencies:** `mod-framework` (`ModUI`, хаб «Моды»).
**Assumptions:** нет.

### FR-13: API для других фич

**User Story:** Как разработчик смежной фичи (`press-reviews`, `historical-events`, `rival-personalities`), я хочу раскрыть или создать брак через API, чтобы обзоры и исторические события работали с той же механикой.

**Priority:** Should

#### Acceptance Criteria

1. WHEN вызывается `FlawRegistry.TryReveal(cpuSaveId, source)` THEN мод SHALL обнаружить скрытый брак этого CPU (если он есть) с указанным источником и вернуть `true`; иначе вернуть `false` без побочных эффектов.
2. WHEN вызывается `FlawRegistry.ForceFlaw(cpuSaveId, typeId, severity, discovery)` THEN мод SHALL создать запись (или повысить тяжесть существующей) и сразу запустить обнаружение.
3. WHEN вызывается `FlawRegistry.GetKnownFlaws(company)` THEN мод SHALL вернуть только не-`Hidden` записи.
4. WHERE фича выключена методы API SHALL возвращать `false` или пустой список и SHALL NOT бросать исключения.

#### Scenarios

- **AC-13.1** Given `historical-events` в событии 2018 года вызывает `ForceFlaw(cpu, "security", Major, External)`, When вызов выполнен, Then у владельца CPU открывается окно решения (если это игрок).

**Complexity:** Low
**Dependencies:** FR-4, FR-5.
**Assumptions:** нет.

### FR-14: Оценка риска в конструкторе CPU

**User Story:** Как игрок, я хочу видеть примерный риск скрытого брака в конструкторе, чтобы взвешивать его до выпуска.

**Priority:** Could

#### Acceptance Criteria

1. WHERE настройка `showRiskHint` включена (по умолчанию включена, независимо от сложности — решение по умолчанию) конструктор CPU (`CreatorCpu.UpdateInfoTexts`) SHALL показывать строку «Риск скрытого брака: ~N %», округлённую до 5 %.
2. WHEN параметры в конструкторе меняются THEN оценка SHALL пересчитываться той же функцией, что и бросок (FR-2), без вызова `ModRandom`. Оценка SHALL учитывать состояние переключателя «Ускоренный проект» (FR-20).

#### Scenarios

- **AC-14.1** Given включён разгон, When слайдер частоты сдвинут к максимуму, Then оценка растёт.

**Complexity:** Low
**Dependencies:** FR-2.
**Assumptions:** нет.

### FR-15: Настройки и контент баланса

**User Story:** Как владелец, я хочу менять коэффициенты и включать фичу без перекомпиляции, чтобы балансировать по отзывам.

**Priority:** Must

#### Acceptance Criteria

1. WHEN мод загружает контент THEN все числа формул (FR-2–FR-11, FR-20) SHALL читаться из `Content/design-flaw-recalls/flaws.json` через `ModContent` и SHALL проверяться на диапазоны (раздел Security в design).
2. IF значение вне диапазона или файл повреждён THEN мод SHALL записать ошибку в `ModLog`, использовать встроенные значения по умолчанию и продолжить работу.
3. WHEN игрок меняет в `ModSettings` переключатели (фича вкл/выкл, «брак у ИИ», «подсказка риска», «ускоренный проект», множитель частоты брака 0.5–2.0) THEN изменения SHALL действовать без перезапуска игры.

#### Scenarios

- **AC-15.1** Given в `flaws.json` `pMax` = 3.0, When контент загружается, Then в логе `[PTMod] [design-flaw-recalls] ERROR pMax out of range [0,1]`, используется 0.5.

**Complexity:** Low
**Dependencies:** `mod-framework` (`ModContent`, `ModSettings`, `ModLog`).
**Assumptions:** нет.

### FR-16: Сохранение и загрузка

**User Story:** Как игрок, я хочу, чтобы инциденты, отсчёты и множители переживали сохранение и загрузку, чтобы игра была последовательной.

**Priority:** Must

#### Acceptance Criteria

1. WHEN игра сохраняется THEN мод SHALL записать в секцию `design-flaw-recalls` бокового файла:
   - все записи брака;
   - множество `SaveID` с выполненным броском;
   - множество `SaveID` CPU, созданных со спешкой, и ожидающие проекты со спешкой;
   - котировки;
   - отсчёты;
   - день последней активности (`lastActiveDay`).

   Версию схемы секции (`_schema`) пишет ядро; в данных фичи собственного поля версии SHALL NOT быть.
2. WHEN сейв загружается THEN мод SHALL восстановить записи и отсчёты (сроки хранятся датами окончания). Записи `ModModifiers` (рейтинг CPU и `contract.signChance`) восстанавливает фреймворк со своими сроками; фича SHALL проверить, что идентификаторы этих записей в её секции существуют.
3. IF секции нет (старый сейв или мод добавлен посреди партии) THEN мод SHALL начать с пустого состояния. Уже выпущенные CPU SHALL NOT получать бросок задним числом.
4. IF мод удалён THEN сейв игры SHALL загружаться без ошибок. В игровом сейве остаются только уже применённые изменения денег и популярности.

#### Scenarios

- **AC-16.1** Given ревизия с остатком 40 дней, When сохранение и загрузка, Then отсчёт продолжается с 40, ежедневное списание то же.

**Complexity:** Medium
**Dependencies:** `mod-framework` (`ModSave`).
**Assumptions:** нет.

### FR-17: Точка расширения для rival-personalities

**User Story:** Как автор поведения ИИ (`rival-personalities`), я хочу влиять на выбор реакции ИИ и узнавать об инцидентах соперников, чтобы архетипы по-разному реагировали на брак и обжёгшийся ИИ проектировал осторожнее.

**Priority:** Should

#### Acceptance Criteria

1. WHEN `rival-personalities` вызывает `FlawRegistry.SetResponseBias(IFlawResponseBias bias)` THEN `AiFlawPolicy` SHALL умножать веса реакций на `bias.Multipliers(company, isPublic)` в порядке [Recall, Stepping, Patch, Ignore]. `SetResponseBias(null)` снимает смещение. Исключение в `Multipliers` SHALL давать множители 1.0 и засчитываться вызывающей фиче.
2. WHEN запись ИИ переходит в `Public` THEN `FlawRegistry.OnFlawStateChanged` SHALL поднимать событие с `FlawRecordView`, где есть `CompanyKey`, `Severity`, `State`, `PublicSinceDay`. По нему `rival-personalities` ведёт осторожность ИИ после брака (множитель допустимого `FailureRate` в своём патче на `AIBehaviourCreation.AcceptableFailureRate`).
3. Фича SHALL NOT патчить `AIBehaviourCreation.AcceptableFailureRate` (решение владельца: осторожность ИИ — зона `rival-personalities`).
4. WHERE `rival-personalities` отсутствует или выключена `AiFlawPolicy` SHALL использовать базовые веса из контента, осторожности ИИ нет.

#### Scenarios

- **AC-17.1** Given `rival-personalities` задала смещение [0.5, 1, 1, 2] и у ИИ публичный брак с базовыми весами [0.30, 0.30, 0.25, 0.15] при достаточном запасе денег, When ИИ выбирает, Then итоговые веса [0.15, 0.30, 0.25, 0.30] до нормировки.
- **AC-17.2** Given у ИИ публичный `Critical`, When `FlawRegistry.OnFlawStateChanged` поднят, Then подписчик видит `PublicSinceDay` = текущий день и `Severity` = `Critical`.

**Complexity:** Low
**Dependencies:** FR-11, FR-13; `rival-personalities` (необязательно).
**Assumptions:** порядок множителей и имя интерфейса `IFlawResponseBias` согласованы со спекой `rival-personalities` (FR-13 п. 5 той спеки).

### FR-18: Связь с прессой

**User Story:** Как игрок, я хочу, чтобы обзоры прессы учитывали известный брак CPU, чтобы скандал отражался и в оценках.

**Priority:** Should

#### Acceptance Criteria

1. WHERE фича `press-reviews` активна мод SHALL зарегистрировать корректировщик обзоров (`PressReviewsApi.RegisterAdjuster`) с идентификатором `design-flaw-recalls`.
2. WHEN пресса рецензирует CPU с известным незакрытым браком THEN корректировщик SHALL уменьшить итог обзора на `press.overallAdjustment[тяжесть]` (−8 / −15 / −15, подтверждено владельцем) и добавить примечание «Пресса знает о дефекте».
3. IF брак скрыт (`Hidden`) или закрыт THEN корректировщик SHALL NOT менять обзор.
4. WHEN брак становится публичным THEN статью о нём SHALL публиковать `press-reviews` по событию `FlawRegistry.OnFlawStateChanged`; фича SHALL NOT публиковать статью сама.

#### Scenarios

- **AC-18.1** Given у CPU публичный `Major` с активной заплаткой, When `press-reviews` публикует обзор, Then метаоценка на 15 ниже, в карточке примечание о дефекте.

**Complexity:** Low
**Dependencies:** `press-reviews` (`PressReviewsApi`, `IReviewAdjuster`); FR-13.
**Assumptions:** корректировщик вызывается до агрегации оценок изданий и не имеет побочных эффектов (контракт `IReviewAdjuster`).

### FR-19: Передача брака вместе с CPU при поглощении

**User Story:** Как игрок, поглощающий соперника, я хочу получать его CPU вместе с их скрытыми дефектами и обязательствами, чтобы покупка компании имела риск.

**Priority:** Should

#### Acceptance Criteria

1. WHEN ядро поднимает `ModEvents.CpuTransferred(from, to, cpu)` и `cpu` — базовый CPU активной записи (не `Resolved`, `Expired`, `Closed`) THEN мод SHALL сменить владельца записи на `ModCompanies.KeyOf(to)` и снять записи `ModModifiers` уровня компании (`contract.signChance`). Записи уровня CPU (`market.rating.cpu`) SHALL остаться.
2. IF запись в состоянии `Hidden`, `InternalKnown`, `Stepping` или `Mitigated` THEN состояние и сроки SHALL сохраниться, а обязательства (ежедневные списания ревизии, утечка, истечение) SHALL перейти к новому владельцу.
3. IF запись в состоянии `Public` с игнором (дренаж репутации, иск) THEN дренаж и иск SHALL остановиться, а новому владельцу SHALL быть предложен выбор по FR-5 (игрок — окно `dfr.decide.public*`, ИИ — `AiFlawPolicy`); флаг `CoverUp` SHALL сниматься.
4. IF `cpu` — вариант (`Cpu.Base != null`) THEN событие SHALL игнорироваться: запись следует за базовым CPU.
5. WHEN CPU переносится THEN `CpuReleased` не поднимается, повторного броска нет и `rolledCpuIds` не меняется.
6. IF `OnCompanyWentBankrupt` для поглощённой компании пришёл до `CpuTransferred` THEN записи прежнего владельца SHALL закрыться по FR-4 п. 5 с записью в лог (контракт `rival-acquisitions`: сначала перенос, потом выведение компании).

#### Scenarios

- **AC-19.1** Given у AMD есть `Hidden` брак `Major` в CPU 3000 и игрок поглощает AMD, When ядро поднимает `CpuTransferred` для этого CPU, Then у записи `companyKey` = `player`; через 8 месяцев брак обнаружен внешне, и у игрока открывается окно решения.
- **AC-19.2** Given у AMD идёт тихая ревизия с остатком 40 дней, When игрок поглощает AMD, Then ревизия продолжается, ежедневное списание идёт с игрока.

**Complexity:** Medium
**Dependencies:** FR-4, FR-5, FR-14 (записи каналов); `mod-framework` (`ModEvents.CpuTransferred`); `rival-acquisitions` (поднимает событие).
**Assumptions:** поглощение выполняет игрок; перенос идёт для базового CPU и вариантов подряд.

### FR-20: Ускоренный проект («спешка») в конструкторе

**User Story:** Как игрок, я хочу ускорить проект ценой повышенного риска скрытого брака, чтобы выпустить CPU раньше соперников.

**Priority:** Should

#### Acceptance Criteria

1. WHERE параметр `rushEnabled` включён (по умолчанию включён) конструктор CPU (`CreatorCpu`) SHALL показывать переключатель «Ускоренный проект» (по умолчанию выключен для каждого нового проекта).
2. WHEN переключатель включён THEN срок проекта SHALL становиться `max(1, round(projectTime × (1 − rushTimeCut)))` (−25 %), стоимость проекта — `projectCost × rushCostMultiplier` (×1,10), а показатели в конструкторе (стоимость, срок, «в месяц», дата завершения) SHALL отображаться уже изменёнными.
3. WHEN игрок создаёт проект со включённой спешкой THEN мод SHALL запомнить признак для будущего CPU и при завершении проекта (`ProjectCompletedHandler.AddCpu`) записать `SaveID` в множество `rushCpuIds`. Вариант CPU наследует признак базового (D10).
4. WHEN вычисляется вероятность брака для CPU из `rushCpuIds` THEN к `p_raw` SHALL добавляться `kRush` (0,06; FR-2).
5. IF цели патчей конструктора не найдены THEN переключатель SHALL не показываться, остальная фича SHALL работать, а в журнал пишется одно предупреждение.
6. ИИ SHALL NOT использовать спешку: его проекты моделирует `AIBehaviourCreation`.

#### Scenarios

- **AC-20.1** Given проект на 400 дней и 80 млн, When включена спешка, Then конструктор показывает 300 дней и 88 млн, а вероятность брака этого CPU выше на `kRush` × множители сложности и эпохи.
- **AC-20.2** Given проект со спешкой завершён и CPU выпущен, When считается p, Then `SaveID` CPU есть в `rushCpuIds` и p включает `kRush`.

**Complexity:** Medium
**Dependencies:** FR-2, FR-14, FR-15, FR-16; `mod-framework` (`ModHooks`, `ModUI.Toggle`).
**Assumptions:** `CreatorCpu.Project` (приватный) вычисляет `projectCost` и `projectTime` до `UpdateInfoTexts`; `CreatorCpu.CreateCpu` создаёт проект из этих полей; `SaveID` нового CPU присваивается при завершении проекта (код `CreatorCpu`, вложенный класс `<>c__DisplayClass92_0`).

## Non-Functional Requirements

### NFR-1: Производительность

- WHEN проходит игровой день THEN суммарная работа фичи (отсчёты ревизий и заплаток, пометки на карточках) SHALL занимать не больше 0.1 мс на типичной партии (до 100 активных записей, до 80 CPU на рынке).
- WHEN проходит месяц THEN проверка обнаружения, утечек и истечения SHALL занимать не больше 2 мс при 500 записях.
- Фича SHALL NOT регистрировать провайдеры на канал `market.rating.cpu`: только записи `ModModifiers.Add` с областью CPU, которые фреймворк кеширует на день.
- Пометка на карточке CPU SHALL находить запись за O(1) (словарь `SaveID → запись`).
- Подписчик `ModEvents.CpuReleased` SHALL работать ≤ 0,1 мс на CPU.

### NFR-2: Надёжность

- IF в обработчике события, тика, патча или эффекта возникает исключение THEN мод SHALL перехватить его на границе (`ModHooks.Guard`), записать в `ModLog` с идентификатором записи и SHALL NOT пропускать исключение в код игры. Свои счётчики ошибок фича не ведёт.
- IF исключения фичи превышают порог `ModHooks` (circuit breaker фреймворка) THEN фича SHALL перейти в состояние `Faulted` до перезапуска, а игра SHALL продолжить работу.
- WHEN фичу выключают посреди партии THEN её записи `ModModifiers` SHALL храниться и не применяться (правило применимости фреймворка; записи не удаляются и не пересоздаются, их сроки идут по календарю), ревизия SHALL не идти и не оплачиваться, записи брака SHALL сохраниться без изменений. WHEN фичу включают снова THEN сроки ревизии SHALL сдвигаться на длительность паузы, а `OnEnabled` SHALL NOT пересоздавать записи `ModModifiers`.

### NFR-3: Совместимость сейвов

- Старые сейвы без секции SHALL загружаться (FR-16 п. 3).
- Поля в классы игры SHALL NOT добавляться. Всё состояние хранится в `ModSave`.
- Версию секции (`_schema`) ведёт ядро; миграции между версиями схемы SHALL быть описаны в design и выполняться в `Read(section, schema)`. В секции фичи поля `schema` SHALL NOT быть.

### NFR-4: Локализация

- Все тексты (окна, кнопки, письма, уведомления, названия типов и тяжестей, причины репутации и модификаторов) SHALL браться из `ModL10n` с ключами `dfr.*`, языки ru (по умолчанию) и en.
- Суммы SHALL форматироваться игровым `StringFormatter.FloatToMoney`.
- Названия компаний SHALL браться из игры (`ICompany.get_Name`); в тексты и контент они не вшиваются (реальные названия задаёт русификатор).

### NFR-5: Удобство

- Перед любым списанием больше 1 % денег компании игрок SHALL видеть сумму в окне выбора или в журнале.
- Окно решения SHALL ставить игру на паузу (`PauseTrigger`, через окно `event-system`).
- Числа в журнале и письмах SHALL совпадать с применёнными (котировка считается один раз).

### NFR-6: Детерминизм

- Все случайные броски SHALL идти через `ModRandom` фичи (`ModRandom.Stream("design-flaw-recalls")`). После загрузки сейва и одинаковых действий игрока результаты SHALL повторяться.

### NFR-7: Безопасность и валидация данных

- WHEN загружается контент (встроенный или из `<папка игры>/PTMod/content/design-flaw-recalls/`) THEN мод SHALL проверить диапазоны всех чисел и длины массивов (раздел Security в design) и SHALL NOT применять непроверенные значения.
- WHEN загружается секция сейва THEN мод SHALL отклонять недопустимые значения enum, отрицательные сроки и нечисловые суммы (`NaN`, бесконечность), закрывая такие записи.
- Фича SHALL NOT обращаться к сети и запускать внешние процессы.

### NFR-8: Вклад в общие каналы и баланс

- Фича SHALL использовать только каналы реестра ядра: `market.rating.cpu` (заплатка) и `contract.signChance` (ожидание реакции и игнор). Новых каналов она не объявляет.
- Максимальные вклады фичи (множители одной фичи на один CPU или компанию): `market.rating.cpu` ∈ [0,75; 1,00] (контент по умолчанию; жёсткий предел валидатора 0,5); `contract.signChance` ∈ [0,70; 1,00] на компанию (ожидание ×0,80 и игнор ×0,70…0,95 могут действовать одновременно: худший случай 0,56). Канал `popularity.gain` фича не использует: популярность снижается разовым умножением `CpuBase.Popularities`.
- Общий предел [0,5; 2,0] на CPU для `market.rating.cpu` применяет ядро (балансовый диапазон); тесты эффекта SHALL учитывать это ограничение, а `Explain` показывает «(ограничено)».

## Edge Cases

| Случай | Ожидаемое поведение |
|---|---|
| CPU выпущен во время перемотки новой игры | Без броска (FR-1 п. 4): история до старта игрока «чистая» |
| Фича включена посреди партии | Броски только для CPU, выпущенных после включения |
| Вариант CPU выпущен после того, как брак базового стал `Resolved` | Вариант считается исправленным: `Resolved` до выпуска означает исправленный кристалл |
| Вариант выпущен, пока брак `Mitigated` | Вариант получает тот же множитель на оставшийся срок |
| CPU произведён по аутсорсингу (`Cpu.IsOutsourced`) | Платит компания-разработчик (`Cpu.Company`); литейщик не участвует |
| Компания-владелец обанкротилась | Запись `Closed`, отсчёты и множители сняты |
| `Cpu.Price` = 0 или CPU не продавался | Обнаружение невозможно (`U` = 0), запись истекает по FR-4 п. 4 |
| Несколько браков у игрока одновременно | Очередь окон (FR-5 п. 6), каждое со своим таймером после показа |
| Сумма реакции больше денег компании | Списание проходит: компания уходит в минус, дальше действует банковская логика игры (`BankruptcyHandler`) |
| Загрузка во время открытого окна решения | `event-system` восстанавливает таймер; котировка берётся из записи, а не пересчитывается |
| Удаление мода | Сейв грузится; в игре остаются уже применённые деньги и популярность |
| Выделение SolarFoundries переносит производство CPU AMD (`CompanyEventHandler.TriggerSolarFoundriesSpinOff`) | Владелец записи — `Cpu.Company` (AMD), не меняется |
| Решение возникло во время пакетного прогона (`NextMonth`) | Письмо и окно показывает ядро/движок после `BatchEnded`; срок таймера — от доставки |
| Фича выключена посреди ревизии | Списания стоят, сроки ревизии при включении сдвигаются на длительность паузы; заплатка не применяется, срок идёт по календарю |
| CPU поглощён игроком (`CpuTransferred`) | Запись следует за CPU и новым владельцем (FR-19); бросок не повторяется |
| `ModEvents.CpuReleased` не поднят (фича отключена ядром как `Faulted`/`Unavailable`) | Бросков нет; записи сохраняются; после восстановления фичи броски идут только для новых CPU |
| Цели патчей конструктора не найдены | Нет подсказки риска и переключателя спешки; остальная фича работает |

## Constraints and Assumptions

### Technical Constraints

- Патчи только через Harmony (`ModHooks`), без правки `Assembly-CSharp.dll` (решения 0001, 0002). Выпуск и перенос CPU — только через `ModEvents`; патчи фичи на `Company.AddCpu` и `AICompany.AddCpu` запрещены.
- Изменение рейтинга CPU — только через канал `market.rating.cpu` с областью CPU. Метод `Market.CalculateRatings` зарезервирован каналом (`ModHooks.IsReservedByChannel`), его единственный патч принадлежит `mod-framework`.
- Компании в состоянии фичи хранятся по ключу `ModCompanies.KeyOf` (`player` / `ai:<UniqueID>`), CPU — по `SaveID`.
- `ExpenseOrigin` нельзя расширить без правки игры. Используются `Fines` и `Development` (D5).
- Окно выбора — из `event-system`. Своё окно у фичи только одно: журнал.
- Код `Logic/` — общее подмножество API .NET Framework 4.8 и `mscorlib` Unity (без `init`, `record`, `Index`, `Range`); тесты — мини-раннер ядра (`[Test]`, `[Covers(typeof(X))]`), запуск `python mod/build.py --tests`.

### Business Constraints

- Числа баланса — в контент-JSON, а не в коде (`steering/context.md`, «Баланс»).
- Ручная проверка в игре — шаг владельца, вне онлайн-игр с античитом.

### Assumptions

- `event-system` поддерживает `EventBus.Fire(eventId, EventFireContext)` с позиционными `Args`, таймер с `defaultChoice` (от даты доставки письма), предвычисление эффектов (`Resolve`) и регистрацию типов эффектов `EventEffects.Register`.
- `mod-framework` объявляет канал `market.rating.cpu` с областями компании, CPU и сегмента и сохраняет записи `ModModifiers.Add` со сроком; поднимает `ModEvents.CpuReleased` и `ModEvents.CpuTransferred`.
- `ModReputation.Add(company, delta, reason)` ограничивает значение диапазоном 0..100; `reason` — ключ L10n.

## Success Criteria

### Definition of Done

- [ ] Все FR с приоритетом Must реализованы; Should — реализованы или явно перенесены владельцем.
- [ ] Юнит-тесты чистой логики (`FlawRiskModel`, `DiscoveryModel`, `ResponseCostCalculator`, `AiFlawPolicy`, `FlawStateMachine`, валидация контента, сериализация секции) зелёные в мини-раннере; каждый публичный тип `Logic/` указан в `[Covers]`.
- [ ] Самопроверка на старте находит все цели патчей и регистрирует события и типы эффектов.
- [ ] Ручные сценарии из design (раздел Testing) пройдены владельцем.
- [ ] Старый сейв без секции загружается; сейв с секцией грузится без мода.

### Acceptance Metrics

- Симуляция Монте-Карло (тест `FlawBalanceSimulationTests`) на 10 000 типичных дизайнов, сложность 2: средняя вероятность брака 8–15 %, доля `Critical` среди браков ≤ 20 %.
- Среднее время до обнаружения при 1 млн проданных единиц: 6–18 месяцев.
- Отзыв `Major` для массового CPU стоит 2–8 % выручки компании за 12 месяцев (калибровка по FDIV: списание 475 млн $ при выручке Intel около 11.5 млрд $ в 1994 году — около 4 %).
- 0 исключений `[PTMod]` уровня Error в `Player.log` за 10 игровых лет на скорости 3.

### Решения, принятые по общему правилу при переработке v0.2

| Вопрос | Решение | Обоснование |
|---|---|---|
| Причины репутации и модификаторов | ключи L10n фичи (`dfr.rep.public`, `dfr.rep.recall`, `dfr.mod.patch`…); идентификатор записи — в `ModLog` | соглашение об идентификаторах (правило 5) |
| Страховочный срок записи ожидания реакции | `timerDays + pendingGraceDays` (14), снимается при решении | таймер движка идёт от доставки письма, фиксированный срок мог бы истечь раньше |
| Выключение посреди ревизии | ревизия стоит, при включении сроки сдвигаются на длительность паузы; срок заплатки идёт по календарю (как у записи `ModModifiers`) | записи канала не пересоздаются (замечание кросс-ревью), поэтому срок заплатки не должен расходиться с записью |
| Параметры спешки | срок −25 %, стоимость ×1,10, риск +0,06 к `p_raw`; ИИ спешку не использует | черновые значения, лежат в контенте |
| Привязка признака спешки к CPU | по имени проекта и плановой дате завершения → `SaveID` при `ProjectCompletedHandler.AddCpu` | `SaveID` присваивается только при завершении проекта |
| Судьба записи при поглощении | следует за базовым CPU к новому владельцу; штрафные эффекты уровня компании не наследуются | купленные CPU приносят риски, но не чужие репутационные штрафы |
| Приоритет писем фичи | новости об ИИ и письмо при отключённом движке — `Normal`; письма выбора отправляет движок (`Critical`) | `Critical` только для выборов с таймером |
| `IFlawResponseBias` | один слот; `SetResponseBias(null)` снимает | единственный потребитель — `rival-personalities` |
| Выбор реакции ИИ при нулевых весах | игнор | поведение политики ИИ из v0.1 |

## Glossary

| Термин | Значение |
|---|---|
| Скрытый брак | Дефект дизайна, который прошёл фабричный контроль и проявляется у покупателей. Не путать с отбраковкой `FailureRate` на фабрике |
| Запись брака | Состояние инцидента в `ModSave`: CPU, тип, тяжесть, статус, реакция, отсчёты |
| Тяжесть | `Minor` / `Major` / `Critical`, масштабирует шансы и стоимость |
| Обнаружение внутреннее | Брак нашли свои инженеры: публика не знает, доступны тихие реакции |
| Обнаружение внешнее | Брак нашли пресса или покупатели: удар по репутации сразу |
| Отзыв (recall) | Публичная замена бракованных единиц, разовые затраты |
| Ревизия (степпинг) | Исправленная версия кристалла, проект на `D_step` дней |
| Заплатка (mitigation) | Микрокод или ПО, временно снижает производительность |
| Игнор | Отказ реагировать |
| Утечка | Внутренний брак становится публичным |
| Сокрытие (`CoverUp`) | Брак утёк после тихой реакции или игнора; репутационный штраф удваивается |
| Затронутые единицы `U_aff` | Проданные единицы CPU и его вариантов до исправления |
| Котировка | Однократно рассчитанные стоимости и сроки реакций, хранятся в записи |
| Спешка (ускоренный проект) | Режим конструктора: проект короче на 25 % и дороже на 10 %, риск скрытого брака выше |
| `ModEvents.CpuReleased` | Событие ядра «CPU выпущен» (`owner`, `cpu`, `isVariant`, `duringFastForward`) |
| `ModEvents.CpuTransferred` | Событие ядра «CPU перенесён между компаниями» (`from`, `to`, `cpu`) |
