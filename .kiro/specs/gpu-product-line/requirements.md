## Introduction

В Processor Tycoon есть только одна продуктовая линия — CPU. Разработчик называл GPU следующим крупным дополнением после архитектур, игроки об этом просят, но игру забросили до этого шага. После 2000-х года у игрока, который уже обогнал соперников по CPU, мало новых целей.

Фича добавляет вторую продуктовую линию — видеокарты. У игрока (IDM или fabless; чистый литейщик подразделение открыть не может) появляется своё GPU-подразделение со своей мини-веткой исследований (архитектуры, видеопамять, охлаждение). В упрощённом конструкторе GPU собирается из техпроцессов, которые компания уже исследовала для CPU. Видеокарты производятся на тех же линиях фабрики, что и CPU, и продаются на отдельном рынке GPU, где каждая эпоха открывает свои сегменты: 2D-адаптеры, 3D-ускорители, вычисления, ИИ. На рынке GPU игрок встречает реальных производителей (NVIDIA, ATI, 3dfx, Matrox, S3, а также AMD и Intel, привязанные к компаниям ИИ). Если компания продаёт и CPU, и GPU, она получает платформенную синергию: бренд в одном рынке поднимает рейтинг в другом. На этапе 3 (Could) производители консолей присылают игроку крупные OEM-заказы на GPU.

Модель GPU повторяет подход игры. Транзисторы считаются как в `CpuMath.TransistorCount`, выход годных кристаллов — по `ProductionMath.DiesPerWafer`, себестоимость кристалла — по `CpuMath.RealUnitCost`, а рейтинги, покупатели и популярность — портом формул `Market` (`Market.CalculateRatings`, `Market.NormalizeRatings`, `Market.DiluteRatings`, `Market.CalculatePotentialBuyers`, `Market.UpdatePopularities`). Классы игры не меняются. GPU не становятся объектами `Cpu` и не попадают в сейв игры: всё состояние фичи хранится в секции `gpu-product-line` бокового файла `ModSave`. Фича — обычная `[ModFeature]` ядра (`IModFeature`), без собственных точек входа и без патчей на `Company.AddCpu` / `AICompany.AddCpu`.

Работа разбита на три этапа:
- **этап 1 (MVP)** — подразделение, исследования, конструктор, разработка, производство, один рынок «Видеокарты» с фоновой конкуренцией;
- **этап 2** — эпохи с сегментами и именные соперники;
- **этап 3** — синергия CPU+GPU, интеграция с другими фичами и консольные OEM-заказы (Could).

### Feature Summary
Вторая продуктовая линия — видеокарты: мини-дерево исследований GPU, упрощённый конструктор на модели в духе `CpuMath`, разработка, производство на общих линиях фабрики, рынок GPU по эпохам с реальными соперниками, синергия CPU+GPU и консольные заказы. Числа задаются в контент-JSON, состояние хранится только в `ModSave`.

### Business Value
- **Для игрока**: новая долгая цель на середину и конец партии. Нужно решить, сколько линий фабрики отдать под GPU, войти ли в 3D-эпоху раньше соперников, закрепиться ли в сегменте вычислений и ИИ. Исследования CPU (техпроцессы, частоты) начинают работать на вторую линию, а синергия награждает компанию, которая делает обе.
- **Доказательства спроса**: в IDEAS.md I16 — спрос «medium», fun 4/5. Разработчик сам называет GPU следующим крупным дополнением; игроки прямо просят видеокарты и платформенные продукты (itch.io, ссылки выше). Дополнения с новыми продуктовыми линиями — самые популярные моды в похожих tycoon-играх (cubiq.ru).
- **Для проекта**: фича проверяет, что фреймворк выдерживает новую экономическую подсистему целиком: свой рынок, свои тики, своих соперников. Она же читает контент-каналы ядра (`gpu.demand`, `gpu.rating`, `gpu.vramCost`) для событий и исторического календаря (криптобумы 2017 и 2021 годов).

### Scope

**Входит:**
- GPU-подразделение: основание решением игрока (стоимость `2,5e7 × инфляция`, догоняющая разблокировка технологий; чистому литейщику недоступно), окно «Видеокарты» из хаба «Моды»;
- мини-дерево исследований GPU (ветки «Архитектура», «Видеопамять», «Охлаждение»), своя лаборатория с финансированием, предпосылки на технологии игры;
- упрощённый конструктор GPU: архитектура, техпроцесс игры, тип и объём видеопамяти, ширина шины, площадь кристалла, частота, охлаждение; живой расчёт характеристик и оценка по сегментам;
- проекты разработки GPU (стоимость, срок, пауза, отмена), диалог выпуска;
- производство на общих линиях фабрики игрока (резерв линий до производства CPU; переключатель «CPU в приоритете» отдаёт GPU только остаток), абстрактный аутсорс для fabless;
- рынок GPU: этап 1 — один сегмент и «Прочие производители»; этап 2 — эпохи и сегменты (2D, 3 игровых, вычисления, ИИ) с требованиями к функциям и VRAM;
- управление линейкой: цена, продажа, линии и «авто», снятие с производства, хранение, помесячная бухгалтерия;
- соперники на рынке GPU: виртуальные производители с реальными названиями (NVIDIA, ATI, 3dfx, Matrox, S3) и производители, привязанные к компаниям ИИ по `UniqueID` (AMD, Intel); генерация их продуктов, каденция, цены, мощности, вход, уход и слияния; выпуск соперников абстрактный, линий фабрики они не резервируют;
- письма-новости рынка GPU;
- синергия CPU+GPU: взаимные бонусы рейтинга провайдерами каналов `market.rating.cpu` (вклад ≤ ×1,08) и `gpu.rating` (вклад ≤ ×1,10), общий опыт техпроцесса, скидка совместной разработки;
- консольные OEM-заказы производителей консолей (Sony, Nintendo, Microsoft) на GPU игрока — собственная модель без `ContractType` игры (Could, этап 3);
- чтение каналов ядра `gpu.demand`, `gpu.demand.<segmentId>`, `gpu.rating`, `gpu.vramCost` (объявлены в реестре ядра, пишут их другие фичи) и read-only `GpuApi` с предикатами `gpu.*` для других фич; передача линейки при поглощении компании ИИ (`GpuApi.TransferVendorProducts`);
- весь баланс — в `Content/gpu-product-line/*.json`, строки — в `ModL10n` (ru/en).

**Не входит:**
- встроенная графика в CPU (iGPU) — вне скоупа (решение владельца): нужен новый атрибут дизайна CPU в `CreatorCpu`;
- системный уровень из I16: платы, чипсеты, эталонные ноутбуки — вне скоупа (решение владельца), возможна отдельная будущая спека;
- OEM-контракты на GPU через `ContractType` игры (он только для CPU) и OEM-заказы для ноутбуков; консольные заказы реализованы собственной моделью (FR-19, Could), прозрачность контрактов — зона `contract-transparency`;
- урезанные версии (binning) из бракованных кристаллов и ревизии (stepping) GPU; отзывы GPU — `design-flaw-recalls` работает только с CPU;
- обзоры GPU в прессе — зона `press-reviews`, обзоров GPU там нет; рынок GPU лишь читает стандартный канал `popularity.gain` (репутация бренда влияет на уровне компании);
- изменение формул рынка CPU: бонус синергии идёт только через провайдер канала `market.rating.cpu`, его патч принадлежит `mod-framework`;
- производство GPU на линиях ИИ-компаний: их выпуск абстрактный, линий они не резервируют (решение владельца);
- ярлык на рабочем столе: `ModUI` ярлыков не предоставляет, окно открывается из хаба «Моды»;
- патчи на `Company.AddCpu` / `AICompany.AddCpu`, `DateController.NextMonth`, `GameManager.StartNewGame`, `MenuGameSetup.InitializeUI`, `MenuGameSetup.UpdateInitialData`, `EmailWindow.GetEmails`, `EmailWindow.UpdateEmailText`: эти цели закреплены за ядром;
- правка `data.unity3d`, новые поля в классах игры, объекты `Cpu`/`Project` игры для GPU.

## Requirements

### FR-1: GPU-подразделение и точка входа

**User Story:** Как игрок, я хочу открыть GPU-подразделение в момент, который выберу сам, и попадать в окно «Видеокарты» из хаба «Моды», чтобы начать вторую продуктовую линию осознанно, а не получить её навязанной.

**Priority:** Must (этап 1)

#### Acceptance Criteria (EARS)
1. WHERE фича `gpu-product-line` включена (`ModFeatures.IsActive`) мод SHALL показывать на своей странице хаба «Моды» (`FeatureContext.HubPage`) кнопку «Видеокарты», которая открывает окно GPU.
2. IF фича выключена в хабе «Моды» THEN мод SHALL не показывать окно, не обрабатывать тики GPU (`ModTicks` не вызывает подписчиков неактивной фичи) и не резервировать линии фабрики.
3. WHEN игрок открывает окно GPU до основания подразделения THEN мод SHALL показать экран основания: стоимость `foundingCost × InflationHandler.Instance.Inflation` и список узлов дерева GPU, которые откроются бесплатно.
4. IF текущий год меньше года открытия рынка GPU (`market.opensYear`, по умолчанию 1981) THEN мод SHALL заблокировать кнопку основания с подсказкой, в каком году откроется рынок.
5. IF после списания стоимости `MoneyAmount` компании игрока станет меньше порога дефолта `ModCredit.ThresholdOf(компания игрока)` (отрицательное число; в него уже входят `bank.creditLimit` и глобальный множитель) THEN мод SHALL заблокировать кнопку основания и показать причину. Значение `CentralBank.DebtLimit` фича напрямую не читает.
6. WHEN игрок подтверждает основание THEN мод SHALL списать стоимость через `Company.SpendMoney(value, ExpenseOrigin.Development)`, пометить подразделение основанным с датой и открыть все узлы дерева GPU с годом ≤ текущий год − `catchUpLagYears` (по умолчанию 3).
7. WHEN подразделение основано THEN окно GPU SHALL показывать вкладки «Исследования», «Конструктор», «Линейка», «Рынок».
8. Мод SHALL открывать окно GPU только из хаба «Моды»: ярлык на рабочем столе не создаётся, потому что `ModUI` ярлыков не предоставляет.
9. IF компания игрока — чистый литейщик (`ICompany.get_IsCpuCompany` возвращает false, то есть `ICompany.get_IsFoundry`) THEN мод SHALL заблокировать основание с подсказкой «Подразделение недоступно литейщику без CPU-подразделения» (решение владельца). Состав подразделений `Divisions.Cpu` задаётся только при старте партии (`Company.InitializeAsNewGame`), поэтому повторная проверка после основания не нужна.

#### Сценарии приёмки
- **AC-1.1** Given 1995 год, IDM, подразделение не основано, денег 300 млн; When игрок нажимает «Открыть GPU-подразделение» и подтверждает; Then списано `2.5e7 × Inflation` по статье «Разработка», открыты узлы до 1992 года включительно (`arch.2d`, `arch.gui`, `vram.dram`, `vram.vram`, `cool.passive`), появились 4 вкладки.
- **AC-1.2** Given фича выключена в хабе «Моды»; When игрок играет 2 года; Then окно «Видеокарты» недоступно, `ProductionCapacity` и загрузка фабрики не отличаются от ванильных.
- **AC-1.3** Given 1975 год; When игрок открывает окно GPU; Then кнопка основания неактивна, подсказка «Рынок видеоадаптеров откроется в 1981 году».
- **AC-1.4** Given порог дефолта игрока `ModCredit.ThresholdOf` = −200 млн, `MoneyAmount = −200 млн + 1 млн`; When он открывает экран основания; Then кнопка неактивна с причиной «Не хватает кредитного лимита».
- **AC-1.5** Given игрок начал партию литейщиком (`Divisions.Cpu = false`), 1995 год, денег 300 млн; When он открывает окно GPU; Then кнопка основания неактивна, подсказка «Подразделение недоступно литейщику без CPU-подразделения».

- **Complexity:** Medium
- **Dependencies:** `mod-framework` (`ModUI`, `ModSettings`, `ModSave`, `ModCredit`), FR-2, FR-9
- **Assumptions:** подразделение доступно IDM и fabless; чистому литейщику — нет (решение владельца, «Решения по умолчанию» п. 2).

### FR-2: Мини-дерево исследований GPU

**User Story:** Как игрок, я хочу исследовать архитектуры GPU, типы видеопамяти и охлаждение в отдельной лаборатории, чтобы видеокарты развивались по своей траектории, но опирались на мои исследования CPU.

**Priority:** Must (этап 1)

#### Acceptance Criteria (EARS)
1. Мод SHALL предоставлять дерево из трёх веток: «Архитектура», «Видеопамять», «Охлаждение». Узлы, их годы, стоимость и предпосылки берутся из `Content/gpu-product-line/research.json`.
2. WHEN игрок выбирает узел, у которого выполнены все предпосылки (узлы GPU и технологии игры) THEN мод SHALL сделать его текущим исследованием GPU-лаборатории или поставить в очередь (до 5 узлов).
3. IF узел требует технологию игры (например, `DDR2`), которую компания не исследовала THEN мод SHALL показывать узел заблокированным с названием недостающей технологии.
4. WHILE идёт исследование и время не на паузе мод SHALL ежедневно (фаза `TickPhase.Tick`) прибавлять к прогрессу `ResearchMath.ResearchSpeed(funding, company) / T_eff`.
5. WHILE идёт исследование мод SHALL ежедневно списывать `monthlyCost × Modifiers.GetModifier(ModifierType.ResearchCost, company) / 30 × funding` через `Company.SpendMoney(…, ExpenseOrigin.Research)`.
6. Мод SHALL вычислять `T_eff` по правилу `TechnologyTimeUpdater.UpdateTechnologyTimes`: за каждый год до года узла время растёт на 350 %, после года узла (через год) — уменьшается на 15 % в год, но не больше чем на 75 %.
7. WHEN игрок меняет финансирование ползунком (10–100 %) THEN мод SHALL применять новое значение со следующего дня, а интерфейс SHALL сразу показать новые срок и стоимость в месяц.
8. WHEN прогресс узла достигает 1 THEN мод SHALL пометить узел исследованным, открыть его содержимое в конструкторе, начать следующий узел очереди и показать уведомление `ModNotify`.
9. Мод SHALL не давать ИИ-соперникам доступ к дереву: их технологии берутся по году с отставанием (FR-13).

#### Сценарии приёмки
- **AC-2.1** Given 1 января 1996 года, `arch.3d` (год 1995, 200 дней, 2e7 в месяц) доступен, финансирование 100 %, IDM; When игрок запускает исследование; Then ежедневный прогресс = `sqrt(1.0) × 1.05 / T_eff`, `T_eff = 200` (с 1 января 1995 прошло ровно 365 дней, бонус 0), списание ≈ 666 667 в день по статье «Исследования».
- **AC-2.2** Given 1990 год; When игрок ставит `arch.3d` (год 1995); Then `T_eff = 200 × (1 + 3.5 × 5) ≈ 3700` дней, и интерфейс показывает срок ≈ 10 лет с пометкой «опережает время».
- **AC-2.3** Given узел `vram.gddr3` требует технологию игры `DDR2`, а она не исследована; When игрок открывает вкладку; Then узел серый с подсказкой «Нужно: DDR2».
- **AC-2.4** Given в очереди 2 узла; When первый завершается; Then приходит уведомление, второй становится текущим без действий игрока.

- **Complexity:** Medium
- **Dependencies:** FR-1, FR-10; `mod-framework` (`ModTicks`, `ModConditions` — предикат ядра `techResearched`)
- **Assumptions:** лаборатория GPU работает параллельно с исследованиями CPU и не отнимает у них команду; цена — только деньги.

### FR-3: Упрощённый конструктор GPU

**User Story:** Как игрок, я хочу собрать видеокарту из нескольких понятных параметров и сразу видеть производительность, нагрузку на память, нагрев, брак, себестоимость и шансы в каждом сегменте, чтобы проектировать под рынок, а не наугад.

**Priority:** Must (этап 1)

#### Acceptance Criteria (EARS)
1. Мод SHALL давать выбрать:
   - архитектуру (исследованные);
   - техпроцесс (из `Company.ProcessNodes` игрока);
   - тип видеопамяти (исследованные) и ширину шины (из списка, разрешённого типом памяти);
   - охлаждение (исследованные);
   - ползунками: площадь кристалла (мм², от `minDie` до `maxDieByYear`), частоту (МГц, 25–100 % от `maxClock`), объём VRAM (МБ, степени двойки до `mem.maxVramMB`);
   - имя (до 32 символов).
2. WHEN игрок меняет любой параметр THEN мод SHALL в том же кадре пересчитать и показать:
   - транзисторы и число вычислительных блоков;
   - вычислительную мощность и пропускную способность памяти (ПСП);
   - эффективную производительность;
   - мощность (Вт), температуру и брак;
   - себестоимость единицы;
   - стоимость и срок разработки;
   - оценку рейтинга в каждом открытом сегменте относительно текущего рынка.
3. IF эффективная производительность ограничена ПСП (`B / Breq < 1`) THEN мод SHALL показывать предупреждение «Упор в память» с процентом потерь.
4. IF температура выше 95 °C THEN мод SHALL подсвечивать брак красным и подсказывать более мощное охлаждение.
5. IF `ProductionMath.DiesPerWafer(die, waferDiameter, 1.0) < 1` или любая характеристика не является конечным числом THEN мод SHALL заблокировать кнопку «Разработать» с причиной.
6. IF объём VRAM ниже требования сегмента на текущий год THEN мод SHALL показывать в оценке сегмента штраф VRAM.
7. WHEN игрок нажимает «Разработать» THEN мод SHALL сохранить снимок дизайна (входы и вычисленные характеристики) и создать проект (FR-4).
8. WHEN игрок выбирает «На основе…» у существующего GPU THEN мод SHALL заполнить конструктор его параметрами (Could).

#### Сценарии приёмки
- **AC-3.1** Given 2005 год, `arch.shader`, 90 нм, кристалл 300 мм², частота 510 МГц (= максимум), GDDR3, шина 256 бит, 256 МБ, вентилятор; When открыт конструктор; Then блоков 30, вычислительная мощность 122 400, ПСП 51 200 МБ/с, без упора в память, ≈ 79 Вт, ≈ 74 °C, брак ≈ 11.4 % (контрольный пример из design.md).
- **AC-3.2** Given тот же дизайн с шиной 128 бит; When игрок меняет шину; Then ПСП 25 600, отношение к требуемой 0.837, множитель `0.837^0.7 ≈ 0.883`, производительность ≈ 108 000, показано «Упор в память: −12 %».
- **AC-3.3** Given кристалл 800 мм² на пластине 100 мм; When игрок двигает ползунок; Then кнопка «Разработать» неактивна: «Кристалл не помещается на пластину».

- **Complexity:** High
- **Dependencies:** FR-2, FR-10; формулы — design.md «Формулы и баланс» F1–F13
- **Assumptions:** максимальная частота GPU берётся из частоты CPU компании (`ICompany.get_MaxFrequency`), умноженной на `arch.clockRatio`: исследования частот CPU работают и на GPU.

### FR-4: Разработка и выпуск GPU

**User Story:** Как игрок, я хочу запускать разработку GPU как проект со стоимостью и сроком, ставить его на паузу или отменять, а по готовности выпускать карту с выбранной ценой, чтобы управлять деньгами и временем вывода на рынок.

**Priority:** Must (этап 1)

#### Acceptance Criteria (EARS)
1. WHEN игрок создаёт проект THEN мод SHALL вычислить стоимость `(arch.projectCost + node.ProjectCost × nodeProjectShare + mem.projectCost) × Modifiers.GetModifier(ModifierType.DevelopmentCost, company)` и срок `arch.projectDays + mem.projectDays` (по аналогии с `CpuMath.ProjectCost` / `CpuMath.ProjectTime`).
2. WHILE проект активен и не на паузе мод SHALL ежедневно прибавлять к прогрессу `1 / срок` и списывать `стоимость / срок × Inflation_сейчас / Inflation_старт` через `Company.SpendMoney(…, ExpenseOrigin.Development)`.
3. IF уже идут `maxParallelProjects` (по умолчанию 3) проектов GPU THEN мод SHALL заблокировать создание нового с причиной.
4. WHEN игрок ставит проект на паузу THEN мод SHALL остановить прогресс и списания; WHEN снимает с паузы THEN — продолжить с того же прогресса.
5. WHEN игрок отменяет проект и подтверждает THEN мод SHALL удалить проект без возврата потраченных денег.
6. WHEN прогресс достигает 1 THEN мод SHALL открыть модальный диалог «Выпуск GPU» с паузой времени. В диалоге — предложенная цена (бюджет целевого сегмента × 0.9), выбор «Продавать на рынке» и число линий.
7. WHEN игрок подтверждает выпуск THEN мод SHALL добавить продукт в линейку со стартовой популярностью по FR-6 и с датой выпуска.
8. IF игрок закрывает диалог без подтверждения THEN мод SHALL оставить продукт в линейке со статусом «Готов к выпуску» и кнопкой «Выпустить».

#### Сценарии приёмки
- **AC-4.1** Given дизайн AC-3.1, IDM; When игрок нажимает «Разработать»; Then стоимость = `(8e7 + 5e7 × 0.5 + 4e7) × 1.0 = 1.45e8` (`ProjectCost` техпроцесса `90nm` = 5e7), срок = 220 + 200 = 420 дней, в линейке проект «В разработке 0 %».
- **AC-4.2** Given проект на 40 %; When игрок ставит паузу на 30 дней; Then прогресс 40 %, за 30 дней списаний по проекту нет.
- **AC-4.3** Given проект завершился; When открылся диалог; Then время на паузе, цена предложена, после «Выпустить» карта в линейке со статусом «В продаже».
- **AC-4.4** Given fabless-компания (модификатор разработки 0.67); When создаётся тот же проект; Then стоимость = `1.45e8 × 0.67 ≈ 9.72e7`.

- **Complexity:** Medium
- **Dependencies:** FR-3, FR-7; `mod-framework` (`ModUI`, `ModNotify`, `ModTicks`)
- **Assumptions:** проекты GPU не используют `Project` / `TimerScheduler` игры: `SaveHandler.Save` сохраняет все таймеры типа `Project`, и GPU-проект попал бы в ванильный сейв. Стоимость проекта читает множитель `development.cost` через `Modifiers.GetModifier(ModifierType.DevelopmentCost, company)`; канал `development.cost.design` (патч ядра на `CpuMath.ProjectCost`) к GPU не применяется, поэтому надбавки и скидки `cpu-architectures` и `platform-generations` на проекты GPU не действуют.

### FR-5: Производство на общих линиях фабрики

**User Story:** Как IDM, я хочу отдать часть линий своей фабрики под видеокарты и видеть, сколько линий осталось на CPU, чтобы сам выбирать между двумя продуктами при одной мощности.

**Priority:** Must (этап 1)

#### Acceptance Criteria (EARS)
1. Мод SHALL позволять назначить каждому GPU игрока целое число линий ≥ 0 или режим «авто».
2. WHEN наступает `TickPhase.PreContractSellTick` (событие `DateController.OnPreContractSellTick`) THEN мод SHALL зарезервировать сумму линий GPU в `Factory` игрока: увеличить приватные счётчики `totalAllocatedLines` и `totalDemandedLines`. Этот тик идёт раньше любых событий производства CPU в тот же день.
3. IF сумма линий GPU больше `ProductionCapacity` минус мощность, законтрактованная клиентами-литейщиками (`BusinessContract.ContractedProductionCapacity`) THEN мод SHALL пропорционально урезать линии GPU на этот день и показать в линейке предупреждение «Не хватает линий».
4. WHEN линии зарезервированы THEN мод SHALL в том же тике выпустить GPU по формуле `Factory.ProduceWafers`: 50 пластин на линию, `ProductionMath.DiesPerWafer` с выходом годных `Company.CurrentNodeYield(node)`, брак по FR дизайна. Затраты мод SHALL списать через `Company.SpendMoney(…, ExpenseOrigin.Factories)`.
5. Мод SHALL учитывать линии GPU в загрузке фабрики так, чтобы `Factory.SpendOperationCost` и месячные отчёты мощности (`DailyLinesDemand`) включали GPU.
6. WHERE компания игрока fabless мод SHALL производить GPU на аутсорсе: игрок задаёт выпуск в штуках в день, себестоимость кристалла считается с наценкой `ProductionMath.BaseMarkupPrice` (2.0) по статье `ExpenseOrigin.Outsourcing`, с продаж удерживаются роялти `ProductionMath.BaseRoyalties` (5 %) по статье `ExpenseOrigin.Royalties`.
7. WHEN у GPU включён режим «авто» THEN мод SHALL раз в день ставить линии = `ceil(1.1 × средний спрос за 7 дней × 30 / (50 × DiesPerWafer × (1 − FR)))`, но не больше `autoMaxShare` (50 %) от `ProductionCapacity`.
8. WHEN открыт экран производства игры THEN мод SHALL показывать число линий под GPU в строке «Использовано» и (в режиме по умолчанию) уменьшать на это число свободные линии, доступные строкам CPU (Should).
9. WHEN мод считает материал пластин и себестоимость кристалла GPU THEN он SHALL вызывать `ProductionMath.WaferMaterialCost` (каждый день, а не константу 2000) и `CpuMath.RealUnitCost` (где этот вызов уже есть), чтобы шоки пластин канала `production.waferCost` (`market-shocks`) действовали на GPU так же, как на CPU. Канал `production.memoryCost` меняет только память CPU (`CpuMath.MaterialCost`) и на видеопамять не действует: цену VRAM меняет канал `gpu.vramCost`.
10. WHERE на странице фичи в хабе «Моды» включён переключатель «CPU в приоритете» (`ParamSpec` `cpuPriority`, по умолчанию выключен; решение владельца) мод SHALL резервировать линии GPU только из остатка мощности: `avail = ProductionCapacity − Σ ContractedProductionCapacity клиентов-литейщиков − Σ (CurrentProductionLines + CurrentContractedProductionLines) CPU игрока без аутсорса` (те же суммы, что в `ProductionWindow.UpdateAvailableProductionLines`). Линии CPU при этом не урезаются, строки CPU на экране производства не ограничиваются числом GPU, а линейка GPU показывает «Не хватает линий».

#### Сценарии приёмки
- **AC-5.1** Given фабрика на 20 линий, ручное производство CPU на 15 линий, GPU на 5 линий; When проходит день; Then CPU получили 15 линий, GPU выпустили `floor(5 × 50 × DPW × yield / 30)` годных минус брак, утилизация в `SpendOperationCost` = 20/20.
- **AC-5.2** Given 20 линий, CPU на 18, GPU на 5; When проходит день; Then GPU получают все 5 (резерв раньше CPU), CPU получают 15, в экране производства «Использовано 23 (−3)», в строке GPU нет предупреждения.
- **AC-5.3** Given игрок-литейщик, клиенты законтрактовали 12 из 20 линий, GPU назначены 10; When проходит день; Then GPU получают 8 линий, показано «Не хватает линий: 8 из 10».
- **AC-5.4** Given fabless, выпуск 1000 шт./день, себестоимость кристалла c наценкой; When проходит день; Then запас +1000 × (1 − FR), расход по статье «Аутсорсинг».
- **AC-5.5** Given «CPU в приоритете» включён, фабрика на 20 линий, CPU занимают 18, GPU назначены 5; When проходит день; Then CPU получают свои 18, GPU получают остаток 2, в линейке «Не хватает линий: 2 из 5», строки CPU на экране производства не урезаны.
- **AC-5.6** Given шок `production.waferCost` ×1,5 (`market-shocks`); When проходит день производства GPU; Then затраты на материал пластин GPU выросли ×1,5 (вызов `ProductionMath.WaferMaterialCost` даёт шок), а затраты на VRAM не изменились.

- **Complexity:** High
- **Dependencies:** FR-3, FR-7; `mod-framework` (`ModTicks`, `ModHooks` — самопроверка рефлексии, `ModSettings`)
- **Assumptions:** приватные поля `Factory.totalAllocatedLines` / `totalDemandedLines` доступны через Harmony `AccessTools`; при отсутствии полей самопроверка отключает производство GPU (не всю фичу).

### FR-6: Рынок GPU и продажи

**User Story:** Как игрок, я хочу, чтобы видеокарты продавались на живом рынке с бюджетами, конкурентами и популярностью, по тем же правилам, что и CPU, чтобы хорошая карта по правильной цене выигрывала, а устаревшая уходила.

**Priority:** Must (этап 1)

#### Acceptance Criteria (EARS)
1. WHERE `marketMode = "single"` (этап 1) мод SHALL моделировать один сегмент «Видеокарты». Годовой размер сегмента = `baseSize × Lerp(m_a, m_b, t)`, где `t = DateHelper.DecadeTransitionValue(year, 2030)` (как в `PopulationData.GetCurrentSize`), умноженный на каналы `gpu.demand` и `gpu.demand.<segmentId>` (FR-18); бюджет интерполируется по десятилетиям.
2. WHEN наступает `TickPhase.MarketSellTick` THEN мод SHALL продать GPU в 3 прохода (с учётом запаса, затем дважды без учёта пустых — как `Market.Sell`). Рейтинг считается портом `Market.CalculateRatings`, `Market.NormalizeRatings`, `Market.DiluteRatings`, `Market.CalculatePotentialBuyers`, с дополнительными множителями сегмента (функции, VRAM) и канала `gpu.rating` (читается `ModModifiers.Get` с контекстом компании-владельца).
3. WHEN продан GPU THEN мод SHALL уменьшить запас и зачислить выручку владельцу через `EarnMoney(revenue, RevenueOrigin.Sales)` (для игрока — `Company.EarnMoney`).
4. Мод SHALL ежедневно обновлять популярность GPU по правилам `Market.UpdatePopularities`: прирост от доли продаж в сегменте с множителями эпох (×1 до 1990, ×2.5 в 1990–2009, ×5 с 2010), обнуление базового прироста при упущенных продажах, затухание 0.0005 в день у устаревших, пол 0.05 (у устаревших 0), потолок 1.0. Положительный прирост мод SHALL умножать на канал `popularity.gain`, прочитанный `ModModifiers.Get` с контекстом `{Company = владелец, Cpu = null, Segment = Segment.Any}`: действуют записи и провайдеры уровня компании (в том числе репутация бренда `press-reviews`), записи уровня CPU не применяются, а произведение ограничено балансовым диапазоном ядра [0,5; 2,0]. Рынок GPU сам в `popularity.gain` не пишет.
5. Мод SHALL держать в каждом открытом сегменте фоновый продукт «Прочие производители». Его дизайн генерируется по технологиям года с отставанием `background.techLagYears` (2 года) и обновляется раз в 12 месяцев; популярность фиксирована (`background.popularity`, 0.35), запас бесконечный, цена = бюджет сегмента.
6. WHEN выпускается новый GPU THEN мод SHALL задать ему в каждом сегменте стартовую популярность `max(0.05, brandCarry × лучшая популярность активных GPU того же владельца в сегменте)`, где `brandCarry` = 0.5.
7. IF цена ≤ 0, или цена ≥ 3 × бюджет сегмента, или продукт снят, или «Продавать» выключено THEN продукт SHALL не получать покупателей в сегменте.
8. WHILE подразделение игрока не основано мод SHALL продолжать симулировать рынок (фон и соперники), чтобы вкладка «Рынок» и последующий вход игрока опирались на живые данные.

#### Сценарии приёмки
- **AC-6.1** Given 1997 год, сегмент «Видеокарты», на рынке только фоновый продукт; When игрок выпускает GPU с производительностью вдвое выше фона по цене бюджета; Then в первом проходе дня покупателей у игрока `round(N × 0.05 × O_p / (O_p + O_b))` при `O_p > O_b`, выручка в отчёте «Продажи» растёт, а через 60 дней продаж популярность карты выше стартовой 0.05.
- **AC-6.2** Given GPU игрока с ценой 3 × бюджет; When проходит день; Then продаж 0, рейтинг 0.
- **AC-6.3** Given GPU 2000 года в 2006 году (старше 5 лет); When проходит 100 дней без продаж; Then его популярность уменьшилась на 0.05 и не ниже 0.
- **AC-6.4** Given у игрока GPU с популярностью 0.6; When он выпускает следующую карту; Then её стартовая популярность 0.3.

- **Complexity:** High
- **Dependencies:** FR-3, FR-5, FR-10; FR-11 (сегменты этапа 2); `mod-framework` (`ModModifiers`, `ModTicks`)
- **Assumptions:** выручка GPU попадает в финансовый отчёт как «Продажи»: в `RevenueOrigin` нет отдельной категории, а добавить её нельзя без правки игры (принято по умолчанию, «Решения по умолчанию» п. 7). Свою P&L по GPU мод показывает в линейке (FR-7). Сегменты GPU (`consumer`, `gaming.high`, …) — собственные идентификаторы рынка GPU и не связаны с `PTMod.Core.Segment` (HighEnd…Industries); `ModSegments` фича не использует.

### FR-7: Управление линейкой

**User Story:** Как игрок, я хочу видеть по каждой видеокарте запас, продажи, прибыль и популярность и менять цену, продажу, линии или снимать карту с производства, чтобы вести линейку как бизнес.

**Priority:** Must (этап 1)

#### Acceptance Criteria (EARS)
1. Мод SHALL показывать по каждому GPU игрока: статус (в разработке / готов к выпуску / в продаже / снят), цену, запас, линии (или шт./день для fabless), продажи, выручку, затраты и прибыль за прошлый месяц, популярность по сегментам и метку «устарел».
2. WHEN игрок меняет цену THEN мод SHALL применить её со следующего рыночного тика.
3. WHEN игрок выключает «Продавать на рынке» THEN продукт SHALL выйти из рынка, а запас и линии SHALL сохраниться.
4. WHEN игрок снимает GPU с производства и подтверждает (`ModUI.Confirm`) THEN мод SHALL освободить его линии, продать остаток запаса по `liquidationShare × price` (10 %) через `EarnMoney(…, RevenueOrigin.Sales)` и перевести продукт в архив. IF по продукту действует консольный заказ (FR-19) THEN текст подтверждения SHALL предупредить о расторжении заказа и штрафе к репутации.
5. Мод SHALL ежедневно списывать хранение запаса `stock × storageCostPerUnitMonth / 30` (0.5 в месяц за единицу — как `StorageMath.Cost`) через `ExpenseOrigin.Factories`.
6. Мод SHALL вести помесячную бухгалтерию каждого GPU (продано, выпущено, брак, выручка, затраты) глубиной не больше 600 месяцев.
7. IF возраст GPU ≥ `oldYears` (5 лет; 7 лет, если выпущен до 1990 — как `Cpu.IsOld`) THEN мод SHALL помечать его «устаревшим».

#### Сценарии приёмки
- **AC-7.1** Given GPU с запасом 20 000 и ценой 200; When игрок снимает его; Then начислено 20 000 × 200 × 0.1 = 400 000 по статье «Продажи», линии освобождены, карта в архиве.
- **AC-7.2** Given запас 100 000; When проходит месяц без продаж; Then списано ≈ 50 000 за хранение.
- **AC-7.3** Given карта выпущена в 1988; When наступает 1995; Then в линейке метка «устарел».

- **Complexity:** Medium
- **Dependencies:** FR-4, FR-5, FR-6
- **Assumptions:** архивные продукты хранятся в сейве для истории, но не участвуют в рынке.

### FR-8: Окно рынка GPU

**User Story:** Как игрок, я хочу видеть размер и бюджет каждого сегмента, требования эпохи, лидеров и доли производителей, чтобы понимать, куда целиться следующей картой.

**Priority:** Must (этап 1; сегменты и доли вендоров — этап 2)

#### Acceptance Criteria (EARS)
1. Мод SHALL показывать по каждому открытому сегменту:
   - покупателей в месяц и бюджет;
   - требования (функции архитектуры, минимальный VRAM на текущий год);
   - топ-5 продуктов по продажам за 30 дней с производителем, ценой и производительностью;
   - долю продаж каждого производителя за 30 дней, включая «Прочих».
2. Мод SHALL показывать долю игрока на рынке GPU за 30 дней и таблицу помесячных продаж игрока за последние 24 месяца.
3. WHILE окно открыто мод SHALL обновлять его раз в игровой день; WHILE окно закрыто мод SHALL не пересчитывать UI.
4. WHERE включена синергия (FR-15) окно SHALL показывать текущие бонусы к рейтингу CPU (вклад в `market.rating.cpu`) и GPU (вклад в `gpu.rating`) компании игрока; подсказка берёт разбивку из `ModModifiers.Explain` (причины `gpu.synergy.cpu` и `gpu.synergy.gpu`, пометка «(ограничено)» от ядра).

#### Сценарии приёмки
- **AC-8.1** Given 2004 год, режим эпох; When игрок открывает «Рынок»; Then видны сегменты «Офисные 2D», «Игровые: энтузиасты/массовые/бюджетные» с требованием `shader` и VRAM ≥ 128/256/64 МБ; «Вычисления» нет (откроется в 2007).
- **AC-8.2** Given окно открыто, скорость 3; When проходит 30 дней; Then доли обновлялись ежедневно без заметного падения FPS (NFR-1).

- **Complexity:** Medium
- **Dependencies:** FR-6, FR-11, FR-12, FR-15; `mod-framework` (`ModUI`)
- **Assumptions:** графики не нужны — табличного вида (`InfoText`) достаточно; график — пожелание на будущее.

### FR-9: Сохранение и совместимость

**User Story:** Как игрок, я хочу, чтобы видеокарты, исследования и рынок GPU переживали сохранение и загрузку, а старые сейвы и удаление мода ничего не ломали.

**Priority:** Must (этап 1)

#### Acceptance Criteria (EARS)
1. WHEN игра сохраняется THEN мод SHALL отдать ядру данные секции `gpu-product-line` через `IModSaveParticipant.Write()` (в боковой файл `ModSave`). Версию секции (`_schema`) пишет и читает ядро; в данных фичи поля версии нет.
2. WHEN загружается сейв без секции `gpu-product-line` THEN `ModSave` SHALL вызвать `ResetToDefaults()` (подразделение не основано), а мод на `ModTicks.GameReady(Loaded)` SHALL засеять рынок GPU для текущего года (фон и активные соперники).
3. WHEN начинается новая игра THEN мод SHALL засеять рынок для стартового года один раз на `TickPhase.FastForwardEnded` (состояние ИИ к старту — политика владельца), не симулируя годы перемотки; во время перемотки никакие обработчики фичи не вызываются.
4. IF фича выключена посреди игры или мод удалён THEN сейв игры SHALL загружаться без ошибок, линии фабрики SHALL быть свободны со следующего дня, а секция SHALL сохраняться в `ModSave` без изменений (при удалённом моде ядро хранит чужую секцию как есть).
5. IF значение в секции некорректно (NaN, отрицательный запас, неизвестный id контента, превышен лимит списка) THEN мод SHALL заменить его значением по умолчанию или отбросить запись, записать причину в `ModLog` и продолжить загрузку.
6. Мод SHALL не добавлять поля в классы игры и не создавать для GPU объекты `Cpu`, `Project` или `CustomHardware` игры.
7. IF версия схемы секции (параметр `schema` метода `Read`) старше текущей `SchemaVersion` THEN мод SHALL выполнить миграцию внутри `Read`; IF секция новее THEN ядро SHALL выдать фиче значения по умолчанию и сохранить исходную секцию без изменений (passthrough), а мод в этой сессии SHALL работать с пустым состоянием.
8. Мод SHALL записывать компании в секции только ключами `ModCompanies` (`player`, `ai:<UniqueID>`; пустая строка — виртуальный производитель); числовой SaveID компании (интерфейс `ISaveID`) в секцию не пишется.

#### Сценарии приёмки
- **AC-9.1** Given сейв 2003 года без мода; When он загружается с модом; Then подразделение не основано, во вкладке «Рынок» есть фоновый продукт и соперники 2003 года.
- **AC-9.2** Given партия с 3 GPU в продаже; When игрок сохраняет, выходит в меню и загружает; Then запас, цены, линии, популярность, прогресс исследований и проектов совпадают.
- **AC-9.3** Given партия с GPU; When мод удалён и сейв загружен в ванильной игре; Then игра работает, CPU производятся на всех линиях.
- **AC-9.4** Given в секции у продукта `stock = -5` и `archId = "arch.unknown"`; When сейв загружается; Then запас 0, продукт сохраняет снимок характеристик, в `Player.log` строка `[PTMod] gpu-product-line: …`.
- **AC-9.5** Given сейв, в котором секция `gpu-product-line` записана с `_schema`, большим текущей `SchemaVersion`; When он загружается и сохраняется снова; Then фича получила состояние по умолчанию, а в новом боковом файле секция совпадает с исходной.

- **Complexity:** Medium
- **Dependencies:** `mod-framework` (`ModSave`, `ModLog`, `ModCompanies`), все FR с состоянием
- **Assumptions:** `ModSave` сохраняет секции выключенных фич как есть (контракт фреймворка).

### FR-10: Контент и баланс в JSON

**User Story:** Как владелец и как игрок-моддер, я хочу менять архитектуры, память, сегменты, соперников и все балансные числа в JSON без пересборки, чтобы быстро калибровать фичу.

**Priority:** Must (этап 1)

#### Acceptance Criteria (EARS)
1. Мод SHALL брать все числа фичи из `Content/gpu-product-line/*.json`: `balance`, `research`, `architectures`, `memory`, `coolers`, `segments`, `eras`, `vendors`, `consoles`, `timeline`. Файлы записей имеют вид `{ "schema": 1, "records": [ … ] }` (`ModContent.LoadRecords`), `balance` и `timeline` — объекты (`ModContent.LoadConfig`). Переопределение — файлами из `<папка игры>/PTMod/content/gpu-product-line/` по полю `id` записи: та же `id` заменяет встроенную запись, `"disabled": true` удаляет (решение 0006, FR-10 ядра).
2. WHEN контент загружается THEN мод SHALL проверить схему: уникальность id, ссылки между файлами, диапазоны чисел, наличие обязательных полей. Битые записи мод SHALL пропускать с записью в `ModLog`.
3. IF после проверки нет ни одной архитектуры, памяти, охлаждения или сегмента THEN мод SHALL отключить фичу и один раз показать `ModNotify` с причиной.
4. Мод SHALL брать тексты контента из ключей `ModL10n` (префикс `gpu.`) или из объекта `{ "ru": "…", "en": "…" }`.
5. IF узел исследования ссылается на технологию игры, которой нет среди `DataFinder.FindAllTechnologies` (сравнение по `Technology.get_Name`) THEN мод SHALL считать предпосылку невыполнимой и записать предупреждение.
6. Компании в контенте (`vendors.json`) мод SHALL указывать ключом `ai:<UniqueID>` (AMD — `ai:1`, Intel — `ai:0`); отображаемое имя привязанного производителя берётся из игры (`ICompany.get_Name`), поле `name` в контенте — только запасное для виртуального режима.
7. Идентификаторы записей GPU (`arch.*`, `vram.*`, `cool.*`, `matrox`, …) — локальные ID файлов фичи. Они не являются ключами L10n, предикатами или ID событий, поэтому таблица префиксов ядра к ним не применяется: совпадение первой части `arch.` с префиксом `cpu-architectures` ни к какому конфликту не ведёт.

#### Сценарии приёмки
- **AC-10.1** Given в `architectures.json` две записи с id `arch.3d`; When игра стартует; Then используется первая, в логе предупреждение о дубликате.
- **AC-10.2** Given игрок положил свой `segments.json` в `PTMod/content/gpu-product-line/` с записью `consumer` и бюджетом 999; When загружается партия; Then запись `consumer` заменена, окно рынка показывает 999.

- **Complexity:** Medium
- **Dependencies:** `mod-framework` (`ModContent`, `ModJson`, `ModL10n`, `ModLog`, `ModCompanies`)
- **Assumptions:** парсер JSON — `ModJson` ядра (`ModJson.Bind`), `JsonUtility` не используется (решение 0006); DTO фичи плоские: поля, `List<T>` вместо массивов и словарей.

### FR-11: Эпохи и сегменты рынка GPU

**User Story:** Как игрок, я хочу, чтобы рынок GPU менялся по эпохам — от 2D-адаптеров к 3D, вычислениям и ИИ — и чтобы старые архитектуры теряли актуальность, чтобы исследования GPU имели ясную цель.

**Priority:** Must (этап 2)

#### Acceptance Criteria (EARS)
1. WHERE `marketMode = "eras"` мод SHALL открывать и закрывать сегменты по годам из `segments.json`:
   - `office2d` — 1981–2009;
   - `gaming.high`, `gaming.mid` — с 1996;
   - `gaming.low` — с 1998;
   - `compute` — с 2007;
   - `ai` — с 2016.
2. Мод SHALL умножать рейтинг продукта в сегменте на `missingFeatureFactor` за каждую функцию, которую сегмент требует в текущем году, а архитектура не имеет (по умолчанию 0.35; для `compute` и `ai` — 0, то есть без функции продаж нет).
3. Мод SHALL умножать рейтинг на `clamp(vram / vramReq(year), 0.25, 1)`, где `vramReq` интерполируется по контрольным годам сегмента в логарифмической шкале.
4. WHEN открывается новый сегмент THEN мод SHALL дать всем активным продуктам в нём популярность 0.05 и отправить письмо об эпохе (FR-14).
5. WHEN сегмент закрывается THEN мод SHALL прекратить продажи в нём, не удаляя продукты.
6. WHEN режим меняется с `single` на `eras` в существующей партии THEN популярность сегмента `consumer` SHALL переноситься в открытые сегменты (`gaming.mid` и `office2d`) с коэффициентом 1.0.

#### Сценарии приёмки
- **AC-11.1** Given 1996 год, у игрока 2D-карта на `arch.gui`; When открываются игровые сегменты; Then в них рейтинг карты × 0.35 (нет `3d`), пришло письмо «Эпоха 3D-ускорителей».
- **AC-11.2** Given 2008 год, карта без функции `compute`; When открыт «Рынок»; Then в сегменте «Вычисления» у карты рейтинг 0 и пометка «Нет: compute».
- **AC-11.3** Given 2010 год, игровой средний сегмент требует 1024 МБ; When у карты 512 МБ; Then множитель VRAM 0.5.

- **Complexity:** Medium
- **Dependencies:** FR-6, FR-10, FR-14
- **Assumptions:** функции архитектур накопительные (у `arch.shader` есть `2d`, `gui`, `3d`, `tnl`, `shader`).

### FR-12: Соперники на рынке GPU

**User Story:** Как игрок, я хочу встречать на рынке GPU узнаваемых производителей, которые выходят, уходят и сливаются по ходу истории, а часть из них — те же компании ИИ, что и на рынке CPU, чтобы рынок ощущался живым.

**Priority:** Must (этап 2)

#### Acceptance Criteria (EARS)
1. Мод SHALL загружать производителей (вендоров) из `vendors.json`: виртуальные (существуют только на рынке GPU: NVIDIA, ATI, 3dfx, Matrox, S3) и привязанные к компаниям ИИ по ключу `ai:<UniqueID>` (`ModCompanies.Resolve`; AMD — `ai:1`, Intel — `ai:0`). Названия — реальные, как в русификаторе; даты входа, ухода и слияний приближены к истории и могут правиться контентом.
2. WHEN наступает `entryYear` вендора THEN он SHALL выйти на рынок с продуктом в каждом своём открытом сегменте.
3. WHEN наступает `exitYear` вендора THEN мод SHALL снять его продукты и отправить письмо; WHEN срабатывает `mergeInto` THEN продукты SHALL перейти к поглотителю с сохранением популярности.
4. IF привязанной компании ИИ нет в партии (`ModCompanies.Resolve` вернул null) или она обанкротилась (`ICompany.get_IsBankrupt`; проверка ежедневно на `TickPhase.DayPassed`, прямой подписки на `BankruptcyHandler.OnCompanyWentBankrupt` фича не держит) THEN вендор SHALL уйти с рынка, а при `fallbackVirtual = true` — стать виртуальным.
5. WHERE на странице фичи в хабе «Моды» выключен переключатель `rivals` (`ParamSpec`) мод SHALL оставлять на рынке только «Прочих производителей».
6. Мод SHALL не создавать новые компании игры: виртуальные вендоры не появляются в списках компаний, финансах и `MarketShareWindow`.
7. WHEN компанию ИИ с привязанным вендором покупает игрок (`rival-acquisitions`) THEN вендор SHALL перейти в состояние `merged` (поглотитель — игрок) через `GpuApi.TransferVendorProducts` (FR-18); без вызова вендор уходит с рынка, как при банкротстве.

#### Сценарии приёмки
- **AC-12.1** Given новая игра 1990 года; When наступает 1996; Then на рынке появляется вендор 3dfx с продуктами в `gaming.high` и `gaming.mid`, приходит письмо.
- **AC-12.2** Given 2006 год, вендор ATI с `mergeInto: amd.gpu`; When срабатывает слияние; Then продукты ATI принадлежат вендору «AMD», выручка с них идёт в финансы компании AMD (`ai:1`).
- **AC-12.3** Given Intel (вендор `intel.gpu`, `fallbackVirtual = false`) обанкротилась в 2024; When проверка на `DayPassed` видит `get_IsBankrupt`; Then её GPU снимаются, письмо «Intel уходит с рынка видеокарт».
- **AC-12.4** Given AMD нет в партии (`ModCompanies.Resolve("ai:1")` = null), 2006 год; When вендор `amd.gpu` должен выйти на рынок; Then он выходит как виртуальный (`fallbackVirtual = true`) под названием «AMD», финансов компании ИИ не затрагивает.

- **Complexity:** Medium
- **Dependencies:** FR-11, FR-13, FR-14; `rival-acquisitions` (переход линейки через `GpuApi.TransferVendorProducts`); `mod-framework` (`ModCompanies`)
- **Assumptions:** реальные названия утверждены владельцем («Решения по умолчанию» п. 5); отображаемое имя привязанного вендора берёт игра (`ICompany.get_Name`).

### FR-13: Поведение ИИ-соперников на рынке GPU

**User Story:** Как игрок, я хочу, чтобы соперники регулярно выпускали карты на технологиях своего времени, держали разумные цены и мощности, чтобы с ними можно было соревноваться, а не побеждать их одной картой навсегда.

**Priority:** Must (этап 2)

#### Acceptance Criteria (EARS)
1. WHEN наступает `TickPhase.MonthPassed` THEN для каждого активного вендора и каждого его сегмента, где с последнего запуска прошло не меньше `designIntervalMonths` плюс 0–3 случайных месяца (поток `ModRandom` `gpu-product-line/rivals`), мод SHALL выпустить новый GPU, сгенерированный по технологиям года `год − techLag`. Срок считается по разности дат, поэтому после простоя (фича была выключена) запуск наступает на ближайшем месячном тике.
2. Генератор SHALL выбирать:
   - последнюю архитектуру, память и охлаждение с годом ≤ techYear;
   - техпроцесс — последний из `ICompany.get_ProcessNodes` привязанной компании, для виртуальных — из `timeline.json`;
   - частоту — 95 % от `maxClock` по `ICompany.get_MaxFrequency` привязанной компании или по передовой частоте среди всех компаний;
   - площадь — `rivalDieShare` сегмента × `maxDieByYear`;
   - VRAM — требование сегмента × `tierFactor`;
   - охлаждение — минимальное, при котором температура ≤ 85 °C.
3. Мод SHALL назначать цену `max(1.3 × себестоимость, бюджет × priceFactor вендора)`.
4. Мод SHALL ограничивать дневные продажи вендора мощностью `capacityShare × дневные покупатели сегмента`: запас пополняется до этого значения каждый день.
5. WHERE вендор привязан к компании ИИ мод SHALL:
   - зачислять выручку через `AICompany.EarnMoney(…, RevenueOrigin.Sales)`;
   - списывать себестоимость проданных единиц через `AICompany.SpendMoney(…, ExpenseOrigin.Factories)`;
   - списывать стоимость разработки при запуске через `ExpenseOrigin.Development`.
6. IF привязанная компания в дефолте (`ICompany.get_IsInDefault`) или стоимость разработки уведёт её баланс ниже порога дефолта (`MoneyAmount − стоимость < ModCredit.ThresholdOf(компания)`) THEN вендор SHALL не выпускать новые GPU и повторить попытку на следующем месячном тике.
7. Мод SHALL держать у вендора не больше 2 активных продуктов на сегмент: при выпуске третьего самый старый снимается.
8. Правила генерации, цен и мощности SHALL быть одинаковыми для всех вендоров и для игрока там, где формулы общие (одна модель `GpuDesignMath`); эффекты для вендоров на низкой сложности игры не ослабляются (сложность влияет на ИИ самой игрой).

#### Сценарии приёмки
- **AC-13.1** Given сид `ModRandom` и сейв 2001 года; When игру дважды загружают и проматывают 24 месяца; Then последовательности запусков соперников совпадают (NFR-6).
- **AC-13.2** Given вендор с `techLag = 0.5`, 1 марта 2003 года (techYear ≈ 2002.7); When он выпускает карту; Then архитектура `arch.shader` (год 2002 ≤ techYear), а не `arch.unified` (2006); память `vram.ddr` (GDDR3 — 2004); в карточке на вкладке «Рынок» видны техпроцесс и частота.
- **AC-13.3** Given AMD в дефолте; When проходит 12 месяцев; Then у вендора AMD нет новых карт.
- **AC-13.4** Given баланс AMD на 5 млн выше порога дефолта, а проект GPU стоит 80 млн; When вендор должен запустить карту; Then запуск отложен, баланс компании не изменился.

- **Complexity:** High
- **Dependencies:** FR-3 (общая модель), FR-11, FR-12; `mod-framework` (`ModRandom`, `ModCredit`)
- **Assumptions:** соперники не резервируют линии своих фабрик; их выпуск абстрактный (решение владельца, «Решения по умолчанию» п. 3).

### FR-14: Новости рынка GPU

**User Story:** Как игрок, я хочу получать письма о смене эпох, выходе и уходе производителей и о новых лидерах, чтобы не пропускать важные изменения рынка.

**Priority:** Should (этап 2)

#### Acceptance Criteria (EARS)
1. WHEN открывается сегмент или начинается эпоха THEN мод SHALL отправить письмо `ModMail` (приоритет `Normal`, тег `gpu:era:<eraId>` или `gpu:segment:<segmentId>`) с описанием и подсказкой, какие узлы GPU-дерева нужны.
2. WHEN вендор выходит на рынок, уходит или поглощается THEN мод SHALL отправить письмо (приоритет `Normal`, тег `gpu:vendor:<vendorId>:<enter|exit|merge>`).
3. WHEN продукт соперника становится самым быстрым в сегменте THEN мод SHALL отправить письмо (приоритет `Low`, тег `gpu:leader:<segmentId>`), но не чаще одного раза в 3 месяца на сегмент.
4. WHILE идёт перемотка новой игры или загрузка мод SHALL не создавать письма и не ставить их в очередь.
5. WHERE на странице фичи в хабе «Моды» выключен переключатель `news` мод SHALL не отправлять письма о лидерах (письма об эпохах остаются).
6. IF событие произошло раньше предыдущего календарного месяца (догоняющее обновление после повторного включения фичи) THEN письмо SHALL не отправляться (тихая миграция состояния).
7. Мод SHALL не выбирать ID писем и не вводить собственных дневных лимитов: ID выдаёт `ModMail.Send`, доставку по приоритетам и лимитам (`mail.maxDeliveredPerDay`, `mail.maxPerFeaturePerDay`) ведёт ядро, письма различаются по `Tag`. Показ писем в пакетном прогоне «Следующий месяц» ядро откладывает до `ModTicks.BatchEnded`.

#### Сценарии приёмки
- **AC-14.1** Given 2006 год; When вендор выпускает карту быстрее всех в `gaming.high`; Then письмо «Новый лидер: …», в следующие 3 месяца повторов по этому сегменту нет.
- **AC-14.2** Given фича была выключена с 2001 до 2005 года и включена снова; When наступает ближайший месячный тик; Then состояние вендоров догнало 2005 год, а письма о событиях 2001–2004 годов не отправлены.

- **Complexity:** Low
- **Dependencies:** FR-11, FR-12; `mod-framework` (`ModMail`, `ModIds`)
- **Assumptions:** возвращённый `Send` ID письма фича хранит только там, где ей нужно связать письмо с состоянием (консольные заказы, FR-19); блоков ID писем нет.

### FR-15: Платформенная синергия CPU+GPU

**User Story:** Как игрок, который делает и CPU, и видеокарты, я хочу, чтобы сильный бренд в одном рынке поднимал рейтинг в другом, чтобы вторая линия усиливала первую.

**Priority:** Must (этап 3)

#### Acceptance Criteria (EARS)
1. WHEN наступает `TickPhase.MonthPassed` THEN для каждой компании, у которой есть хотя бы один продаваемый CPU (не снят, `SellOnMarket`) и хотя бы один продаваемый GPU, мод SHALL вычислить:
   - `s_cpu = min(cpuMax, cpuK × доля компании на рынке GPU за 30 дней)`;
   - `s_gpu = min(gpuMax, gpuK × средняя MarketDataProvider.MarketShare за 30 дней)`.
2. Мод SHALL отдавать для этой компании множитель `1 + s_cpu` провайдером канала `market.rating.cpu` и `1 + s_gpu` провайдером канала `gpu.rating` (`ModModifiers.RegisterReasonedProvider`, регистрация один раз в `Register`; причины `gpu.synergy.cpu` и `gpu.synergy.gpu` попадают в `Explain`). После месячного пересчёта мод SHALL вызвать `ModModifiers.Invalidate` для обоих каналов. Правило одинаково для игрока и для компаний ИИ с привязанным вендором — спека задаёт это явно.
3. IF у компании нет продаваемого CPU или GPU THEN провайдеры SHALL вернуть 1.0.
4. WHERE на странице фичи в хабе «Моды» выключен переключатель `synergy` провайдеры SHALL возвращать 1.0 (записей, которые нужно снимать, нет).
5. Мод SHALL показывать текущие бонусы в окне рынка GPU (FR-8) с пояснением формулы.
6. Максимальный вклад фичи в общие каналы SHALL быть явным и проверяться тестами:
   - `market.rating.cpu` — множитель в диапазоне [1,00; 1,08] (`cpuMax` = 0,08);
   - `gpu.rating` — множитель в диапазоне [1,00; 1,10] (`gpuMax` = 0,10);
   - `popularity.gain` — фича не пишет;
   - произведение всех вкладов на один CPU ограничивает ядро балансовым диапазоном [0,5; 2,0] (`market.rating.cpu`), у `gpu.rating` балансового диапазона нет, действует предохранитель [0,25; 4,0]. Тесты эффектов SHALL учитывать это ограничение.

#### Сценарии приёмки
- **AC-15.1** Given игрок держит 40 % рынка GPU и 20 % рынка CPU; When наступает 1-е число; Then `s_cpu = min(0.08, 0.2 × 0.4) = 0.08`, `s_gpu = min(0.10, 0.25 × 0.2) = 0.05`; в окне «+8 % к рейтингу CPU, +5 % к рейтингу GPU».
- **AC-15.2** Given игрок снял все GPU; When наступает 1-е число; Then оба множителя 1.0.
- **AC-15.3** Given остальные поставщики канала `market.rating.cpu` дали на CPU игрока ×1,90, синергия ×1,08; When `ModModifiers.Get` считает канал; Then итог ограничен 2,0 (`IsBalanceCapped`, подсказка «(ограничено)»), а вклад синергии в разбивке `Explain` остаётся ×1,08.

- **Complexity:** Medium
- **Dependencies:** FR-6, FR-18; `mod-framework` (`ModModifiers`: `RegisterReasonedProvider`, `Invalidate`, `Explain`; стандартный канал `market.rating.cpu`; канал `gpu.rating`)
- **Assumptions:** множители разных фич в одном канале перемножаются (контракт `ModModifiers`); провайдеры выключенной фичи ядро пропускает.

### FR-16: Общий опыт техпроцесса

**User Story:** Как IDM, я хочу, чтобы выпуск видеокарт на техпроцессе ускорял освоение этого техпроцесса так же, как выпуск CPU, чтобы общая фабрика давала общий опыт.

**Priority:** Should (этап 3)

#### Acceptance Criteria (EARS)
1. Мод SHALL прибавлять к результату `Company.TotalLinesAllocated(processNode)` компании игрока сумму линий GPU, фактически занятых в этот день на этом техпроцессе, умноженную на `gpuLearningShare` (1.0). Так `ProductionMath.NodeOptimizationRate` учитывает выпуск GPU.
2. IF фича или переключатель `synergy` выключены THEN прибавка SHALL быть 0.
3. Патч (GP2 в design.md) SHALL быть необязательным (`Optional`): при сбое применения общий опыт отключается, остальная фича работает.

#### Сценарии приёмки
- **AC-16.1** Given на 90 нм работают 4 линии CPU и 4 линии GPU; When `WaferCostUpdater` применяет обучение; Then скорость обучения считается от 8 линий, а не от 4.

- **Complexity:** Low
- **Dependencies:** FR-5; `mod-framework` (`ModHooks`, `ModSettings`)
- **Assumptions:** других патчей на `Company.TotalLinesAllocated` в проекте нет; если появятся, нужен порядок Harmony.

### FR-17: Скидка совместной разработки

**User Story:** Как игрок, я хочу, чтобы GPU на техпроцессе, где я недавно выпустил CPU, стоил дешевле в разработке, чтобы обе линии вместе осваивали новые техпроцессы.

**Priority:** Could (этап 3)

#### Acceptance Criteria (EARS)
1. IF у компании есть выпущенный CPU с `CpuBase.Year ≥ текущий год − coDevYears` (2) на том же техпроцессе (`Cpu.ProcessNode`) THEN мод SHALL умножать стоимость проекта GPU на `coDevFactor` (0.85).
2. WHEN скидка применяется THEN конструктор SHALL показывать её отдельной строкой.

#### Сценарии приёмки
- **AC-17.1** Given CPU на 65 нм выпущен в 2006; When в 2007 игрок проектирует GPU на 65 нм; Then стоимость × 0.85, строка «Совместная разработка: −15 %».

- **Complexity:** Low
- **Dependencies:** FR-4
- **Assumptions:** скидка действует только на GPU; CPU-скидки от GPU нет.

### FR-18: Каналы ModModifiers и API для других фич

**User Story:** Как автор смежной спеки (события, исторический календарь, сценарии, поглощения), я хочу влиять на рынок GPU через каналы и читать его состояние через API, чтобы не трогать код фичи.

**Priority:** Should (этап 3; чтение каналов — с этапа 1)

#### Acceptance Criteria (EARS)
1. Мод SHALL читать в своих формулах каналы GPU, объявленные в реестре ядра до `Register` фич (`core.json`, владелец `gpu-product-line`): мод сам каналы не объявляет (`DeclareChannel` не вызывается), а читает их через `ModModifiers.Get` и константы `ModChannels`:
   - `gpu.demand` и `gpu.demand.<segmentId>` (семейство `gpu.demand.*`, `ModChannels.GpuDemandSegment`) — множитель числа покупателей, предохранитель [0,1; 3,0], глобальный;
   - `gpu.rating` — множитель рейтинга по компании, предохранитель [0,25; 4,0]; в него пишет и синергия (FR-15);
   - `gpu.vramCost` — множитель стоимости видеопамяти, предохранитель [0,5; 2,0], глобальный и по компании.
2. Мод SHALL читать для GPU стандартные каналы `production.unitCost`, `production.output`, `popularity.gain` (контекст `{Company = владелец}`, без CPU). Каналы `research.speed`, `research.cost` и `development.cost` действуют автоматически через `Modifiers.GetModifier`. К GPU не применяются: `cpu.failureRate`, `development.cost.design`, `production.memoryCost`, `market.rating.cpu` (кроме вклада синергии) и CPU-каналы спроса `market.demand.*`.
3. Мод SHALL предоставить `GpuApi` только для чтения: основано ли подразделение компании, список её продуктов, её доля на рынке GPU, текущие бонусы синергии, открытые сегменты.
4. Мод SHALL зарегистрировать предикаты `ModConditions` (`ModConditions.Register(type, "gpu-product-line", factory)`): `gpu.divisionFounded`, `gpu.hasProductOnMarket`, `gpu.marketShareAtLeast` (параметр `share`), `gpu.researched` (параметр `node`). Имена предикатов начинаются с префикса `gpu.`; пространство предикатов не пересекается с каналом `gpu.rating`.
5. Мод SHALL предоставить `GpuApi.TransferVendorProducts(fromCompany, toCompany)` для `rival-acquisitions`: решение владельца — при покупке компании ИИ её GPU-линейка передаётся игроку, если фича включена. Продукты получают владельца «игрок» со статусом «в продаже», линиями 0, запасом и популярностью как были; вендор переходит в `merged`. IF подразделение игрока не основано THEN передача SHALL основать его без оплаты на дату сделки (с догоняющей разблокировкой узлов).

#### Сценарии приёмки
- **AC-18.1** Given событие `historical-events` («Криптобум 2017 года») добавляет запись `gpu.demand × 1.5` на 90 дней (`ModifierTimed`); When идёт рынок GPU; Then число покупателей во всех сегментах × 1.5 ровно 90 дней.
- **AC-18.2** Given сценарий с целью `{ "type": "gpu.marketShareAtLeast", "share": 0.25 }`; When доля игрока достигает 25 %; Then цель засчитана.
- **AC-18.3** Given `rival-acquisitions` купила AMD (у неё 6 GPU в продаже), подразделение игрока основано; When она вызывает `GpuApi.TransferVendorProducts(AMD, игрок)`; Then 6 продуктов в линейке игрока (статус «в продаже», линии 0, запас и популярность сохранены), вендор AMD в состоянии `merged`.
- **AC-18.4** Given у игрока нет GPU-подразделения; When вызвана та же передача; Then подразделение основано бесплатно на дату сделки, продукты переданы.

- **Complexity:** Medium
- **Dependencies:** `mod-framework` (`ModModifiers`, `ModConditions`, `ModChannels`); потребители — `market-shocks`, `historical-events`, `scenarios-achievements`, `rival-acquisitions`
- **Assumptions:** сигнатуры задаёт `mod-framework/design.md`; фича изолирует обращения к ядру в `GpuModifierBridge` и `GpuApi`.

### FR-19: Консольные OEM-заказы

**User Story:** Как игрок с сильной игровой видеокартой, я хочу получать от производителей консолей крупные заказы по фиксированной цене, чтобы иметь стабильный канал сбыта помимо розничного рынка.

**Priority:** Could (этап 3; решение владельца — «консольные OEM-заказы — Could»)

#### Acceptance Criteria (EARS)
1. WHERE включён переключатель `consoleOrders` (по умолчанию включён) AND подразделение основано, WHEN наступает год предложения (`offerYear`) записи из `consoles.json` THEN мод SHALL отправить письмо-предложение (`ModMail`, приоритет `Critical`, тег `gpu:console:<orderId>`, `TimeoutDays` = 60, вариант по умолчанию «Отказаться») с вариантами «Принять» / «Отказаться» и действием «Открыть линейку». Производители консолей — реальные (Sony, Nintendo, Microsoft), как в списке OEM-клиентов игры.
2. WHILE предложение не принято мод SHALL раз в `revalidateDays` (7) дней и при доставке письма проверять условие `EffectivePerf ≥ minPerfShare × лучшая производительность среди продаваемых в целевом сегменте` для продаваемых GPU игрока и вызывать `ModMail.SetChoiceState` для «Принять»: IF подходящего GPU нет THEN вариант неактивен с причиной «Нет подходящей карты».
3. WHEN игрок принимает предложение THEN мод SHALL закрепить за заказом лучший подходящий GPU, зафиксировать цену `max(1.15 × себестоимость, priceFactor × бюджет сегмента)` и суточный объём `floor(unitsShare × покупателей сегмента в день)` на срок `termYears`.
4. WHILE заказ действует мод SHALL ежедневно на `TickPhase.ContractSellTick` (раньше розницы) поставлять `min(запас, суточный объём)` единиц, начислять выручку `EarnMoney(…, RevenueOrigin.Contracts)` и считать недопоставку. Канал `contract.reward` на консольные заказы не действует (он ограничен областью `ContractSeller.SellContracts`).
5. IF недопоставка за последние `graceDays` (90) дней превышает `failCancelShare` (25 %) объёма THEN мод SHALL расторгнуть заказ, снизить репутацию игрока `ModReputation.Add(…, −reputationPenalty, "gpu.console.failed")` и отправить письмо (`Normal`).
6. WHEN срок заказа истёк THEN мод SHALL завершить его и отправить письмо (`Low`) без штрафа.
7. IF игрок снимает закреплённый GPU с производства либо выключает фичу с действующими заказами THEN мод SHALL расторгнуть заказы со штрафом по п. 5; выключение в хабе SHALL требовать подтверждения (`FeatureContext.ConfirmBeforeDisable`), программное выключение расторгает заказы без вопроса.
8. Консольные заказы получает только игрок: выпуск вендоров ИИ абстрактный (FR-13), поэтому их заказы не моделируются.

#### Сценарии приёмки
- **AC-19.1** Given 1998 год (запись `sony.2`), подразделение основано, у игрока GPU `arch.3d` в продаже с производительностью выше порога; When наступает 1 января; Then приходит письмо Sony с активной кнопкой «Принять» и сроком ответа 60 дней.
- **AC-19.2** Given письмо получено, а подходящих карт нет; When игрок открывает письмо; Then кнопка «Принять» неактивна, причина «Нет подходящей карты»; When через неделю выходит подходящая карта; Then кнопка становится активной без закрытия письма.
- **AC-19.3** Given принятый заказ на 2 000 шт./день, запас 1 500; When проходит день; Then поставлено 1 500, выручка по статье «Контракты», недопоставка 500 записана в окно 90 дней.
- **AC-19.4** Given недопоставка за 90 дней составила 30 % объёма; When проходит день; Then заказ расторгнут, репутация снижена на `reputationPenalty`, письмо отправлено.
- **AC-19.5** Given действующий заказ; When игрок выключает фичу в хабе; Then показано подтверждение с числом заказов и штрафом, «Отмена» оставляет фичу включённой.

- **Complexity:** Medium
- **Dependencies:** FR-5, FR-6, FR-7, FR-14; `mod-framework` (`ModMail`, `ModReputation`, `FeatureContext.ConfirmBeforeDisable`)
- **Assumptions:** числа заказов (`balance.console`, `consoles.json`) — черновые, калибруются в баланс-прогоне; `ContractType` игры не используется, заказ живёт только в секции `ModSave`.

## Non-Functional Requirements

### NFR-1: Производительность на тик
- WHEN проходит игровой день при ≤ 150 активных продуктах GPU (игрок, соперники, фон) и ≤ 6 сегментах THEN дневная работа фичи (резерв, производство, рынок, популярность) SHALL занимать ≤ 0.5 мс на эталонной машине владельца (замер `Stopwatch` в отладочной сборке, лог раз в месяц).
- WHEN наступает 1-е число THEN месячная работа (соперники, синергия, бухгалтерия, кэши) SHALL занимать ≤ 5 мс.
- IF вызывается дневной тик THEN фича SHALL не вызывать `Object.FindObjectsByType` и `DataFinder.FindLithography`: техпроцессы кэшируются при загрузке и раз в месяц.
- WHILE открыт конструктор фича SHALL пересчитывать характеристики только при изменении параметра, а не каждый кадр.

### NFR-2: Надёжность
- WHEN в обработчике тика, патче или UI фичи возникает исключение THEN обработчик SHALL быть обёрнут в `ModHooks.Guard(FeatureId, siteId, …)`: исключение ловится на границе хука, пишется в `ModLog` и засчитывается фиче; после `hooks.faultThreshold` (5) исключений ядро переводит фичу в `Faulted` и показывает уведомление. Собственных счётчиков ошибок и отключения подсистем по исключениям фича не ведёт.
- IF самопроверка на старте не нашла цель патча или поле для рефлексии THEN мод SHALL отключить зависящую возможность (производство GPU, строку на экране производства или общий опыт техпроцесса), а не всю фичу, и показать это на странице фичи в хабе «Моды».
- Фича SHALL никогда не бросать исключения в код игры. После резерва GPU значение `Factory.totalAllocatedLines` SHALL быть не больше `ProductionCapacity`.

### NFR-3: Совместимость сейвов
- Ванильный сейв SHALL загружаться с модом, сейв с модом — без мода.
- Секция `gpu-product-line` SHALL мигрировать по параметру `schema` метода `Read` (поле `_schema` ведёт ядро); неизвестные поля SHALL игнорироваться, отсутствующие — получать значения по умолчанию.
- Снимок характеристик продукта SHALL храниться в сейве: изменение контента не меняет уже выпущенные карты, как и у CPU (`CreatorCpu.CreateCpu` сохраняет готовые значения).

### NFR-4: Локализация
- Все строки фичи SHALL идти через `ModL10n` с ключами `gpu.*`, язык по умолчанию — ru, фолбэк — en.
- Деньги, частоты и проценты SHALL форматироваться функциями игры (`StringFormatter.FloatToMoney`, `StringFormatter.FloatToFrequency`, `StringFormatter.FloatToPercentageString`).

### NFR-5: Удобство
- WHEN подразделение основано и нужная архитектура исследована THEN выпуск первой карты SHALL требовать не больше 6 действий: открыть конструктор → выбрать архитектуру → «Разработать» → дождаться → «Выпустить» → назначить линии.
- Модальные окна фичи (основание, выпуск, подтверждения `ModUI.Confirm`) SHALL ставить время на паузу через `PauseTrigger`.
- Каждая характеристика в конструкторе SHALL иметь подсказку с формулой простыми словами через мост `ModUI.Tooltip` (собственного моста к `TooltipHandler` фича не пишет).
- Окна SHALL следовать теме `ThemeManager` (светлая и тёмная).

### NFR-6: Детерминизм
- Все случайные решения фичи (каденция и разброс параметров соперников и фона) SHALL идти через `ModRandom` (потоки `gpu-product-line/rivals` и `gpu-product-line/background`; состояние потоков сохраняет ядро). Из одного сейва при одинаковых действиях игрока получаются одинаковые запуски соперников.

### NFR-7: Баланс (ориентиры для калибровки)
Проверяется прогоном симуляции в тестах (`mod/tests/`) на контенте по умолчанию:
- эталонная партия — IDM, старт 1990, Normal, подразделение основано в 1995: к 2005 выручка GPU составляет 15–45 % общей выручки игрока;
- «Прочие производители» держат ≥ 15 % рынка GPU до 2000 года;
- ни один вендор не держит > 70 % сегмента дольше 3 лет подряд без вмешательства игрока;
- первая карта в 3D-эпоху окупает разработку не позже чем за 24 месяца при цене не выше бюджета сегмента.

### NFR-8: Безопасность
- Фича SHALL не обращаться к сети. Файлы она читает и пишет только через `ModContent` и `ModSave`.
- Значения из контента и сейва SHALL проходить проверку диапазонов. Размеры списков ограничены: продуктов ≤ 500, вендоров ≤ 32, месяцев бухгалтерии ≤ 600, очередь исследований ≤ 5, консольных заказов (действующих и завершённых) ≤ 32.

## Edge Cases

- **Мощность уменьшилась** — продажа линий через `ManageLinesWindow.SellLines` или продажа подразделения: резерв GPU урезается до новой мощности в тот же день, ручные значения линий сохраняются, и игрок видит предупреждение.
- **Компания стала fabless** (`CompanyHelper.SellManufacturingDivision`): все GPU переходят в режим аутсорса, линии превращаются в выпуск в шт./день по последнему фактическому выпуску.
- **Смена размера пластины.** `Company.get_CurrentWaferSize` — средний диаметр по линиям; выпуск GPU пересчитывается по нему каждый день, как у CPU.
- **Нулевой или NaN-результат.** При `DiesPerWafer ≤ 0` производство GPU в этот день пропускается с предупреждением; бесконечного цикла, как в `ProductionMath.RequiredProductionLines`, нет. При нулевых суммах рейтингов продаж нет.
- **Пакетный прогон «Следующий месяц»** (`DateController.NextMonth`, `ModTicks.IsBatchRun`): обработчики фичи идут по дням как обычно, отдельных счётчиков пакета фича не ведёт; письма и уведомления ядро откладывает до `ModTicks.BatchEnded`. `DateController.set_CurrentDate` событий не поднимает, поэтому исследования, проекты и соперники не догоняют пропущенное — так же, как игра.
- **Фича выключена и включена снова.** Секция и состояние сохраняются; помесячные правила считаются по разности дат, поэтому вендоры, эпохи и фон догоняют текущий год на ближайшем месячном тике без писем о пропущенных событиях (FR-14 п. 6). Консольные заказы при выключении расторгаются (FR-19 п. 7). Записи и провайдеры каналов выключенной фичи ядро хранит и не применяет; фича их при выключении не удаляет.
- **Банкротство игрока.** Фича не вмешивается: меню спасения — `bankruptcy-recovery`, активы GPU при этом не продаются и не передаются, линейка и запасы остаются.
- **Компания ИИ поглощена игроком** (`rival-acquisitions`): она вызывает `GpuApi.TransferVendorProducts` (решение владельца), линейка переходит к игроку; без вызова вендор уходит с рынка, как при банкротстве.
- **Игрок начал партию литейщиком.** Подразделение недоступно (FR-1 п. 9); состав подразделений `Divisions.Cpu` в течение партии не меняется.
- **Контент поменялся между сессиями.** Узел исследования исчез — он молча пропадает из «исследованных»; архитектура исчезла — выпущенные карты работают по снимку, новые на ней проектировать нельзя.
- **Сегмент закрылся** при активной ручной цене: продукт остаётся в линейке, продажи в оставшихся сегментах.
- **Перемотка новой игры.** Тики GPU не идут (`ModTicks` не вызывает подписчиков), письма и реакции не создаются; засев рынка один раз по `TickPhase.FastForwardEnded`.
- **Загрузка во время открытого диалога выпуска.** Сцена перезагружается, продукт сохраняет статус «Готов к выпуску».
- **Несколько фич пишут в `market.rating.cpu`** (`platform-generations`, `cpu-architectures`, `historical-events`, `design-flaw-recalls`, синергия): множители перемножаются, итог на CPU ограничивает ядро балансовым диапазоном [0,5; 2,0]. Вклад синергии не превышает ×1,08 (`cpuMax`).
- **Высокая скорость** (12 дней в секунду): вся работа фичи привязана к тикам, а не к кадрам.

## Constraints and Assumptions

### Technical Constraints
- Классы игры не меняются. Новые типы `HardwareType`, `ContractType`, `RevenueOrigin` и `ExpenseOrigin` недоступны: GPU живут в модели мода, деньги идут по существующим статьям.
- Патчи — только Harmony через `ModHooks` (решение 0002); фича ставит два необязательных патча, их список и полей для рефлексии — в design.md, всё проходит самопроверку. Цели, закреплённые за ядром (`Company.AddCpu`, `AICompany.AddCpu`, `DateController.NextMonth`, `GameManager.StartNewGame`, `MenuGameSetup.InitializeUI`, `EmailWindow.GetEmails`, формулы каналов), фича не патчит.
- Точка входа — `[ModFeature] sealed class GpuFeature : IModFeature` (`Register(FeatureContext)`); тики — `ctx.OnTick`, старт — `ModTicks.GameReady` / `TickPhase.FastForwardEnded`, состояние — `IModSaveParticipant`, настройки — `ctx.Param`, страница хаба — `ctx.HubPage`.
- UI строится в рантайме из шаблонов игры (`ModUI`, решение 0005); своих ассетов нет.
- Рынок CPU фича не патчит: на рейтинг CPU она влияет только через провайдер канала `market.rating.cpu`.
- Состояние хранится только в `ModSave` (решение 0004); числа — только в контенте (решение 0006).
- Сборка и тесты — по решению 0003: `python mod/build.py`, мини-раннер `[Test]` / `[Covers]`; код `Logic` использует общее подмножество API .NET Framework 4.8 и mscorlib Unity (без `init`, `record`, `Index`, `Range`).

### Business Constraints
- XL-спека реализуется этапами: каждый этап — отдельная поставка с ручной проверкой владельцем.
- Запуск игры для проверки — ручной шаг владельца, не во время онлайн-игр с античитом.
- Названия реальные, как в русификаторе (NVIDIA, ATI, 3dfx, Matrox, S3, AMD, Intel, Sony, Nintendo, Microsoft); компании ИИ указываются по `UniqueID`, отображаемое имя берётся из игры.

### Assumptions
- Контракт `mod-framework` (имена сервисов, перемножение множителей в канале, сохранение секций выключенных фич) реализован, как описано в `.kiro/steering/context.md` и `mod-framework/design.md`.
- `ModTicks` вызывает подписчиков фазы `TickPhase.PreContractSellTick` до `ClientProductionTick` — это гарантирует порядок `DateController.TriggerTicks`.
- Игроки принимают, что выручка GPU в финансовом отчёте игры видна как «Продажи» (консольные заказы — как «Контракты»).

## Glossary

| Термин | Значение |
|---|---|
| GPU, видеокарта | продукт фичи: графический процессор с памятью и платой; не является `Cpu` игры |
| GPU-подразделение | состояние «компания делает GPU»; открывается решением игрока |
| Архитектура GPU | узел ветки «Архитектура»: задаёт транзисторов на блок, операций за такт, долю частоты CPU, требования к памяти, функции |
| Вычислительный блок | условная единица GPU (конвейер, шейдерный блок); число блоков = транзисторы / транзисторов на блок |
| Функции (features) | метки архитектуры (`2d`, `3d`, `tnl`, `shader`, `unified`, `compute`, `rt`, `tensor`); сегменты требуют их по годам |
| ПСП | пропускная способность памяти, МБ/с = ширина шины / 8 × скорость памяти (МТ/с) |
| Упор в память | эффективная производительность ниже вычислительной, потому что ПСП меньше требуемой |
| VRAM | объём видеопамяти; сегменты требуют минимум по годам |
| Сегмент GPU | группа покупателей с размером, бюджетом, весами рейтинга и требованиями (аналог `PopulationData`) |
| Эпоха | период, когда открыты определённые сегменты и действуют требования к функциям |
| Прочие производители (фон) | виртуальный продукт в каждом сегменте, представляющий остальной рынок |
| Вендор | производитель GPU на рынке: виртуальный (NVIDIA, ATI, 3dfx, Matrox, S3) или привязанный к компании ИИ по `UniqueID` (AMD, Intel) |
| Резерв линий | линии фабрики, занятые GPU в этот день до производства CPU |
| «CPU в приоритете» | режим (`cpuPriority`): GPU резервируют только остаток мощности после линий CPU и клиентов-литейщиков |
| Синергия | взаимный бонус рейтинга CPU и GPU для компании, продающей оба продукта; реализуется провайдерами каналов `market.rating.cpu` и `gpu.rating` |
| Консольный заказ | долгосрочный заказ производителя консоли на GPU игрока по фиксированной цене (FR-19, Could) |
| Ключ компании | строка `ModCompanies`: `player` или `ai:<UniqueID>`; пустая строка — виртуальный производитель |
| `marketMode` | режим рынка из `balance.json`: `single` (этап 1) или `eras` (этап 2) |
| techLag | отставание технологий вендора от текущего года, в годах |
