## Implementation Overview

Фреймворк строится снизу вверх: сначала каркас сборки и мини-раннер тестов, три спайка (загрузка DLL, Harmony 2.3.6, тулчейн `csc`), затем чистая логика без Unity с юнит-тестами, потом интеграция с игрой (бутстрап, патчи, тики, сейв, каналы, события выпуска CPU), UI (шаблоны, окна, письма с действиями и приоритетами, хаб, слот новой игры), самопроверка, установщик, релизный пакет и проверка владельцем. Фаза 7 содержит задачи v0.2 (механизмы по решениям владельца); номера TSK-001…054 сохранены, потому что на них ссылаются спеки фич.

### Implementation Strategy
- Гейт TSK-001 пройден: владелец одобрил решения 0001–0006 и реализацию 2026-10-10; Harmony 2.3.6 уже лежит в `mod/lib/0Harmony.dll`. Других загрузок нет (ни .NET SDK, ни xUnit, ни NuGet).
- Если спайк провален, включается условная задача фолбэка (TSK-007, TSK-008). Остальной план не меняется, потому что API ядра от бэкенда не зависит.
- Код, который не трогает Unity и игру, лежит в `Core/Logic/` и пишется вместе с тестами (тест-первым для JSON, ГСЧ, модификаторов, условий, очереди писем, правила сегмента, порога кредита, идентификаторов). Логика компилируется под .NET Framework 4.8 (тесты) и под `mscorlib` Unity (мод).
- Каждая интеграционная задача проверяется служебной фичей `framework-sample` (только отладочная сборка) и самопроверкой. Запуск игры делает только владелец.
- Задачи фазы 7 встраиваются в график по зависимостям (см. Dependency graph): логические (TSK-055 логика, TSK-058, TSK-059, TSK-061, TSK-066, TSK-067) можно делать сразу после TSK-002; интеграционные — после соответствующих задач фазы 2–3.

### Development Approach
- **Testing Strategy**: свой мини-раннер на .NET Framework 4.8 для `Core/Logic/**` (каждый публичный тип в `[Covers]`, ключевые случаи таблицы design.md), Python `unittest` для установщика и инструментов, самопроверка при каждом старте, ручные сценарии M1–M24 из design.md.
- **Integration Strategy**: один Harmony ID на фичу; ядро — единственный патчер формул каналов и общих хуков (выпуск CPU, пакетный прогон, старт новой игры); подписки на события переустанавливаются на каждой сцене.
- **Deployment Strategy**: `install.py --with-mods` (идемпотентно, с бэкапом и манифестом; `--mods-only`; готовые DLL из GitHub Release или сборка через `csc`), откат — `--remove-mods` / `--restore`.

Задачи рассчитаны на 2–4 часа. Пометка «(владелец)» — шаг требует запуска игры или решения владельца.
