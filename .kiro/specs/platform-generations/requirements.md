## Introduction

В игре есть корпуса и сокеты: 16 технологий `Package` от DIP 1970 до LGA 2030 A/B. Есть и свои сокеты игрока и ИИ (`CustomSocket` на базе `Package`, `CreatorSocket.CreateSocket`, `AIBehaviourSocket.CreateSocket`). Но сокет — это только набор параметров для дизайна CPU. У платформы нет поколений, нет установленной базы и нет лояльности покупателей. Единственный «переход платформы» зашит в код: при первом CPU на PGA/LGA (`MarketEventHandler.TriggerPgaEvent`) рейтинг не-PGA CPU в потребительских сегментах за 5 лет падает до нуля (`Market.PgaDebuffMultiplier`).

Фича делает платформу стратегическим решением:

- **Поколения** приходят по календарю: анонс, запуск первым CPU, окно ранних последователей, зрелость, устаревание. Поколения называются по реальным сокетам (DIP-40, Socket 7, LGA 1151 и т. д.).
- **Установленная база** копится от продаж CPU на сокете. Компания с большой базой на своём сокете получает бонус рейтинга, потому что покупатели обновляются в пределах платформы. Стандартный сокет делит базу между всеми компаниями.
- **Ранние последователи** нового поколения получают долгий бонус.
- **Смена сокета** раньше срока стоит покупателей.
- **OEM-клиенты** со временем принимают новые поколения: у каждого контракта свой предпочитаемый стандарт. Отстающие от поколения клиента CPU реже выигрывают его контракты, а «полная платформа» (сокет и память одного поколения) получает небольшую надбавку.

Влияние на рейтинг идёт только через канал `ModModifiers` `market.rating.cpu`, на контракты — через стандартный канал `contract.signChance`. Формулы игры фича не патчит.

### Feature Summary
Мод добавляет поколения платформ из контент-JSON, установленную базу по компаниям и сокетам, бонусы и штрафы рейтинга через `market.rating.cpu` и принятие поколений OEM-клиентами через `contract.signChance` (предпочтение каждого контракта хранится в сейве, множитель зависит от контракта и стандарта памяти CPU). Причины множителей отдаются ядру и видны в разборе `ModModifiers.Explain`.

### Business Value
- **Ценность для игрока.**
  - Выбор сокета и момента перехода начинает влиять на продажи и контракты.
  - Появляются «войны платформ»: свой закрытый сокет против общего стандарта.
  - Есть награда за ранний переход и цена за метания.
- **Доказательства спроса** (I24). Комментатор itch.io просит лояльность платформе; разработчик ответил, что сокеты планируется расширять. В модах похожих тайкунов (Game Dev Tycoon) платформы и их жизненный цикл — среди самых популярных.
- **Для проекта.** Волна 4 роадмапа. Fun 4/5. Фича почти целиком данные (контент-JSON) плюс две чистые модели, а это хорошо тестируется.

### Scope

**Входит:**
- модель поколения платформы (сокеты, стандарт памяти, даты анонса и устаревания, окно ранних последователей, кривая принятия OEM) в контент-JSON; 10 поколений 1971–2030 по реальным технологиям игры, названия — реальные сокеты;
- анонс поколения по расписанию и запуск поколения первым CPU (событие ядра `ModEvents.CpuReleased`); уведомления и письма;
- установленная база по компаниям и сокетам, рассчитанная из помесячной статистики продаж CPU (`CpuBase.MarketData`);
- множитель рейтинга CPU через канал `market.rating.cpu`: база, ранний последователь, смена сокета;
- штраф за смену сокета и предупреждение перед выпуском CPU;
- принятие поколений OEM-клиентами и множитель шанса контракта через `contract.signChance` (по контрактам, с учётом стандарта памяти CPU; запасной «рыночный» режим);
- окно «Платформы» (поколения, установленная база, разбор множителей своих CPU);
- причины множителей для `ModModifiers.Explain` (видны в `contract-transparency`);
- предикаты `ModConditions` и события (Could);
- нейтральность во время перемотки новой игры и однократное восстановление состояния на `TickPhase.FastForwardEnded`; восстановление для старых сейвов.

**Не входит:**
- изменение ванильного PGA-перехода (`Market.PgaDebuffMultiplier`, `MarketEventHandler.TriggerPgaEvent`, `Cpu.get_AveragePopularity`) — остаётся как есть (решение владельца);
- патчи формул рынка и контрактов. Единственный патч на `Market.CalculateRatings` и на шанс контракта принадлежит `mod-framework`, фича только регистрирует провайдеры в каналах;
- патчи на `Company.AddCpu` / `AICompany.AddCpu`: выпуск CPU приходит событием ядра `ModEvents.CpuReleased`;
- материнские платы как товар, чипсеты как продукт, синергия CPU+GPU — это `gpu-product-line`;
- архитектуры и ISA — это `cpu-architectures`;
- изменение поведения ИИ (выбор сокета с учётом платформ) — это `rival-personalities` (отдельной задачей позже);
- скидка на разработку CPU на основном сокете (канал `development.cost.design` фичей не используется);
- новые технологии корпусов. Поколения ссылаются только на существующие 16 `Package` и 9 `Memory`;
- лицензирование сокета соперникам (идея I17 в план не входит).

## Requirements

### FR-1: Модель поколений платформ из контента

**User Story:** Как владелец баланса, я хочу описывать поколения платформ в JSON (сокеты, память, годы, окно ранних последователей, кривую принятия OEM), чтобы менять историю платформ без пересборки мода.

**Priority:** Must

#### Acceptance Criteria

1. WHEN мод загружает контент THEN мод SHALL прочитать `Content/platform-generations/generations.json` через `ModContent` с перекрытием файлом из `<папка игры>/PTMod/content/platform-generations/`.
2. WHEN мод валидирует поколение THEN мод SHALL требовать: уникальный `id`; уникальный `order`; `name` (`ru`/`en`); `announceYear` от 1971 до 2035; непустой список `sockets` из имён существующих `Package` (сверка с `DataFinder.FindPackage`); `memories` из имён существующих `Memory` (сверка с `DataFinder.FindMemory`); `obsoleteYear` больше `announceYear` или `null`; параметры OEM в диапазонах из design.md.
3. IF запись поколения не проходит валидацию THEN мод SHALL пропустить её, записать причину в `ModLog` и продолжить с остальными.
4. IF один сокет указан в двух поколениях THEN мод SHALL оставить его в поколении с меньшим `order` и записать предупреждение.
5. WHEN мод определяет поколение CPU THEN мод SHALL брать имя базового корпуса: `Package.Name` для стандартного корпуса или `CustomSocket.BasePackage.Name` для своего сокета — и искать его в `sockets` поколений. IF совпадения нет THEN CPU SHALL считаться «вне поколений», и множители поколения на него не действуют.
6. WHEN контент поставляется с модом THEN он SHALL содержать 10 поколений 1971–2030, покрывающих все 16 корпусов игры (таблица в design.md).
7. WHEN мод показывает имя поколения THEN имя SHALL быть реальным названием сокета (решение владельца): DIP-40, PLCC-68, PGA-132, Socket 1–3, Socket 5/7, «LGA 775 / Socket 939» и т. д. (`name.ru` и `name.en`); технические `id` поколений остаются неизменными. Игровые `announceYear` заданы технологиями игры и могут отличаться от годов реальных запусков.

#### Scenarios
- **AC-1.1** Given встроенный `generations.json`. When мод стартует. Then загружено 10 поколений, все 16 корпусов сопоставлены, в `ModLog` нет предупреждений.
- **AC-1.2** Given оверрайд с поколением, где сокет `"PGA 1999"` не существует. When мод стартует. Then это поколение пропущено с записью в `ModLog`, остальные работают.
- **AC-1.3** Given CPU на своём сокете «Socket Z», построенном на `PGA 1995`. When мод определяет поколение. Then CPU относится к поколению, где есть `PGA 1995`.

#### Additional Details
- **Complexity:** Medium
- **Dependencies:** `mod-framework` (ModContent, ModL10n, ModLog)
- **Assumptions:** имена `Package` и `Memory` стабильны: они хранятся в сейвах как имена технологий (`CODEMAP`, Gotchas «Renaming any of those techs breaks load»).

### FR-2: Анонс поколения по расписанию

**User Story:** Как игрок, я хочу заранее узнавать о новом поколении платформ, его сокетах и памяти, чтобы спланировать исследования и переход.

**Priority:** Must

#### Acceptance Criteria

1. WHEN наступает 1 января года `announceYear` поколения (подписка `ctx.OnTick(TickPhase.YearPassed, …)`; в перемотку и при загрузке обработчик не вызывается) и поколение ещё не анонсировано THEN мод SHALL отметить поколение анонсированным с этой датой.
2. WHEN поколение анонсировано вне перемотки и вне загрузки THEN мод SHALL отправить письмо `ModMail` «Анонс платформы: {имя}» (`Tag = "pg:announce:<genId>"`, `Priority = MailPriority.Normal`) с сокетами, стандартом памяти, окном ранних последователей в месяцах и сроком устаревания, а также показать уведомление `ModNotify`.
3. IF первый CPU поколения выпущен раньше `announceYear` THEN мод SHALL анонсировать поколение в момент запуска (FR-3) и не анонсировать его повторно 1 января.
4. WHILE идёт перемотка новой игры мод SHALL не вести хронологию и не создавать писем и уведомлений (политика владельца: фичи нейтральны в перемотке); анонсы за перемотанные годы отмечаются один раз на `TickPhase.FastForwardEnded` (FR-12.3) с правильными датами.

#### Scenarios
- **AC-2.1** Given игра идёт 1989 год, поколение `gen-1990-pga` («Socket 1–3») с `announceYear` 1990. When наступает 1 января 1990. Then приходит одно письмо «Анонс платформы: Socket 1–3» и одно уведомление.
- **AC-2.2** Given новая игра со стартом в 1995 году. When перемотка завершилась. Then поколения 1971, 1980, 1985, 1990, 1995 анонсированы с датами 1 января своих лет, писем об анонсах нет.

#### Additional Details
- **Complexity:** Low
- **Dependencies:** FR-1, FR-12; `mod-framework` (ModTicks, ModMail, ModNotify)
- **Assumptions:** подписка обычная (`TickOptions.None`): по политике владельца фича в перемотке нейтральна, состояние к старту восстанавливается один раз на `TickPhase.FastForwardEnded`.

### FR-3: Запуск поколения и ранние последователи

**User Story:** Как игрок, я хочу получать долгий бонус, если одним из первых выпущу CPU на новом поколении, чтобы ранний переход окупался.

**Priority:** Must

#### Acceptance Criteria

1. WHEN ядро поднимает `ModEvents.CpuReleased(owner, cpu, isVariant, duringFastForward)` для игрока или ИИ, `isVariant` и `duringFastForward` равны `false`, поколение CPU известно и ещё не запущено, THEN мод SHALL отметить поколение запущенным: дата и компания-первопроходец.
2. WHEN компания выпускает первый CPU поколения в окне `[дата запуска; дата запуска + earlyWindowMonths]` и число ранних последователей поколения меньше `earlyAdopterSlots` THEN мод SHALL записать компанию ранним последователем с датой.
3. WHEN игрок становится первопроходцем или ранним последователем THEN мод SHALL показать уведомление `ModNotify` и отправить письмо (`Tag = "pg:early:<genId>"`, `Priority = MailPriority.Normal`) с величиной и сроком бонуса.
4. WHEN поколение запускает ИИ THEN мод SHALL показать одно уведомление «{компания} первой выпустила CPU на платформе {имя}» (имя компании берётся из игры).
5. WHEN идёт загрузка сейва THEN `CpuReleased` не поднимается (правило ядра), и мод SHALL восстановить состояние из `ModSave`; события с `duringFastForward = true` мод SHALL игнорировать (политика нейтральности).
6. WHEN CPU — вариант (`isVariant`, `Cpu.Base` не `null`) или выпущен на сокете, уже известном компании, THEN мод SHALL не считать его «первым CPU поколения» для этой компании повторно.

#### Scenarios
- **AC-3.1** Given `gen-2000` анонсировано, ни у кого нет CPU на `PGA 2000`/`LGA 2000`. When игрок выпускает CPU на `LGA 2000` в марте 2000. Then поколение запущено игроком, игрок — ранний последователь №1, приходит письмо «бонус +6 % к рейтингу CPU поколения на 60 месяцев».
- **AC-3.2** Given окно 24 месяца и 3 слота, уже заняты 3 компаниями. When четвёртая компания выпускает CPU поколения через 10 месяцев. Then она не становится ранним последователем.

#### Additional Details
- **Complexity:** Medium
- **Dependencies:** FR-1, FR-2; `mod-framework` (`ModEvents.CpuReleased`, ModNotify, ModMail)
- **Assumptions:** `Company.AddCpu` и `AICompany.AddCpu` вызываются и при загрузке (`SaveHandler.Load`), но события ядра при загрузке нет; фича своих патчей на эти методы не ставит (`ModHooks` отклонил бы такой патч).

### FR-4: Установленная база по компаниям и сокетам

**User Story:** Как игрок, я хочу видеть, сколько моих CPU работает у покупателей на каждом сокете, чтобы понимать силу своей платформы.

**Priority:** Must

#### Acceptance Criteria

1. WHEN мод считает установленную базу THEN мод SHALL для каждого CPU брать помесячные продажи `CpuBase.MarketData.Sold` (вес 1) и `CpuBase.MarketData.SoldByContracts` (вес `contractUnitWeight`, по умолчанию 0.5), затухающие с коэффициентом `δ = 1 − 1/lifetimeMonths` в месяц (по умолчанию `lifetimeMonths` = 60), и суммировать по ключу «компания-владелец CPU (`Cpu.Company`) × сокет».
2. WHEN наступает `TickPhase.LateMonthPassed` (подписка `ctx.OnTick`, не в перемотку и не при загрузке) THEN мод SHALL обновить базу инкрементально: `ib_cpu = ib_cpu × δ + units_последнего_полного_месяца`, затем пересобрать суммы по компаниям и сокетам по текущему владельцу CPU.
3. WHEN загружается сейв (`ModTicks.GameReady(Loaded)`) или завершается перемотка новой игры (`TickPhase.FastForwardEnded`) THEN мод SHALL пересобрать базу полностью из ledger-списков всех CPU (`CpuDataProvider.GetAllCpus`), включая снятые с производства.
4. WHEN ключ сокета строится для CPU THEN мод SHALL использовать `pkg:<Package.Name>` для стандартного корпуса и `custom:<CustomSocket.CustomHardwareID>` для своего сокета; стандартные сокеты SHALL считаться общими для всех компаний.
5. IF у CPU нет `MarketData` или список короче двух месяцев THEN мод SHALL считать его вклад нулевым.
6. WHEN владелец CPU меняется (спин-офф `CompanyEventHandler.TriggerSolarFoundriesSpinOff`, покупка компании из `rival-acquisitions` с событием `ModEvents.CpuTransferred`) THEN база этого CPU SHALL уйти к новому владельцу со следующего месячного пересчёта, а кэш множителей этого CPU SHALL обновиться сразу.

#### Scenarios
- **AC-4.1** Given CPU продал 100 000 шт. в январе и 0 потом, `lifetimeMonths` = 60. When наступает 1 января следующего года (первый пересчёт 1 февраля добавил 100 000, затем 11 пересчётов с затуханием). Then его вклад = 100 000 × (59/60)¹¹ ≈ 83 120.
- **AC-4.2** Given сохранённая игра. When её загружают. Then полная пересборка даёт те же суммы, что инкрементальный расчёт до сохранения (допуск 0.1 %).

#### Additional Details
- **Complexity:** Medium
- **Dependencies:** FR-1; `mod-framework` (ModTicks, ModEvents)
- **Assumptions:** ledger-списки `CpuBase.MarketData` выровнены по индексу месяца от начала игры (`MarketDataHandler.FixMarketIndex`) и сохраняются в сейве. Базу хранить не нужно — она выводится из сейва.

### FR-5: Влияние платформы на рейтинг CPU через `market.rating.cpu`

**User Story:** Как игрок, я хочу, чтобы большая установленная база моего сокета и ранний переход на поколение помогали продажам, чтобы стратегия платформы имела значение.

**Priority:** Must

#### Acceptance Criteria

1. WHEN фича инициализируется (`Register`, один раз) THEN мод SHALL зарегистрировать в `ModModifiers` провайдер канала `market.rating.cpu` с фиксированной причиной (`reasonKey` = `pg.reason.rating`), который для CPU и сегмента рынка возвращает множитель `m = clamp(1 + w_seg × (B_ib + B_early − P_churn), minMult, maxMult)` (формулы и числа — в design.md).
2. WHEN мод считает `B_ib` THEN доля SHALL быть `effShare = (IB[компания][сокет] + sharedWeight × (IB_все[сокет] − IB[компания][сокет]) × [сокет стандартный]) / IB_всего`, а `B_ib = ibMaxBonus × min(1, effShare / ibSaturationShare)`. Вес общей базы `sharedWeight` = 0.25 (решение владельца).
3. WHEN CPU принадлежит раннему последователю своего поколения THEN `B_early` SHALL равняться `earlyBonus`, линейно затухая до 0 за `earlyDurationMonths` от даты попадания в ранние последователи.
4. WHEN мод применяет множитель к сегменту «Промышленность» (`ctx.Segment == Segment.Industries`) THEN вес `w_seg` SHALL равняться `industriesWeight` (0.5, решение владельца), для остальных сегментов — 1.0.
5. WHILE игра идёт мод SHALL отдавать множитель из кэша, пересчитываемого раз в месяц (`TickPhase.LateMonthPassed`) и при выпуске нового CPU. Провайдер SHALL не делать аллокаций и не обходить списки при вызове.
6. WHEN множитель применяется THEN мод SHALL применять его одинаково к CPU игрока и ИИ (решение владельца: эффект моделирует поведение покупателей, а не бонус игроку; на низкой сложности эффект для ИИ не ослабляется).
7. IF CPU вне поколений, его компания не найдена, кэш не готов или идёт перемотка новой игры (`ModTicks.IsFastForwarding`) THEN провайдер SHALL вернуть 1.0.
8. WHEN выпуск CPU (`ModEvents.CpuReleased`) или смена владельца (`ModEvents.CpuTransferred`) меняет состояние провайдера внутри игрового дня THEN мод SHALL обновить кэш CPU и сбросить дневной кеш ядра для компании (`ModModifiers.Invalidate(channel, companyKey)`).

#### Scenarios
- **AC-5.1** Given у игрока 30 % всей установленной базы на своём сокете, `ibMaxBonus` 0.10, `ibSaturationShare` 0.40. When считается рейтинг CPU игрока в сегменте `Segment.HighEnd`. Then множитель 1.075; в «Промышленности» — 1.0375.
- **AC-5.2** Given две компании используют стандартный `PGA 1995`, у A 10 % базы, у B 20 % на этом сокете, `sharedWeight` 0.25. When считается множитель A. Then `effShare = 0.10 + 0.25 × 0.20 = 0.15`, `B_ib = 0.10 × 0.375 = 0.0375`.
- **AC-5.3** Given в настройках выключены «Эффекты на рейтинг». When идёт рыночный тик. Then провайдер возвращает 1.0 для всех CPU (сразу: обработчик `ModSettings.Changed` вызывает `ModModifiers.Invalidate`).
- **AC-5.4** Given идёт перемотка новой игры. When рынок считает рейтинги. Then провайдер возвращает 1.0 для всех CPU.

#### Additional Details
- **Complexity:** Medium
- **Dependencies:** FR-3, FR-4, FR-6; `mod-framework` (канал `market.rating.cpu` с контекстом «CPU + сегмент»)
- **Assumptions:** по `mod-framework/design.md` (патч P4) ядро после `Market.CalculateRatings` и до `Market.NormalizeRatings` умножает `Cpu.Ratings.Overall` на `M(market.rating.cpu, company, cpu, populationIndex)`. Провайдер получает `ModifierContext {Company, CompanyKey, Cpu, Segment}`, результат кешируется ядром на игровой день. Произведение множителей всех фич на CPU ограничено ядром балансовым диапазоном [0,5; 2,0]; Explain показывает «(ограничено)».

### FR-6: Штраф за смену сокета

**User Story:** Как игрок, я хочу, чтобы частая смена сокета стоила покупателей, а долгая поддержка платформы окупалась, чтобы решение о новом сокете было взвешенным.

**Priority:** Must

#### Acceptance Criteria

1. WHEN компания выпускает первый CPU на сокете, новом для неё (событие `ModEvents.CpuReleased`, не вариант, не в перемотке), THEN мод SHALL записать «появление сокета»: компания, сокет, дата, основной сокет компании на этот момент (сокет с наибольшей `IB[компания]` среди других) и его возраст в месяцах (от первого CPU компании на нём).
2. WHEN основной сокет есть, его доля базы `IB[компания][основной] / IB_всего ≥ churnMinBaseShare` (0.02), его возраст `< minSocketLifeMonths` (36) и новый сокет с ним несовместим, THEN мод SHALL назначить новому сокету штраф `P_churn = churnPenalty × (1 − возраст / minSocketLifeMonths)`, линейно затухающий до 0 за `churnDurationMonths` (24).
3. WHEN мод проверяет совместимость THEN сокеты SHALL считаться совместимыми, если у них одинаковое имя базового корпуса (стандартный `Package` и свой сокет на его основе), или если пара перечислена в `compatibleSockets` поколения.
4. WHEN штраф назначен THEN он SHALL действовать на все CPU компании на новом сокете через `P_churn` в FR-5.
5. WHEN штраф назначен игроку THEN мод SHALL показать уведомление со значением и сроком.

#### Scenarios
- **AC-6.1** Given у игрока основной сокет «Socket A» (возраст 12 мес., 25 % базы). When игрок выпускает первый CPU на «Socket B» (база другая). Then штраф 0.10 × (1 − 12/36) = 6.7 %, затухает за 24 месяца.
- **AC-6.2** Given ИИ выпускает CPU на своём сокете, построенном на `PGA 1995`, а основной сокет ИИ — стандартный `PGA 1995`. When CPU выпущен. Then штрафа нет (совместимы по базе).

#### Additional Details
- **Complexity:** Medium
- **Dependencies:** FR-4, FR-5
- **Assumptions:** ИИ создаёт по одному своему сокету на каждый новый настраиваемый корпус (`AIBehaviourSocket.SelectBasePackage`). Правило совместимости по базе защищает ИИ от ложных штрафов. ИИ в отношении платформ не осознан (решение владельца): штрафы он получает по тем же правилам, но не избегает их сознательно.

### FR-7: Предупреждение о смене сокета перед выпуском CPU

**User Story:** Как игрок, я хочу увидеть предупреждение о штрафе за смену сокета до выпуска CPU, чтобы не получить штраф по незнанию.

**Priority:** Should

#### Acceptance Criteria

1. WHEN открывается окно выпуска CPU (postfix на `ProjectReleaseWindow.Open(Cpu)`) и выпуск этого CPU назначит штраф по FR-6 THEN мод SHALL показать уведомление `ModNotify` «Смена сокета: −{N} % к рейтингу CPU на {сокет} на {M} мес. Основной сокет {S} поддерживается {K} мес. из {L}».
2. WHEN выпуск CPU сделает компанию ранним последователем THEN мод SHALL показать уведомление «Ранний переход на {поколение}: +{N} % на {M} мес.».
3. IF CPU не меняет сокет и не даёт статуса раннего последователя THEN мод SHALL ничего не показывать.

#### Scenarios
- **AC-7.1** Given условия AC-6.1 до выпуска. When открывается окно выпуска CPU на «Socket B». Then видно уведомление «Смена сокета: −6.7 % … Socket A поддерживается 12 мес. из 36».

#### Additional Details
- **Complexity:** Low
- **Dependencies:** FR-3, FR-6; `mod-framework` (ModNotify)
- **Assumptions:** окно выпуска нельзя отменить (в нём только «Выпустить»). Предупреждение информирует, а планирование — в окне «Платформы» (FR-9).

### FR-8: Принятие поколений OEM-клиентами

**User Story:** Как игрок, я хочу, чтобы OEM-клиенты со временем переходили на новые поколения и предпочитали CPU актуальной платформы, чтобы отставание по платформе стоило контрактов.

**Priority:** Must

#### Acceptance Criteria

1. WHEN мод считает принятие поколения G на дату t THEN доля SHALL быть `A_G(t) = min(maxAdoption, maxAdoption × clamp01((m − delayMonths) / rampMonths) + ibAccel × IBshare_G(t))`, где m — месяцы с запуска G, `IBshare_G` — доля установленной базы на сокетах G. Для незапущенного поколения `A = 0`.
2. WHEN мод регистрирует провайдер канала `contract.signChance` (`RegisterReasonedProvider`, один раз) THEN он SHALL выбирать режим по контексту вызова: IF `ModifierContext.Contract` ≠ null THEN режим «по контрактам» (FR-8.3–8.4), иначе («рыночный» запасной режим, FR-8.5: объяснение без контракта или контекст без контракта) — ожидание по рынку. Настройка `oem.mode = marketAverage` принудительно включает «рыночный» режим (для отладки и сравнения); по умолчанию `auto`.
3. WHEN появляются новые контракты (`ContractManager.OnNewContracts`; переподписка на `PTModHost.SceneReady`) или провайдер впервые видит контракт без предпочтения (контракты из перемотки, E9) THEN мод SHALL назначить каждому контракту типа из `contractTypes` (по умолчанию Computer 1 и Console 2, `Contract.ContractType`; Calculator исключён, решение владельца) предпочтительное поколение. Запущенные и не устаревшие на дату создания поколения перебираются от новых к старым, и выбирается первое G, у которого `roll(ContractKey, G) < A_G(t_создания)`; иначе «без предпочтения». `t_создания = Contract.AcceptanceDate − 12 месяцев`. `roll` — детерминированный хэш ключа контракта, `id` поколения и `ModRandom.WorldSeed`. Предпочтение хранится в `ModSave` по `ContractKey`.
4. WHERE включён режим «по контрактам» множитель для контракта с предпочтением Gp и CPU поколения Gc SHALL быть: `1 + adoptBonus`, если `order(Gc) ≥ order(Gp)`; `1 − lagPenalty1`, если отстаёт на одно поколение; `1 − lagPenalty2`, если на два и более; плюс `fullPlatformBonus` (по умолчанию 0.05), если стандарт памяти CPU (`Cpu.Memory`) входит в `memories` его поколения Gc («полная платформа», стандарт памяти влияет — решение владельца); 1.0, если CPU вне поколений, у контракта нет предпочтения или тип контракта не в `contractTypes`.
5. WHERE включён «рыночный» режим мод SHALL возвращать для CPU поколения Gc ожидаемый множитель по распределению предпочтений рынка на текущую дату: `c̄ = Σ_G p_G × c_plat(Gc, G) + p_none × 1`, где `c_plat` включает надбавку за полную платформу, `p_G = A_G × Π_{H новее G}(1 − A_H)` и `p_none = Π_H (1 − A_H)`. Для CPU поколений с `order < marketAverageMinGenOrder` (по умолчанию 2: DIP и PLCC — рынок калькуляторов, где тип контракта неизвестен) множитель SHALL быть 1.0.
6. WHEN множитель платформы рассчитан (любой режим) THEN мод SHALL умножить его на лояльность OEM `1 + oemLoyaltyBonus × min(1, effShare / ibSaturationShare)` и ограничить `[minChanceMult, maxChanceMult]`.
7. WHEN множитель шанса применяется THEN мод SHALL применять его одинаково к предложениям игрока и ИИ; во время перемотки новой игры провайдер возвращает 1.0.
8. WHEN контракт исчез из `ContractManager.GetAvailableContracts` и `GetActiveContracts` THEN мод SHALL удалить его предпочтение из состояния при ближайшем месячном пересчёте.

#### Scenarios
- **AC-8.1** Given `gen-2000` запущено в марте 2000, `delayMonths` 6, `rampMonths` 36, `maxAdoption` 0.9, `ibAccel` 0.5, доля базы на сокетах поколения 15 %. When в январе 2002 считается принятие (m = 22). Then `A = 0.9 × 16/36 + 0.075 = 0.475`.
- **AC-8.2** (по контрактам) Given контракт Computer предпочитает `gen-2000`; CPU игрока на `PGA 2000` с памятью DDR (IPS 600), CPU Intel на `PGA 1995` с памятью SDR (IPS 900); лояльность не учитывается. When считается шанс. Then множители ×1.25 (поколение предпочтения + полная платформа) и ×0.80 (отставание на поколение 0.75 + полная платформа 0.05); ванильные шансы 40/60 становятся 50/48; фактическая вероятность игрока 35.1 % против 21.1 % без платформы.
- **AC-8.3** (по контрактам) Given контракт Calculator. When считается шанс. Then множитель 1.0 для всех.
- **AC-8.4** («рыночный» режим) Given январь 2002: `A(gen-2000) = 0.475`, `A(gen-1995-pga) = 0.9`; `gen-1990-pga` и старше устарели (`obsoleteYear` ≤ 2002) и не участвуют. When считается множитель CPU на `PGA 1995` с памятью SDR (Gc = gen-1995-pga, полная платформа). Then `p(gen-2000) = 0.475`, `p(gen-1995) = 0.9 × 0.525 = 0.4725`, `p_none = 0.525 × 0.1 = 0.0525`, `c̄ = 0.475 × 0.80 + 0.4725 × 1.25 + 0.0525 ≈ 1.023`; для CPU на `PGA 2000` с памятью DDR: `c̄ = 0.475 × 1.25 + 0.4725 × 1.25 + 0.0525 ≈ 1.237`; для CPU на `PGA 1995` с памятью, не входящей в поколение (без полной платформы): `c̄ = 0.475 × 0.75 + 0.4725 × 1.20 + 0.0525 ≈ 0.976`.
- **AC-8.5** (по контрактам) Given контракт предпочитает `gen-2000`; CPU игрока на `LGA 2000` с памятью SDR (не входит в `memories` поколения `gen-2000`). When считается шанс. Then множитель ×1.20 (без надбавки за полную платформу).
- **AC-8.6** Given тот же сейв загружают повторно. When считается предпочтение контрактов. Then предпочтения те же (читаются из `ModSave`, `roll` детерминирован).

#### Additional Details
- **Complexity:** High
- **Dependencies:** FR-1, FR-3, FR-4; `mod-framework` (канал `contract.signChance`, патчи P8 и P23: контракт в `ModifierContext`; `RegisterReasonedProvider`), ModSave, ModRandom
- **Assumptions:** у `Contract` нет уникального ID. Предпочтения хранятся по составному `ContractKey` (как в `contract-transparency`). Ядро различает контракты в дневном кеше; если ключ кеша строится только по `Contract.ContractID` (индекс шаблона, не уникален), значения двух контрактов одного шаблона могут смешаться (см. «Открытые вопросы», п. 2).

### FR-9: Окно «Платформы»

**User Story:** Как игрок, я хочу открыть окно с поколениями, установленной базой и разбором множителей своих CPU, чтобы планировать переходы и видеть эффект.

**Priority:** Must

#### Acceptance Criteria

1. WHEN игрок выбирает «Платформы» в хабе «Моды» THEN мод SHALL открыть окно с тремя вкладками: «Поколения», «Установленная база», «Мои CPU».
2. WHEN открыта вкладка «Поколения» THEN мод SHALL показать для каждого поколения: имя (реальный сокет), сокеты, память, статус (ожидается / анонсировано / окно ранних последователей / зрелое / устарело), даты анонса и запуска, первопроходца, ранних последователей и текущую долю принятия OEM `A_G` (полоса и процент).
3. WHEN открыта вкладка «Установленная база» THEN мод SHALL показать строки «сокет × компания» по убыванию базы: имя сокета (`CustomSocket.Name` или `Package.Name`), стандартный или свой, компания, база в штуках, доля от всей базы, возраст сокета у компании. Фильтр — «мои / все».
4. WHEN открыта вкладка «Мои CPU» THEN мод SHALL показать для каждого CPU игрока на рынке: сокет, поколение, признак «полная платформа» (память CPU входит в стандарты поколения) и составляющие множителя рейтинга (`B_ib`, `B_early`, `P_churn`, итог для потребительских сегментов и для «Промышленности»), а также множитель шанса OEM. В режиме «по контрактам» это число доступных контрактов, где поколение CPU отстаёт от предпочтения клиента, и средний множитель по таким контрактам; в запасном «рыночном» режиме — `c̄` с лояльностью.
5. WHEN игрок наводит на сокет на вкладке «Мои CPU» THEN мод SHALL показать «риск смены сокета»: возраст основного сокета, сколько месяцев осталось до `minSocketLifeMonths`, ожидаемый штраф при переходе сейчас.

#### Scenarios
- **AC-9.1** Given игра 2003 года. When игрок открывает «Платформы → Поколения». Then `gen-2000` в статусе «зрелое» (если окно 24 мес. прошло) с долей принятия; `gen-2010` — «ожидается».

#### Additional Details
- **Complexity:** Medium
- **Dependencies:** FR-1…FR-8; `mod-framework` (ModUI, хаб «Моды»)
- **Assumptions:** нет.

### FR-10: Причины множителей для `ModModifiers.Explain`

**User Story:** Как игрок, смотрящий разбор шанса контракта (`contract-transparency`) или рейтинг CPU, я хочу видеть, что часть множителя пришла от платформы и почему, чтобы связать платформу с результатом тендера.

**Priority:** Should

#### Acceptance Criteria

1. WHEN провайдеры каналов `market.rating.cpu` и `contract.signChance` возвращают множитель, отличный от 1.0, THEN мод SHALL отдать ядру причину: провайдер рейтинга регистрируется с фиксированным `reasonKey` (`pg.reason.rating`), провайдер шанса — через `RegisterReasonedProvider` с `ProviderResult` (`ReasonKey`: `pg.reason.oemPrefers`, `pg.reason.oemLag`, `pg.reason.oemAdoption`, `pg.reason.oemLoyalty`; `ReasonArgs` — название платформы, число поколений отставания, процент принятия).
2. WHEN `ModModifiers.Explain` запрашивает разбивку (окно «Платформы», `contract-transparency`, подсказки рейтинга) THEN запись с `FeatureId = "platform-generations"` SHALL нести причину из п. 1. Собственного публичного метода `Explain` у фичи нет: по составляющим (`B_ib`, `B_early`, `P_churn`) её детально разбирает только окно «Платформы» (`PlatformInsights`).
3. WHEN причина формируется для горячего канала `market.rating.cpu` THEN мод SHALL не создавать строки и массивы на вызове; для `contract.signChance` аргументы причины SHALL браться из заранее подготовленных массивов поколений.

#### Scenarios
- **AC-10.1** Given контракт Computer предпочитает `gen-2000` («LGA 775 / Socket 939»), CPU игрока на `LGA 2000` с памятью DDR, лояльность нулевая. When игрок открывает разбор шанса из `contract-transparency`. Then видна строка «platform-generations ×1.25 — OEM предпочитает платформу LGA 775 / Socket 939».

#### Additional Details
- **Complexity:** Low
- **Dependencies:** FR-5, FR-8; `mod-framework` (`ModModifiers.RegisterReasonedProvider`, `Explain`); `contract-transparency` FR-2.3
- **Assumptions:** ядро v0.2 принимает причины провайдеров (`ProviderResult`, `RegisterProvider(…, reasonKey)`); обход через собственный публичный `Explain` фичи не нужен.

### FR-12: Перемотка новой игры и старые сейвы

**User Story:** Как игрок, начинающий новую игру с позднего года или загружающий сейв, сделанный до установки мода, я хочу, чтобы история платформ была правдоподобной, чтобы эффекты сразу работали корректно.

**Priority:** Must

#### Acceptance Criteria

1. WHEN начинается новая игра (ядро вызывает `IModSaveParticipant.ResetToDefaults` при подготовке новой игры в prefix `GameManager.StartNewGame`, `ModSave.Status` = `NewGame`) THEN мод SHALL сбросить состояние фичи до начала перемотки. Ролл OEM использует `ModRandom.WorldSeed` новой игры.
2. WHILE идёт перемотка (`ModTicks.IsFastForwarding`) мод SHALL быть нейтральным (политика владельца): не вести хронологию, не создавать событий, писем и уведомлений, не применять эффектов (провайдеры возвращают 1.0); подписки года и месяца в перемотку не вызываются (`TickOptions.None`), `ModEvents.CpuReleased` с `duringFastForward = true` игнорируется.
3. WHEN наступает `TickPhase.FastForwardEnded` (приходит после сброса `IsFastFowardSimulating`; единственная точка однократной инициализации состояния к старту новой игры) THEN мод SHALL выполнить реконструкцию по CPU рынка. Анонсы — все поколения с `announceYear ≤` текущего года (даты 1 января своих лет). Запуск — минимальный `Cpu.Year` среди CPU поколения, дата 1 января. Ранние последователи — первые компании по `(Cpu.Year, Cpu.SaveID)` в пределах окна. Появления сокетов — по минимальному `Cpu.Year` компании на сокете, с `severity` 0: штрафы за смену сокета задним числом не назначаются. Предпочтения доступных контрактов назначаются по FR-8.3. База — полная пересборка, затем пересборка кэша множителей. Писем и уведомлений нет. Реконструкция идемпотентна: она дополняет только недостающие записи, поэтому повторный запуск на `ModTicks.GameReady(NewGame)` ничего не меняет.
4. WHEN загружается сейв без секции `platform-generations` THEN мод SHALL выполнить ту же реконструкцию на `ModTicks.GameReady(Loaded)`.
5. WHEN загружается сейв с секцией THEN мод SHALL восстановить анонсы, запуски, ранних последователей, появления сокетов и предпочтения, а базу и кэш множителей пересобрать на `ModTicks.GameReady(Loaded)`.
6. IF в секции есть `id` поколения, которого нет в текущем контенте, THEN мод SHALL сохранить запись без изменений и игнорировать её в расчётах.

#### Scenarios
- **AC-12.1** Given сейв 2005 года без бокового файла. When его загружают. Then `gen-2000` запущено в год первого CPU на `PGA 2000`/`LGA 2000`, ранние последователи определены, множители рейтинга работают с первого рыночного тика.
- **AC-12.2** Given новая игра со стартом в 1995 году. When перемотка завершилась. Then во время перемотки множители были 1.0, а после `FastForwardEnded` анонсы, запуски, ранние последователи, база и кэш восстановлены один раз, писем нет.

#### Additional Details
- **Complexity:** Medium
- **Dependencies:** FR-2…FR-8; `mod-framework` (`IModSaveParticipant`, `ModSave.Status`, `ModTicks.GameReady`, `TickPhase.FastForwardEnded`, `ModRandom.WorldSeed`)
- **Assumptions:** `Cpu.Year` — год выпуска CPU (`CpuBase.Year`); месяц выпуска игра не хранит. Игра вызывает `DateController.SimulateUntilYear` в `Player.InitializeAsNewGame` всегда, поэтому `OnFastFowardEnded` приходит и при старте 1971 года.

### FR-13: Настройки и выключение

**User Story:** Как игрок, я хочу выключить фичу целиком или отдельно эффекты на рейтинг, на контракты и уведомления, чтобы настроить сложность.

**Priority:** Must

#### Acceptance Criteria

1. WHEN игрок открывает настройки фичи в хабе «Моды» THEN мод SHALL показать переключатели: «Включено», «Эффекты на рейтинг», «Эффекты на контракты (OEM)», «Уведомления и письма».
2. WHEN фича или эффект выключены THEN соответствующие провайдеры SHALL возвращать 1.0 без перезапуска: при выключении фичи — сразу (ядро пропускает провайдеры неактивной фичи и сбрасывает кеш `ModModifiers` по `ModFeatures.StateChanged`), при изменении отдельного эффекта — сразу (фича вызывает `ModModifiers.Invalidate` из `ModSettings.Changed`).
3. WHILE выключены только эффекты (фича включена) мод SHALL продолжать вести хронологию (анонсы, запуски, база) без влияния на игру. WHEN включают ранее выключенную фичу целиком THEN мод SHALL догнать пропущенный период реконструкцией (FR-12.3 для недостающих записей) и полной пересборкой базы. Секция `ModSave` сохраняется в обоих случаях. Провайдеры при включении и выключении не пересоздаются.
4. WHEN мод удалён THEN сейв игры SHALL загружаться в ванильной игре: фича не пишет в `SaveObject` и не меняет объекты игры.

#### Scenarios
- **AC-13.1** Given выключены «Эффекты на контракты». When открыт разбор шанса контракта. Then строки платформы нет, шанс ванильный (если нет других модов).

#### Additional Details
- **Complexity:** Low
- **Dependencies:** `mod-framework` (ModSettings)
- **Assumptions:** нет.

## Non-Functional Requirements

### NFR-1: Производительность
- WHEN идёт рыночный тик THEN вызов провайдера `market.rating.cpu` SHALL занимать в среднем ≤ 0.2 мкс (поиск в кэше без аллокаций). Суммарная добавка на игровой день при 300 CPU на рынке (3 прохода × 4 сегмента) SHALL быть ≤ 0.3 мс.
- WHEN выполняется месячный пересчёт THEN он SHALL занимать ≤ 5 мс при 1000 CPU.
- WHEN выполняется полная пересборка базы THEN она SHALL занимать ≤ 50 мс при 1000 CPU × 720 месяцев; реконструкция на `FastForwardEnded` вместе с пересборкой — ≤ 100 мс.
- WHEN идёт перемотка с 1971 по 2000 год THEN фича не добавляет работы в тики (одна проверка флага), а общее время перемотки вырастет не больше чем на 5 % от ванильного (с учётом одной реконструкции в конце).
- WHEN `contract.signChance` вызывается провайдером (десятки раз в год и по клику) THEN вызов SHALL занимать ≤ 20 мкс.

### NFR-2: Надёжность
- IF провайдер или обработчик события бросает исключение THEN мод SHALL перехватить его (`ModHooks.Guard` для провайдеров и патча, `ModHooks.Raise` для обработчиков событий ядра), вернуть 1.0 (провайдер) или ничего не менять (обработчик), записать в `ModLog`. По достижении порога `hooks.faultThreshold` (5, circuit breaker `mod-framework`) фича переходит в `Faulted` (эффекты 1.0 до перезапуска), ядро показывает одно уведомление. Своих счётчиков ошибок фича не ведёт.
- IF у `CustomSocket` не найден `CustomHardware` (`CustomSocket.get_BasePackage` бросает) THEN CPU SHALL считаться «вне поколений».

### NFR-3: Совместимость сейвов
- WHEN загружается сейв без бокового файла THEN мод SHALL восстановить состояние по FR-12.4 без ошибок.
- WHEN мод удалён THEN сейв SHALL оставаться ванильным (FR-13.4).
- WHEN меняется версия секции THEN мод SHALL мигрировать данные по версии `schema`, которую ядро передаёт в `IModSaveParticipant.Read` (поле `_schema` пишет и читает ядро; в данных фичи поля версии нет).

### NFR-4: Детерминизм
- WHEN тот же сейв загружается повторно THEN предпочтения OEM, ранние последователи и множители SHALL совпадать (хронология и предпочтения — в `ModSave`, сид — `ModRandom.WorldSeed`, сохраняемый ядром, база выводится из сейва игры, `roll` — хэш).

### NFR-5: Баланс через контент и вклад в общие каналы
- Все числа фичи (бонусы, штрафы, сроки, кривые, веса) SHALL лежать в `Content/platform-generations/*.json`. В коде — только дефолты на случай битого контента.
- WHEN баланс по умолчанию применён THEN вклад фичи SHALL быть ограничен так:

| Канал | Вклад фичи (минимум … максимум) | Общий предел |
|---|---|---|
| `market.rating.cpu` | ×0,90 … ×1,16 по умолчанию (`1 − churnPenalty` … `1 + ibMaxBonus + earlyBonus`); клампы контента `minMult` 0,85 и `maxMult` 1,20 — страховка от оверрайдов; для «Промышленности» вклад вдвое слабее | произведение всех фич на CPU ограничено ядром до [0,5; 2,0]; Explain показывает «(ограничено)» |
| `contract.signChance` | ×0,50 … ×1,375 по умолчанию (`1 − lagPenalty2` … `(1 + adoptBonus + fullPlatformBonus) × (1 + oemLoyaltyBonus)`); клампы `minChanceMult` 0,40 и `maxChanceMult` 1,40 | предохранитель канала [0; 5], балансового диапазона нет |

- Тесты эффектов SHALL учитывать, что при совместном действии других фич итог на CPU ограничен ядром ([0,5; 2,0]); собственный вклад фичи кламп ядра не повышает.

### NFR-6: Локализация
- Все строки фичи SHALL браться из `ModL10n` по ключам `pg.*` (ru по умолчанию, en фолбэк). Имена поколений в контенте — `{ "ru": …, "en": … }`, реальные названия сокетов.
- Числа SHALL форматироваться функциями игры (`StringFormatter.FloatToIntString` для штук, проценты — с одним знаком).

### NFR-7: Справедливость
- Правила SHALL быть одинаковыми для игрока и ИИ (FR-5.6, FR-8.7). Отступление — только с явным решением владельца.

### NFR-8: Безопасность данных
- WHEN мод читает контент или секцию `ModSave` THEN он SHALL проверять типы, диапазоны, даты (не позже текущей), существование `Package`, `Memory` и компании. Невалидные записи отбрасываются или хранятся без участия в расчётах (FR-12.6), с записью в `ModLog`.
- WHEN мод выводит строки из контента и сейва THEN он SHALL экранировать TMP-разметку.
- Фича SHALL не обращаться к сети и не читать файлы, кроме контента `ModContent` и бокового файла `ModSave`.

## Edge Cases

| # | Ситуация | Ожидаемое поведение |
|---|---|---|
| E1 | Первый CPU поколения выпущен до `announceYear` (исследования опережают календарь) | Анонс и запуск в один день (FR-2.3) |
| E2 | Поколение анонсировано, но годами никто не выпускает CPU | Принятие OEM = 0, ранних последователей нет, статус «анонсировано» |
| E3 | Компания-ранний последователь обанкротилась | Статус сохраняется, CPU продолжают получать бонус, пока на рынке; база затухает |
| E4 | CPU перешёл к другой компании (спин-офф, покупка, `ModEvents.CpuTransferred`) | База CPU уходит новому владельцу; кэш множителей CPU обновляется сразу; статус раннего последователя остаётся у прежней компании |
| E5 | Свой сокет на базе корпуса, которого нет в поколениях (битый контент) | CPU «вне поколений», множители 1.0 |
| E6 | Ванильный PGA-переход | Не меняется; множители фичи применяются поверх его результата (умножение на 0 даёт 0) |
| E7 | В рынке нет CPU (тик рынка выходит рано) | Провайдер не вызывается; месячный пересчёт идёт по ledger |
| E8 | Сумма установленной базы равна 0 (начало 1971) | `effShare = 0`, `B_ib = 0`, `IBshare_G = 0` |
| E9 | Контракт создан в перемотку или не 1 января (`ContractInstantiator.AddNewContracts`) | Предпочтение назначается лениво при первом вызове провайдера или при реконструкции |
| E10 | Игрок переименовал свой сокет (`SocketEditWindow`) | Ключ `custom:<ID>` не меняется, в окне видно новое имя |
| E11 | Два CPU компании на разных сокетах выпущены в один день | Появления сокетов обрабатываются по порядку событий `CpuReleased`; основной сокет — по базе на момент события |
| E12 | Контент изменён между сессиями (поколение удалено) | Записи с неизвестным `id` сохраняются и игнорируются (FR-12.6) |
| E13 | Память CPU не входит в стандарты поколения его сокета (например, SDR на `LGA 2000`) | «Полной платформы» нет, надбавка `fullPlatformBonus` не применяется; остальные множители без изменений |
| E14 | Провайдер `contract.signChance` вызван без контракта (разбор вне контракта, патч P23 не применён) | Запасной «рыночный» режим (FR-8.5) |

## Constraints and Assumptions

### Technical Constraints
- Только сервисы `PTMod.Core`. Поля в классы игры не добавляются, состояние — в `ModSave`. Точка входа — `[ModFeature] sealed class PlatformGenerationsFeature : IModFeature`.
- Влияние на рейтинг — только через канал `market.rating.cpu`, на контракты — только через `contract.signChance`. Фича не патчит `Market.CalculateRatings`, `Contract.GetBestOffers`, `Contract.CpuOffer.DefineChance`.
- Выпуск и перенос CPU приходят событиями `ModEvents.CpuReleased` и `ModEvents.CpuTransferred`; патчи на `Company.AddCpu` / `AICompany.AddCpu` запрещены (цели закреплены ядром, `ModHooks` отклонит патч).
- Собственный патч фичи один: postfix `ProjectReleaseWindow.Open` (`Optional`).
- Ванильные `Market.PgaDebuffMultiplier`, `MarketEventHandler.TriggerPgaEvent`, `Cpu.get_AveragePopularity` не трогаются.
- Новых каналов `ModModifiers` фича не объявляет. Провайдеры регистрируются один раз (`Register`); `OnEnabled`/`OnDisabled` их не пересоздают.
- Тесты чистой логики — мини-раннер ядра (`python mod/build.py --tests`, `mod/tests/PTMod.Tests/Features/PlatformGenerations/`); код `Logic/` использует общее подмножество API .NET Framework 4.8 и `mscorlib` Unity (без `init`, `record`, `Index`, `Range`). Сборка — `python mod/build.py --game-dir <папка игры>`.

### Business Constraints
- Баланс по умолчанию — умеренный (NFR-5). Окончательные числа подбирает владелец после ручной проверки.
- Ручная проверка в игре — шаг владельца.

### Assumptions
- По `mod-framework/design.md` v0.2: провайдер `market.rating.cpu` получает `ModifierContext {Company, CompanyKey, Cpu, Segment}` (P4); провайдер `contract.signChance` получает `{Company, CompanyKey, Cpu, Contract}` (P8 + P23). Ядро кеширует результат на день по ключу «канал, компания, CPU, сегмент, контракт».
- `ModTicks` (`FeatureContext.OnTick`) вызывает подписчиков фаз `YearPassed` и `LateMonthPassed` вне перемотки и загрузки; `TickPhase.FastForwardEnded` приходит один раз после перемотки.
- Новая игра сбрасывает участников сейва: ядро вызывает `IModSaveParticipant.ResetToDefaults` в prefix `GameManager.StartNewGame` (P17) до перемотки.
- Компании в состоянии фичи идентифицируются ключами `ModCompanies.KeyOf` (`player`, `ai:<UniqueID>`).

- [ ] `python tools/check_spec_refs.py --code pt-modding/code --core-api .kiro/specs/mod-framework/design.md` не находит несуществующих `Class.Method` и несуществующих имён API ядра в спеках этой фичи.

### Acceptance Metrics
- Множитель рейтинга по умолчанию в `[0.85; 1.20]` (практически `[0.90; 1.16]`) на всей симуляции 1971–2030 (офлайн-симуляция TSK-022, лог min/max); множитель шанса — в `[0.40; 1.40]`.
- Инкрементальная база совпадает с полной пересборкой с точностью 0.1 % (тест).
- Перемотка 1971→2000 медленнее ванильной не больше чем на 5 % (замер владельца).
- Повторная загрузка сейва даёт те же предпочтения OEM для 100 % контрактов (тест на детерминизм).

## Открытые вопросы владельцу

Остались вопросы, которых `owner-decisions.md` не решает. Они не блокируют реализацию: действуют решения по умолчанию.

1. **Баланс стартовых величин.** Подтвердить или скорректировать числа из таблицы выше после плейтеста (офлайн-симуляция TSK-022 печатает min/max/среднее множителей; финальное решение — после ручной проверки TSK-024). По умолчанию: числа из `balance.json` v0.2.
2. **Различение контрактов в дневном кеше ядра.** `mod-framework` включает «ID контракта» в ключ дневного кеша `contract.signChance`. Если это `Contract.ContractID`, то он — индекс шаблона данных (`ContractInstantiator.AddNewContracts`), а не уникальный номер: два контракта одного шаблона от разных клиентов могут получить общее значение кеша, и предпочтение OEM одного контракта «перетечёт» на другой в тот же день. По умолчанию: в ядре ключ кеша стоит строить по идентичности объекта `Contract`; ручной сценарий M7 проверяет разбор двух контрактов одного шаблона. Решает владелец `mod-framework`.

## Glossary

| Термин | Значение |
|---|---|
| Сокет (socket) | Корпус CPU: стандартный `Package` (технология из дерева) или свой `CustomSocket` компании на базе `Package` |
| Ключ сокета | `pkg:<Package.Name>` или `custom:<CustomHardwareID>` |
| Базовый корпус | `Package.Name` для стандартного, `CustomSocket.BasePackage.Name` для своего сокета |
| Стандартный сокет | Стандартный `Package`, им пользуются все компании; установленная база частично общая |
| Поколение платформы | Запись контента: набор базовых корпусов, стандарт памяти, даты, окно ранних последователей, кривая принятия OEM; называется по реальным сокетам |
| Полная платформа | CPU, у которого стандарт памяти входит в `memories` поколения его сокета; получает надбавку `fullPlatformBonus` в OEM-множителе |
| Анонс | Плановая дата (1 января `announceYear`), с которой поколение известно рынку |
| Запуск | Выпуск первого CPU поколения любой компанией |
| Ранний последователь | Одна из первых `earlyAdopterSlots` компаний, выпустивших CPU поколения в окне после запуска |
| Установленная база (IB) | Затухающая сумма проданных CPU (рынок + 0.5 × контракты) по компании и сокету |
| Смена сокета (churn) | Выпуск CPU на новом для компании несовместимом сокете, пока основной сокет моложе `minSocketLifeMonths` |
| Принятие OEM | Доля OEM-контрактов, предпочитающих поколение (`A_G`) |
| Предпочтение контракта | Режим «по контрактам»: поколение, которое предпочитает клиент контракта (назначается один раз, хранится по `ContractKey`) |
| «Рыночный» режим OEM | Запасной режим без контракта в контексте канала: множитель шанса — ожидание по распределению предпочтений рынка на текущую дату (FR-8.5) |
| ContractKey | `Company|AcceptanceYear-AcceptanceMonth|Units|round(PaymentPerUnit)|ContractType` |
| Канал `market.rating.cpu` | Стандартный канал `ModModifiers`: множитель к `Cpu.Ratings.Overall` |
| Канал `contract.signChance` | Стандартный канал `ModModifiers`: множитель к шансу предложения в контракте |
