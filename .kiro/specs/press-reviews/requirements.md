## Introduction

Сейчас выпуск процессора в Processor Tycoon проходит беззвучно. Игрок не получает внятной обратной связи, хорош ли CPU относительно конкурентов и «эпохи». Причины плохих продаж приходится вычислять по таблицам. Рейтинги рынка и популярность в игре есть, но они скрыты и не объяснены.

Мод добавляет прессу:
- Через 7–21 день после выпуска любого CPU (игрока и соперников) вымышленные издания публикуют обзоры. Каждый обзор оценивает CPU по четырём осям: производительность, цена/производительность, энергоэффективность, нагрев.
- Сравнение идёт с лидерами сегмента с поправкой на их возраст, поэтому планка растёт с каждым годом, а «прошлогодний уровень» оценивается как «средне».
- Слабая ось ограничивает итог.
- На высокой сложности рецензенты строже.
- Обзоры своих CPU игрок получает письмами; обзоры CPU соперников приходят одним ежемесячным дайджестом.

Итоговая метаоценка двумя путями влияет на продажи — через прирост популярности, без второй формулы рейтинга:
- **Ажиотаж конкретного CPU** — растёт его популярность.
- **Репутация бренда** (`ModReputation`) — растёт популярность всех CPU компании.

Оба вклада перемножаются с вкладами других фич в канал `popularity.gain` в общем пределе ядра [0,5; 2,0] на CPU (решение владельца). Раз в год пресса подводит итоги, раз в квартал публикует заметки о том, что сейчас ценит рынок. Репутацию к 50 со временем возвращает ядро, а не эта фича.

### Feature Summary
Пресса оценивает каждый выпущенный CPU относительно соперников и года, пишет рецензии и годовые рейтинги. Оценки через ажиотаж и репутацию бренда влияют на прирост популярности CPU.

### Business Value
- **Для игрока.**
  - Понятная и эмоциональная обратная связь на каждый запуск («8.4/10 — Отлично», цитаты изданий).
  - Цель «выпустить процессор года».
  - Явная причина, почему продукт продаётся хуже.
  - Механика бренда: репутация копится годами и смягчает неудачи.
- **Доказательства спроса.**
  - В сравнимом тайкуне (Steam app 1342330) игроки сами реконструировали модель обзоров и обсуждают её — это любимая механика.
  - Hardware Tycoon (app 4490710) и app 5193810 продают обзоры и бенчмарки как фичу.
  - Подборка модов Game Dev Tycoon (cubiq.ru) показывает популярность «оценок прессы».
  - В комментариях к Processor Tycoon (itch.io, comments и comments?after=87) просят обратной связи по продажам и балансу.
  - Оценка в `IDEAS.md`: fun 4/5.

### Scope

**Входит:**
- Расписание обзоров при выпуске CPU игрока и ИИ (событие ядра `ModEvents.CpuReleased`): задержка 7–21 день, мгновенный режим.
- Формула оценки: оси, эталон соперников, рост планки по годам, строгость по сложности, ограничение слабой осью.
- Вымышленные издания (контент): годы работы, сегменты, акценты, шум; метаоценка и вердикт.
- Письмо-рецензия и карточка обзора для CPU игрока; ежемесячный дайджест обзоров соперников.
- Эффекты:
  - ажиотаж CPU (множитель канала `popularity.gain` для конкретного CPU);
  - изменение `ModReputation`;
  - эффект репутации на прирост популярности (тот же канал `popularity.gain`, уровень компании) для всех компаний.
- Отображение репутации и архива: окно «Пресса» с вкладками «Обзоры», «Репутация», «Итоги года», «Статьи».
- Годовые рейтинги 1 января, квартальные заметки прессы.
- API для других фич: событие публикации, публикация статей, корректировщики обзоров.
- Состояние в `ModSave`.

**Не входит:**
- Хранение репутации и её API `Add/Get` — `mod-framework` (`ModReputation`).
- Дрейф репутации к 50 — `mod-framework` (`ModReputation.Drift`, 3 % в месяц, без записи в историю). Эта фича не дрейфует репутацию и не пишет причину `press.drift`.
- Классификатор сегмента CPU по цене и перехват выпуска CPU — `mod-framework` (`ModSegments`, `ModEvents`).
- Патч формулы популярности `Market.UpdatePopularities` — единый патч `mod-framework` читает каналы. Эта фича только регистрирует множители.
- Изменение рейтинга CPU (`Market.CalculateRatings`, канал `market.rating.cpu`): обзор не участвует в рейтинге, чтобы не дублировать оценку производительности. Вклада в `market.rating.cpu` у фичи нет.
- Скрытый брак, отзывы, ревизии — `design-flaw-recalls`.
- Исторические события прессы — `historical-events`. Он может публиковать через API этой фичи.
- Рецензии на GPU (`gpu-product-line`): в этой версии пресса рецензирует только CPU.
- Колонка в таблице рынка — только Could (FR-13).

## Requirements

### FR-1: Обзор при выпуске CPU

**User Story:** Как игрок, я хочу, чтобы после выпуска каждого процессора — моего и конкурентов — выходил обзор, чтобы понимать, как пресса восприняла продукт.

**Priority**: Must

#### Acceptance Criteria
1. WHEN ядро поднимает `ModEvents.CpuReleased` для компании игрока (`isVariant = false`, `duringFastForward = false`) THEN мод SHALL поставить обзор в очередь с датой публикации через 7–21 игровой день (`ModRandom`).
2. WHEN `ModEvents.CpuReleased` поднято для ИИ-компании (`isVariant = false`, `duringFastForward = false`) THEN мод SHALL поставить обзор в очередь по тем же правилам.
3. WHERE в `ModSettings` включён режим «Мгновенные обзоры» (`instantReviews`, по умолчанию выключен), мод SHALL публиковать обзор в день выпуска.
4. IF CPU с этим `SaveID` уже рецензирован или стоит в очереди THEN мод SHALL не создавать второй обзор.
5. WHEN наступает дата публикации THEN мод SHALL рассчитать оценку (FR-2, FR-3) по текущему состоянию рынка и CPU (цена на день публикации) и сохранить запись обзора.
6. IF CPU к дате публикации снят с продажи или компания обанкротилась THEN мод SHALL отменить обзор без записи и уведомлений.
7. WHEN выпускается вариант CPU (`isVariant = true`) THEN мод SHALL не делать отдельный обзор (решение владельца: отдельных обзоров вариантов нет). Для эффектов (FR-5) вариант наследует обзор базового CPU.
8. WHEN CPU переносится между компаниями (`ModEvents.CpuTransferred`, `rival-acquisitions`) THEN мод SHALL не создавать обзор: перенос — не выпуск.

#### Сценарии
- **AC-1.1** Given игрок выпускает CPU 1985-03-01, When проходят дни, Then между 1985-03-08 и 1985-03-22 публикуется обзор, приходит письмо.
- **AC-1.2** Given загрузка сейва, When `SaveHandler.Load` вызывает `AddCpu` для всех CPU, Then `ModEvents.CpuReleased` не поднимается и новых обзоров нет.
- **AC-1.3** Given мгновенный режим, When игрок выпускает CPU, Then обзор публикуется в тот же день.
- **AC-1.4** Given CPU выпущен во время перемотки новой игры (`duringFastForward = true`), When событие дошло до обработчика, Then обзор не создаётся.

#### Additional Details
- **Complexity**: Medium
- **Dependencies**: `ModEvents`, `ModTicks`, `ModRandom`, `ModSave`
- **Assumptions**: ядро поднимает `CpuReleased` не чаще одного раза на объект CPU и не при загрузке (`GameManager.get_IsLoading`). Собственных патчей на `Company.AddCpu` и `AICompany.AddCpu` у фичи нет (`ModHooks` их отклонит).

### FR-2: Формула оценки обзора

**User Story:** Как игрок, я хочу, чтобы оценка честно отражала, насколько мой CPU лучше или хуже лидеров на сегодня, с учётом растущих ожиданий и сложности, чтобы по ней можно было принимать решения.

**Priority**: Must

#### Acceptance Criteria
1. WHEN рассчитывается обзор THEN мод SHALL определить сегмент обзора:
   - для CPU ИИ — `Strategy.TargetMarket`;
   - для CPU игрока — сегмент с наибольшими продажами за период ожидания (`ModSegments.FromSales` по накопленным продажам; ничья — меньший индекс);
   - при нулевых продажах (`Segment.Any`) или в мгновенном режиме — `ModSegments.Classify(cpu)` по цене и текущим бюджетам рынка. Правило задаёт ядро (`segments.priceBand` = 1,25): High End, если `Price > 1.25 × MidRangeBudget`; Mid Range, если `> 1.25 × LowEndBudget`; Low End, если `> 1.25 × IndustriesBudget`; иначе Industries (бюджеты — `Market.get_MidRangeBudget`, `Market.get_LowEndBudget`, `Market.get_IndustriesBudget`). Собственного классификатора у фичи нет.
2. WHEN рассчитывается обзор THEN мод SHALL выбрать эталонную группу: до 5 самых продаваемых CPU сегмента за последние 3 полных месяца (`MarketDataProvider.MostSoldCpus`) других компаний, не на пенсии.
3. WHEN эталонная группа выбрана THEN мод SHALL привести `Ips` каждого эталона к текущей дате множителем `g^(τ × возраст_лет)`:
   - `g` — темп эпохи из контента: 1.35 до 1985, 1.45 в 1985–1999, 1.30 в 2000–2009, 1.15 с 2010;
   - `τ` = 0.6;
   - возраст — от даты выпуска эталона (если она неизвестна — от 1 июля его `Year`).
4. WHEN эталоны готовы THEN мод SHALL оценить четыре оси от 0 до 100:
   - производительность — `Ips` к лучшему приведённому эталону;
   - цена/производительность — `Ips/Price` к медиане эталонов;
   - энергоэффективность — `Ips/PowerConsumption` к медиане эталонов;
   - нагрев — по запасу до `min(SafeTemperature корпуса, 95)`.

   Первые три оси считаются по кривой `S(r) = clamp(65 + 35 × ln(r / s_d) / ln 1.5, 0, 100)`. Строгость `s_d` по `Player.DifficultyLevel` 0…5: 0.85 / 0.92 / 1.00 / 1.08 / 1.16 / 1.25.
5. WHEN оси посчитаны THEN мод SHALL сложить их с весами сегмента из контента и ограничить итог сверху значением «слабейшая ось с весом ≥ 0.15 плюс 30».
6. IF эталонная группа пуста THEN мод SHALL сравнивать с предыдущим CPU той же компании в сегменте (приведённым по возрасту). Если такого нет, ось производительности SHALL равняться 70 с пометкой «без аналогов».
7. WHEN к обзору подключены корректировщики (FR-11) THEN мод SHALL применить их поправки к осям или итогу до агрегации изданиями.

#### Сценарии
- **AC-2.1** Given High End, сложность 2, `r_perf` = 1.1, `r_value` = 1.0, `r_eff` = 0.9, `T = Ts − 20`, When считается обзор, Then оси ≈ 73.2 / 65.0 / 55.9 / 62.5, базовый итог ≈ 67.4, ограничение 85.9 не срабатывает.
- **AC-2.2** Given CPU равен по `Ips` прошлогоднему лидеру (возраст 1 год, `g` 1.45), When считается обзор, Then ось производительности ≈ 46 (r = 1/1.45^0.6 ≈ 0.80).
- **AC-2.3** Given та же ситуация на сложности 5, Then ось производительности ≈ 26.5.
- **AC-2.4** Given ось нагрева 10, остальные 90, веса High End, When агрегируется итог, Then итог ≤ 40.
- **AC-2.5** Given CPU игрока без продаж за период ожидания и ценой 312 при бюджетах 599/249/149/79, When определяется сегмент, Then High End (`ModSegments.Classify`).

#### Additional Details
- **Complexity**: High
- **Dependencies**: FR-1; `ReviewMath` (чистая логика), `MarketDataProvider`, `ModSegments`
- **Assumptions**: `PowerConsumption`, `Temperature`, `Ips` фиксируются при создании CPU и потом не меняются (CODEMAP Hardware). Цена — текущая.

### FR-3: Издания и метаоценка

**User Story:** Как игрок, я хочу видеть оценки нескольких изданий со своим характером (энтузиасты, деловая пресса, встраиваемые системы), чтобы обзоры читались как живая пресса, а не как одна цифра.

**Priority**: Must

#### Acceptance Criteria
1. WHEN мод загружает контент THEN мод SHALL прочитать издания из `Content/press-reviews/outlets.json` через `ModContent`: `id`, название (ru/en), годы работы, сегменты, сдвиги весов осей, смещение оценки, шум. Мод SHALL провалидировать записи и пропускать битые.
2. WHEN публикуется обзор THEN мод SHALL получить оценку от каждого издания, которое работает в текущем году и освещает сегмент: итог с весами издания + смещение + шум `N(0, σ)` из `ModRandom`, клип 0–100.
3. IF ни одно издание не освещает сегмент в текущем году THEN мод SHALL использовать издание, у которого текущий год попадает в его интервал `fallback`. По умолчанию это «Электроника сегодня» в 1971–1992, «КилоБайт» в 1993–1996 и «Кремниевый обзор» с 1997.
4. WHEN оценки изданий получены THEN мод SHALL рассчитать метаоценку (среднее, округлённое до целого) и вердикт: ≥ 90 «Шедевр», 80–89 «Отлично», 70–79 «Хорошо», 55–69 «Средне», 40–54 «Слабо», < 40 «Провал».
5. WHEN издание пишет рецензию THEN мод SHALL сопроводить её одной цитатой из шаблонов `ModL10n` по самой сильной или самой слабой оси (если ось < 50).

#### Сценарии
- **AC-3.1** Given 1990 год и CPU High End, When публикуется обзор, Then оценки дают «Электроника сегодня», «КилоБайт» и «Мир разгона» (3 издания), метаоценка — их среднее.
- **AC-3.2** Given одинаковый сид `ModRandom` и одинаковое состояние, When обзор пересчитывается, Then оценки изданий совпадают (детерминизм).

#### Additional Details
- **Complexity**: Medium
- **Dependencies**: FR-2; `ModContent`, `ModRandom`, `ModL10n`
- **Assumptions**: названия изданий вымышленные; реальные бренды изданий не используются (решение владельца: издания вымышленные).

### FR-4: Рецензия игроку и дайджест обзоров соперников

**User Story:** Как игрок, я хочу получить письмо с рецензией на свой процессор и открыть подробную карточку, а также раз в месяц узнавать о громких обзорах конкурентов одним письмом, чтобы реагировать, не заваливая почту.

**Priority**: Must

#### Acceptance Criteria
1. WHEN опубликован обзор CPU игрока THEN мод SHALL отправить письмо через `ModMail.Send` (приоритет `Normal`, `Tag` = `press:review:<cpuSaveId>`):
   - тема «Обзоры: <CPU> — <метаоценка>/100»;
   - вердикт, оценки изданий, по одной цитате;
   - эффекты: Δ репутации, множитель ажиотажа и срок;
   - действие «Открыть обзор» (`ModMailAction`; письмо не закрывается).
2. WHEN игрок нажимает «Открыть обзор» THEN мод SHALL открыть карточку обзора (`ModUI`):
   - метаоценка и вердикт;
   - четыре оси с полосами и значениями;
   - строки изданий с оценкой и цитатой;
   - сегмент и эталоны (имена CPU, без формул);
   - эффекты.
3. WHEN наступает 1-е число месяца THEN мод SHALL собрать обзоры CPU соперников, опубликованные за прошлый месяц, и отправить одно письмо «Пресса: обзоры соперников» (приоритет `Low`, `Tag` = `press:digest:<yyyy-MM>`). В письмо попадают до 10 строк «<компания> <CPU> — <оценка>/100 (<вердикт>)» в порядке убывания |оценка − 65|: обзоры с метаоценкой ≥ 85 или ≤ 40 и обзоры в сегментах, где у игрока есть продаваемый CPU. Остальные сворачиваются в строку «и ещё N обзоров в архиве». IF подходящих обзоров нет THEN письмо не отправляется.
4. WHERE в `ModSettings` выключен параметр «Дайджест обзоров соперников» (`rivalDigest`, по умолчанию включён), мод SHALL не отправлять письмо (п. 3). Архив при этом пополняется.
5. Обзоры соперников SHALL не создавать отдельных писем и уведомлений `ModNotify` (решение владельца: обзоры ИИ приходят дайджестом).

#### Сценарии
- **AC-4.1** Given обзор CPU игрока с метаоценкой 84, When он публикуется, Then приходит письмо «Обзоры: X — 84/100», вердикт «Отлично», действие «Открыть обзор» открывает карточку, письмо остаётся открытым.
- **AC-4.2** Given в январе опубликован обзор CPU Intel 91, When наступает 1 февраля, Then в письме «Пресса: обзоры соперников» есть строка «Intel Y — 91/100 (Шедевр)».
- **AC-4.3** Given за месяц нет ни одного подходящего обзора соперников, When наступает 1-е число, Then письмо не отправляется.

#### Additional Details
- **Complexity**: Medium
- **Dependencies**: FR-1–FR-3; `ModMail` (`ModMailAction`, `MailPriority`, `Tag`), `ModUI`, `ModL10n`
- **Assumptions**: пакетный прогон месяца (`ModTicks.IsBatchRun`) не влияет на дайджест: письма откладывает ядро.

### FR-5: Ажиотаж — влияние обзора на прирост популярности CPU

**User Story:** Как игрок, я хочу, чтобы хорошо принятый прессой процессор быстрее набирал популярность, а провальный — медленнее, чтобы обзоры имели вес в продажах.

**Priority**: Must

#### Acceptance Criteria
1. WHEN обзор опубликован THEN мод SHALL учитывать для этого CPU множитель ажиотажа `H = clamp(1 + 0.5 × (M − 65)/35 × decay, 0.6, 1.5)` в провайдере канала `popularity.gain` (запрос с CPU в `ModifierContext`). Здесь `M` — метаоценка, `decay = max(0, 1 − дни_с_публикации/365)`.
2. WHILE `decay > 0`, мод SHALL пересчитывать множитель раз в игровой день. После 365 дней множитель SHALL равняться 1.0 и сниматься.
3. WHEN у CPU есть варианты (`Base` = этот CPU) THEN множитель ажиотажа SHALL действовать и на варианты.
4. IF фича выключена THEN провайдер `popularity.gain` этой фичи SHALL перестать влиять: ядро не применяет вклады выключенной фичи, а провайдер дополнительно возвращает 1.0.
5. WHEN множитель применяется THEN мод SHALL действовать одинаково для CPU игрока и ИИ (политика владельца: одинаковые правила).
6. WHEN итоговое произведение вкладов всех фич в канал `popularity.gain` для CPU выходит за балансовый диапазон [0,5; 2,0] THEN ядро SHALL ограничить его; фича SHALL не обходить предел. Ажиотаж складывается с вкладами других фич (`ms.launch_hype`, испытания, `ModifierTimed`) мультипликативно в этом пределе (решение владельца).

#### Сценарии
- **AC-5.1** Given метаоценка 90, When обзор опубликован, Then множитель ≈ 1.357. Через 183 дня ≈ 1.18, через 365 дней — 1.0.
- **AC-5.2** Given метаоценка 30, Then множитель 0.6 (нижняя граница; без границы было бы 0.5).
- **AC-5.3** Given ажиотаж 1.357, репутация 80 (R = 1.18) и множитель `ms.launch_hype` 1.2, When считается `Get("popularity.gain")`, Then произведение 1.92 (в пределе); при добавлении ещё ×1.3 итог 2.0 и `Explain` показывает «(ограничено)».

#### Additional Details
- **Complexity**: Medium
- **Dependencies**: FR-1–FR-3; канал `popularity.gain` (`perCompany`, `perCpu`, `perSegment`), патч P5 `mod-framework`
- **Assumptions**: единый патч фреймворка на `Market.UpdatePopularities` умножает положительный дневной прирост популярности CPU на `M(popularity.gain, company, cpu, k)`. Затухание старых CPU не затрагивается.

### FR-6: Репутация бренда — изменения и игровой эффект

**User Story:** Как игрок, я хочу, чтобы череда сильных продуктов создавала моей компании репутацию, которая помогает новым продуктам, а провалы её подтачивали, чтобы долгая стратегия качества окупалась.

**Priority**: Must

#### Acceptance Criteria
1. WHEN обзор опубликован THEN мод SHALL вызвать `ModReputation.Add(company, Δ, "press.review:<SaveID>")` с `Δ = clamp(round((M − 65)/5), −6, +6)`.
2. WHILE фича включена, провайдер канала `popularity.gain` SHALL возвращать для CPU каждой компании (игрока и ИИ) `R × H`, где `R = 1 + 0.3 × (rep − 50)/50` (от 0.7 до 1.3), `rep = ModReputation.Get(company)`, а `H` — ажиотаж CPU (FR-5; 1.0, если обзора нет). Максимальный вклад фичи в канал — от 0,7 × 0,6 = 0,42 до 1,3 × 1,5 = 1,95; итог на CPU ограничивает ядро.
3. WHEN наступает 1-е число месяца THEN репутацию каждой не обанкротившейся компании к 50 на 3 % разницы сдвигает ядро (`ModReputation.Drift`, `reputation.driftMonthlyRate`; не в перемотку; без записи в историю и без `Changed`). Мод SHALL не вызывать `ModReputation.Add` для дрейфа и не писать причину `press.drift`.
4. WHERE в `ModSettings` выключено «Репутация влияет на ИИ» (`reputationAffectsAI`, по умолчанию включено), мод SHALL регистрировать множитель только для компании игрока.
5. WHEN другие фичи меняют репутацию (например, `design-flaw-recalls`) THEN эффект п. 2 SHALL учитывать новое значение со следующего дня без участия этой фичи.

#### Сценарии
- **AC-6.1** Given репутация игрока 50 и обзор 90, When он публикуется, Then репутация 55, множитель популярности всех CPU игрока 1.03.
- **AC-6.2** Given репутация 80, When проходит месяц без обзоров, Then репутация 79.1 (дрейф ядра), а в `ModReputation.History` новых записей нет.
- **AC-6.3** Given репутация Intel 70, Then все CPU Intel набирают популярность с множителем 1.12.

#### Additional Details
- **Complexity**: Medium
- **Dependencies**: `ModReputation`, канал `popularity.gain` (mod-framework); FR-1–FR-3
- **Assumptions**: `ModReputation` хранит float 0…100 по ключу компании (`"player"` / `"ai:<UniqueID>"`), по умолчанию 50, даёт `Get`, `Add` с клипом, `Drift`, `History` (последние 50 записей `Add`/`Set`) и событие `Changed` (только от `Add`/`Set`).

### FR-7: Отображение репутации

**User Story:** Как игрок, я хочу видеть свою репутацию и репутацию конкурентов, её динамику и причины изменений, чтобы понимать, что на неё влияет.

**Priority**: Must

#### Acceptance Criteria
1. WHEN игрок открывает окно «Пресса» → вкладка «Репутация» THEN мод SHALL показать таблицу компаний (игрок первым):
   - текущая репутация и её уровень: «Культовый бренд» ≥ 80, «Уважаемый» 65–79, «Обычный» 36–64, «Сомнительный» 21–35, «Токсичный» ≤ 20;
   - изменение за 12 месяцев;
   - эффект на популярность (`×1.12`);
   - три последних причины изменения.
2. WHEN открыт хаб «Моды» THEN мод SHALL показывать строку «Репутация: <значение> (<уровень>)» для компании игрока.
3. WHEN другая фича вызывает `PressReviewsApi.FormatReputation(company)` или `GetReputationLevelKey(company)` THEN мод SHALL вернуть локализованную строку или ключ уровня.
4. WHEN нужно показать изменение за 12 месяцев и причины THEN мод SHALL брать их из `ModReputation.History(companyKey)`. Свои копии истории фича не хранит. Ядро не записывает дрейф в историю, поэтому в ней только значимые изменения (`Add`/`Set`).

#### Сценарии
- **AC-7.1** Given репутация игрока 68 при 60 год назад, When открыта вкладка «Репутация», Then строка игрока «68 Уважаемый, +8 за год, ×1.11».

#### Additional Details
- **Complexity**: Medium
- **Dependencies**: FR-6; `ModUI`, `ModL10n`
- **Assumptions**: причины изменений других фич приходят в `ModReputation.History` строкой `reason`, начинающейся с ключа L10n их фичи (`press.*`, `dfr.*`, `rec.*`, `acq.*`) или `event:<id>`. Фича переводит известные причины в текст, неизвестные показывает как «прочее».

### FR-8: Годовые рейтинги прессы

**User Story:** Как игрок, я хочу 1 января узнавать «Процессор года» в каждом сегменте, «Компанию года» и «Разочарование года», чтобы у меня была цель и повод гордиться.

**Priority**: Must

#### Acceptance Criteria
1. WHEN наступает 1 января THEN мод SHALL подвести итоги по обзорам, опубликованным в прошедшем году:
   - «Процессор года» в каждом сегменте — максимальная метаоценка ≥ 75;
   - «Компания года» — максимальная средняя метаоценка при ≥ 2 обзорах;
   - «Разочарование года» — минимальная метаоценка < 45.
2. WHEN итоги подведены THEN мод SHALL начислить репутацию: +4 за каждый «Процессор года», +3 «Компании года», −3 за «Разочарование года» (`ModReputation.Add` с причинами `press.award:*`).
3. WHEN итоги подведены THEN мод SHALL отправить письмо «Итоги года прессы <год>» (приоритет `Normal`, `Tag` = `press:awards:<year>`) с таблицей победителей и сохранить итоги в архив.
4. IF за год нет ни одного обзора THEN мод SHALL не отправлять письмо.

#### Сценарии
- **AC-8.1** Given в 1995 году CPU игрока получил 88 в High End (лучший), When наступает 1996-01-01, Then письмо с «Процессор года High End — <CPU игрока>», репутация игрока +4.

#### Additional Details
- **Complexity**: Medium
- **Dependencies**: FR-1–FR-6; `ModTicks` (фаза `LateYearPassed`), `ModMail`
- **Assumptions**: годовое письмо игры (ID 0) не трогаем: ID письма мода выдаёт ядро (≥ 100000), письма различаются по `Tag`.

### FR-9: Архив обзоров

**User Story:** Как игрок, я хочу листать все обзоры с фильтрами по компании, сегменту и году, чтобы сравнивать продукты и следить за конкурентами.

#### Acceptance Criteria
1. WHEN игрок открывает окно «Пресса» → «Обзоры» THEN мод SHALL показать список обзоров (новые сверху): дата, компания, CPU, сегмент, метаоценка, вердикт.
2. WHEN игрок выбирает фильтр компании, сегмента или года THEN мод SHALL показать только подходящие записи.
3. WHEN игрок выбирает строку THEN мод SHALL открыть карточку обзора (FR-4 п. 2).
4. WHEN архив превышает 2000 записей THEN мод SHALL сжимать самые старые записи до краткой формы (без осей и цитат).

#### Сценарии

- **Assumptions**: нет.

### FR-10: Квартальные заметки прессы

**User Story:** Как игрок, я хочу периодически читать заметки, что сейчас ценит рынок (рост планки производительности, давление цен, важность экономичности), чтобы понимать тренды без формул.

**Priority**: Should

#### Acceptance Criteria
1. WHEN наступает 1 января, 1 апреля, 1 июля или 1 октября THEN мод SHALL выбрать до 2 заметок из `Content/press-reviews/notes.json`, чьи условия выполнены, и отправить их одним письмом «Пресса: обзор рынка» (приоритет `Low`, `Tag` = `press:notes:<yyyy-MM>`).
2. WHEN заметка содержит числа THEN мод SHALL округлять их до качественной формы («около +30 %», «цены падают»). Коэффициенты формул SHALL не раскрываться.
3. IF у заметки кулдаун (по умолчанию 4 квартала) не истёк THEN мод SHALL не выбирать её.

#### Сценарии
- **AC-10.1** Given производительность лидера High End выросла за год на 42 %, When наступает 1 апреля, Then может прийти заметка «Покупатели High End ждут прироста около 40 % в год».

#### Additional Details
- **Complexity**: Low
- **Dependencies**: `ModMail`, `ModContent`
- **Assumptions**: условия заметок (`leaderGrowth`, `medianPriceChange`, `pgaShift`, `segmentFocus`, `reputationTrend`, `newEntrant`) вычисляются этой фичей по данным рынка (рост `Ips` лидеров, медиана цен, доля PGA) и в `ModConditions` не регистрируются; если понадобится, их имена — `press.<name>`.

### FR-11: API для других фич

**User Story:** Как разработчик других модов (`design-flaw-recalls`, `rival-personalities`, `historical-events`, `cpu-architectures`), я хочу подписываться на публикацию обзоров, публиковать статьи и добавлять поправки в обзор, чтобы пресса была общей площадкой.

**Priority**: Should

#### Acceptance Criteria
1. WHEN обзор опубликован THEN мод SHALL поднять событие `PressReviewsApi.ReviewPublished(ReviewRecord)`.
2. WHEN фича вызывает `PressReviewsApi.PublishArticle(PressArticle)` THEN мод SHALL отправить письмо в категории «Пресса» (приоритет `Normal`, `Tag` = `press:article:<n>`) и сохранить статью в архив (вкладка «Статьи» окна «Пресса»).
3. WHEN фича регистрирует `IReviewAdjuster` THEN мод SHALL вызывать его перед агрегацией каждого обзора. Корректировщик может:
   - добавить поправку к оси (−30…+30);
   - добавить поправку к итогу (−20…+20);
   - добавить строку-примечание.
4. WHEN фича вызывает `GetReview(cpuSaveId)` THEN мод SHALL вернуть запись обзора или `null`.
5. IF корректировщик бросает исключение THEN мод SHALL пропустить его поправку, записать ошибку в лог и опубликовать обзор.
6. WHERE включена фича `design-flaw-recalls`, при публикации обзора мод SHALL с шансом `revealChance` из контента (по умолчанию 0.10) вызвать `FlawRegistry.TryReveal(cpuSaveId, DiscoverySource.External)`. Есть ли у CPU скрытый брак, решает сама `design-flaw-recalls`; при `false` ничего не происходит, и брак игроку не раскрывается.
7. WHEN `FlawRegistry.OnFlawStateChanged` сообщает, что брак стал публичным THEN мод SHALL опубликовать статью «Пресса: дефект в <CPU>» (как `PublishArticle`) и добавить примечание к записи обзора этого CPU, если она есть.

#### Сценарии
- **AC-11.1** Given `design-flaw-recalls` регистрирует корректировщик −15 к итогу для CPU с известным браком, When публикуется обзор такого CPU, Then метаоценка на 15 ниже, в карточке примечание «Пресса знает о дефекте».
- **AC-11.2** Given у CPU есть скрытый брак и бросок `revealChance` успешен, When публикуется обзор, Then `TryReveal` возвращает `true`, `design-flaw-recalls` переводит брак в публичный и приходит статья прессы о дефекте.

#### Additional Details
- **Complexity**: Medium
- **Dependencies**: FR-1–FR-4; `design-flaw-recalls` (`FlawRegistry`, мягко)
- **Assumptions**: связь с `design-flaw-recalls` подключается на `ModTicks.GameReady` и при `ModFeatures.StateChanged`, а не в `Register`.

### FR-12: Сохранение, загрузка и выключение

**User Story:** Как игрок, я хочу, чтобы обзоры, очередь, ажиотаж и итоги переживали сохранение и загрузку, а выключение мода не ломало сейв.

**Priority**: Must

#### Acceptance Criteria
1. WHEN игра сохраняется THEN мод SHALL записать в секцию `press-reviews` `ModSave` (версию секции `_schema` пишет ядро; поля версии в данных фичи нет):
   - очередь обзоров (включая накопленные продажи по сегментам);
   - записи обзоров;
   - итоги лет;
   - статьи;
   - кулдауны заметок;
   - годовые снимки рынка для заметок;
   - месяц последнего дайджеста.
2. WHEN сейв загружается THEN мод SHALL восстановить состояние (`ModSave.AfterRead`). Провайдер `popularity.gain` регистрируется один раз при регистрации фичи и после загрузки читает восстановленные обзоры.
3. IF секции нет (старый сейв) THEN мод SHALL начать с пустого архива. Уже выпущенные CPU обзоров не получают.
4. WHEN фича выключается посреди партии THEN её вклад в канал SHALL прекратиться (ядро не применяет вклады выключенной фичи; провайдер остаётся зарегистрированным и не пересоздаётся), публикации SHALL остановиться, секция SHALL сохраниться без изменений. Значения `ModReputation` SHALL остаться: ими владеет ядро.
5. IF мод удалён THEN сейв игры SHALL загружаться ванильно.

#### Сценарии
- **AC-12.1** Given очередь из 2 обзоров, When сохранение и загрузка, Then оба обзора публикуются в свои даты.
- **AC-12.2** Given фича выключена, When проходит день, Then популярность растёт по ванильной формуле (множители сняты).

#### Additional Details
- **Complexity**: Medium
- **Dependencies**: `ModSave` (решение 0004), `ModSettings`
- **Assumptions**: нет.

## Non-Functional Requirements

### NFR-1: Производительность
- WHEN проходит игровой день THEN фича SHALL тратить в среднем ≤ 0.2 мс: учёт продаж очереди, пересчёт ажиотажа, выдача множителей каналам (300 CPU, 13 компаний).
- WHEN публикуется обзор THEN расчёт SHALL занимать ≤ 2 мс (выборка эталонов по ~1000 CPU).
- WHEN фреймворк запрашивает множитель канала для CPU THEN ответ SHALL быть O(1) (словарь по `SaveID`, кэш на день).

### NFR-2: Надёжность
- IF в обработчике, тике, корректировщике или UI фичи возникает исключение THEN мод SHALL перехватить его на границе (`ModHooks.Guard`), записать в `ModLog` и не пропустить в код игры. Обзор, на котором произошла ошибка, откладывается на следующий день, максимум 3 попытки, затем отменяется. Собственных счётчиков ошибок фича не ведёт.
- IF контент изданий пуст или битый THEN мод SHALL использовать одно встроенное издание-заглушку (`fallback`) и записать ошибку.

### NFR-3: Совместимость сейвов
- WHEN мод добавлен в партию, удалён или выключен THEN сейв SHALL загружаться. В классы игры поля не добавляются.
- WHEN версия секции меняется THEN мод SHALL мигрировать её в `Read(section, schema)` по версии, которую передаёт ядро (`_schema`). Секция новее мода обрабатывается ядром (значения по умолчанию и passthrough).

### NFR-4: Локализация
- WHEN показываются названия изданий, вердикты, цитаты, письма и окна THEN мод SHALL брать строки из `ModL10n` (ru по умолчанию, en обязателен), ключи `press.*`.

### NFR-5: Удобство
- WHEN игрок читает обзор THEN каждая ось SHALL быть подписана словом и числом, а эффекты — в понятной форме («+4 к репутации», «популярность растёт быстрее на 36 % в течение года»).
- WHEN приходит письмо обзора THEN оно SHALL не открывать окна само и не ставить паузу.
- Формулы и коэффициенты в UI SHALL не раскрываться. Объяснения — качественные.

## Edge cases

- **Рынок пуст (1971, только Intel и Texas Instruments).** Эталонов нет → сравнение с предыдущим CPU компании → «без аналогов» (70).
- **CPU игрока продаётся только по контрактам** (`SellOnMarket` = false). Продаж по сегментам нет → сегмент по цене. Обзор публикуется: у CPU для OEM тоже бывают обзоры.
- **Цена CPU ≤ 0 к дате публикации.** Ось цены = 0, в карточке примечание «цена не объявлена».
- **`PowerConsumption` ≈ 0.** Деление защищено: `max(PowerConsumption, 0.5)`, как клип в `Market.CalculateRatings`.
- **Компания обанкротилась после обзора.** Запись остаётся в архиве. Множители снимаются (CPU сняты с продажи игрой). Репутация заморожена: ядро банкротов не дрейфует.
- **Два CPU игрока в один день.** Два независимых обзора и два письма.
- **Перемотка новой игры.** CPU, выпущенные в перемотке (`duringFastForward = true`), не рецензируются. Репутация всех компаний на старте 50.
- **Смена года между выпуском и публикацией.** Обзор относится к году публикации (для годовых итогов).
- **Вариант CPU выпущен раньше, чем опубликован обзор базового.** Ажиотаж начинает действовать на вариант с публикации обзора базового CPU.
- **Сложность меняется в процессе** (если игра позволяет). Строгость берётся на дату публикации.
- **Пакетный прогон месяца** (`ModTicks.IsBatchRun`). Обзоры публикуются по дням как обычно, письма откладывает ядро до `BatchEnded`; дайджест 1-го числа не дублируется (`lastDigest`).
- **CPU перенесён `rival-acquisitions` игроку.** Обзор не создаётся (`CpuTransferred`); уже существующая запись обзора и ажиотаж базового CPU сохраняются за `SaveID`.

## Constraints and Assumptions

### Technical Constraints
- Нельзя патчить `Market.UpdatePopularities` и `Market.CalculateRatings` из этой фичи. Единственный патч формул — в `mod-framework`, фича только регистрирует множители каналов.
- Фича не патчит `Company.AddCpu` и `AICompany.AddCpu` (`ModHooks` отклонит патч, фича станет Unavailable): выпуск CPU берётся из `ModEvents.CpuReleased`.
- Классы `Review` (пространство имён `ProcessorTycoon.PopupSystem`) и `ReviewWindow` в игре — пустые заглушки. UI строится заново через `ModUI` (решение 0005).
- Поля в `CpuBase` не добавляем (вопреки предложению в IDEAS). Всё — в `ModSave`, ключ — `SaveID` CPU.
- `JsonUtility` не сериализует словари: состояние в списках.
- Код `Logic` — общее подмножество API .NET Framework 4.8 и mscorlib Unity (без `init`, `record`, `Index`, `Range`).
- Вклад в общие пределы: `popularity.gain` — от ×0,42 до ×1,95 на CPU (репутация ×0,7…1,3 и ажиотаж ×0,6…1,5), итог ограничивает ядро [0,5; 2,0]; `market.rating.cpu` — вклада нет.

### Business Constraints
- Все числа (темпы эпох, веса, строгость, кривые, эффекты) — в `Content/press-reviews/review-config.json`.
- Вымышленные названия изданий: никаких реальных брендов СМИ. Названия компаний в текстах — реальные, как в русификаторе (Intel, AMD и т. д.); в контенте компании указываются по ключам `player` / `ai:<UniqueID>`.

### Assumptions
- `ModReputation` существует в ядре с API `Get`, `Add`, `Drift`, `History`, событием `Changed`, клипом 0…100 и значением по умолчанию 50 (mod-framework/design.md).
- Канал `popularity.gain` в `mod-framework` поддерживает области «компания», «CPU» и «сегмент» и читается одним патчем P5 на `Market.UpdatePopularities`. Новых каналов эта фича не объявляет.
- `MarketDataProvider.MostSoldCpus` корректно работает с периодом 3 месяца (исключает текущий месяц).

## Glossary

| Термин | Определение |
|------|------------|
| Обзор | Запись оценки CPU: оси, оценки изданий, метаоценка, вердикт, эффекты |
| Ось | Один аспект оценки: производительность, цена/производительность, энергоэффективность, нагрев |
| Эталон | CPU другой компании из топ-5 продаж сегмента, с которым сравнивают |
| Приведённый IPS | `Ips` эталона, умноженный на `g^(τ × возраст)`: где был бы эталон, если бы шёл в ногу с прогрессом |
| Метаоценка | Среднее оценок изданий, 0–100 |
| Вердикт | Словесная категория метаоценки |
| Ажиотаж (hype) | Временный множитель прироста популярности конкретного CPU по итогам обзора |
| Репутация бренда | Значение `ModReputation` компании 0–100; через канал `popularity.gain` влияет на прирост популярности всех её CPU |
| Строгость | Множитель ожиданий по уровню сложности |
| Корректировщик | Зарегистрированный другой фичей объект, вносящий поправки в обзор до публикации |
| Дайджест | Ежемесячное письмо `Low` со сводкой обзоров CPU соперников за прошлый месяц |
| Балансовый диапазон | Предел [0,5; 2,0] на произведение вкладов всех фич в канал для одного CPU; ставит ядро |
