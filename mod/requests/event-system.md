# Запросы фичи event-system к итоговому интегратору

Папка `mod/src/PTMod/Features/EventSystem/Api/` (публичный API движка) готова: `python mod/build_feature.py event-system` собирается без ошибок и предупреждений. Чужие файлы не менялись; ниже то, что нужно сделать вне `Api`.

## 1. Чистые типы Api/Model должны попасть в сборку тестов

В `Features/EventSystem/Api/Model/` лежат чистые публичные типы, которые нужны и потребителям (`market-shocks`, `design-flaw-recalls`, `historical-events`, `rival-personalities` собираются с одной лишь папкой `Api`), и чистой логике движка (`Features/EventSystem/Logic/**`): `EventDefinition` (+ `EventTrigger`, `EventTargetSpec`, `EventChoice`, `EventEffect`), `IEffectParams`, `FloatRange`, `EventInstanceDto`, `ChoiceOptionDto`, `AppliedEffect`, `EventLogEntry`, `EffectRecord`, `EventInstance`, `EffectText`, `EventFireContext`, `EventFireResult`, `PackOptions`, `ChoiceOption`, `IEffectModifiers`, перечисления и классы строковых констант (`EventInstanceKinds`, `EventInstanceStates`, `AppliedEffectStates`, `EventLogKinds`, `EventCompanyKeys`, `EffectParamKeys`, `EffectScopes`).

Файлы чистые: только `PTMod.Core.*` из `Core/Logic` (`LocText`, `ICondition`, `IContentRecord`, `JsonObject`, `CompanyKey`), без Unity, Harmony и `Assembly-CSharp`. Проверено компиляцией `Core/Logic` + `Core/Compat` + `Api/Model` с `build.framework_references()` (.NET Framework 4.8): ошибок нет.

Но `build.py --tests` и `build_feature.py <slug> --tests` собирают только `Core/Logic`, `Core/Compat`, `Features/*/Logic` и тесты, поэтому в тестовой сборке `Api/Model` не видно, а логика (агрегатор вкладов, формулы денег, лотерея, цепочки, сохранение) работает именно с этими типами.

Просьба: в `build.py` (`build_tests`) и в `build_feature.py` (`build_feature_tests`) добавить в список папок `Features/<Pascal>/Api/Model` (если папка есть). Правило как для Logic: файлы в `Api/Model` не ссылаются на Unity, Harmony и `Assembly-CSharp`; желательно проверять это и в архитектурном тесте `LogicSources_DoNotReferenceUnityOrTheGame`. Те же файлы нужны фичам `design-flaw-recalls` и остальным, у которых есть `Api/Model` (запрос там тот же).

Пока этого нет: агентам, пишущим `Logic/**`, можно строить логику на примитивах (`float`, `int`, `string`) и держать работу с `AppliedEffect`/`EventInstanceDto` в слое, который не собирается в тестах.

**Обход, который применён в куске 1 (TSK-001..003).** Логика загрузки (`DefinitionMapper`, `ContentValidator`, `PackCatalog`) работает именно с `EventDefinition`, `EventEffect`, `IEffectParams`, `PackOptions` и константами, поэтому ей нужны эти типы в тестовой сборке. Копии пяти файлов лежат в `mod/tests/PTMod.Tests/Features/EventSystem/ApiModelShim/` (`EventDefinition.cs`, `EventEnums.cs`, `EffectParams.cs`, `EventConstants.cs`, `PackOptions.cs`): побайтно те же файлы из `Api/Model`, компилируются только в тестовую сборку (в `PTMod.dll` их нет, там остаются оригиналы). Тест `ApiModelShimTests.ShimFiles_AreIdenticalToApiModel` (в `ApiModelContractTests.cs`) падает, если оригинал изменили, а копию не обновили. Следующим кускам, которым нужны другие файлы `Api/Model` (`EventInstanceDto`, `AppliedEffect`, `IEffectModifiers`, `EventFireContext`...), достаточно скопировать их туда же и добавить имя в список `Files` этого теста.

**Что сделать интегратору, когда правка в `build.py` / `build_feature.py` сделана:** удалить папку `ApiModelShim/` и класс `ApiModelShimTests` (иначе в тестовой сборке будет CS0101: тип объявлен дважды); остальные тесты менять не нужно. Архитектурный тест `EveryPublicLogicType_IsListedInCovers` после правки потребует `[Covers]` для всех публичных типов `Api/Model`: типы пяти скопированных файлов уже указаны в `ApiModelContractTests`, для остальных (`EventInstanceDto`, `AppliedEffect`, `EventLogEntry`... ) тесты напишут куски, которые к ним обращаются (или `[Covers]` добавят при правке). Правило «в `Api/Model` нет Unity, Harmony и `Assembly-CSharp`» стоит добавить в `LogicSources_DoNotReferenceUnityOrTheGame`.

Адаптер `IEffectParams` над `JsonObject` и `DefinitionMapper` пишет реализация (в `Model/`/`Logic/`, не в `Api`) |

| TSK-014 `EventBus`, `EventEffects`, `EventAi`, `PackOptions` | статические фасады в `Api/EventBus.cs`, `Api/EventEffects.cs`, `Api/EventAi.cs` (см. раздел 3) |
| TSK-019 `Log/EventLog.cs` | статический фасад `Api/EventLog.cs`; хранилище журнала и окно пишет реализация под другим именем (например `EventLogStore`) |

## 3. Как реализация подключается к API

Статические классы (`EventBus`, `EventEffects`, `EventAi`, `EventRegistry`, `EventLog`) не хранят данных: они вызывают `EventSystemApi.Instance` (интерфейс `IEventSystemApi`). Пока реализации нет, там `NullEventSystemApi`: запросы отвечают `null`/пустым списком, `EventBus.Fire` возвращает `Disabled`, регистрации до `Install` запоминаются и проигрываются по порядку при установке (порядок `Register` фич не важен).

Реализация обязана:

1. Написать класс, реализующий `IEventSystemApi` (регистрация паков, таблица обработчиков эффектов с правилом «повторная регистрация типа — предупреждение, первая остаётся», цепочка выборщиков ИИ по убыванию приоритета, `Fire`, `ApplyDirect`, журнал, окно журнала), и вызвать в `EventSystemFeature.Register` `EventSystemApi.Install(backend)` до собственных `EventEffects.Register`/`EventRegistry.RegisterPack`/`EventConditions.Register` (иначе они всё равно сработают, но через очередь).
2. Поднимать события шины через внутренние методы: `EventBus.RaiseEventFired(EventInstance)`, `EventBus.RaiseChoiceResolved(EventInstance, string choiceId, bool auto)`, `EventBus.RaiseEffectExpired(AppliedEffect)`. Они идут через `ModHooks.Raise`: подписчик выключенной фичи пропускается, исключение подписчика считается на его фичу, следующий подписчик вызывается (AC-6.2).
3. Не вызывать `IEventSystemApi.Fire`/`ApplyDirect`/`OpenLogWindow` самой: фасады вызывают их только при `EventSystemApi.IsActive` (реализация установлена и `ModFeatures.IsActive("event-system")`), иначе возвращают `Disabled` / `null` / ничего не делают. Запросы и регистрации (`GetDefinition`, `GetDefinitions`, `GetEffectHandler`, `GetEffectTypes`, `GetLogEntries`, `RegisterPack`, `RegisterEffectHandler`, `AddChooser`, `RemoveChooser`) доходят до реализации и при выключенной фиче: она хранит регистрации, пока фича выключена. `Fire` для события выключенного пака реализация сама отвечает `EventFireResult.Disabled`.
4. Каждый вызов реализации из фасада обёрнут в `ModHooks.Guard("event-system", "api/…", …)`: исключение реализации не доходит до вызывающей фичи, но считается на `event-system`.

## 4. Отличия от текста design.md

- `EventPredicate`: в комментарии design.md сказано «`ctx.Subject` — компания-цель». У `ConditionContext` ядра есть `SubjectKey` (ключ компании), свойства `Subject` нет. Сигнатура `delegate bool EventPredicate(JsonObject args, ConditionContext ctx)` сохранена, подлежащее читается из `ctx.SubjectKey`.
- Добавлено без изменения сигнатур из спеки: конструкторы `FloatRange(lo, hi)`, `EffectText(key, params args)`, `EventInstance(data, definition)`, значение по умолчанию `path = "$"` у `EventConditions.Parse`, классы строковых констант (список в разделе 1), `EventSystemApi` (`Instance`, `IsInstalled`, `IsActive`, `Install`, `Uninstall`) и `IEventSystemApi`/`NullEventSystemApi`.
- `EventInstance.DaysLeft(today)` = `max(0, deadlineDay - today)`, 0 при `deadlineDay = 0`; `IsPlayer` = `Data.companyKey == "player"`. Больше логики в `Api` нет.
- `PackOptions` движок хранит по ссылке и читает поля при каждом использовании: фича меняет `Severity`/`Frequency` на месте при смене параметра (так используют `market-shocks` и `historical-events`).
- Списки и строковые массивы DTO (`options`, `common`, `args`, `textArgs`, `effects`) по умолчанию пустые, а не `null`; `EventInstanceDto.kind` по умолчанию `Event`, `chosen` и `channel` — пустая строка, `AppliedEffect.chance = 1`, `hit = true`.

## 6. Кусок 1 (TSK-001..003): что готово и как подключается

Готово и проверено тестами (`python mod/build_feature.py event-system --tests`): чтение `JsonObject` в `EventDefinition` (`Logic/Model/DefinitionMapper`, `EffectParams`), хранилище паков с загрузкой (`Logic/Content/PackCatalog`), правила проверки записей (`ContentValidator`, `StandardEffectRules`), `config.json` паков с объединением категорий и пределов каналов (`EventConfig`, `Content/event-system/config.json`). Склейка с ядром лежит в `Features/EventSystem/Content/` и в тестах не участвует: `CoreContentSource` (поверх `ModContent`), `CoreContentEnvironment` (`ModConditions.Parse`, таблица обработчиков, `ModModifiers.IsDeclared`, перечисления `ExpenseOrigin` / `RevenueOrigin` игры), `GamePackCatalog.Create(handlerOf)`, `PackLoader`.

Подключение, которое остаётся за куском с `EventSystemFeature` (TSK-006) и реализацией `IEventSystemApi` (TSK-014):
1. `var catalog = GamePackCatalog.Create(type => <таблица обработчиков движка>)`, `var loader = new PackLoader(catalog)`.
2. `ModTicks.GameReady += loader.OnGameReady` в `Register` и `loader.EnsureLoaded()` в `OnEnabled` (ядро пропускает обработчики выключенной фичи, поэтому при выключенной на старте фиче паки прочтутся при включении).
3. `IEventSystemApi.RegisterPack(packId, folder, options)` → `catalog.RegisterPack(...)`; `GetDefinition(id)` → `catalog.Get(id)`; `GetDefinitions()` → `catalog.All`; планировщику — `catalog.InCategory(id)`, `catalog.Config` (категории, `MaxPendingChoices`, `LogLimit`), агрегатору — `catalog.Config.LimitMin(channel)` / `LimitMax(channel)`.

Решения этого куска, которых нет в `design.md`:
- **Владелец префикса пака.** `RegisterPack` не принимает фичу-владельца, поэтому ID событий пака проверяются по префиксам фичи с id, равным id пака (`event-system` → `es.`, `market-shocks` → `ms.`); если у такого id нет строки в таблице префиксов, берётся фича из `PackOptions.SettingsFeatureId`.
- **Порядок.** Паки читаются по возрастанию id (не в порядке регистрации): порядок событий в `EventRegistry.All` и `InCategory`, а значит и результат лотереи, не зависят от порядка `Register` фич. Категория, заданная в `config.json` двух паков, остаётся у пака с меньшим id (предупреждение в логе).
- **Пределы каналов.** Внутри одного пака побеждает самая точная запись (имя, затем семейство `x.*` с самым длинным префиксом, затем `*`); между паками берётся самый узкий предел (наибольший минимум, наименьший максимум). Иначе `*` [0,25; 4,0] перекрывало бы `production.output` [0,1; 3,0] из `design.md`. Канал, которого не касается ни один пак, получает [0,25; 4,0].
- **Проверка записи.** Событие с выбором обязано иметь `timerDays ≥ 1` и `defaultChoice`; категория обязательна у `DailyChance` и должна быть описана в `config.json` какого-нибудь пака (для остальных триггеров — предупреждение); ID варианта — буквы, цифры, `_`, `-`, без точки и не `common` (он стоит между косыми чертами в `AppliedEffect.id`); неизвестный канал в `params.channel` отклоняет запись и у типов паков (`ModifierRamp`, `ModifierWave`), а не только у `ModifierTimed`. Параметры девяти стандартных типов проверяет `StandardEffectRules` до вызова `IEventEffectHandler.Validate`, обработчикам стандартных типов повторять эти проверки не нужно.
- **Строки лога.** Пропущенная запись даёт `WARN skip '<id>': <причина> (<место>)` (AC-1.2); те же причины попадают в `ContentReport` и в строки `content: …` ядра.

## 8. Кусок 2 (TSK-004..009): что готово и как подключается

Готово и проверено тестами (`python mod/build_feature.py event-system --tests`: 1339 тестов, из них 225 — event-system, все зелёные; `python mod/build_feature.py event-system` — без ошибок и предупреждений): фича `EventSystemFeature`, движок `EventEngine` (реализация `IEventSystemApi`), планировщик дня `Logic/Scheduling/EventScheduler` с `Pacing`, `SchedulerState`, `TargetSelector`, `EventRandom`/`DerivedRng`, предикаты `es.*` (`Logic/Conditions/BuiltinPredicates`, `EventHistory`, `ActiveEventIndex`), игровой фасад `Game/GameFacade` и `Game/CompanyDirectory`, часть секции сейва (`Logic/Scheduling/EventSaveSection`, `EventPersistence`), строки `L10n/{ru,en}/event-system.json`.

**Для интегратора.**
1. В `tests/PTMod.Tests/Features/EventSystem/ApiModelShim/` добавлена копия `EventFireContext.cs` (планировщик возвращает `EventFireResult`) и её имя в списке `ApiModelShimTests.Files`. Удаляется вместе с остальными копиями, когда `Api/Model` попадёт в сборку тестов (раздел 1).
2. Остаток TSK-002 сделан: `EventEngine.RegisterPack` / `GetDefinition` / `GetDefinitions` отдают `PackCatalog`, `ModTicks.GameReady` → `PackLoader.OnGameReady`, `OnEnabled` → `PackLoader.EnsureLoaded`. Чекбокс TSK-002 в `tasks.md` не мой — его можно закрыть.
3. Файл `Content/event-system/events.json` появится в TSK-025. До этого `CoreContentSource.LoadRecords` при отсутствии встроенного файла пишет одно предупреждение и отдаёт пустой список вместо ошибки `ModContent`: переопределение без встроенного файла ядро всё равно не применяет.
4. После проверки `build_feature.py event-system` файл `build/features/event-system/PTMod.dll` удалён: архитектурные тесты `BuiltDll_*` сверяют его со всеми папками `Content/` и `L10n/` и падают на сборке одной фичи (без него они пропускаются).

**Как подключаются следующие куски.**
1. Экземпляры (TSK-010): реализовать `ISchedulerRuntime` (`ExpireEffects`, `TickEffects`, `RunDeadlines`, `Fire(FiringPlan)` → число созданных экземпляров) и подключить через `EventEngine.SetRuntime(...)`. До этого стоит `DryRunRuntime`: срабатывание пишется в лог один раз на событие, ничего не создаётся, откат и история не тратятся. `FiringPlan.Expand()` раскладывает эффекты: `scope: "Global"` — только на первый экземпляр группы (D8), выборы — на каждый. Генератор экземпляра — `EventRandom.ForInstance(id)`. Рантайм обязан вести `EventHistory.Active` (`ActiveEventIndex.Set/Remove`): по нему планировщик считает ожидающие выборы игрока (`maxPendingChoices`) и активные события категории (`maxActive`), а `es.activeInCategory` видит активные события (после загрузки индекс строится заново из экземпляров, он не сохраняется).
2. Выборы (TSK-016): `EventHistory.RecordChoice(eventId, choiceId, companyKey, day)` — источник `es.choiceMade`.
3. Цепочки (TSK-013): `FireEvent` → `EventScheduler.Fire(eventId, new EventFireContext { DelayDays, CompanyKey, ParentInstanceId, IgnoreConditions = true })`, задержка кладётся в `State.Scheduled`; флаги — `EventHistory.SetFlag/ClearFlag` (`es.eventFlag`).
4. API (TSK-014): `IEventSystemApi.Fire` уже идёт в `EventScheduler.Fire`. В `EventEngine` есть таблица обработчиков эффектов (повторная регистрация типа — предупреждение, первый остаётся) и цепочка выборщиков ИИ по убыванию приоритета (`Choosers`); `ApplyDirect`, журнал и его окно пока отвечают «ничего».
5. Сохранение (TSK-021): секцию `event-system` держит чистый `EventSaveSection` (`ISideFileParticipant`) за тонким `EventPersistence`. Ключи: `lastProcessedDay`, `scheduled`, `cooldowns`, `categories`, `firedOnce`, `flags`, `edges` — как в примере design.md, плюс `deferred` (очередь за лимитом выборов), `fired` и `choices` (память `es.eventFired` / `es.choiceMade`). TSK-021 добавляет `instances`, `active`, `log` и `nextInstanceId`, сохраняя эти ключи.
6. Подписки, которые ещё не сделаны (в `EventSystemFeature.Host.SubscribeCoreEvents`): `ModTicks.BatchEnded` (TSK-018/022), `ModMail.Delivered` и `ModMail.RegisterChoiceHandler` (TSK-017), `ModFeatures.StateChanged` (заморозка вкладов пака, TSK-011/023; планировщик сам читает состояние выключателя пака каждый день), `ModL10n.LanguageChanged` (TSK-019); `ctx.HubPage` (TSK-023). Параметры `frequency`, `pauseAllChoices`, `rivalNews` объявлены уже сейчас.

**Решения этого куска, которых нет в design.md.**
- **День** — целые дни от 1971-01-01 (`EventDays`); `ModTicks.Today` без даты (вне сцены) день не обрабатывает; один и тот же день дважды не обрабатывается (`lastProcessedDay`).
- **hash32** производных генераторов — правило сида потоков `ModRandom`: `WorldSeed XOR FNV-1a(UTF-8)` над `event-system/inst/<instanceId>` и `event-system/trg/<eventId>/<day>`, затем xoshiro128** ядра (`Xoshiro128`).
- **Лотерея.** Категории берутся в порядке объединённого `config.json` (паки по id, затем файл), если в категории есть хотя бы одно событие `DailyChance`; три числа дневного потока каждой такой категории тратятся каждый день, и при частоте «Выкл», и при замороженном паке, и при неподходящих событиях.
- **Веса** действуют для `RandomAI`, `RandomCompany` и `AllCompanies` (компания без линий при `FactoryCapacity` не входит и в группу); `Player`, `Specific` и компания, названная вызывающим, не взвешиваются.
- **`IgnoreConditions`** пропускает `conditions` и откат; фильтр `targets.filter` пропускается только вместе с названной компанией (иначе он задаёт круг кандидаток).
- **Лимит выборов для группы.** Если в группу `AllCompanies` с выбором входит игрок с полным лимитом, ждёт всё срабатывание (лотерея пропускает день, другие триггеры ставят в очередь).
- **`Date`.** В пределах `graceDays` триггер пробует каждый день, пока не найдётся цель (условия, фильтр); сработав или встав в очередь, событие помечается в `firedOnce`. **`Condition`** с `edge` хранит уровень в `edges`; пока срабатывание стоит в очереди, событие не проверяется.
- **Очередь** (`deferred`) — до 30 дней, потом срабатывание отбрасывается со строкой в логе; отложенные `scheduled` замороженного пака ждут его включения.
- **`minGapDays`** считается от любого срабатывания события категории (лотерея, дата, условие, `Fire`); **`maxActive`** считает группы, а не экземпляры.
- **`es.eventFired`** читает историю срабатываний по компаниям (для группы — по каждой компании группы); `withinDays = N` — истинно, если `today − lastDay ≤ N`.
- **Сбои.** Каждый сбой шага или события уходит в `ModHooks.ReportFault("event-system", "scheduler/<шаг>[/<eventId>]")`; событие, упавшее 3 раза, выключено до конца сессии (NFR-2).

**Ядро.** Недостающего в ядре нет.

Индекс в `id` эффекта (`<id>/<choice|common>/<index>`) — место эффекта в определении (у неглавных экземпляров группы глобальных эффектов просто нет), поэтому по `id` находится `EventEffect` для `Apply`.
- **Пределы канала** применяются и к не-`scalable` `ModifierTimed` / `FactoryOutput` / `MarketDemand` (с `Severity = 1`): показанное число всегда равно применённому. `MarketDemand` с `segment: all` пишет `channel = "market.demand.*"` и вкладывается в четыре канала сегментов; зажим — по самому узкому из них.

- **`global`** для `Popularity` и `Reputation` — все живые компании; для `Money` и `ResearchProgress` — `Skipped`.
- **`Popularity`**: `clamp(p + δ, 0.05, 1.0)`, но значение не сдвигается против знака δ (CPU ниже пола не поднимается падением).
- **`SendMail`**: только игроку (или `global`), для ИИ — `Skipped`; тег `es:fx:<id эффекта>` (письмо самого экземпляра — `es:<instanceId>`, поиск по точному тегу их не путает); аргументы — `args` экземпляра; отказ `ModMail.Send` — эффект `Failed`.
- **`FireEvent`** всегда ставит запись в `scheduled` (`dueDay = today + delay`, задержка тянется при `Resolve`) и никогда не срабатывает внутри `Apply`; задержка 0 срабатывает в следующий обработанный день. Глубина: `FireEvent` экземпляра глубины 8 — `Skipped`; `EventBus.Fire` с `ParentInstanceId` берёт глубину живого родителя + 1.
- **Решение ИИ** (до TSK-016): цепочка `EventAi` (`AiChooserChain`: фильтр `IEventAiChooserFilter`, первый ответ с доступным вариантом, исключение — `null` и сбой фичи владельца по `ModFeatures.FeatureOfType`), иначе `defaultChoice` — в день срабатывания. Политику по умолчанию `aiWeight` + `aiMinCashMultiple` добавит TSK-016 в `EventEngine.DecideForAi`.
- **Дедлайн** (до TSK-016/017): `EffectRuntime` закрывает ожидающий экземпляр `defaultChoice` при `today ≥ deadlineDay` (`EffectRuntimeOptions.DeadlineDue` — точка подмены). Писем ещё нет, поэтому выбор игрока сейчас всегда истекает по таймеру.
- **`ApplyDirect`** пишет в журнал `Fired` с `eventId = sourceId`, но `EventBus.OnEventFired` не поднимает (это не срабатывание события).
- **Шина.** `OnEventFired` — после применения `common`, `OnChoiceResolved` — после эффектов выбора и журнала, `OnEffectExpired` — после снятия вклада. Исключение слушателя ловится и в рантайме (`bus/<имя>`), поверх изоляции `ModHooks.Raise`.

**Для интегратора.**

**Наблюдения о ядре (желательно исправить, обход есть).**
- **`ModSave.OnFeatureStateChanged` → `Restore` для фичи, которая уже держит состояние.** Горячее выключение и включение фичи (`SupportsHotToggle`) снимает её с `Handed` (`Handed.Remove`), а при включении `Restore` отдаёт участнику результат `RestoreParticipant`: сохранённый текст секции (если после загрузки был хотя бы один сейв, `_retained` хранит последний `Write()`) или, когда его нет, `ResetToDefaults`. Для фичи, которая работала с момента `GameReady`, это старее или пустее её состояния в памяти: замороженные эффекты (AC-11.1) пропали бы. Обход: `SessionGate` игнорирует выдачу после `GameReady`, пока состояние привязано к игре. Желательно в ядре: не вызывать `Restore` для участника, который получил данные в этой сцене (или не снимать его с `Handed` при выключении в игре).
- **Секция фичи, выключенной в игре, может пропасть из файла.** После успешного `Read` модель удаляет секцию из `_retained` (`SideFileModel.ReadSection`), а `BuildSection` для неактивного участника отдаёт только `_retained`. Если игрок выключил фичу после загрузки и сохранился, не сохранившись до этого с включённой фичей, секции в файле не будет, и состояние событий потеряется (FR-11 п. 2 «запись в сейве осталась»). Обхода нет: фиче не дают записать секцию, пока она выключена. Желательно: при `StateChanged` (не `Enabled`) один раз вызвать `Write()` участника и положить результат в `_retained`, либо не удалять `_retained` после `Read` для секции, которую ещё не собирали.
- **Паки фич, выключенных в момент загрузки.** `Register` вызывается только у включённых фич, поэтому пак выключенной фичи (`market-shocks`, `historical-events`...) не зарегистрирован, и его сохранённые экземпляры при `GameReady(Loaded)` отменяются по FR-10 п. 4 (письмо закрывается, эффекты пропадают). Заморозка из D10 действует только в пределах одной сессии. Если владелец хочет сохранять такие экземпляры, ядру пришлось бы регистрировать паки (или хотя бы их id и префиксы) и у выключенных фич.

**Решения этого куска, которых нет в design.md.**
- **Шлюз `SessionGate`.** Выдача секции ядром до `GameReady` (загрузка, новая игра, меню) принимается всегда. Выдача после `GameReady` игнорируется, пока состояние привязано к игре (`EventRuntime.OnGameReady` привязывает, `PTModHost.SceneLeaving` снимает). Фиче, которая была выключена в момент `GameReady` (обработчик ядро пропустило), секция приходит при включении; шлюз отмечает «поздние данные», и по `ModFeatures.StateChanged` для самой фичи (или в первый обработанный день) `EventRuntime.CompleteLateStart` делает то, что сделал бы `GameReady` (причина берётся из `ModTicks.ReadyReason`).
- **Время, когда движок не работал, не списывается с игрока.** Выключение: день запоминается (`OnDisabled`), при включении дедлайны ожидающих выборов игрока сдвигаются на разницу дат (`ChoiceController.ShiftDeadlines`). После загрузки сдвиг равен разнице между сегодня и `lastProcessedDay` сохранённого состояния: после обычного сейва это 0 (автосейв 1 января идёт после дневного тика фичи), после секции, записанной до выключения фичи, — число дней, когда движок не работал. Эффекты не сдвигаются: их даты окончания абсолютны (AC-11.1).
- **Выбор замороженного пака стоит.** `ChoiceController.DeadlineDue`: пока пак заморожен, дедлайн его ожидающего выбора игрока двигается на +1 за каждый обработанный день и ничего не истекает (так же, как в пакетном прогоне). Отдельного списка замороженных паков в сейве нет (в примере `design.md` был `suspendedPacks`): заморозка — состояние выключателя, она восстанавливается ежедневной сверкой, а удержание по дням не требует хранить дату начала.
- **Закрытие истёкших эффектов при включении.** `EventRuntime.OnEnabled` и загрузка вызывают `EffectRuntime.ExpireEffects(today)`: эффект, чей срок прошёл, пока фича стояла, закрывается записью в журнале сразу, а не на следующий день, и один лишний день не вкладывается в канал.
- **Новая игра** сбрасывает и планировщик (`SchedulerState`, `EventHistory`), не только рантайм эффектов: после перемотки нет ни экземпляров, ни журнала, ни кулдаунов (FR-10 п. 5, AC-13.1).
- **Диапазоны сейва** (NFR-7), кроме прежних: `SaveChecks.MaxDay` (365 × 930, год 2900), `MaxDurationDays` (36 500 дней), `MaxAmount` (1e12), шанс эффекта вне [0; 1], `lastProcessedDay` вне игровых дат. Дедлайны складываются с насыщением (`BatchGuard.AddDays`), `int.MaxValue` не переполняется.
- **Страница хаба**: параметры рисует сам хаб из `EventParams`; страница фичи добавляет строку «Частота: 0 — Выкл, 1 — Редко (×0,5), 2 — Обычно (×1), 3 — Часто (×1,5).», кнопку «Журнал событий» (закрывает хаб, потому что он модальный, и открывает окно журнала) и, только при `ModSettings.Debug("debug.events")`, прокручиваемый список событий реестра по пакам с кнопкой «Запустить сейчас» (`EventBus.Fire`, цель — игрок, `IgnoreConditions`, сегодня; результат — строка над списком; строка замороженного пака серая). Ключи `es.hub.*` есть в обеих таблицах.

**Как подключаются следующие куски.**
1. TSK-025 (контент и строки): `es.req.*` для предикатов, которые стартовый набор использует в `requires`; ключи `es.hub.*` уже на месте. Тест `AC_11_2_...` в `SettingsTests` читает `events.starter.json` из фикстур; когда появится `Content/event-system/events.json`, его можно проверять так же.

3. TSK-028 (ручная проверка владельцем): сценарии, которых не заменяют тесты, — хаб «Моды» (ползунок частоты, переключатели, пояснение, кнопка журнала), список «Запустить сейчас» в отладочной сборке при `debug.events`, горячее выключение и включение фичи при живом выборе (AC-11.1, AC-11.3), сохранение и загрузка с письмом на экране (AC-10.1, AC-10.3), «Следующий месяц» с ожидающим выбором (AC-13.2).

**Ядро (желательно, не блокирует).**
- **Точка для находок фичи в `ModSelfCheck`.** Задача TSK-026 называет результат «вкладом в `ModSelfCheck`», но у ядра нет места, куда фича добавляла бы находки (так же у `design-flaw-recalls`, `market-shocks` и других). **Решения этого куска, которых нет в design.md.**
- **`requires: researchActive` у варианта `fund` гранта** (`es.university_grant`). Таблица баланса его не называет, но сценарий M11 ждёт серую кнопку «Профинансировать» с «Нужно: текущее исследование», пока исследования нет (запуск из отладочного списка не проверяет условия события). Вариант по умолчанию `decline` без `requires`, как требует FR-1. Условие события `researchActive` остаётся: в обычной игре без исследования событие не сработает.
- **`origin: Development` у `small_booth`** (`es.trade_show`). В таблице у малого стенда источник трат не указан; без него `Spend` шёл бы как `Fines` (штраф), что для выставки неверно. Взят тот же, что у большого стенда.
- **Тексты событий без аргументов и без названий.** Название компании письму даёт строка «Компания: …» (новости о конкурентах), суммы и сроки — строки эффектов письма, так что в `es.<событие>.text` нет `{0}`, нет имён реальных компаний, а текст не зависит от эпохи (годы 1971–2000+).
- **Самопроверка строк смотрит только строки собственного пака** (владелец `event-system`): ключи чужих паков (`ms.*`, `dfr.*`) в таблицах движка не лежат, их проверяет своя фича. Остальное — по всем событиям всех паков (типы, каналы, цепочки, id).
- **Самопроверка может сработать дважды**: на `OnEnabled` при старте сессии (пак движка уже прочитан) и на `GameReady` (прочитаны паки остальных фич, больше типов и событий). Повтор с тем же итогом пишется на уровне `DEBUG`, с другим — новой строкой.
- **Таймер вынимает UI из дня.** Бюджет 3 мс из NFR-1 — «без UI»: письмо, уведомление и окно события строят UI, они внутри `Ui.OnFired` / `OnResolved` / `OnCancelled`, и таймер вычитает их время (в строке оно отдельно: `with the UI`, `ui … in all`). Время `EventUiController.DailyRefresh` в `ProcessDay` не входит вовсе (оно после него в `OnDayPassed`).
- **Замер на логике без игры** проверяет сами числа (0,3 / 3 мс) и повторяется до трёх раз: сборщик мусора или чужой процесс может испортить один день. Приёмка в игре на реальных данных (`CpuDataProvider`, `CompanyFinance`) остаётся за владельцем.
