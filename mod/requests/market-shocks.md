# Запросы фичи market-shocks к итоговому интегратору

Первый кусок (TSK-001, TSK-002, TSK-003): дневной кеш каналов, три читающих патча, формулы и тесты. Второй кусок (TSK-004 … TSK-008): кривые, типы эффектов `ModifierRamp` / `ModifierWave` / `InventoryLoss`, предикаты `ms.sellsBelowCost` / `ms.hasRecentCpu`, тесты. Третий кусок (TSK-009 … TSK-014): класс фичи `MarketShocksFeature`, `config.json`, 21 запись `shocks.json`, строки `ru` / `en`, тесты каталога и строк. Четвёртый кусок (TSK-015 … TSK-017): симулятор баланса и тесты паритета, настройки пака и его выключение посреди игры, самопроверка (раздел 7). Чужие файлы не менялись. От `event-system` используется только его публичный `Api\` (`IEventEffectHandler`, `ITimedEffectHandler`, `ICurveEffectHandler`, `EventContext`, `AppliedEffect`, `IEffectModifiers`, `EventConditions`, `PackOptions`); от ядра — `ModModifiers`, `ModTicks`, `ModFeatures`, `ModHooks`, `ModL10n`, `ModLog`, `ModCompanies`, `ModConditions`-типы как есть.

## 1. Архитектурные тесты `BuiltDll_*` падают после `build_feature.py <slug>` в той же папке

`python mod/build_feature.py market-shocks` кладёт `PTMod.dll` в `mod/build/features/market-shocks/`, и туда же `--tests` кладёт `PTMod.Tests.exe`. `BuiltDll.TryGet` (`tests/PTMod.Tests/Architecture/ArchitectureTests.cs`) берёт `TestEnv.BuildDir/PTMod.dll`; если он свежее исходников, тест `BuiltDll_EmbedsContentAndL10nResources` сверяет ресурсы DLL со **всем** деревом `Content/` и `L10n/`, а фичевая сборка встраивает только ядро и свою фичу (`feature_resources` в `build_feature.py`). Итог: после сборки DLL фичи её же тесты краснеют («files of Content/ and L10n/ that PTMod.dll does not embed: ...»).

Обход, принятый здесь: после проверки сборки файлы `PTMod.dll` и `PTMod.pdb` из `mod/build/features/market-shocks/` удалены, тесты в этом состоянии зелёные (три теста `BuiltDll_*` печатают `skip`).

Просьба: в `BuiltDll_EmbedsContentAndL10nResources` (и по смыслу в соседних) пропускать DLL из `build/features/<slug>/` либо ограничивать ожидаемый набор ресурсов ядром и этой фичей, как делает `feature_resources`.

## 2. Регистрация (сделано в третьем куске, TSK-009)

`MarketShocksFeature.Register` вызывает в порядке design.md: `EventEffects.Register` для `ModifierRamp`, `ModifierWave`, `InventoryLoss`; `ShockPredicates.Register()`; `EventRegistry.RegisterPack("market-shocks", "market-shocks", ShockPack.Options)`; `ctx.Patch` для `MaterialCostPatch`, `WaferCostPatches`, `MemoryDescriptionPatch`; `ctx.Param` для `intensity` и `frequency` (значения сразу попадают в `ShockPack.Options.Severity` / `Frequency` на месте, дальше по `ModSettings.Changed`); `ShockChannels.Attach()`. `OnEnabled` и `OnDisabled` вызывают `ShockChannels.Invalidate()`. `ModModifiers.DeclareChannel` не вызывается (тест сканирует исходники).

- `build.py` теперь добавляет в игру три патча, три типа эффектов, два предиката и пак этой фичи.
- Строка AC-1.1 пишется на `ModTicks.GameReady` по числу событий пака в `EventRegistry.All` (`definition.packId == "market-shocks"`). Если на этот момент движок ещё не прочитал паки (порядок подписчиков `GameReady` не определён), строка пишется через один кадр (корутина `PTModHost.Run`). Если и тогда событий 0 — предупреждение «the event system has accepted none of the events of the pack». Просьба к `event-system`: читать паки в своём обработчике `GameReady`, как в design.md (тогда задержки нет).

## 4. Допущения о контракте с `event-system` (проверить при интеграции)

Движок `event-system` в репозитории пока только в виде `Api\`; обработчики написаны по `event-system/design.md`. Что в них зашито:

1. **`Resolve` возвращает `AppliedEffect` целиком.** Обработчик заполняет `type`, `instanceId` (из `ctx.Instance.Data.id`), `companyKey` (`ctx.CompanyKey`), `channel`, `value`, `curve`, `durationDays` (длина кривой), `chance = 1`, `hit = true`, `state = Pending`, `textKey` / `textArgs` (результат `Describe`). `id`, `startDay`, `endDay`, `group` и бросок `chance` — дело движка. Для `ModifierRamp` / `ModifierWave` движок должен брать `endDay` из `durationDays`, который вернул `Resolve`, а не из `EventEffect.durationDays` (в `shocks.json` его у этих типов нет). Движок не должен второй раз масштабировать `value` / `curve` этих типов по `Severity`: масштаб и зажим пределами канала делает сам обработчик (D15, `IEffectModifiers.LimitMin` / `LimitMax`).
2. **Интенсивность.** Обработчику не передаются `PackOptions` пака. Типы читают `Severity` из `ShockPack.Options`, того же объекта, который фича отдаёт `RegisterPack`. Если `event-system` добавит `Severity` в `EventContext`, переходники (`ModifierRampEffect.CurrentSeverity` и два аналога) перейдут на него одной правкой.
3. **Параметры `scalable` по умолчанию `true`** у `ModifierRamp`, `ModifierWave`, `InventoryLoss` (design.md: «scalable (true)»); общий ключ движка по умолчанию `false`, но эти типы читают ключ сами. В примерах `design.md` (и в записях `shocks.json`, TSK-010 … TSK-013, стоит писать так же) `scalable` указан явно.
4. **Пометка «ограничено» (AC-7.4).** У `AppliedEffect` нет поля «зажато». Обработчик кладёт признак в `curve`: пятое число `1` у рампы и четвёртое у волны, а `Describe` дописывает `ms.fx.clamped` («(ограничено)») к числу пика / амплитуды. Строки письма и журнала поэтому показывают пометку сами. Если движок хочет заполнять `EffectRecord.clamped` в журнале для типов пака, ему нужен либо разбор этого числа, либо необязательный интерфейс вроде `IClampedEffectHandler.WasClamped(AppliedEffect)`; без этого журнал показывает `clamped = false`, письмо и окно эффектов — верный текст.
5. **Испорченная кривая при `Restore`** (пик 10, период 0, не-число): значение не выставляется, вклад снимается через `IEffectModifiers.Clear`, лог `WARN`, `AppliedEffect.state = Failed`. Исключение не бросается, чтобы битый боковой файл не набирал счётчик сбоев фичи (`hooks.faultThreshold`). Если движок после `Restore` перезаписывает `state`, эффект просто остаётся в списке без вклада.
6. **`Tick` в день старта.** `Apply` берёт возраст эффекта как `today − startDay`, если движок уже дал `endDay > 0`, иначе 0; множитель первого дня любой кривой равен 1, так что порядок «движок ставит `startDay` / `endDay` до или после `Apply`» не важен.
7. **Фаза волн.** Одна фаза на `phaseGroup` внутри одного срабатывания держится в `WavePhaseBook` обработчика, ключ — (id экземпляра, день). Каждая волна берёт ровно одно число из `ctx.Rng` (`Value()`), также при фиксированной фазе и при уже известной фазе группы (D5). Для общей фазы все волны экземпляра должны резолвиться подряд в одном экземпляре с одним `ctx.Instance.Data.id`.
8. **`InventoryLoss` и область `Global`.** Для `scope: Global` (`ctx.CompanyKey == "global"`) списание идёт по CPU любых производителей; для `Target` — только по CPU, у которых `Cpu.get_Manufacturer()` — это `ctx.Company` (или компания, найденная `ModCompanies.Resolve(ctx.CompanyKey)`).
9. **Строки.** Добавлены в `L10n/{ru,en}/market-shocks.json` ключи `ms.fx.ramp`, `ms.fx.wave`, `ms.fx.wave.up_first`, `ms.fx.wave.down_first`, `ms.fx.inventory`, `ms.fx.inventory.units` (без суммы, если CPU недоступны), `ms.fx.clamped` и названия каналов `ms.channel.*` для семи каналов, на которые пишут шоки (память, пластины, расходы фабрик, четыре сегмента спроса). Остальные строки пака — TSK-014.

## 5. Контент пака и допущения о контракте с `event-system` (третий кусок)

Проверено: все 21 запись `shocks.json` и `config.json` проходят настоящий `DefinitionMapper` + `ContentValidator` + `PackConfigReader` движка без предупреждений (одноразовая сборка вне репозитория: логика ядра + `EventSystem/Logic` + `ApiModelShim` + логика этой фичи в роли обработчиков `Validate`; 21 событие загружено, 0 пропущено). В репозитории такую проверку на этой сборке положить нельзя: `build_feature.py <slug> --tests` не берёт `Logic` чужой фичи. Поэтому тесты фичи (`ShockCatalogTests`, `ShockTextTests`) проверяют структуру и числа сами, а проверку настоящим валидатором стоит добавить в `PackContentTests` (TSK-015) под полной сборкой.

Допущения, на которые опирается контент (проверить при интеграции):

1. **Аргументы текстов.** `{0}` в `title`, `text`, `cause` — название компании-цели (`ICompany.get_Name`). Только его и используют записи, которые бьют по одной компании (`RandomCompany`: №1–4, №20, №21); у глобальных шоков, групп `AllCompanies` и предупреждений аргументов нет. Доли мощностей в числах в причине нет (design.md в примере `ms.fab_fire.cause` показывает `{1}`, но договорённости, чем движок его заполнит, нет): причина говорит о доле словами. Если движок начнёт отдавать долю мощностей вторым аргументом, её можно будет вписать в `ms.*.cause` двух языков одной правкой.
2. **`maxActive` и `Manual`.** Категории `ms.price` и `ms.demand` имеют `maxActive = 1`, а удар (`ms.dram_spike`, `ms.recession`) — той же категории, что и предупреждение, и запускается `FireEvent` через 21 или 45–75 дней. Нужно, чтобы `maxActive` ограничивал только лотерею категории, а срабатывание `Manual` через `FireEvent` его не блокировало (при выбранном `hedge` предупреждение держит эффект на 180 дней).
3. **`notifyPlayer`.** Стоит только у записей, которые бьют по одной случайной компании (№1–4, №20, №21). У групп `AllCompanies` (№5–7, оба предупреждения) его нет, чтобы одно землетрясение не давало до пяти новостей о ИИ: игрок получает письмо по своему экземпляру, если он среди целей.
4. **`FireEvent`.** `scope: "Global"` и `target: "Player"` — как в design.md: глобальный эффект применяется один раз на группу `AllCompanies`, удар несёт экземпляр игрока. `delayDays` у рецессии — пара `[45, 75]`.
5. **Циклы `ms.cycle`.** `Condition` раз в месяц с откатом, равным длине волны (1460 и 1825 дней), и `maxActive = 2`; следующая волна начинается в первый месячный проход после конца предыдущей. Допущено, что откат считается от дня срабатывания, а не от конца эффекта. Частота пака (`Frequency`) на циклы не действует (у категории `dailyChance = 0`, тип триггера `Condition`): так сказано в подсказке параметра.
6. **`scalable` у `hedge`.** Пример `ms.dram_spike_warning` в design.md не пишет `scalable` у `ModifierTimed` варианта `hedge`, а общее правило каталога — «все эффекты пака `scalable`». Принято правило каталога: расход (`Money`) и выигрыш (×0,95) масштабируются вместе.
7. **`Money` у групп.** У землетрясения (`AllCompanies`) `Money` стоит в `effects` события без `scope`, т. е. платит каждая компания с фабрикой; на глобальный эффект `ModifierRamp` памяти (`scope: Global`) приходится один вклад.
8. **ИИ.** У каждого выбора явно задан `aiWeight` (1); `aiMinCashMultiple` — только у вариантов с тратой денег (`expedite` 3, `rent` 3, `hedge` 4, `lobby` 3). У `ms.recession_warning` оба варианта бесплатные, веса 1 / 1. Стоит ли ИИ чаще брать `expedite` при достатке денег, чем 1:1 — решение `rival-personalities` через `EventAi.AddChooser`.
9. **Настройки.** Ярлыки слайдеров — `ms.settings.intensity`, `ms.settings.frequency` (и `.tooltip`); названия уровней «Мягко / Обычно / Жёстко / Хаос» — `ms.settings.intensity.mild|normal|harsh|chaos` (их использует страница настроек пака, TSK-016).

## 7. Четвёртый кусок: баланс, настройки, самопроверка (TSK-015 … TSK-017)

### 7.1 Правка `config.json`: `ms.industry.dailyChance` 0,0018 -> 0,0035 (нужно обновить `design.md`)

Симулятор баланса (`BalanceSimulationTests`, 20 прогонов по 50 лет с 1971-01-01) показал, что отраслевые шоки при числе из таблицы `design.md` дают 0,28 срабатывания в год, а FR-10.1 и AC-10.1 требуют 0,4 ± 25 % (0,30 ... 0,50). Причина не в лотерее: три отраслевых шока ждут 3650, 2190 и 2190 дней между своими срабатываниями, поэтому категория не может бить чаще 365 · (1/3650 + 1/2190 + 1/2190) = 0,43 в год при любом шансе, а шанс из таблицы (номинально 0,40) использовал из этого потолка лишь 0,28. С 0,0035 категория бьёт 0,34 в год (потолок упирается в откаты; дальнейший рост шанса почти ничего не добавляет: 0,0045 даёт 0,35). Остальные категории при числах таблицы укладываются в ±25 %: `ms.supply` 1,34, `ms.price` 0,85, `ms.demand` 0,33, `ms.trade` 1,08.

Что сделано: `Content/market-shocks/config.json` (одно число) и строка `ms.industry` в `ShockCatalogTests.Config_Categories_AreTheTableOfDesign` (с комментарием). Что нужно от владельца спеки: в `design.md` (таблица «Частоты категорий» и раздел «config.json пака») заменить 0,0018 на 0,0035 и пересчитать колонку «≈ в год» (формула `365 / (1/(dailyChance·F) + minGapDays)` не учитывает откаты событий; для `ms.industry` и `ms.demand` они определяют результат). Копия старого конфига лежит в `mod/tests/PTMod.Tests/Features/EventSystem/Fixtures/config.market-shocks.json` (фикстура тестов `event-system`, не этой фичи; её 0,0018 безвредно).

### 7.2 Симулятор и настоящий движок

- Тесты фичи собираются без `Logic` движка (`build_feature.py` берёт из фичи только свою `Logic`), поэтому `ShockSimulator` (в `mod/tests/PTMod.Tests/Features/MarketShocks/`) — **модель правил** `event-system` (лотерея категории из трёх чисел в день, `minGapDays` от последнего срабатывания любого события категории, `maxActive` по идущим экземплярам, откат события на компанию или `*` у группы, групповые экземпляры, `Condition` раз в месяц, `FireEvent` с задержкой и шансом, фильтр цели `es.activeInCategory`, формулы денег и зажим множителей при `Resolve`), а не его код. Модель сверена построчно с `EventScheduler`, `Pacing`, `TargetSelector`, `ActiveEventIndex`.
- Один раз (вне репозитория, в scratchpad) прогон повторён на **настоящем** движке: `DefinitionMapper` + `ContentValidator` + `PackCatalog` + `EventScheduler` + `BuiltinPredicates` над теми же файлами пака, фальшивый мир и маленький рантайм, который ведёт индекс активных экземпляров. Результат: 21 событие принято, 0 пропущено, 0 предупреждений (проверка валидатором движка вместе с `Validate` типов пака); 200 прогонов по 50 лет, срабатываний лотереи в год: `ms.supply` 1,29, `ms.industry` 0,34, `ms.price` 0,83, `ms.demand` 0,33, `ms.trade` 1,05, циклы 0,42; доля игрока среди 12 879 инцидентов `ms.supply` — 18,5 % при 20 % линий. Те же 200 прогонов модели: 1,31 / 0,34 / 0,85 / 0,33 / 1,08, доля игрока 19,0 % (13 051 инцидент). Расхождение внутри шума (около 0,5 п. п. на долю при погрешности 0,3).
- Разовую проверку настоящим движком в репозиторий положить нельзя: любой тест в `Features/MarketShocks/` компилируется и в сборке одной фичи, где нет `Logic` движка, а тесты вне `Features/` (в `Integration/`) входят в сборку каждой фичи. Если интегратору нужна постоянная проверка, ей нужна папка тестов, которую собирает только `build.py --tests`.
- Что модель говорит о настройке: откат на компанию (1095 дней у трёх из четырёх инцидентов) заметно сдвигает цель от крупных компаний к мелким. Игрок с 20 % линий получает 18,5 ... 19,0 % инцидентов (допуск AC-2.1 / AC-9.1 — ± 2 п. п., запас у настоящего движка около 0,5 п. п.); игрок с 5 % линий среди десяти компаний — 6,0 %. В компании из четырёх (игрок 5 %, три ИИ по 20 ... 45 %) по модели сдвиг уже вдвое (9,5 % вместо 5 %). Если игра когда-либо будет работать с такой малой группой, откаты инцидентов придётся ослабить.

### 7.3 Настройки и выключение (TSK-016)

- `Settings/MarketShocksSettings.cs` объявляет два ползунка и страницу хаба (`ctx.Param`, `ctx.HubPage`), кладёт значения в `ShockPack.Options` (`Severity`, `Frequency`) при объявлении, при включении фичи (`OnEnabled`) и при каждом `ModSettings.Changed` обоих ключей; значения вне сетки (рукой правленный `ptmod_settings.json`) прилипают к ближайшему уровню (`ShockParamSpecs.SnapIntensity` / `SnapFrequency`). Добавлены строки `ms.settings.title` и `ms.settings.now` в оба языка.
- Выключение посреди шока держится на правилах других частей, которые пока не написаны или не запускались: движок замораживает эффекты пака по `PackOptions.SettingsFeatureId` (`EventEngine.IsPackActive` уже читает `ModFeatures.IsActive`; замораживание самих эффектов и `Restore` при включении — дело фабрики экземпляров `event-system`, её в репозитории ещё нет); ядро снимает патчи фичи при остановке. Доля фичи (кривая при `Restore`, кеш каналов, арифметика патча) проверена тестами `FreezeThawTests` на заменителе движка: `Restore` в день включения даёт значение кривой этого дня, дата окончания прежняя, истёкший шок не возвращается. Допущение: `Restore` вызывается для эффектов пака при `ModFeatures.StateChanged(market-shocks, Enabled)`; кеш каналов сбрасывают `OnEnabled` и `ModModifiers.ChannelChanged`, так что порядок «первый вызов патча» и «`Restore`» в день включения не важен: вклад, появившийся позже, сбросит кеш сам.

### 7.4 Самопроверка (TSK-017)

- `SelfCheck/MarketShocksSelfCheck.cs` собирает факты (патчи через `ModHooks.Report` и `ModHooks.IsReserved`, каналы через `ModModifiers.IsDeclared`, типы через `EventEffects.RegisteredTypes`, предикаты через `ModConditions.KnownTypes`, события через `EventRegistry.All`, ключи через `ModL10n.Keys`), правила — чистый `Logic/ShockSelfCheck.cs`. Запускается из `ReportPack` на каждом `GameReady` после чтения пака (то же место, что строка AC-1.1); итог в лог: `[PTMod] [market-shocks] INFO selfcheck OK: 21 events, 4 patches` или по строке на находку (`Error` / `Warn`) и итоговая строка `selfcheck found N problem(s): ...`. Необязательный патч, которого нет в игре, — предупреждение, не ошибка.
- В ядре нет входа, через который фича добавила бы свои находки во вкладку «Диагностика» (`ModSelfCheck` собирает только проверки ядра), поэтому находки пака видны только в логе. Просьба к ядру (необязательная): интерфейс вида `ModSelfCheck.Contribute(Func<IEnumerable<SelfCheckItem>>)` или событие `ModSelfCheck.Collecting`, чтобы фичи могли дописывать находки в тот же отчёт.
- `ModL10n.Keys` — `internal` в сборке PTMod; фича обращается к нему из той же сборки. Если ядро закроет его, самопроверка потеряет проверку ключей по языкам (останется `ModL10n.Has`).
