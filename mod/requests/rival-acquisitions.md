# Запросы фичи rival-acquisitions к итоговому интегратору

## 1. Сборки тестов должны компилировать `Api/Contracts/**` фичи: ЗАКРЫТО (справка)

**Статус (проверено 2026-10-11, доработка после QA).** Правка уже в сборочных скриптах: `build.py: build_tests` и `build_feature.py: build_feature_tests` добавляют `Api/Contracts` (и `Api/Model`, `Api/Dto`) рядом с `Logic/` через `build.pure_api_folders` (`PURE_API_FOLDERS = ('Model', 'Dto', 'Contracts')`). Файла-обхода `Logic/Model/ContractStubs.cs` в дереве нет (поиск по `ContractStubs*` пуст), тесты `Logic` собираются с настоящими `DealType`, `DealRecord`, `WaferLines`. Ничего делать не нужно; не создавать копии типов заново (CS0101). Ниже сохранена исходная постановка.

**Что нужно.** В обе сборки тестов (`build.py: build_tests` и `build_feature.py: build_feature_tests`) добавить папку `src/PTMod/Features/<Pascal>/Api/Contracts/` рядом с `Features/<Pascal>/Logic/` (для `build_tests` — для каждой фичи, у которой такая папка есть).

**Почему.** Публичные типы, которыми пользуются другие фичи, обязаны лежать в `Api/`: сборка фичи-потребителя берёт ядро, свою фичу и только `Api/` зависимостей (`build_feature.py: feature_sources`), а `Logic/` зависимости в неё не входит. Это `DealType`, `DealRecord`, `WaferLines` (`rival-personalities` читает `DealRecord.type` и `targetUniqueId`). Но чистая логика самой `rival-acquisitions` использует те же типы: `AcquisitionsState.deals` (`List<DealRecord>`), `DealRules.Quote(DealType, …)`, `DealQuote.Type`. Тесты же собирают только `Logic/`, поэтому без этой правки `Logic` фичи не соберётся под тестами (CS0246 на `DealType` / `DealRecord`).

**Безопасность правки.** Все файлы `Api/Contracts/**` чистые: без `PTMod.Core`, `UnityEngine`, `Assembly-CSharp`. Проверено компиляцией отдельно под .NET Framework 4.0.30319 (mscorlib, System, System.Core) без остального кода: ошибок и предупреждений нет. Файл `Api/RivalAcquisitionsApi.cs` (статический фасад) использует `ModHooks` и `ModFeatures` и в тесты не входит; корневая папка `Api/` целиком в сборки тестов попадать не должна.

**Бывший обход (в дереве его больше нет).** В первой редакции куска rival-acquisitions#1 до правки скриптов тесты `Logic` обходились файлом `Logic/Model/ContractStubs.cs` (копии `DealType`, `DealRecord`, `WaferLines` под `#if PTMOD_TESTS`). После того как сборки тестов стали компилировать `Api/Contracts`, файл не нужен и удалён; тесты `AcquisitionsStateTests` покрывают настоящие типы через `[Covers]`.

## 2. Подключение в Register / OnEnabled / OnDisabled — СДЕЛАНО (справка для авторов следующих кусков)

`RivalAcquisitionsFeature.OnEnabled` вызывает `RivalAcquisitionsApi.Register(service)` (реализация — `RivalAcquisitionsService`, читает `AcquisitionsState`), `OnDisabled` — `RivalAcquisitionsApi.Unregister(service)`. События поднимаются только методами `RaiseDealCompleted`, `RaiseStakeChanged`, `RaiseRivalDefaulted`, `RaiseRivalBankrupt` (внутренние, в той же сборке). Фасад сам отдаёт нейтральные ответы, когда фича не `Enabled`. Файла `RivalAcquisitionsApi.cs` («заглушки», TSK-001) в корне фичи нет: публичный фасад уже лежит в `Api/RivalAcquisitionsApi.cs`.

Контракты цели нужно переназначить до `TriggerBankruptcy` (шаг 7 раньше шага 11). `BusinessContract.Initialize(provider, client)` публичный, ставит `ProviderID`/`ClientID` и ссылки.

- `Cpu.manufacturer` и `Cpu.currentContract` — private-поля нужных типов. Геттер `Manufacturer` кэширует: `OutsourcedID != -1` → `FindCompany(OutsourcedID)`, иначе `Company`; поэтому при переходе CPU к игроку кэш надо сбросить (для собственного производства цели — обязательно, иначе производителем останется выведенная цель). `MarkupPrice` кэширует `currentContract`, без активного контракта литейных услуг даёт 2,0.

- Оповещение о банкротстве. `BankruptcyHandler.OnCompanyWentBankrupt` — полевое событие (`public event Action<ICompany>`, поле с тем же именем), вызвать его можно только через рефлексию. Единственный ванильный подписчик — `LicenseHelper.<Start>b__12_1`: для `CompanyHelper.IsInlet(c) || IsEMD(c)` ставит `X86LicenseHasBeenRevoked` и поднимает `OnX86LicenseRevoked` → `AIBehaviourController.ReformCyrux(true)` → уведомление «Cyrux no longer has patent issues!» (не при загрузке и перемотке). Баннер банкротства ИИ (`BankruptcyAIEvent`) рисует только приватный `BankruptcyHandler.Bankrupt`, которого наш путь не вызывает.

Цели нет в таблице зарезервированных (`ReservedTargets.cs`: заняты `TickBankruptcies` — P10, `UpdateUI` — P11), prefix не будет отклонён. Через P10 аргумент `negativeBalanceLimit` — порог именно этой компании.

**Находки, меняющие реализацию (учесть в TSK-010/TSK-011):**

1. Проходов `Update(true)` может не хватить. Один проход = `UpdateResearchCompletion` (пропускает `IsLocked`), затем `UpdateResearchAvailability`: за проход открывается один уровень зависимостей. В сцене 97 технологий (`Technology`), самая длинная цепочка — 26 (процессы 10µm → 1nm, каждый зависит от предыдущего). Значение `techUnlockMaxPasses = 20` меньше, чем длина цепочки. Рекомендация: открывать разрыв по порядку глубины зависимостей и вызывать `Update(true)` после каждой технологии (так делает ванильный `UnlockNodeTechnology`), а `techUnlockMaxPasses` оставить как предохранитель общего числа проходов и поднять по умолчанию до 30 (в `balance.json` пока 20, как в design: файл не менялся).
2. `Company.ExpandFactory(int, float, int waferId)` берёт `WaferSizes.Where(ID == waferId).First()` и бросает `InvalidOperationException`, если у игрока нет такой пластины; `operatingCostIncrease` игнорируется (затраты пересчитываются). `Factory.AddLinesToWafer` меняет только существующую группу линий этой пластины и молча ничего не делает, если группы нет, а `ProductionCapacity` при этом уже увеличена. План обязан отображать отсутствующую пластину на меньшую известную, а исполнитель — сверять `Factory.AmountOfLines(пластина)` до и после (расхождение → `partial`).
3. `Divisions.FoundryServices` в коде игры читают только выбор литейщика (`CompanyDataProvider.GetFoundryCompanies`: не банкрот, `Manufacturing`, `FoundryServices`; `HardwareSelectorWindow`) и ИИ (`AIBehaviourBusiness`, `ConsiderGoingFabless`). В путях производства игрока флаг не читается: контракт поставщика, перенесённый на игрока, по коду должен работать и без флага; флаг нужен, чтобы игрока выбирали литейщиком. Переключатель окна производства пишет флаг (`ProductionWindow.cs:427`), поэтому `SetFoundryServicesToggle(true)` включает флаг.
4. Контракт хранит `ContractValues[2]` — число линий в абсолютном виде (по мощности поставщика на момент подписания); `LinesPercentage()` = это число / `Provider.Factory.ProductionCapacity`. После переноса линий и смены поставщика доля пересчитывается сама, но абсолютное число не меняется: исполнитель не должен «поправлять» его.
5. AI-завод производит чужие (outsourced) CPU только при существующем контракте литейных услуг (`GetFoundryServicesContract(this, cpu.Company)`, `AICompany.<InitializeFactory>`): CPU клиента без контракта у литейщика-цели не производился бы; для завода игрока то же самое проверяется в игре (пункт Acceptance TSK-003 про CPU «у литейщика без контракта»).

**Не проверено (нужна игра), пункты Acceptance:** TSK-003 — перенос семейства по шагам 5 и 8 и работа CPU в окне производства игрока, OEM-контракты, `CpuTransferred` без `CpuReleased`, цикл сохранение → загрузка без ошибок в `Player.log`, переназначенный контракт цели-клиента, сброс `Cpu.manufacturer`/`currentContract` рефлексией, выбор «как в design» или «снятие с компенсацией». ## 4. Справка для авторов следующих кусков (кусок 2: снимки, оценка, правила, план, доли) — запросов к ядру и чужим фичам нет

Всё нужное нашлось в ядре (`ModCredit`, `ModModifiers`, `ModTicks.Today`, `ModLog`, `ModHooks.ReportFault`) и в игре. Что полезно знать при работе над исполнителем (TSK-010…TSK-012), окнами (TSK-015…TSK-017) и хуками (TSK-013, TSK-014):

- **Контракты в плане названы `ContractSnapshot.Id`**: это индекс контракта в копии `BusinessContractManager.GetContracts()`, снятой адаптером. У контракта игры нет собственного идентификатора (`ContractID` — тип, 0 = литейные услуги), поэтому исполнитель перед работой строит снимок и план заново в том же вызове и ищет контракты по `GameSnapshotAdapter`-индексу в свежей копии списка, либо сверяет пару `ProviderId`/`ClientId` с контрактом. Индекс из старого плана после изменения списка контрактов (подписание, расторжение) недействителен.
- **Порядок разблокировки технологий** — порядок `plan.TechUnlockIds` / `plan.TechUnlocks`: по возрастанию `TechSnapshot.Depth` (глубины в дереве зависимостей), внутри уровня по `Id`. Исполнитель вызывает `ResearchSector.Update(true)` после каждого уровня (спайк TSK-004: один проход открывает один уровень, цепочки до 26; `techUnlockMaxPasses` = 20 — предохранитель общего числа проходов, см. п. 3, находка 1).
- **Идентификатор пластины = идентификатор её технологии** (`WaferSize.ID` берётся с компонента `Technology`): `plan.LineMoves[i].ToWaferId` годится как последний аргумент `Company.ExpandFactory(N, 0, waferId)`; пластина, которой у игрока нет и которую сделка не открывает, уже заменена планом на наибольшую меньшую известную (с предупреждением `acq.plan.warn.linesRemapped`).
- **Семьи CPU** (`plan.TransferFamilies`): члены идут «база первой»; у каждого `CpuFate` — `Live` (в продаже и остаётся), `Revive` (банкрот: `IsRetired = false`), `StaysRetired` (уже снят, едет снятым), `Retire` (в продаже, но после сделки делаться не может: снять `TriggerRetirement`, семья при этом едет). `FamilyMember.ToInHouse` — CPU цели, которые делал игрок (`OutsourcedID` = `SaveID` игрока): после сделки `OutsourcedID = -1` и сброс кеша производителя, иначе игрок платил бы себе наценку ×2 и роялти. `plan.RetireCpuIds` — все CPU, которые нужно снять явно, в том числе из семей, остающихся у цели. Для `DealRecord`: `plan.TransferredCpuIds()` → `cpuSaveIds`, `plan.TransferredRetiredCpuIds()` → `retiredCpuSaveIds`, `plan.RepointProviderContractIds.Count` / `RepointClientContractIds.Count` → `providerContracts` / `clientContracts`, `plan.TechUnlockIds.Count` → `techCount`.
- **Блокировки**: `plan.BlockingErrors` (ключи `AcqKeys`) и параллельный `plan.BlockingArgs`; первой идёт причина недоступности сделки (`DealQuote.ReasonKey`). План строится целиком и при недоступной сделке, чтобы превью показало, что было бы. Последствия `plan.Consequences` с `RequiresAck` требуют галочки (`PlanOptions.ConsequencesAcknowledged`); предупреждения `plan.Warnings` ничего не блокируют.
- **Вызов адаптера**: `GameSnapshotAdapter.Player()` возвращает `null` вне игровой сцены; `Of(...)`/`All(...)` берут `valuation.cpuIncomeMonths` из `balance.json` третьим/последним аргументом (по умолчанию 12). Канал цены: `GameSnapshotAdapter.PriceChannelOf(цель)` → `priceChannel` для `DealRules.Quote`. Внутри `ModHooks.Guard` вызывать надо самим (адаптер сам не ловит, кроме отдельной компании в `All`).
- **Деньги в причинах**: `DealQuote.ReasonArg` для нехватки денег — целое число долларов строкой (`"1500000"`), `ReasonValue` — то же числом; окно форматирует его `StringFormatter.FloatToMoney`. Даты в причинах — `dd.MM.yyyy`.
- **Ключи L10n** этого куска лежат в `L10n/ru|en/rival-acquisitions.json` (причины `acq.reason.*`, ошибки плана `acq.plan.error.*`, предупреждения `acq.plan.warn.*`, последствия `acq.consequence.*` и `acq.preview.becomesIdm`, причины отказа спасения `acq.rescue.reason.*`); константы — `AcqKeys`, тест `EveryKeyOfTheLogic_IsDefinedInBothLanguages` не даст добавить ключ в код без строки.
- **Имя члена кредитного лимита.** Тест ядра `CreditMathTests.Sources_OnlyTheCreditClasses_ReadCentralBankDebtLimit` запрещает во всём `src` запись `.DebtLimit`, поэтому поля снимков называются `CreditLimit` (а не `DebtLimit`, как в design). Вызовы `ModCredit.DebtLimitOf` / `PlayerDebtLimit` это правило не задевает.

## 5. Справка и находки куска 3 (исполнитель, хуки банкротства ИИ, доли) — запросов к ядру и чужим фичам нет

Всё нужное нашлось в ядре (`ModHooks.Guard`, `ModEvents.RaiseCpuTransferred`, `ModMail` с `ModMailAction`, `ModNotify`, `ModReputation`, `ModCredit`, `ModTicks`) и в `CapitalLedger` (`bankruptcy-recovery/Api`). Для авторов следующих кусков (окна TSK-015…TSK-017, TSK-024) и для интегратора:

- **Как вызвать сделку (TSK-016).** `AcquisitionExecutor.Execute(DealType type, int uniqueId, int saveId, PlanOptions options, double shownPrice, CompanyStatus? expectedStatus)` → `DealOutcome` (`Executed`, `CancelReasonKey`/`CancelReasonArg` — ключи `AcqKeys`, `Record`, `Paid`, `Log`). Снимки, котировка и план строятся заново внутри вызова (идентификаторы контрактов плана живут только в нём); цена выше показанной (`shownPrice`), сменившийся статус или цель отменяют сделку без изменений (`acq.reason.priceChanged` / `statusChanged` / `targetChanged`). `AcquisitionExecutor.IsBusy` — идёт сделка (кнопки неактивны), повторный вызов даёт `acq.reason.busy`. - **Порядок шагов и правила** — чистая `Logic/DealExecution.cs` (`IDealWorld` — игровая сторона, `AcquisitionExecutor` в трёх файлах `Services/`). Обработчик действий (`ModMail.RegisterActionHandler` в `Register`) пока минимальный: «Сделки» и «Поручение на спасение» вызывают `RivalAcquisitionsApi.OpenWindow(uniqueId)` (для письма-итога — цель сделки). - **Срок аукциона** — `дата банкротства + auctionDays` календарными днями (`AddDays(365)`): для банкротства 1987-05-03 последний день 1988-05-02 (1988 високосный), а не «03.05.1988», как в примере AC-3.1. **Решено 2026-10-11:** код и тест остаются, а текст требования приведён к ним (`requirements.md`: FR-3 п. 1, AC-3.1 — «аукцион до 02.05.1988», AC-3.3; пример секции в `design.md`); срок считается в днях, не в годах.
- **Самопроверка P1–P3** — запись в лог фичи на `Register` (`AcquisitionPatches.CheckTargets`: цели существуют и не зарезервированы ядром, четыре члена рефлексии на месте), как у `contract-transparency`; строк в `ModSelfCheck` фича не добавляет (у ядра нет API для фич).
- **Находка для владельца (баланс, не правилось): деньги из «Продать линии».** Инвариант `NetCash < 0` (TSK-007) считает только цену и остаток цели, а выручка от продажи линий (`SaleCost`, шаг 6) идёт игроку отдельно. Завод в оценке стоит `kFab × ManufacturingDivisionValue = 2 × SaleCost`, поэтому цена его части — `m × 2 × SaleCost × Ch × (1 − σ_p)`. Для аукциона банкрота `0,4 × 2 = 0,8 < 1`: купить завод банкрота и сразу продать линии выгодно (+0,2 × SaleCost, при `Ch = 0,5` — +0,6), если `E_min` не выше. При максимальных скидках (`Ch = 0,5`, `σ_p = 0,49`) цена части завода: дефолт `0,7 × 2 × 0,5 × 0,51 ≈ 0,36`, враждебное поглощение `1,5 × 2 × 0,5 × 0,51 ≈ 0,77` (`≈ 0,89` при множителе 1,75) — везде меньше `1,0`. Варианты: при «Продать линии» поднимать нижнюю границу цены до `C⁺ + SaleIncome + E_min` (план знает `SaleIncome`), либо оценивать завод для продажи не ниже `SaleCost`. Решает владелец; код ведёт себя по design. **Открытый вопрос — см. п. 10.**

~~~markdown
### Сделки с соперниками

Фича «Сделки с соперниками» (`rival-acquisitions`) позволяет покупать активы банкротов, покупать компании в дефолте, враждебно поглощать здоровых соперников, брать в них доли и поручать моду спасать компанию от банкротства. Окно «Сделки» открывается со страницы фичи в хабе «Моды» и из писем о дефолте или банкротстве соперника. Пока окно открыто, время стоит. Перед любой покупкой показывается просмотр сделки: из чего сложилась цена, что перейдёт к вам, что будет снято или расторгнуто и какие последствия. Подтверждение двухшаговое. Пока ваша компания в дефолте, все сделки закрыты. Фичу можно выключить в хабе: уже перенесённые активы остаются у вас, а доли, аукционы и поручения ждут в боковом файле до включения.

**Виды сделок**

| Сделка | Когда доступна | Цена |
|---|---|---|
| Покупка активов банкрота | После банкротства соперника, в течение 365 дней (аукцион) | 40 % оценки, но не меньше нижней границы. Деньги и долги банкрота остаются у него |
| Покупка компании в дефолте | Соперник в дефолте, но ещё не банкрот | 70 % от суммы оценки и его денег (если они есть). Его долг переходит к вам |
| Враждебное поглощение | Здоровый соперник; не чаще раза в 365 дней | 150 % от суммы оценки и его денег (175 %, если у цели доля рынка больше вашей). Его деньги переходят к вам. Репутация −5 |
| Доля 10, 25 или 49 % | Любой соперник, кроме банкрота | Доля от стоимости компании (в дефолте на 40 % дешевле). Деньги идут на счёт компании, а не продавцу, и могут вывести её из дефолта. В 1-е число вы получаете дивиденд: половину прибыли компании за прошлый месяц, умноженную на вашу долю, если у компании хватает денег |
| Поручение на спасение | Компания, в которой вы хотите защитить вложение | Когда компания дойдёт до банкротства, мод сам вольёт деньги и даст долю, если сумма не больше вашего лимита, у вас хватает денег и доля не превысит 49 %. Иначе придёт письмо «Спасти не удалось», и всё пойдёт как в обычной игре |

Если у вас уже есть доля в компании, которую вы потом покупаете целиком, цена уменьшается на вашу долю, а доля и поручение закрываются вместе со сделкой.

**Как считается цена.** Сначала мод оценивает операционные активы цели:

- завод: вдвое больше, чем игра платит при продаже его линий (около 30 % цены постройки);
- технологии: половина полной цены исследования тех технологий, которые есть у цели и которых нет у вас;
- CPU: выручка каждого CPU за последние 12 полных месяцев, умноженная на его маржу (долю цены сверх себестоимости, от 0 до 100 %). CPU банкрота учитываются с коэффициентом 0,5;
- всё вместе умножается на (1 + доля рынка цели). У банкрота доля рынка считается равной нулю.

У оценки есть нижняя граница: 25 % порога дефолта цели. Затем оценка умножается на множитель сделки (см. таблицу), на модификатор цены от других модов и событий и на (1 − ваша доля в цели). Цена округляется вверх до тысячи долларов.

**Почему полная покупка всегда дороже денег цели.** Цена компании в дефолте и враждебного поглощения никогда не бывает ниже её денег плюс нижняя граница оценки, какие бы скидки ни действовали. К вам вместе с компанией переходят её деньги (или её долг), поэтому итог для вашего баланса, «цена минус её деньги», всегда отрицательный. Заработать на покупке компании с большим счётом нельзя. Покупать в долг тоже нельзя: после сделки на счёте должно остаться не меньше нуля.

**Что переходит к вам.**

- Технологии цели, которых у вас нет (без окон «Исследование завершено»), прогресс начатых исследований и опыт техпроцессов.
- Линии цели. Вы выбираете: «Забрать линии» (они переезжают на ту же пластину; если вы её не знаете, то на ближайшую меньшую, а содержание завода растёт на показанную сумму) или «Продать линии» (вы получаете игровую цену продажи). Если цель производит ваши CPU, линии нужно забрать.
- CPU цели вместе с вариантами и контрактами OEM. Если вы не разрабатываете CPU, CPU цели просто снимаются с производства.
- Контракты литейных услуг: если цель была литейщиком, вы становитесь поставщиком её клиентов; если цель была клиентом чужого литейщика, контракт переходит к вам (эксклюзивный контракт расторгается, если у вас уже есть такой). Флаг литейных услуг включается, если он был у цели.
- Если включены фичи «Архитектуры CPU» и «Видеокарты», к вам переходят исследованные семейства архитектур (поддержка берётся максимальная) и линейка видеокарт компании. У банкрота линейка видеокарт не переходит: его вендор ушёл с рынка вместе с ним.

Купленная компания выбывает из игры как банкрот. Её название, номер и данные остаются на месте, поэтому сейв остаётся обычным сейвом игры. В таблице компаний игры у неё стоит «Поглощена игроком».

**Intel, AMD, GlobalFoundries.** Их покупать можно. Последствия показаны в просмотре, и кнопка покупки включается только после галочки «Я понимаю последствия»:

- при покупке Intel или AMD игра по своим правилам отзывает x86-лицензию, а Cyrix избавляется от патентных ограничений. Лицензия к вам **не переходит**;
- покупка AMD до появления GlobalFoundries отменяет её выделение; покупка Intel, когда в игре ещё нет литейщиков, означает, что Intel не откроет литейные услуги; при покупке GlobalFoundries к вам переходит её эксклюзивный контракт с AMD (его клиент и условия не меняются);
- если вы разрабатываете CPU без собственного завода (fabless) и забираете линии, вы становитесь IDM и теряете скидку fabless на разработку.

**Что остаётся после удаления мода.** Перенесённые линии, технологии, CPU и контракты хранятся в обычном сейве игры и остаются у вас. Купленные компании остаются банкротами. Пропадает то, что хранится только в боковом файле: ваши доли, открытые аукционы, поручения и журнал сделок. Деньги, вложенные в доли, не возвращаются. Сейв, сделанный более новой версией мода, загрузится, но сделок в нём мод не предложит.

Числа баланса лежат в `mod\src\PTMod\Content\rival-acquisitions\balance.json`; их можно переопределить файлом `Processor Tycoon\PTMod\content\rival-acquisitions\balance.json`. Подробности и формулы: [.kiro/specs/rival-acquisitions](.kiro/specs/rival-acquisitions) (`requirements.md`, `design.md`, `tasks.md`).
~~~

## 10. Открытые вопросы владельца (решения нет; код ведёт себя по design, ничего не менялось)

1. **Арбитраж «Продать линии» (баланс).** Решение владельца «арбитраж закрыт» здесь не выполняется до конца. Инвариант `NetCash < 0` (TSK-007) считает только цену и остаток цели, а выручка от продажи линий (`SaleCost`, шаг 6) идёт игроку отдельно, как деньги от ванильной продажи. Завод в оценке стоит `kFab × ManufacturingDivisionValue = 2 × SaleCost`, поэтому цена его части — `m × 2 × SaleCost × Ch × (1 − σ_p)`, и:
   - аукцион банкрота: `0,4 × 2 = 0,8 < 1` — купить завод банкрота и сразу продать линии выгодно на `0,2 × SaleCost` (при `Ch = 0,5` — на `0,6 × SaleCost`), если нижняя граница `E_min` не выше;
   - при максимальных скидках (`Ch = 0,5`, `σ_p = 0,49`, то есть `Ch × (1 − σ_p) = 0,255`) цена части завода против `1,0 × SaleCost` выручки: дефолт — `0,7 × 2 × 0,255 ≈ 0,36 × SaleCost`; враждебное поглощение — `1,5 × 2 × 0,255 ≈ 0,77 × SaleCost` (`1,75 × 2 × 0,255 ≈ 0,89 × SaleCost`, если доля рынка цели больше вашей). Без скидок эти сделки дают `1,4` (дефолт) и `3,0` / `3,5` (враждебное), то есть выше `1,0`: без скидок арбитраж есть только в аукционе банкрота, а в дефолте и враждебном поглощении он появляется, лишь когда `Ch × (1 − σ_p)` ниже примерно `0,71` и `0,33` (`0,29` при множителе 1,75) соответственно.

   Варианты решения: **(A)** при «Продать линии» поднимать нижнюю границу цены до `C⁺ + SaleIncome + E_min` (`SaleIncome` плану известен), так инвариант `NetCash < 0` включает выручку; **(B)** оценивать завод для продажи не ниже `SaleCost` (меняется `ValuationMath`/`kFab` для случая продажи); **(C)** оставить как есть и принять арбитраж как цену удобства (тогда пересмотреть формулировку решения «арбитраж закрыт» в `owner-decisions.md`). Места правки при (A)/(B): `Logic/DealRules.cs` (`Quote`), `Logic/ValuationMath.cs`, `Logic/AcquisitionPlanBuilder.cs`; тесты, которые придётся обновить: `DealRulesTests` (цены примеров и сетка `NetCash < 0`), `ValuationMathTests`, `DealPreviewModelTests`. Баланс агентом не менялся.
2. **Вывод по FR-8/FR-9** после спайков TSK-003 и TSK-004: перенос CPU-семейства и контрактов «как в design» или «снятие CPU с компенсацией». Инструменты прогона готовы (п. 11).
3. **`techUnlockMaxPasses` = 20 при цепочке зависимостей до 26** (спайк рекомендует 30). Исполнитель открывает технологии по уровням глубины с `Update(true)` на уровень, так что параметр — предохранитель добивочных проходов; поднимать ли значение по умолчанию в `balance.json` и в `AcquisitionsBalance` (вместе с примером в design), решает владелец.
4. **Заметки частичной сделки** показываются на вкладке «История» только у частичных сделок; пометка «GPU-линейка не передана» у обычной сделки не видна (п. 9).

## 11. Справка: отладочные действия (TSK-021) и инструменты спайков (TSK-003, TSK-004)

**Как включить.** Нужна отладочная сборка (обычная `python mod/build.py`; в `--release` этого кода нет вовсе) и флаги в разделе `debug` файла `ptmod_settings.json` (лежит в `Application.persistentDataPath` игры):

```json
{ "debug": { "acqActions": true, "acqSpikes": true } }
```

`acqActions` показывает блок «Отладка» на странице фичи в хабе «Моды» (под кнопкой «Сделки»), `acqSpikes` добавляет в этот блок кнопки спайков. Каждое действие пишет в `Player.log` строку `[PTMod] [rival-acquisitions] INFO debug: …` (спайки — `debug: spike 003: …` и `debug: spike 004: …`) и показывает короткое уведомление. Отказ (нет цели, лимита `D`, аукциона, даты, контракта, денежных операций модов) тоже пишет строку с причиной: `debug: refused: …` (у спайков `debug: spike 00N: refused: …`); уведомление об отказе отсылает к ней. Остальные флаги раздела `debug` у фичи: `acqApiProbe`, `acqApiProbeThrow` (п. 7).

**Кнопки и сценарии (design.md, «Ручные сценарии в игре»).**

| Кнопка | Что делает | Сценарий |

| «Дать игроку N млн» (ползунок 100…5000) | `CapitalLedger.CapitalIn`, деньги игрока | M1 (2 000 млн) |

**Находка по M3:** в сценарии стоит «баланс −1,2 × D», но на последний день дефолта ИИ с заводом продаёт линии по одной, пока баланс не вернётся к −0,75 × D (`AIBehaviourController.SellProductionLinesToAvoidBankruptcy`), и выходит из дефолта, поэтому действие кладёт баланс на −100 × D (глубже, чем покрывают линии любого завода); для цели без завода (fabless) хватило бы и −1,2 × D. Если компания всё же выжила, действие можно повторить. Действия над ИИ-компанией не работают для банкрота и для компании без лимита долга `D`.
