# Сценарии, испытания и достижения: контент

Фича `scenarios-achievements` даёт восемь стандартных сценариев с целями и медалями, восемь испытаний и 37 достижений, которые копятся в профиле игрока. Всё это лежит в JSON, поэтому цели, пороги и тексты можно править и добавлять без пересборки `PTMod.dll`. Этот файл описывает форматы записей, виды проверок, метрики, события, каналы испытаний, правило порогов медалей и способ переопределить контент. Всё, что здесь написано, проверяют тесты фичи: примеры из раздела «Примеры» проходят ту же проверку (`ContentMapper` и `ContentValidator`), что и встроенные записи, а таблицы метрик, событий и видов проверок сверяются с кодом.

## Для игроков

- **Выбор сценария.** В окне новой игры, в панели «Моды…», раздел «Режим»: «Свободная игра» или сценарий. Выбранный сценарий блокирует тип компании, сложность и год старта в окне игры и показывает цели, срок и лучший результат. Кнопка «Испытания (N)…» открывает список испытаний, кнопка «Достижения» показывает достижения и рекорды.
- **Правка файлов не ломает игру.** Если запись в вашем файле неверна, мод пропустит её, напишет причину в `Player.log` и продолжит со встроенной записью. Идущая игра не меняется: сценарий хранится в сохранении целиком (снимок на момент старта), правки файла действуют только на новые прогоны.
- **Изменённый сценарий помечается** (см. «Флаг custom»): результат записывается в историю, но не попадает в рекорды.
- **Профиль и достижения** живут в `ptmod_profile.json` и не зависят от сохранений. Сбросить профиль можно в окне достижений (два подтверждения подряд).

## Как переопределить контент

Ваши файлы лежат в папке игры и накладываются поверх встроенных. Папку `PTMod` создайте сами, если её нет.

| Что переопределяется | Путь |
|---|---|
| Сценарии | `<папка игры>/PTMod/content/scenarios-achievements/scenarios.json` |
| Испытания | `<папка игры>/PTMod/content/scenarios-achievements/challenges.json` |
| Достижения | `<папка игры>/PTMod/content/scenarios-achievements/achievements.json` |
| Параметры | `<папка игры>/PTMod/content/scenarios-achievements/config.json` |
| Тексты, русский | `<папка игры>/PTMod/l10n/ru/scenarios-achievements.json` |
| Тексты, английский | `<папка игры>/PTMod/l10n/en/scenarios-achievements.json` |

Правила слияния:

- **`scenarios.json`, `challenges.json`, `achievements.json`** имеют вид `{ "schema": 1, "records": [ ... ] }`. Запись с `id` встроенной записи **заменяет её целиком** (поля не сливаются, запись должна быть полной). Запись с новым `id` добавляет сценарий, испытание или достижение. Запись `{ "id": "...", "disabled": true }` убирает встроенную запись; остальные поля такой записи не читаются.
- **Неверная запись** не вытесняет встроенную: она пропускается, а причина попадает в `Player.log` (`[PTMod] [scenarios-achievements] WARN scenario 'x' rejected: start.year 1998 not allowed`). Остальные записи грузятся.
- **Файл целиком** игнорируется, если у него другая `schema`, синтаксическая ошибка или нет массива `records`; тогда работает встроенный.
- **Неизвестное поле в записи** — ошибка записи (опечатка не должна пройти молча); поле `disabled` читает ядро.
- **`config.json`** сливается по полям: достаточно указать только то, что меняете. Число вне допустимого диапазона заменяется значением по умолчанию с предупреждением в логе.
- **Тексты** — плоский JSON `{ "ключ": "текст" }`. Ключ из вашего файла заменяет встроенный текст, новый ключ добавляется. Для новой записи нужен текст хотя бы в одном языке; русский основной, английский запасной, лучше написать оба.
- Переопределения читаются при старте игры. После правки перезапустите игру.
- Идентификатор записи: `id` из строчных латинских букв, цифр и дефиса, 3–40 знаков (`workshop-1980`). Идентификаторы целей и правил провала внутри записи: 1–40 знаков тех же символов, без повторов в пределах записи.

## Сценарий: поля записи

Файл `scenarios.json`, запись в `records[]`. Поле «обяз.» — нужно ли оно в записи.

| Поле | Обяз. | Что значит | Допустимо |
|---|---|---|---|
| `id` | да | Идентификатор; ключ переопределения | 3–40 знаков `a-z0-9-` |
| `order` | нет | Место в списке окна новой игры (меньше — выше), по умолчанию 0 | 0…10000 |
| `titleKey`, `descKey`, `briefingKey` | да | Ключи текстов: название, описание (до 6 строк в окне), брифинг | ключ с префиксом `scn.`, `chl.` или `ach.` |
| `start` | да | Параметры старта (ниже) | |
| `onboarding` | нет | Обучение первого года: `allowed` (по выбору игрока), `forcedOn`, `forcedOff`; по умолчанию `allowed` | три значения |
| `modifiers` | нет | Модификаторы, которые добавляются один раз при старте (формат ниже) | до 16 |
| `deadline` | да | Последний день сценария, `гггг-мм-дд`, строго после 1 января года старта | дата |
| `timeBonusMax` | нет | Наибольший бонус за раннюю победу, по умолчанию 0 | 0…2000 |
| `goals` | да | Цели (раздел «Цели»), хотя бы одна обязательная | до 32 |
| `fail` | нет | Правила проигрыша (раздел «Цели»), по умолчанию нет | до 16 |
| `medals` | да | Пороги медалей `bronze`, `silver`, `gold` | строго возрастают |
| `allowedChallenges` | нет | Какие испытания можно выбрать с этим сценарием; пусто — ни одного | `id` существующих испытаний |

Поля `start`:

| Поле | Обяз. | Что значит | Допустимо |
|---|---|---|---|
| `year` | да | Год старта | 1975, 1980, 1985, 1990, 1995, 2000 (годы меню игры) |
| `companyType` | да | Тип компании | `idm`, `fabless`, `foundry` |
| `difficultyLevel` | да | Сложность: 0 очень лёгкая, 1 лёгкая, 2 нормальная, 3 сложная, 4 очень сложная, 5 невозможная | 0…5; 5 только с `idm` |
| `startingTechnology` | да | Технологии на старте: 0 опережают время, 1 на уровне рынка, 2 отстают, 3 сильно отстают, 4 немного отстают | 0…4 |
| `startingFunds` | да | Деньги при старте; отрицательное число — долг | −1 000 000 000…100 000 000 000 |
| `factorySize` | да | Производственные линии при старте | 0…1000; для `fabless` только 0 |
| `allowCheats` | нет | Разрешить читы в окне новой игры, по умолчанию нет (читы делают прогон «с помощью») | да/нет |
| `techYear` | нет | 0 — не применять; иначе год, технологии которого открываются игроку после старта | 0 или 1971…2030 |

Модификатор (`modifiers` сценария и испытания): `channel` — канал реестра ядра (см. «Каналы»), `multiplier` — множитель 0,1…10, `appliesTo` — кому: `player` (игрок, по умолчанию), `ai` (все ИИ), `all` (все компании).

## Цели, провалы и конец сценария

Цель (`goals[]`):

| Поле | Обяз. | Что значит |
|---|---|---|
| `id` | да | Идентификатор цели, уникален в сценарии |
| `required` | нет | Обязательная цель; сценарий выигран, когда выполнены все обязательные. По умолчанию нет |
| `points` | нет | Очки за выполненную цель, 0…10 000, по умолчанию 0 |
| `titleKey` | да | Ключ текста цели (одна строка в трекере) |
| `check` | да | Проверка выполнения (раздел «Проверки») |
| `by` | нет | Промежуточный срок `гггг-мм-дд` после старта, не позже `deadline`: цель, не выполненная к этой дате, считается проваленной; проваленная обязательная цель проигрывает сценарий |
| `progress` | нет | Строка прогресса в трекере: `metric` (метрика), `target` (число), `format` (`percent`, `money`, `count`) |

Правило проигрыша (`fail[]`): `id`, `textKey` (причина, которую видит игрок), `check`. Правило срабатывает, когда его проверка выполнена (с `holdDays` — после нужного числа дней подряд). Допустимые виды проверок в правиле: `metric`, `event`, `condition`, `all`.

Сценарий кончается так:

- **победа** — выполнены все обязательные цели не позже `deadline` (цель, выполненная в день дедлайна, ещё побеждает);
- **поражение** — сработало правило из `fail[]`, банкротство игрока, проиграна гонка с `failOnLose`, провалена обязательная цель по `by`, или наступил `deadline`;
- после итога статусы целей не меняются; игра идёт дальше как свободная.

## Проверки (check)

Одна форма записи для целей, правил проигрыша и достижений: объект с полем `kind`.

| `kind` | Что проверяет | Где разрешён |
|---|---|---|
| `metric` | метрика `metric` сравнивается с `value` оператором `op` (`>=`, `>`, `<=`, `<`, `==`); `holdDays` — сколько дней подряд условие держится | цель, провал, достижение |
| `cpuReleased` | игрок выпустил CPU, подходящий под фильтр `cpu` (CPU, полученные переносом, не считаются) | цель, достижение |
| `race` | гонка: игрок должен выпустить CPU по фильтру `cpu` раньше ИИ; `failOnLose: true` проигрывает сценарий, если первым выпустил ИИ | только цель верхнего уровня |
| `event` | событие `event` случилось `count` раз (по умолчанию 1, до 1 000 000) | цель, провал, достижение |
| `condition` | выражение условий ядра `condition` истинно (с `holdDays`) | цель, провал, достижение |
| `profile` | правило по профилю `profile`: `rule` (сейчас одно, `allScenarioMedals`) — во всех стандартных сценариях есть медаль не хуже `medal` (`gold`, `silver`, `bronze`, `completed`) | только достижение |
| `all` | выполнены все проверки списка `all` (до 16, вложенность `all` до 4 уровней) | всюду, где разрешены дети |

Общие поля любой проверки:

- **`cadence`** — когда проверка вычисляется: `daily` (каждый игровой день после выборки метрик), `monthly` (после закрытия месяца), `event` (в момент события). Не указан — берётся по виду: `metric` по частоте метрики (месячные метрики — `monthly`, остальные — `daily`), `cpuReleased`, `race`, `event` и `profile` — `event`, `condition` — `daily`, `all` — самая частая из частот детей.
- **`holdDays`** — 0…3650 дней подряд (только `metric` и `condition`); разрыв обнуляет счётчик.
- **`require`** — дополнительные условия, **только в достижениях** (у цели и правила проигрыша условий этого рода нет, и проверка с `require` там не выполнится никогда): `difficultyLevel` (0…5, не ниже: берётся меньшая из сложности при старте и текущей), `notBankrupt` (игрок не разорялся за прогон), `companyType` (`idm`, `fabless`, `foundry`), `minChallenges` (не меньше N испытаний в прогоне).

## Метрики

Известные валидатору идентификаторы метрик. Колонка «Обновляется» — как часто метрика получает новое значение: `день` (сэмпл игры раз в игровой день), `месяц` (после закрытия месяца), `событие` (в момент события). Доли рынка — числа от 0 до 1 (0,15 — 15%) по штукам за последние 30 дней. Метрики характеристик (`cpu.*`) не считают CPU, полученные переносом (поглощение, передача).

| ID | Что это | Обновляется |
|---|---|---|
| `money` | деньги компании игрока | день |
| `money.min` | наименьшая сумма денег за прогон | день |
| `money.solventStreakDays` | дней подряд с деньгами не меньше нуля | день |
| `money.negativeStreakDays` | дней подряд с деньгами меньше нуля | день |
| `profit.lastMonth` | прибыль последнего полного месяца (выручка минус расходы по отчёту) | месяц |
| `profit.streakMonths` | прибыльных месяцев подряд | месяц |
| `revenue.last12m` | выручка за 12 последних полных месяцев | месяц |
| `revenue.clients.last12m` | выручка от клиентов-литейщиков за 12 месяцев | месяц |
| `share.total.avg30` | доля рынка по всем сегментам | день |
| `share.highend.avg30` | доля в сегменте High End | день |
| `share.midrange.avg30` | доля в сегменте Mid Range | день |
| `share.lowend.avg30` | доля в сегменте Low End | день |
| `share.industries.avg30` | доля в сегменте Industries | день |
| `share.minSegment.avg30` | наименьшая из четырёх долей по сегментам | день |
| `sales.total` | продано штук за прогон | день |
| `cpu.released.count` | выпущено CPU (снятые с продажи тоже) | день |
| `cpu.maxFrequency` | наибольшая частота выпущенного CPU, кГц | день |
| `cpu.maxCores` | наибольшее число ядер выпущенного CPU | день |
| `cpu.hasSmt` | 1, если выпущен CPU с SMT, иначе 0 | день |
| `popularity.max` | наибольшая популярность своих CPU на рынке, 0…1 | день |
| `oem.active.count` | активных OEM-контрактов | день |
| `oem.signed.total` | подписано OEM-контрактов за прогон | событие |
| `foundry.clients.active` | активных клиентов-литейщиков (игрок — исполнитель) | день |
| `foundry.asClient.count` | активных контрактов, где игрок — клиент | день |
| `factory.lines` | линии фабрики | день |
| `missed.zeroStreakDays` | дней подряд с продажами и без упущенных продаж | день |
| `ips.leaderStreakDays` | дней подряд, когда самый быстрый CPU на рынке (по `Ips`) принадлежит игроку | день |
| `rivals.bankruptCount` | банкротств ИИ после старта (компании, поглощённые игроком, не считаются) | событие |
| `default.recoveredCount` | выходов из дефолта | день |
| `run.days` | дней с начала прогона | день |
| `run.difficulty` | текущая сложность, 0…5 | день |

## События

Внутренние события фичи (это не идентификаторы событий фичи `event-system`, префикс не нужен). Счётчик события растёт за прогон и считается проверкой `event`.

| ID | Когда |
|---|---|
| `cpu.released.player` | игрок выпустил CPU (не полученный переносом) |
| `cpu.released.ai` | ИИ выпустил CPU |
| `oem.signed` | подписан OEM-контракт на CPU игрока |
| `foundry.signed` | игрок подписал бизнес-контракт (литейный) |
| `player.bankrupt` | банкротство игрока |
| `rival.bankrupt` | банкротство ИИ (не поглощённого игроком) |
| `scenario.won` | сценарий выигран |
| `scenario.gold` | сценарий выигран с золотой медалью |
| `scenario.lost` | сценарий проигран |
| `challenge.passed` | испытание пройдено |
| `challenge.failed` | испытание провалено |
| `onboarding.completed.clean` | обучение первого года пройдено до конца, не пропущено |
| `endyear.reached` | наступил последний год игры (2030) |

## Фильтр CPU и условия ядра

Поле `cpu` проверок `cpuReleased` и `race` — фильтр; нужен хотя бы один критерий. CPU подходит, если подходит по всем указанным критериям:

| Поле | Что значит | Допустимо |
|---|---|---|
| `minFrequency` | частота не ниже, кГц (1 000 000 = 1 ГГц) | 0…1 000 000 000 |
| `minCores` | ядер не меньше | 0…256 |
| `maxPower` | мощность не выше, Вт; 0 — не проверять | 0…10 000 |
| `requireSmt` | нужен SMT | да/нет |
| `companyTypeAtRelease` | тип компании игрока в момент выпуска (`idm`, `fabless`, `foundry`) | три значения |
| `releasedBefore` | выпущен до даты `гггг-мм-дд` | дата |

Проверка `condition` берёт выражение условий ядра: объект `{ "type": "имя", ...параметры }` или `all`/`any`/`not` над такими объектами. Имена и параметры предикатов ядра и других фич (`pg.*`, `gpu.*`, `rival.*`, `es.*`, `hist.*`) описаны в документации ядра; валидатор разбирает выражение тем же разбором, что и игра, и отвергает неизвестный предикат. Если фича-владелец предиката выключена, цель недоступна, а валидатор пишет предупреждение.

## Счёт и пороги медалей

```
timeBonus = round(timeBonusMax × дней до дедлайна / дней всего)     // победа раньше срока; при поражении 0
base      = сумма points выполненных целей (обязательных и нет)
score     = round((base + timeBonus) × (1 + сумма scoreBonus выбранных испытаний))     // при поражении 0
medal     = gold, если score ≥ gold; silver, если ≥ silver; bronze, если ≥ bronze; иначе completed
```

Бонусы испытаний складываются: 15% и 10% дают ×1,25. Победа ниже порога бронзы получает «Пройдено» (`completed`).

**Правило порогов медалей** (так посчитаны все стандартные сценарии, и по нему стоит выбирать пороги): пусть `R` — сумма очков обязательных целей, `E` — сумма очков необязательных целей плюс `timeBonusMax`. Тогда

- бронза = `R` (победа с одними обязательными целями в последний день даёт ровно бронзу);
- серебро = `R + 0,5 × E`;
- золото = `R + 0,85 × E` (золото требует почти всех необязательных целей и ранней победы).

Например, `R = 500`, необязательные 100, `timeBonusMax = 300`: `E = 400`, пороги 500 / 700 / 840. Валидатор требует `bronze < silver < gold`, `bronze` не выше наибольшего возможного счёта без испытаний (иначе запись отвергается) и предупреждает, если `gold` выше этого счёта. Если вы меняете цели или очки, пересчитайте пороги по правилу.

## Испытания: поля записи и каналы

Файл `challenges.json`, запись в `records[]`:

| Поле | Обяз. | Что значит |
|---|---|---|
| `id` | да | Идентификатор, 3–40 знаков `a-z0-9-` |
| `titleKey`, `descKey` | да | Ключи названия и описания |
| `scoreBonus` | да | Прибавка к счёту: 0,15 — это +15%; 0…1 |
| `modifiers` | нет | Модификаторы, которые действуют, пока испытание не провалено; формат см. в «Сценарий: поля записи» |
| `fail` | нет | Правила провала (`id`, `textKey`, `check` видов `metric`, `event`, `condition`, `all`) |
| `requiresCompanyType` | нет | Для каких типов компании испытание доступно; пусто — для всех |
| `requiresPerCompanyCredit` | нет | Нужен порог дефолта игрока, который ядро умеет менять для одной компании (так устроено «Жёсткий кредит»); если ядро этого не умеет, испытание недоступно с причиной `chl.<id>.unavailable` |

В записи должен быть хотя бы один модификатор или одно правило провала.

Провал: в свободной игре испытание снимается (его модификаторы убираются), игра идёт дальше, событие `challenge.failed`; внутри сценария провал испытания проигрывает сценарий. Прохождение: в свободной игре испытание считается пройденным через `challengeYears` лет (по умолчанию 10) или в 2030 году, событие `challenge.passed`, запись в профиль.

**Каналы.** Модификатор множит формулу игры через канал реестра ядра. Годятся только каналы, объявленные ядром (27 имён, список — в `mod/src/PTMod/Content/mod-framework/core.json`, раздел `channels`); неизвестный канал отвергает всю запись. Множитель канала ядро зажимает в границах канала. Фича новых каналов не вводит. Каналы стандартных испытаний и сценариев:

| Канал | Множитель | Что меняет |
|---|---|---|
| `research.cost` | 1,5 («Дорогая наука») | стоимость исследований |
| `research.speed` | 1,2 для ИИ («Сильные соперники») | скорость исследований |
| `taxes` | 1,5 («Налоговый пресс») | налог |
| `bank.interest` | 1,5 (сценарий `comeback-1985`) | процент по долгу |
| `bank.creditLimit` | 0,5 («Жёсткий кредит») | порог дефолта и кредитный предел компании |
| `popularity.gain` | 0,7 («Капризный рынок») | прирост популярности CPU |

Остальные каналы реестра (`production.unitCost`, `market.demand.*`, `contract.reward`, `development.cost` и другие) допустимы так же. Общий предел ядра на `market.rating.cpu` и `popularity.gain` — [0,5; 2,0] на CPU, он действует и для вашего множителя.

## Достижения: поля записи

Файл `achievements.json`, запись в `records[]`:

| Поле | Обяз. | Что значит |
|---|---|---|
| `id` | да | Идентификатор, 3–40 знаков `a-z0-9-` |
| `category` | да | Вкладка окна достижений: `career`, `money`, `tech`, `market`, `business`, `meta` |
| `hidden` | нет | Скрытое достижение: до получения в окне «???» |
| `points` | да | Очки достижения, 0…10 000 |
| `titleKey`, `descKey` | да | Ключи названия и описания |
| `check` | да | Проверка (раздел «Проверки»); можно `profile`, нельзя `race` |
| `countsOnlyNewGames` | нет | Не проверять в игре, загруженной из сохранения без мода (у такой игры нет истории всего прогона) |

Достижение открывается один раз и навсегда (в профиле). Прогон, в котором была помощь (читы, выключенная посреди сценария фича), открывает достижения с пометкой «с помощью»; в строгом режиме (параметр `strictAssisted`) не открывает вовсе.

## config.json

```json
{ "schema": 1, "challengeYears": 10 }
```

`challengeYears` — через сколько лет в свободной игре испытание считается пройденным. Целое число 1…50, по умолчанию 10.

## Флаг custom

Сценарий помечается как **изменённый** (`custom`), если его запись пришла из вашего файла и отличается от встроенной с тем же `id` либо встроенной с таким `id` нет. Метка вычисляется при загрузке: по хешу (первые 8 шестнадцатеричных цифр SHA-1 канонического JSON записи), в файл её писать не нужно.

- В окне новой игры и в трекере у такого сценария пометка «Изменённый сценарий: рекорды не записываются».
- Прогон по изменённому сценарию пишется в историю профиля и в счётчики побед и поражений, но **не меняет рекорды сценария**: лучший счёт, попытки и победы.
- Идущий прогон хранит снимок сценария в сохранении; правка файла уже начатый прогон не затрагивает.
- Флаг прогона зависит только от сценария: изменённое испытание или достижение прогон `custom` не делает, оно просто ведёт себя по-новому.

## Тексты

Тексты записей лежат в таблицах строк `l10n/<язык>/scenarios-achievements.json` и подключаются ключами `titleKey`, `descKey`, `briefingKey`, `textKey`. Ключ начинается с префикса фичи (`scn.`, `chl.` или `ach.`), иначе запись отвергается. Принятые имена (их удобно держать):

- сценарий: `scn.<id>.title`, `scn.<id>.desc`, `scn.<id>.briefing`, цели `scn.<id>.g1`, `scn.<id>.g2`, ...;
- общие причины проигрыша: `scn.fail.bankrupt`, `scn.fail.deadline`, `scn.fail.fablessRule`, `scn.fail.debtLimit`; свою причину называйте `scn.<id>.<слово>`;
- испытание: `chl.<id>.title`, `chl.<id>.desc`, `chl.<id>.fail`;
- достижение: `ach.<id>.title`, `ach.<id>.desc`.

Ключа нет ни в одной таблице — запись загрузится с предупреждением, а текст в окне будет виден как `[ключ]`. Описание сценария должно умещаться в 6 строк окна, цель — в одну.

## Если что-то не работает

- **Сценария нет в списке.** Откройте `Player.log` и найдите строку `[PTMod] [scenarios-achievements] WARN scenario 'ваш-id' rejected: ...`: в конце стоит причина (`start.year 1998 not allowed`, `goals: a scenario needs at least one required goal`, `medals: bronze < silver < gold is required`, `channel ... is not declared`). Так же сообщаются отвергнутые испытания и достижения (`challenge '...' rejected`, `achievement '...' rejected`).
- **Файл не действует целиком.** В `Player.log` будет строка о том, что override игнорируется: другая `schema`, синтаксическая ошибка JSON или нет массива `records`. Пока это так, работает встроенный файл.
- **Вместо текста `[ключ]`.** Ключа нет в таблицах строк: допишите его в `l10n/ru/scenarios-achievements.json` (и в английский файл) папки `PTMod`.
- **Самопроверка.** При старте мод пишет одну строку `[PTMod] [scenarios-achievements] INFO self-check: OK`. Если контент или строки встроенных файлов повреждены, вместо неё идёт список проблем (`self-check: 1 error(s), 0 warning(s)` и строка на каждую).
- **Идущая игра не изменилась после правки файла.** Так и задумано: сценарий хранится в сохранении (снимок на момент старта). Начните новую игру.
- **Результат не попал в рекорды.** Сценарий помечен как изменённый (`custom`) либо прогон шёл «с помощью» (читы, выключенная фича): такие результаты пишутся в историю, но рекорд не обновляют.
