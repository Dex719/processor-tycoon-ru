# Замер производительности опроса обучения (NFR-1, TSK-017)

Требование NFR-1: пока обучение идёт, проверка условий текущего шага и ситуативных советов тратит **не больше 0,2 мс за опрос** (`Poll`, 2 раза в секунду реального времени) и **не больше 0,1 мс в среднем на игровой день** (`OnGameDay`). При перемотке новой игры обработчики обучения не вызываются: **0 записей**. После завершения обучения опрос прекращается.

Здесь записаны результаты двух замеров: офлайн-замера на тестовом стенде (он есть в тестах, число обновляется при каждом прогоне) и замера в настоящей игре (его делает владелец в TSK-018 по инструкции ниже).

## Как включить замер в игре

Замер выключен, пока не включён флаг отладки (без флага каждый вход платит за одно чтение флага). Флаг читает только отладочная сборка (`python mod/build.py` без `--release`); в релизной сборке `ModSettings.Debug` всегда ложь.

1. Закройте игру и откройте `ptmod_settings.json` в папке данных игры (`Application.persistentDataPath`).
2. Добавьте раздел `debug` с флагом (если раздел уже есть, допишите флаг в него):

   ```json
   "debug": { "first-year-onboarding.perf": true }
   ```

3. Запустите игру, начните новую игру на треке idm (тип CPU, обучение включено) и играйте до конца второго игрового года, лучше с включённым обучением на всём сроке (`tutorialWindowDays` = 730).
4. В `Player.log` раз в игровой месяц появляется строка уровня INFO (или WARN, если среднее вышло за бюджет):

   ```
   [PTMod] [first-year-onboarding] INFO perf 1975-02: Poll n=57 avg=0.0123 ms max=0.2100 ms (budget 0.2 ms: ok); OnGameDay n=28 avg=0.0210 ms max=0.0900 ms (budget 0.1 ms: ok)
   ```

   `n` — сколько раз вход выполнился за месяц, `avg` — среднее, `max` — самый долгий вызов. Последний месяц пишется при завершении обучения и при выключении фичи.
5. После замера уберите флаг (или поставьте `false`).

Бюджет относится к **среднему**: одиночный выброс из-за сборки мусора в `max` бюджет не нарушает. Пакетный прогон месяца (30 дней за кадр) и перемотка новой игры в замер не попадают: во время них опрос не вызывается (`IsBlocked`, `IsBatchRun`).

## Что именно измеряется

- `Poll` — один вызов `OnboardingController.Poll` корутины опроса: проверка закрытия текущего шага, отправка следующего письма, ситуативные советы, напоминание. Условия берутся из текущего шага и шести советов.
- `OnGameDay` — один вызов `OnboardingController.OnGameDay` на `TickPhase.DayPassed`: счётчики серий, затем та же проверка.
- Часы — `Stopwatch.GetTimestamp` (разрешение сотни наносекунд).
- Вход, который не делал работы (игра грузится, идёт перемотка, прогон месяца, обучение не идёт), записи не даёт: см. `OnboardingPerfTests.WhileTheGameFastForwards_...` и `...TheFastForwardOfANewGameOf2000_IsSilentOnEveryTrack`.

## Офлайн-замер (тестовый стенд)

Тесты `OnboardingPerfTests.TwoGameYearsOnTheIdmTrack_*` прогоняют обучение на настоящем `steps.json` (трек idm) за 735 игровых дней: каждый день один `OnGameDay` и 4 опроса (по 2 Гц столько набегает за игровой день в две секунды реального времени), условия разбирает и вычисляет настоящий разбор условий ядра над поддельным состоянием игры. Перед замером идёт прогрев (первый прогон компилирует код и наполняет кеши), затем три прогона; бюджет проверяется по лучшему среднему каждого входа, потому что на занятой машине (сборка мусора, чужая сборка) один прогон может выйти на порядок медленнее. Среднее по всему сроку считается из месячных строк счётчика, то есть теми же числами, что попадут в `Player.log`.

Стенд: Intel Core i7-13650HX, 32 ГБ, Windows 11, тестовая сборка (отладочная, `-optimize-`) под .NET Framework 4.8, 2026-10-11.

| Сценарий | Вход | Вызовов | Среднее, мс | Максимум, мс | Бюджет среднего, мс | Итог |
|---|---|---|---|---|---|---|
| Игрок ничего не делает, обучение идёт весь срок (самый тяжёлый случай: каждый опрос читает текущий шаг и шесть советов) | `Poll` | 2920 | 0,0015 … 0,0016 | 0,015 … 0,064 | 0,2 | в бюджете (в 100 раз меньше) |
| то же | `OnGameDay` | 731 | 0,0018 … 0,0020 | 0,016 … 0,030 | 0,1 | в бюджете (в 50 раз меньше) |
| Игрок проходит шаги (research → CPU → продажи → OEM → долг), обучение кончается к дню 90 | `Poll` | 360 | 0,0023 … 0,0036 | 0,007 … 0,091 | 0,2 | в бюджете |
| то же | `OnGameDay` | 91 | 0,0028 … 0,0037 | 0,011 … 0,020 | 0,1 | в бюджете |
| Перемотка новой игры 2000 года (`IsBlocked`, 10 000 вызовов `Poll` и `OnGameDay` на каждом из трёх треков) | оба | **0** | — | — | 0 записей | выполнено |

Диапазон — по нескольким прогонам (в самом шумном прогоне при параллельной сборке среднее `Poll` доходило до 0,012 мс, среднее `OnGameDay` до 0,059 мс, максимум до 11 мс — всё равно в бюджете). Тест проверяет бюджеты по среднему за весь срок.

Что стенд не видит: стоимость чтения настоящих объектов игры (`GameOnboardingFacts`: `TimerScheduler`, `Cpu.ProducedLastDay`, `ContractManager`) и обёртки ядра над условиями (`ModHooks`, счётчик ошибок). В стенде их заменяют поддельные факты. Поэтому окончательное число даёт замер в игре.
